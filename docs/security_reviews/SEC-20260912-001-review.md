# SEC-20260912-001 - Process termination safety review

## Mode D Declaration

Target surface: `maintenance/components/process_safety.py` and
`maintenance/actions.py`

D7 threshold: full D7

Risk level: high

Research packs: `security_foundations_pack.md`, `security_testing_pack.md`, and
`security_controls_pack.md`

Reason: process termination is an irreversible safety boundary.

## Security Question

Can platform differences in process identity, protected-process detection,
termination semantics, or access-denied handling allow an unsafe process action?

## Assets, Actors, and Boundaries

- Assets: the operating system, protected services, user processes, and user data.
- Actors: the local user, a same-user malicious process, a foreign-user process,
  and a remote trusted peer requesting a mediated action.
- Entry points: local process dialog actions and typed process-termination requests.
- Trust boundary: UI/request selection to local psutil process operations.
- Required property: protected, foreign-user, inaccessible, stale, or unknown
  processes must not be terminated.

## Existing Controls

- Protected PID set includes PID 0, PID 1, the current process, and ancestry.
- Protected names are centralized and case-folded.
- Windows domain prefixes are normalized before username comparison.
- Incomplete ancestry or lookup failures fail closed.
- Create-time checks defend against PID reuse.
- Graceful and force actions use psutil abstraction and collect access errors.
- Child processes are rechecked before force termination.

#### Entry points traced (repo evidence)

2. **Remote typed-request path** — `maintenance/remote.py` `_solve()` (lines

3. **Direct API surface** — `ProcessManager.request_quit(pids,
   expected_create_times=None)` / `force_quit(...)` accept an optional

   create-time revalidation for those PIDs. No reachable UI/remote caller does
   this today (see 1 and 2), but the API itself permits it.

#### Attack preconditions for an unsafe termination

For any of the required-property violations (protected / foreign-user /
inaccessible / stale / unknown process terminated), an attacker must satisfy
**all** of:

- **P1 — Reach a termination entry point.** Local: the process must be
  rendered with `action_allowed=True` and the user must confirm the dialog.
  Remote: the caller must hold a valid HMAC secret, the node must advertise the
  termination capability, the grant must include the permission, and the
  request must carry a fresh, non-replayed `request_id`.
- **P2 — Pass the protected-PID gate.** PID must not be 0, 1, the app's own
  PID, or any ancestor PID (`protected_process_pids` /
  `ProcessSafetyPolicy._protected_pid_snapshot`). Ancestry lookup failure
  returns `complete=False` and fails closed (`can_manage` → `False`).
- **P3 — Pass the protected-name gate.** `name()` and `exe()` basename are
  case-folded and matched against `PROTECTED_PROCESS_NAMES`. A process whose
  `name()` raises is rejected in `_allowed_processes` (AccessDenied is caught
  and reported, never acted on).
- **P4 — Pass the same-user gate.** `username()` must normalize-equal the
  current user (`usernames_match` / `normalize_username`). A foreign-user
  process is rejected at action time in `_allowed_processes` (line 194) and in
  `_is_allowed_target` for force-quit children (line 225).
- **P5 — Pass the create-time gate (when a token exists).** If
  `expected_create_times` contains the PID, the create time is re-read at
  action time and must match exactly; a mismatch is reported as "changed since
  it was scanned" and the action is skipped (lines 134-139, 185-189).
- **P6 — Pass the OS permission layer.** Even if all app-level gates pass, the
  actual `terminate()`/`kill()` raises `AccessDenied` when the OS denies the
  signal; the error is collected and the process is not reported stopped.

#### Residual TOCTOU analysis (the only exploitable-looking window)

The narrowest window is between `_allowed_processes` (which re-reads
`name()`/`username()` at action time) and `action(target)` in
`_run_process_action` (lines 132-142). In that microsecond window a PID could
exit and be reused by a different process. The create-time re-check (P5)
closes this window **when a create-time token exists** — which is always the
case on the reachable local and remote paths (P1). When a caller omits the
token (direct API use, P3 of entry point 3), the window is not closed by the
app, but:

- The replacement process must still be same-user and non-protected-name at
  `_allowed_processes` time; a foreign-user or protected-name replacement is
  rejected before the window opens.
- A same-user attacker cannot spawn a foreign-user process to take the PID, so
  the only way to hit a protected/foreign process in the window is a
  coincidental foreign-user process starting at the exact PID in the exact
  microsecond — not attacker-controllable.
- psutil's own `terminate()`/`kill()` preemptively checks PID reuse via
  PID + creation time (see Opposer 4 finding F5), adding an independent layer
  even when the app token is absent.

**Conclusion on TOCTOU:** theoretical, not practically exploitable; requires
unreachable preconditions (coincidental foreign-user PID reuse inside a
microsecond window) and is additionally mitigated by psutil's own reuse check.

#### Platform-difference notes

- **Windows domain-prefix normalization** (`normalize_username`): a process
  running as `CORP\alice` and the app running as local `alice` would
  normalize-equal. Exploitation would require the same username to exist in two
  account domains on one machine, and the app to have the OS privilege to
  signal another user's process — otherwise psutil raises `AccessDenied` (P6).
  Not verifiable on this Linux host; flagged as residual risk, not a proven
  bypass.
- **`terminate()` on Windows is an alias for `kill()`** (psutil semantics):
  naming-only concern; all safety gates apply identically before dispatch (see
  Opposer 4 F1). No safety impact.

be read, the manager proceeds with the reduced protected set and will

- Counter-test proof: `test_action_path_terminates_parent_when_ancestry_is_unreadable`

  already-trusted remote peer. The realistic impact is a self-inflicted

  protected-service kill.
- Classification: **hardening opportunity** (align `ProcessManager` with the
  fail-closed policy view), not a vulnerability.

### Opposing Agent 3 - Architecture/Security Skeptic

**Goal:** Verify that trust-boundary transitions, fail-open/fail-closed
semantics, and architecture-level reuse of safety primitives do not weaken the
process-termination surface.

**Security boundary analysis:**

- The local action path is `ProcessDialog` / `AuthenticatedNodeProvider` →
  `ProcessManager` → psutil.
- The remote action path is `RemoteService.handle` → `verify_request` →
  capability/permission checks → `ProcessManager` → psutil.
- The critical trust boundary is the point where a UI or wire request is
  translated into a local `psutil` operation.
- The repo ships two different ancestry-protection primitives:
  1. `maintenance.components.process_safety.protected_process_pids` — the
     **lenient** scan-time snapshot; missing ancestry is ignored and only
     `{0, 1, current_pid}` are protected.
  2. `maintenance.components.process_safety.ProcessSafetyPolicy` — the
     **fail-closed** management policy; missing ancestry returns
     `complete=False` and refuses management.

`ProcessManager._protected_pids` calls the lenient helper
(`protected_process_pids`), not the fail-closed policy. Therefore, when
ancestry cannot be established (sandbox, LSM, permissions, or partial psutil
visibility), the action-time boundary becomes fail-open for ancestor
processes.

**Data flow trace:**

- `maintenance/actions.py:252` — `ProcessManager._protected_pids` delegates to
  `protected_process_pids`.
- `maintenance/components/process_safety.py:78` — `protected_process_pids`
  catches `NoSuchProcess`/`AccessDenied` and returns only the base protected
  set.
- `maintenance/components/process_safety.py:177` —
  `ProcessSafetyPolicy._protected_pid_snapshot` catches the same exceptions but
  returns `complete=False`, causing `can_manage*` to refuse.
- `maintenance/actions.py:163` — `_allowed_processes` uses the lenient set; a
  same-user, non-protected-name ancestor is accepted if ancestry is unreadable.

**Threat model assessment:**

- Actor: local user, or a remote trusted peer granted
  `PROCESS_TERMINATION`/`PROCESS_FORCE_TERMINATION`.
- Precondition: psutil cannot read the current process's parent chain at action
  time.
- Impact: an ancestor process (e.g., shell, terminal emulator, session manager)
  that is owned by the current user and not matched by `PROTECTED_PROCESS_NAMES`
  can be terminated, contrary to the stated “incomplete ancestry … fails closed”
  control.
- The existing create-time check does not mitigate this, because the ancestor
  PID is the originally scanned process and its `create_time` matches.

**Challenge:**

The main auditor’s posture claims “Incomplete ancestry or lookup failures fail
closed.” The action-time code path does not satisfy that claim because it
reuses the scan-time `protected_process_pids` view. This is architecture-level
control reuse across two different safety boundaries (display vs. destructive
action).

**Repo evidence checked:**

- `maintenance/actions.py` — `ProcessManager._protected_pids`,
  `_allowed_processes`, `_run_process_action`.
- `maintenance/components/process_safety.py` — `protected_process_pids` and

- `maintenance/nodes.py` — `ProcessTerminationRequest`, `NodePermission`,
  `NodeCapability`.
- `maintenance/remote_support/protocol.py` — capability/permission tables for

- `maintenance/remote.py` — `RemoteService._solve` process action dispatch.

#### Findings

**F1 — `terminate()` is ungraceful on Windows (SEMANTIC MISMATCH, non-security)**

- **Standard:** psutil `terminate()` on Windows is an alias for `kill()` →
  `TerminateProcess` (immediate, uncatchable).
- **Repo assumption:** `request_quit` uses `process.terminate()` implying
  graceful shutdown.
- **Impact:** On Windows, "Quit" and "Force Quit" are semantically identical
  at the OS level. The naming is misleading but **not a security gap** — all
  safety controls (protected PID, same-user, protected name, create-time
  check) apply identically before dispatch. The user-visible action is
  correctly gated; only the label "graceful" is inaccurate on Windows.
- **Verdict:** Documentation/naming concern, not a safety bypass.

**F2 — `wait_procs` does not cover children (SEMANTIC GAP, non-security)**

- **Standard:** `wait_procs(procs, timeout)` only waits for and reports on
  the exact list of processes passed.
- **Repo code:** `_run_process_action` passes `processes` (original allowed
  list) to `wait_procs`, not `targets` (which includes children when
  `include_children=True`).
- **Impact:** Children killed during `force_quit` are not waited on. The
  result's `stopped`/`force_required` tuples only reflect the originally
  requested PIDs. A child that survives the kill is not reported as
  `force_required`. However, children are still subject to the same safety
  checks (`_is_allowed_target`) before being killed, and the kill itself
  is `SIGKILL`/`TerminateProcess` which is unconditional. The gap is in
  post-action reporting, not in safety gating.
- **Verdict:** Reporting gap, not a safety bypass. Children are correctly
  filtered before action; the missing wait does not allow an unsafe process
  to survive that would otherwise have been blocked.

**F3 — `normalize_username` correctly handles Windows domain prefix (ALIGNED)**

- **Standard:** psutil Windows `username()` returns `"DOMAIN\\user"`.
  `getpass.getuser()` returns plain username.
- **Repo code:** `normalize_username` replaces `/` with `\`, splits on `\`,
  takes last segment, casefolds. Verified by 5 unit tests.
- **Verdict:** Correctly aligned. Domain prefix is stripped from both sides
  before comparison.

**F4 — `ZombieProcess` is caught by `NoSuchProcess` handler (ALIGNED)**

- **Standard:** `ZombieProcess` is a subclass of `NoSuchProcess`.
- **Repo code:** Catches `(NoSuchProcess, AccessDenied)` in all relevant
  places. Zombies are correctly handled.
- **Verdict:** Correctly aligned.

**F5 — PID-reuse protection is defense-in-depth (ALIGNED)**

- **Standard:** psutil `terminate()` and `kill()` preemptively check PID
  reuse via PID + creation time.
- **Repo code:** Also checks `create_time` manually before dispatch.
- **Verdict:** Defense-in-depth. Both layers are present.

**F6 — `parents()` returns empty list for orphaned processes (ALIGNED)**

- **Standard:** `parents()` returns empty list if no parents known.
- **Repo code:** `_protected_pid_snapshot` catches all exceptions and
  returns `complete=False` if ancestry cannot be established, causing
  `can_manage` to return `False` (fail closed).
- **Verdict:** Correctly aligned. Fail-closed on incomplete ancestry.

**F7 — `AccessDenied` is distinct from `NoSuchProcess` (ALIGNED)**

- **Standard:** `AccessDenied` is a direct subclass of `psutil.Error`, not
  `NoSuchProcess`.
- **Repo code:** Catches both explicitly as a tuple `(NoSuchProcess, AccessDenied)`.
- **Verdict:** Correctly aligned.

#### Overall Standards-Skeptic Verdict

All repo assumptions about psutil/Python/OS API semantics are **correctly
aligned** with official documentation for the safety-critical paths:
- Protected PID/name/username gating is semantically sound.
- Fail-closed behavior on inaccessible processes is correct.
- PID-reuse protection is defense-in-depth.
- Windows domain-prefix normalization is correct.

Two **non-security semantic mismatches** were identified:
1. `terminate()` is ungraceful on Windows (naming only, safety controls apply).
2. `wait_procs` does not cover children in force-quit (reporting gap, not

Neither finding allows an unsafe process action. The safety boundary is
semantically sound across all platforms documented.
