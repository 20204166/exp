## Security Question

Can platform differences in discovery lifecycle, TLS certificate handling,
peer identity generation, protocol parsing, replay protection, or capability
authorization cause an untrusted or stale peer to be accepted or granted an
unsafe remote operation?

## Assets, Actors, and Boundaries

- Assets: local telemetry, process/file actions, trust grants, TLS private keys,
  node identity, and cluster state.
- Actors: local operator, unauthenticated LAN host, authenticated trusted peer,
  stale/replayed peer, and a same-network attacker.
- Entry points: Zeroconf advertisements, manual peer endpoints, TLS socket
  accept/connect, pairing requests, signed protocol requests, and discovery UI
  selection.
- Trust boundaries: discovery metadata to trusted-node state; TLS socket to
  authenticated protocol; wire envelope to capability/permission dispatch; and
  peer NodeId to persisted grant lookup.
- Required properties: discovery is untrusted until authenticated; TLS pins are
  verified; malformed/unknown protocol data fails closed; destructive actions
  require capability, grant, replay, identity, and target checks; peer identity
  remains stable across address/name changes.

## Initial Controls To Verify

- Discovery candidates remain non-selectable until explicit trust/pairing.
- TLS transport uses certificate fingerprint pinning and TLS 1.2 minimum.
- Requests require HMAC verification, request identity, replay protection,
  capability, permission, and target checks.
- Protocol parsers reject malformed fields and unknown destructive inputs.
- Local NodeId is a fixed `local` identifier; remote identity is persisted in
  trusted peer records rather than derived from display names or addresses.
- Discovery has IPv4/manual fallback behavior and stop/expiry lifecycle paths.

## Suspected Weaknesses For Opposition

- Zeroconf callbacks and expiry may run on different threads and mutate shared
  peer maps without serialization.
- Certificate-generation and client-context behavior may differ across OSes.
- Remote NodeId creation during discovery/pairing may not inherit local ID
  stability guarantees.
- TLS pinning and HMAC may be composed in different orders across transport
  paths, especially when optional contexts are used in tests or manual flows.
- Protocol compatibility and unknown enum/permission handling may differ during
  mixed-version rollout.

## Opposing Reviews

### Opposing Agent 3 — Architecture/Security Skeptic

**Goal:** Prove impact or severity is overstated, no trust boundary is crossed, or fail-closed behaviour holds for discovery threading/lifecycle, TLS/HMAC/capability composition, replay and identity isolation, privilege escalation, privacy, and availability.

**Security boundary analysis:**

- **Discovery → trusted node boundary:** `NodeRegistry.update_discovered` stores candidates as `UNTRUSTED` with empty capabilities. `selectable_descriptors()` and `select()` explicitly reject any node that is not `LOCAL`, `TRUSTED`, or `AUTHORISED`. Discovery metadata never grants capabilities.
- **TLS boundary:** `client_context()` disables default certificate validation because the design relies on explicit certificate-fingerprint pinning. `build_trusted_transport` rejects any `TrustedNodeRecord` lacking a `transport_fingerprint`. The only code paths that build transports for remote peers (`connect_peer`, `sync_trusted_node_endpoint`) require the pinned fingerprint and verify it via `TLSRemoteTransport`. This is defence-in-depth: TLS supplies encryption; the pin supplies server authentication; HMAC supplies request authentication.
- **HMAC/capability/permission composition:** `verify_request` validates version, envelope fields, signature, freshness, and replay before `RemoteService._solve` checks capability, permission, operation allow-list, and operation-specific parameter validation. Capability and permission are independently enforced, so a capability without a matching permission is denied.
- **Replay and identity isolation:** `ReplayCache` records `(node_id, request_id, nonce)`. Destructive operations additionally record `(node_id, request_id)`, preventing replay even when a fresh nonce is used. Node identity is a stable opaque string (`NodeId`) separate from hostname, address, or display name. A discovered peer with a matching `stable_id` but a different `identity_fingerprint` is marked `MISMATCH`, its pairing state becomes `IDENTITY_CHANGED`, and it is removed from selectable descriptors.
- **Privilege escalation:** `PairingRequest.__post_init__` rejects any permission set that is not a subset of `READ_PERMISSIONS`. `NodeRegistry.promote_to_trusted` enforces the same read-only restriction. Role operations require `REMOTE_MANAGEMENT` capability/permission and matching cluster fence values (`cluster_id`, `epoch`, `fencing_token`), which are set from persisted cluster state, not from discovery.
- **Privacy:** The mDNS advertisement exposes only presence metadata (`stable_id`, display name, hostname, app/protocol version, platform, connectable flag, port, fingerprints). No credentials, tokens, or telemetry content are advertised. `stable_id` is persistent by design so a peer can be re-identified across address changes; it is not a credential.
- **Availability:** `RemoteSocketServer` bounds concurrent handlers with `max_active_handlers`. Frame helpers enforce `MAX_ENVELOPE_BYTES`. `ReplayCache` bounds entries by count and TTL. Discovery `expire_stale` is O(n) over peers and is driven by the UI timer, not an unbounded background thread.

**Data flow trace:**

1. Zeroconf transport callbacks enter `NetworkDiscovery._handle_transport_event`, which acquires `_peer_lock`, checks `_active`, normalises the record, and emits `candidate`/`lost` events.
2. `AppCoordinator.start_discovery` installs a `bridge` callback that delivers events onto the UI thread via `post()` and drops events whose discovery generation no longer matches.
3. UI callbacks (`_on_discovered_candidate`, `_on_discovered_lost`) update `NodeRegistry` only; no trust or capability is granted.
4. Pairing is user-approved and read-only; persisted as `PeerGrantRecord` and loaded into `RemoteService._grants` via `server.update_grants`.
5. Every remote request is TLS-encrypted, certificate-pinned, HMAC-authenticated, freshness-checked, replay-checked, capability-checked, permission-checked, and target-identity-checked before any provider or process manager is invoked.

**Threat model assessment:**

- **LAN attacker without credentials:** Can see presence advertisements and can attempt TLS connections, but cannot produce valid HMAC signatures and cannot pair for destructive permissions. No trust boundary is crossed.
- **LAN attacker impersonating a trusted peer's `stable_id`:** Discovery may update the descriptor, but a mismatched `identity_fingerprint` triggers `MISMATCH` and deselection; the actual RPC transport remains pinned to the persisted host/port and TLS fingerprint. No authenticated request can be hijacked without the paired secret.
- **Stale/replayed request:** Rejected by `ReplayCache` and the destructive request-id cache.
- **Privilege escalation via pairing:** Blocked by read-only pairing validation.
- **Fail-open on malformed input:** Server handler catches all exceptions and closes the connection silently; `verify_request` and `_solve` raise `RemoteProtocolError`/`RemoteAuthError`/`RemoteAuthorizationError` for any malformed/unknown/unauthorised request.

**Challenge:**

The suspected weaknesses in the review posture are largely bounded by existing controls:

- Threading/lifecycle: `RLock` serialises peer-map mutation; `AppCoordinator` generation-checks and UI-thread-delivers callbacks; `NetworkDiscovery._active` check drops late events. The lifecycle is not exploitable for privilege escalation or data corruption.
- TLS/HMAC composition: The combination is sound because pinning is mandatory for trusted transports and HMAC is mandatory for every request.
- Replay: Double replay protection (nonce + destructive request-id) covers the freshness window and beyond.
- Identity: `stable_id` + `identity_fingerprint` separation prevents address/name churn from becoming identity confusion.
- Availability: Bounded resources prevent trivial memory/connection exhaustion.

The one residual architecture note is that `client_context()` deliberately disables certificate validation. This is safe **only because every trusted-peer transport is built through `build_trusted_transport`, which requires an explicit pin, and `SocketRemoteTransport` checks the pin when provided.** A future caller that creates a `SocketRemoteTransport` with `ssl_context` set but no `expected_fingerprint` would lose server authentication. The current codebase does not contain such a path for trusted peers.

### Opposing Agent 4 — External-Research / Official-Standards Skeptic

**Goal:** Prove whether official Python ssl/socket, TLS, Zeroconf/mDNS, HMAC, and
protocol/replay standards contradict the repo's security assumptions or do not
apply to the repo's specific design.

**Research question:**

```text
Research question:
  Do the repo's TLS client_context (CERT_NONE + check_hostname=False),
  certificate fingerprint pinning, HMAC-SHA256 request signing, replay cache
  clock usage, and Zeroconf ServiceBrowser callback threading model contradict
  Python official documentation, RFC 5246/8446 (TLS 1.2/1.3), RFC 6762/6763
  (mDNS/DNS-SD), or standard HMAC-SHA256 semantics?

Repo evidence that triggered it:
  - maintenance/remote_security.py: client_context() sets CERT_NONE and
    check_hostname=False; server_context() and client_context() both set
    minimum_version=TLSv1_2.
  - maintenance/remote_support/transport.py: SocketRemoteTransport calls
    getpeercert(binary_form=True) after handshake with CERT_NONE context,
    then compares SHA-256 fingerprint via hmac.compare_digest.
  - maintenance/remote_support/protocol.py: _signature uses hmac.new with
    hashlib.sha256; ReplayCache defaults to time.monotonic but RemoteService
    injects time.time.
  - maintenance/components/network_discovery.py: _ZeroconfListener callbacks
    (add_service/update_service/remove_service) are invoked from the
    ServiceBrowser thread; _handle_transport_event acquires _peer_lock (RLock).

Pack used: security_controls_pack.md (TLS, replay, authorization controls),
  security_testing_pack.md (standards-semantics test type),
  security_foundations_pack.md (trust boundaries, fail-closed).

Why this pack is enough:
  The controls pack defines the expected properties for TLS, replay, and
  authorization controls. The testing pack defines the standards-semantics
  test type. The foundations pack frames the trust-boundary reasoning.

How the answer could change the decision:
  If official docs prove CERT_NONE prevents getpeercert from returning the
  peer cert on the client side, the entire pinning model is broken.
  If Zeroconf callbacks are not serialized by the repo's lock, the peer map
  could be corrupted. If the replay cache clock is inconsistent, replay
  protection could be bypassed.
```

**External docs used:**

1. **Python ssl module docs** (docs.python.org/3/library/ssl.html):
   - `CERT_NONE`: "Except for PROTOCOL_TLS_CLIENT, it is the default. With
     client-side sockets, just about any cert is accepted. Validation errors,
     such as untrusted or expired cert, are ignored and do not abort the
     TLS/SSL handshake."
   - `getpeercert()`: "for a server SSL socket, the client will only provide
     a certificate when requested by the server; therefore getpeercert() will
     return None if you used CERT_NONE." — This applies to **server** sockets.
     For **client** sockets, the server always sends its certificate during
     the TLS handshake (per RFC 5246 §7.4.2 / RFC 8446 §4.4.2), so
     `getpeercert(binary_form=True)` returns the DER bytes regardless of
     `verify_mode`.
   - `check_hostname`: "Whether to match the peer cert's hostname in
     SSLSocket.do_handshake(). The context's verify_mode must be set to
     CERT_OPTIONAL or CERT_REQUIRED." — The repo correctly sets
     `check_hostname=False` before setting `verify_mode=CERT_NONE` to avoid
     the ValueError that would occur in the reverse order.
   - `minimum_version`: TLSVersion.TLSv1_2 and TLSv1_3 are the only
     non-deprecated members since Python 3.10. PROTOCOL_TLS_SERVER and
     PROTOCOL_TLS_CLIENT already default to TLS 1.2 minimum since 3.10.
   - `ssl.create_default_context()`: Sets CERT_REQUIRED and check_hostname=True
     by default. The repo overrides both for its pinning model.

2. **RFC 5246 (TLS 1.2) §7.4.2 / RFC 8446 (TLS 1.3) §4.4.2**:
   - The server MUST send a Certificate message during the handshake. The
     client always receives the server's certificate regardless of the
     client's verification mode. Verification mode only controls whether
     the client **validates** the certificate, not whether it **receives** it.

3. **python-zeroconf API docs** (python-zeroconf.readthedocs.io):
   - `ServiceBrowser` inherits from `threading.Thread`. Its `run()` method
     processes a queue of service-state-change events and fires listener
     callbacks (`add_service`, `update_service`, `remove_service`) from the
     browser's dedicated thread.
   - The docs state: "This method is designed to be threadsafe" for `cancel()`,
     but listener callbacks are called from the browser thread, not the event
     loop. The repo's `_ZeroconfListener` methods are therefore called from
     the browser thread.

4. **RFC 2104 / FIPS 198-1 (HMAC)**:
   - HMAC-SHA256 is a standard, NIST-approved MAC. The repo's `_signature`
     function uses `hmac.new(secret.encode(), canonical.encode(), sha256)`
     which is the standard Python HMAC-SHA256 construction.

5. **Python time module docs**:
   - `time.time()`: wall-clock, can jump (NTP, manual adjustment).
   - `time.monotonic()`: monotonically increasing, cannot jump.
   - For freshness checking (comparing a wall-clock timestamp against current
     time), `time.time()` is the correct choice because the timestamp in the
     envelope is a wall-clock value.
   - For replay cache TTL (measuring elapsed time since recording), using the
     same clock as freshness is correct for consistency.

**Repo-specific implication:**

1. **TLS pinning model is internally consistent with Python ssl semantics.**
   The repo's `client_context()` sets `CERT_NONE` and `check_hostname=False`,
   then `SocketRemoteTransport.request()` calls `getpeercert(binary_form=True)`
   after the handshake. Per Python docs and TLS RFCs, the client **does**
   receive the server's certificate during the handshake regardless of
   `verify_mode`. The repo then computes SHA-256 of the DER bytes and compares
   against the pinned fingerprint using `hmac.compare_digest`. This is a
   recognized certificate pinning pattern. The Python docs warn against
   `CERT_NONE` for **general** use (because it skips CA chain validation), but
   the repo deliberately replaces CA chain validation with fingerprint pinning.
   The security model is: "I don't trust any CA; I only trust this specific
   certificate fingerprint." This is a valid design choice for a peer-to-peer
   system where trust is established out-of-band via pairing.

2. **TLS 1.2 minimum is correctly set and consistent with Python 3.10+ defaults.**
   Both `server_context()` and `client_context()` explicitly set
   `minimum_version = ssl.TLSVersion.TLSv1_2`. Since Python 3.10,
   `PROTOCOL_TLS_SERVER` and `PROTOCOL_TLS_CLIENT` already default to TLS 1.2
   minimum, so the explicit setting is redundant but not harmful. It provides
   defense-in-depth against future Python version changes.

3. **HMAC-SHA256 signature computation is standard.**
   The repo's `_signature` function uses `hmac.new(secret.encode(), canonical.encode(), hashlib.sha256).hexdigest()` which is the standard Python HMAC-SHA256 construction per RFC 2104 / FIPS 198-1.

4. **ReplayCache clock usage is internally consistent.**
   `ReplayCache.__init__` defaults to `time.monotonic`, but `RemoteService`
   injects `time.time` as the clock. The same clock is used for both freshness
   checking (comparing envelope timestamp against current time) and replay
   cache TTL (measuring elapsed time since recording). Since the envelope
   timestamp is a wall-clock value (`time.time()`), using `time.time()` for
   both freshness and replay TTL is correct and consistent.

5. **Zeroconf callback threading is serialized by the repo's _peer_lock.**
   The `ServiceBrowser` runs on its own thread and calls
   `_ZeroconfListener.add_service/update_service/remove_service` from that
   thread. The `NetworkDiscovery._handle_transport_event` method acquires
   `self._peer_lock` (an `RLock`) before mutating `_peers` and
   `_service_nodes`. This serializes all peer map mutations, addressing the
   suspected weakness about concurrent callback mutation.

6. **Certificate fingerprint computation is standard SHA-256 of DER bytes.**
   `certificate_fingerprint()` computes `hashlib.sha256(der_bytes).hexdigest()`
   and formats it as colon-separated 4-character hex groups. This is a
   standard approach for certificate fingerprinting.

**Local evidence still needed:**

- Native Windows/macOS TLS behavior cannot be verified on this Linux host.
  However, the Python ssl module is a thin wrapper around OpenSSL (or the
  platform's TLS library), and the TLS RFCs guarantee that the server sends
  its certificate during the handshake regardless of the client's verify_mode.
  The `getpeercert(binary_form=True)` behavior is defined by the Python ssl

- Native Windows/macOS Zeroconf behavior cannot be verified on this Linux host.
  However, python-zeroconf is a pure-Python implementation that handles mDNS
  directly (it does not depend on Avahi on Linux or Bonjour on macOS). The
  threading model is the same across platforms.
