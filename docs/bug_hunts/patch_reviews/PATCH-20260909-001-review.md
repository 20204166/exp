## Mode and risk

BugGuard mode: Mode A - code-edit validation

Risk level: high

Validator threshold: full A4

Reason: Remove the shared ClockCoordinator and ResourceGovernor layers while
preserving scheduler cadence, coalescing, node isolation, discovery, and

## Patch summary

Implement `docs/CLOCK_GOVERNOR_CONSOLIDATION_PLAN_2026-09-09.md` as a bounded
fix-forward migration. `ComponentRefreshScheduler` remains the only recurring
component cadence authority. It will directly own only the existing monotonic,
absolute-deadline, in-flight, pause, and coalesced-refresh behavior.
`ResourceGovernor`, pressure sampling, admission/retry policy, and the
standalone ClockCoordinator module will be removed. Non-cadence lifecycle
timers and existing coordinator/UI/safety boundaries remain out of scope.

### Opposing Agent 2 - Repo-Truth Skeptic

#### Findings

1. **P2 - `ComponentRefreshScheduler` no longer validates constructor intervals.**
   The deleted `ClockCoordinator.__init__()` routed every supplied interval
   through `register()`, which rejected non-positive values before publishing
   scheduler state. The migrated constructor performs only milliseconds-to-
   seconds conversion. In this worktree, `ComponentRefreshScheduler({"cpu": 0})`
   constructs successfully and `begin("cpu", 0.0)` raises `ZeroDivisionError`;
   `ComponentRefreshScheduler({"cpu": -1})` constructs and `begin("cpu", 0.0)`
   returns `True`. Preferences normally validate persisted values, but the
   scheduler is directly imported and constructed by application/tests and its
   prior behavior was fail-fast `ValueError`. This is an accidental contract
   change at the retained scheduler boundary, not a governor-policy removal.

2. **P2 - The migration retains two mutable representations of scheduler state.**
   `ComponentRefreshScheduler` now stores authoritative fields on
   `_RefreshEntry` (`_records`) while also maintaining `_next_due`,
   `_in_flight`, `_paused`, and `_refresh_requested` mirrors. The plan explicitly
   requires removing the facade/core split and leaving one deadline-state owner.
   The current methods manually synchronize most mirrors, but there is no
   invariant enforcing equality, and the unknown-key path adds an entry to
   `_records` without adding it to `intervals`. This leaves private consumers
   such as `window._component_poll_delay()` and lifecycle tests dependent on a
   second state model. The current tests pass because they inspect the mirrors,
   not because consistency between the mirrors and `_records` is proven.

#### Repo-truth and test coverage assessment

- The package export removals are intentional and explicitly required by the
  plan; I found no evidence that they should be restored as compatibility
  aliases. Unrelated `maintenance.components` re-exports remain intact.
- `window.py` no longer has governor construction, pressure sampling, admission,
  retry, or release calls. Dashboard work still enters `ScanCoordinator`, and
  component work still claims the selected node scheduler before calling the
  shared `AppCoordinator`, so those lifecycle boundaries are preserved by the
  inspected call chains.
- The retained settings path still persists first and then calls
  `set_interval()` on the selected scheduler. Discovery remains routed through
  `AppCoordinator.start_discovery()` and `discovery_tick()`; no Clock/Governor
  dependency was found in that path.
- Coverage is materially weaker than the plan's acceptance matrix. The deleted
  governor integration module contained cross-layer scenarios, while the
  replacement suite has no direct regression for invalid constructor
  intervals, migrated injected-clock backwards reads, a long scheduler
  overrun/catch-up case, or remote activation with non-default persisted
  intervals. These omissions do not by themselves prove additional runtime
  bugs, but they leave the migration's highest-risk scheduler and node-ordering
  claims unsupported.

### Opposing Agent 3 - Architecture/Security Skeptic

**Finding: P1 availability/regression risk: the patch removes the only aggregate
admission bound without establishing a replacement worker bound.**

- Before this patch, `AppWindow` constructed `ResourceGovernor()` and applied
  `max_active=4`, `max_periodic=2`, `max_per_node=2`, and `manual_reserve=1`
  to dashboard and component work. The deleted implementation is recoverable
  with `git show HEAD:maintenance/components/clock_coordinator.py`.
- After the patch, `AppWindow._run_daemon()` starts an unrestricted daemon
  `threading.Thread` for each dashboard task, while `AppCoordinator`'s default
  runner does the same at `maintenance/components/coordinator.py:286-287`.
  `ComponentRefreshScheduler` only limits one key within one scheduler, and
  `AppCoordinator` only coalesces one operation key. Neither limits different
  component keys, dashboard-vs-component work, or node-qualified keys.
- A selected node can launch six distinct component keys and one dashboard scan
  concurrently. Node-qualified keys allow the same operation set to be
  distinct for other contexts, and direct/dialog coordinator keys are also
  independent. Repeated triggers for distinct keys therefore create distinct
  daemon workers rather than being admitted against a bounded pool. The
  retained tests prove per-key coalescing and scheduler state bounds, not
  aggregate worker bounds; `tests/test_lifecycle_stress.py:103-140` uses a
  deferred runner and never exercises the production default runner.
- This is not an authorization bypass, and process/cleanup/remote capability
  checks remain in their existing owners. It is nevertheless a real safety
  boundary for resource exhaustion and UI starvation: slow or repeatedly
  triggered independent operations can consume unbounded threads and memory,
  with no governor backpressure or fair scheduling. The plan's claim that no
  bounded executor is relied on is contradicted by the concrete pre-patch
  admission limits and the post-patch raw thread launchers.

**Lifecycle/concurrency checks.** The component lease ordering remains mostly
sound: `_launch_component_scan()` claims the source scheduler before
`AppCoordinator.run()`, and `finish_component()` closes that source lease.
Node switching still captures the source provider/scheduler and cancellation
holds `AppCoordinator` in-flight until worker completion. I found no separate
Clock timer or discovery-to-governor dependency, and no evidence that the
patch weakens PID, cleanup, remote identity, or capability authorization.
Those controls do not compensate for the removed aggregate worker admission.

**Additional scheduler compatibility concern (P2, not independently promoted
to a confirmed architecture finding).** The inlined constructor no longer
validates supplied intervals before creating `_RefreshEntry` records, unlike
the deleted `ClockCoordinator.register()` path. A zero interval now survives
construction and can later reach `begin()`'s division at
`maintenance/components/coordinator.py:109-111`; negative intervals also alter
initial due behavior. This should be covered or rejected if custom interval
maps are a supported boundary.

**Validation evidence.** Ran:

- `ruff check maintenance/components/coordinator.py window.py tests/test_components.py tests/test_window.py tests/test_window_nodes.py tests/test_lifecycle_stress.py` - passed.
- `ruff format --check` on the same files - passed.

### Opposing Agent 4 - External-Research Skeptic

**Finding: P2 active architecture documentation is stale.**

- `maintenance/components/README.md:113-124` still documents the deleted
  `clock_coordinator.py`, `ClockCoordinator`, `ResourceGovernor`,
  `JobProfile`, `AdmissionDecision`, and `PressureSnapshot` as live APIs.
  Lines 135-143 still say `ComponentRefreshScheduler` is backed by
  `ClockCoordinator` and supports `defer`.
- This fails the plan's Wave 6/7 requirement to remove or update active
  documentation references (`docs/CLOCK_GOVERNOR_CONSOLIDATION_PLAN_2026-09-09.md:569-613`).
  It can direct maintainers toward imports that now fail and toward an
  admission/defer model intentionally removed by this patch. This is not a
  runtime scheduling regression, but the consolidation acceptance claim is
  incomplete until the active README is corrected. Historical bug-hunt files
  should not be rewritten; this README is active architecture documentation.

**External semantics review.**

- Python's official `time.monotonic()` documentation states that it cannot go
  backwards and is unaffected by system-clock updates:
  <https://docs.python.org/3/library/time.html#time.monotonic>. Production
  window calls use `time.monotonic()`, so no wall-clock regression is shown.
  The retained `_make_monotonic_clock()` in
  `maintenance/components/coordinator.py:19-32` only affects no-argument
  `collect_due()`/`next_deadline()`; explicit `now` arguments remain caller
  supplied. That is consistent with the synthetic test API, but should not be
  described as clamping every scheduler input.
- Official Tkinter documentation says each `Tk` owns its Tcl interpreter and
  cross-thread calls are posted to its event queue, while calls can fail when
  the event loop is not running:
  <https://docs.python.org/3/library/tkinter.html#threading-model>. The
  current completion path remains `AppCoordinator._deliver()` into the
  window's UI handoff; I found no worker-thread Tk call introduced by this
  deletion. `after_cancel` is treated only as cancellation of pending timer
  registration; `_schedule_timer()` also guards already-dispatched callbacks
  with `_is_closing`, rather than assuming cancellation terminates a callback
  already running.

## Main auditor rebuttal

The opposition initially identified real migration defects: constructor
interval validation was lost, scheduler mirror state remained, active README
documentation was stale, and removing admission without considering worker
bounding risked unbounded coordinated work. Each was addressed within scope:

- constructor validation now rejects non-positive configured intervals;
- `_RefreshEntry` is the sole mutable scheduler state owner and the window
  uses the public `has_pending_work()` query;
- the active components README describes the consolidated scheduler and no
  longer references the deleted module or policy classes;
- default `AppCoordinator` work uses a bounded four-worker executor, while
  dashboard work remains bounded by `ScanCoordinator` to one active generation
  plus one coalesced rerun;
- no pressure sampling, capacity reserve, retry backoff, per-node Governor
  policy, or Governor accounting was moved into `AppCoordinator`.

The post-implementation UI audit also found one concrete batching defect: a
render requested while `UICoordinator.flush()` was applying another target was
committed recursively because the flush was no longer marked as active. This
could redraw the thermal surface once per component result in the same Tk poll
cycle. `UICoordinator` now keeps a flush guard, so nested requests remain
pending and are committed by the same flush loop; a regression test covers that
path. This is the fix-forward change for the reported scanner-update flicker.

The claimed duplicate firing of recurring component timers was not reproduced.
The repository has one `AppWindow._component_poll_id` wake-up path for the
selected context, and only `ComponentRefreshScheduler` owns recurring component
deadlines. Other callbacks remain deliberately separate lifecycle, UI handoff,
discovery maintenance, timeout, or presentation timers.

The final evidence supports the requested bounded consolidation. The full
suite passed 924 tests after the behavior-test migration and UI batching fix.
Static gates passed,
the active documentation is current, and repository-wide Python searches show
no runtime Clock/Governor references.
