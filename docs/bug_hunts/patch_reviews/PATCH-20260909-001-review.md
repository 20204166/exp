**Findings**

1. **P1 - target grants are silently lost by normal `AppWindow` state updates.**
   The new target-owned grants are loaded and used to start the listener, but
   ordinary rename, permission, color, revoke, and manual-host state updates
   rebuild `ClusterState` without `peer_grants`. `_save_cluster_state()` writes
   a temporary replacement containing the old grants, then the caller stores
   the grant-less object in `self._cluster_state`. The next state save can
   therefore persist an empty grant list, and runtime state no longer reflects
   the target ACL. This violates the plan's durable, authoritative, immediate
   target-grant boundary. Existing tests cover round-trip persistence but not a
   real `AppWindow` state mutation followed by a second save.

2. **P1 - listener shutdown is not bounded or cancellation-aware at the server
   boundary.** `RemoteSocketServer.stop()` calls `shutdown()` and
   `server_close()` but does not track active sockets, close/interrupt them, or
   signal a request cancellation token. Since handlers are non-daemon and
   `block_on_close=True`, `server_close()` can wait indefinitely when a target
   provider blocks or ignores cooperative cancellation. This directly conflicts
   with the plan's bounded shutdown sequence and can prevent
   `AppWindow._finalize_shutdown()` from reaching coordinator/UI teardown.
   The existing tests exercise ordinary socket round trips, not an active
   blocking handler during stop.

3. **P2 - persisted grant uniqueness is not fail-closed.** The plan requires
   duplicate caller IDs to be rejected. `_parse_grant()` accepts every valid
   item, and `ClusterState.grant()` chooses the first duplicate, making the
   effective secret/permission set depend on JSON order. The synthetic probe
   above reproduces this. This is a malformed-persistence ambiguity at the
   authorization boundary, even though each individual grant passes validation.

4. **P1 - the advertised target listener has no repository caller that creates
   its required grants.** The listener starts only when `peer_grants` already
   exist, but current pairing/manual-host callers create trusted-node records
   only. Thus a normal UI pairing path cannot provision the target ACL, and the
   new listener remains absent on ordinary installations. The plan explicitly
   requires two-sided pairing and target provisioning; the current tests only
   construct `PeerGrant` objects directly in transport tests.

### Opposing Agent 4 - External-Research Skeptic

**Scope and official sources.** I reviewed the current implementation at
`maintenance/remote.py:271-439,515-664,700-870` and
`window.py:1050-1175,1816-1849`, plus the focused transport and persistence
tests. The relevant official references are:

- Python `socketserver`: <https://docs.python.org/3/library/socketserver.html>.
  `ThreadingMixIn` creates a handler thread per request; `daemon_threads=True`
  avoids waiting for those threads, `block_on_close=False` avoids waiting in
  `server_close()`, and `shutdown()` must run while `serve_forever()` is active
  in another thread.
- Python `hmac`: <https://docs.python.org/3/library/hmac.html>.
  `compare_digest()` is the recommended comparison for externally supplied
  digests and is used at `remote.py:300` and `:373`.
- OWASP TLS: <https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html>.
  TLS provides confidentiality, integrity, and authentication; HMAC alone does
  not provide confidentiality.
- OWASP Authorization: <https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html>.
  It recommends deny-by-default and validating permissions on every request.

**Finding: request-handler admission is still unbounded (P2 availability,
medium confidence).** The current server is still a
`socketserver.ThreadingTCPServer` with `request_queue_size = 16` but no active
handler limit (`remote.py:843-850`). A connection obtains a handler thread
before `_recv_frame()` applies the per-socket timeout (`remote.py:821-829`), so
slow clients can retain one daemon thread each. `daemon_threads=True` and
`block_on_close=False` correctly prevent those handlers from blocking
application shutdown (`remote.py:851-869`), but they do not constrain resource
use while the application remains alive. This is a bounded-by-timeout framing
exposure with unbounded concurrent connection count, not proof of the earlier
claimed non-daemon shutdown hang. The queue size only limits pending accepts,
not already-created handler threads.

**No finding: shutdown and readiness claim not reproduced.** A single bounded
probe ran:

```text
python - <<'PY' ... RemoteSocketServer(..., host="127.0.0.1", timeout=0.5) ...
loopback_bound= ('127.0.0.1', 45725)
start_stop=pass
PY
```

The probe returned from `stop()` after immediate `start()`. This does not prove
all scheduler interleavings, but there is no current evidence for a shutdown
hang. The Python documentation's readiness warning remains an uncertainty
because `start()` launches `serve_forever` without an event
(`remote.py:813-858`), while `stop()` calls `shutdown()` immediately
(`remote.py:860-869`).

**No finding: loopback versus LAN binding.** Production composition now uses
`RemoteSocketServer(service, host="127.0.0.1")` at `window.py:1846`; the class
default is also loopback at `remote.py:792-798`. The same bounded probe showed
an explicitly requested non-loopback bind only as:

```text
non_loopback_bound= ('0.0.0.0', 39137)
```

That confirms the API can expose LAN interfaces if a caller deliberately passes
that host, but it does not support the stale claim that this production path
binds all interfaces. HMAC authenticates/integrity-protects messages, not
encrypts them; with the current loopback-only composition, LAN confidentiality
is not exposed by this path. Any future LAN deployment needs an explicit
transport decision and TLS or an accepted confidentiality limitation.

**No findings: grants, pairing, errors, and strict inputs.** Current pairing
creates a target-owned `PeerGrantRecord` using the trusted record secret at
`window.py:1157-1174`; listener startup consumes persisted grants at
`window.py:1816-1846`. Persistence rejects duplicate caller IDs together at
`cluster.py:548-555` and rejects unknown grant permissions at `cluster.py:664-671`.
Execution failures return the stable signed code `execution_failed` without raw
exception text at `remote.py:560-576`, and `create_time` explicitly rejects
booleans at `remote.py:432-438`. Per-request grant selection and permission
checks remain below the UI at `remote.py:515-621`, consistent with the cited
OWASP authorization guidance.

**Framing/protocol no-findings.** `_recv_exact()` handles TCP fragmentation and
`_recv_frame()` enforces the maximum length at `remote.py:685-716`; request and
response envelopes reject unknown fields, invalid timestamps, and malformed
types at `remote.py:279-410`. HMAC verification uses `compare_digest`, freshness
and replay checks are applied at `remote.py:323-334`, and target/caller and
permission checks precede dispatch at `remote.py:536-621`. The focused tests
cover fragmented frames, oversized frames, malformed envelopes, replay,
wrong-target, wrong-secret, grant denial, and signed execution errors; no
additional protocol defect was reproduced.

**Evidence and uncertainty.**

- `python -m unittest tests.test_remote_contract tests.test_cluster tests.test_discovery_session tests.test_window -v` -> **147 tests passed, OK**.
- One bounded start/stop plus loopback/non-loopback bind probe -> **start_stop=pass**; loopback `127.0.0.1`; explicit non-loopback `0.0.0.0`.
- No loops, live services, LAN peers, or production process actions were used.
- I did not run full discovery, type checks, Ruff, or LR checks in this review;

**Conclusion.** The prior P1 claims about non-daemon shutdown, production LAN
