### Opposing Agent 4 - External-Research Skeptic

**Scope and method**

I reviewed the repaired queue delivery, timer cancellation, worker/thread
boundaries, discovery lifecycle, zeroconf adapter, and extracted lifecycle
adapters against the exact repository code and the official documentation
below. This is an independent fallback review; no application code or tests
were changed.

**Official research**

- Python `queue`: https://docs.python.org/3/library/queue.html. The official
  documentation describes `Queue` as implementing the locking semantics for
  multi-producer/multi-consumer threaded exchange, and warns that `empty()` is
  approximate. The code uses `Queue.put()` from workers and `get_nowait()` only
  while draining, not `empty()` as a correctness gate.
- Python `threading`: https://docs.python.org/3/library/threading.html. The
  documentation confirms `Thread.start()` runs the target in a separate thread
  and that daemon threads may be stopped abruptly at interpreter shutdown. The
  extracted workers are daemon threads, and cancellation is cooperative via
  `threading.Event`; this is consistent with the existing application shutdown
  model, but does not make worker termination synchronous.
- Python Tkinter threading model:
  https://docs.python.org/3/library/tkinter.html#threading-model. It states that
  a Tk interpreter belongs to its creating thread and that calls from other
  threads depend on the event loop processing the posted event. The reviewed
  worker paths therefore enqueue data rather than calling Tk from workers.
- Tcl/Tk `after`: https://www.tcl-lang.org/man/tcl8.6/TclCmd/after.htm. The
  authoritative command reference says a delayed command executes once, returns
  an identifier usable by `after cancel`, and cancellation has no effect if the
  command already executed. That matches the wrapper's identifier bookkeeping
  and its idempotent handling of already-fired timers.
- python-zeroconf API:
  https://python-zeroconf.readthedocs.io/en/latest/api.html. The official API
  documents `ServiceBrowser` as a threaded browser with add/remove/update
  callbacks, `ServiceInfo.properties` as bytes-valued TXT properties,
  `ServiceInfo.parsed_addresses()` as the parsed address API, and
  `Zeroconf.close()` as shutting down the sockets and engine and being safe to
  call repeatedly.

**Repo evidence and assessment**

1. `maintenance/components/background_orchestration.py:105-110` places
   success, error, and finished notifications on the shared queue; worker code
   does not call the injected UI-delivery function directly. The main-thread
   guard in `:120-126` prevents a worker from scheduling Tk polling. The drain
   invokes legacy callback tuples through `TimerDelivery.invoke` at `:154-161`,
   and `TimerDelivery.invoke` catches arbitrary callback exceptions at
   `maintenance/ui/window_supports/timer_delivery.py:75-80`. The focused test
   `tests/test_background_orchestration.py:93-103` proves a failing callback
   does not prevent a later task marker from being processed.
2. `maintenance/components/background.py:90-121` schedules the real Tk
   drain before starting the worker and uses a thread-safe `Queue` for worker
   results. The worker only calls `enqueue` at `:137-160`; all widget calls in
   this branch occur in `drain`. The test
   `tests/test_components.py:232-265` records every `after` caller and confirms
   the calls occur on the main thread. The queue itself is unbounded, so this
   path has no producer blocking deadlock, although a pathological producer
   could still create unbounded memory pressure; that is a residual design
   characteristic, not a patch-introduced failure demonstrated here.
3. `maintenance/ui/window_supports/timer_delivery.py:27-53` checks the closing
   state before scheduling and again before invoking. `:55-69` removes the
   identifier even when Tcl reports a teardown failure while closing.
   `window.py:3103-3125` stops discovery, cancels coordinator work, and cancels
   pending timers before destroying the master at `:3162`. This ordering is
   compatible with Tcl's documented best-effort `after cancel` semantics; it
   cannot prevent a callback already executing, but the closing guards prevent
   its application work.
4. Discovery transport callbacks are correctly treated as foreign-thread
   input. `maintenance/components/network_discovery.py:401-403` emits only to
   the injected callback. `maintenance/components/coordinator.py:678-694`
   rejects events from a stopped/replaced discovery and posts accepted events
   through the injected delivery path. The generation identity check at
   `:683-692` drops already-queued events from an older start/stop cycle. The
   coordinator clears ownership and generation before calling `stop()` at
   `:727-739`, which is the necessary ordering for late zeroconf callbacks.
5. The zeroconf adapter's assumptions are supported by the official API and
   the implementation's defensive seams: `:198-209` implements the documented
   service-browser callback names; `:519-533` normalizes bytes TXT keys/values;
   `:557-570` prefers parsed scoped addresses and falls back to raw addresses;
   and `:177-191` cancels the browser and closes zeroconf. Failed startup is
   cleaned at `:291-303` through backend `stop()`. The tests cover byte
   properties, IPv4/IPv6 addresses, startup fallback, partial-start cleanup,
   late events, expiry, and restart (`tests/test_network_discovery.py` and
   `tests/test_coordinator_discovery.py`).
6. `maintenance/components/discovery_session.py:72-129` persists the local
   identity before creating/starting discovery, records the timer only after a
   successful coordinator start, and starts the background poll afterward.
   `:131-142` makes ticking closing-aware and stops the timer before releasing
   coordinator discovery ownership. The adapter's explicit dependency
   callbacks are exercised by `tests/test_discovery_session.py:80-116`.
