## Opposition

### Opposing Agent 1
**Finding 1: P1 — cancellation can roll back locally after the target has durably confirmed.**

The stale-delivery path in `maintenance/ui/window_node_actions.py:734-750`
unconditionally schedules an abort and the cancellation path at `637-649`
restores `attempt.previous_state`, even when the target's confirm request may
already have committed.  `_schedule_pairing_confirm` invokes
`confirm_target_pairing(transaction)` at `760-763` without passing its
`cancel_event`; consequently cancellation cannot interrupt an in-flight
confirm transport and only invalidates the eventual delivery.  The target
does not remove an active grant on abort (`handle_pairing_abort`,
`window_discovery.py:526-544`), so this can leave a durable target grant and no
local trusted record.  A later connection from the target is then rejected or
cannot be represented consistently by the initiator.  This is a real
two-phase consistency failure, not merely stale UI.

Counter-test command:

```text

controller from the committed state; call handle_pairing_abort; assert the
target grant remains ...
PY
```

Result: passed reproduction. After confirm committed, the simulated stale
cancellation produced `post-confirm abort result: False` while the target
grant remained present.  A separate transport probe through
`confirm_target_pairing` printed `confirm transport received cancel event:
False`, confirming that cancellation is not propagated into the confirm
exchange.  Existing `test_cancel_network_pairing_restores_saved_state_before_confirm_delivery`
does not model a target that has already committed the confirm, so it passes
without covering this race.

**Finding 2: P1 — committed confirms are not durable/idempotent across target restart.**

`handle_pairing_confirm` only accepts an already-completed transaction through
the in-memory `_completed_pairings` map (`maintenance/ui/window_discovery.py:483-494`),
which is not persisted.  The durable `ClusterState` retains the resulting
`PeerGrantRecord`, but not the identity/transport/expiry binding needed to
recognise a lost-response retry.  If the target saves the grant, sends no
response (or the process restarts), and the initiator retries the exact
`pair_confirm`, the pending record is gone and `_completed_pairings` is empty;
the request returns `False` even though the target is already paired.

Counter-test command:

```text
python - <<'PY'
... call handle_pairing_confirm once, create a fresh controller from the
committed state, call the same exact confirm request ...
PY
```

Result: reproducibly returned `restart retry confirm result: False`; the
committed grant was still present.  This violates durable two-phase retry
semantics and can make the initiator report confirmation failure after local
trust was saved.  The current unknown-confirm test only covers an unknown
transaction with no committed grant and therefore does not exercise this
lost-response/restart case.

Other checks: expiry-at-deadline, malformed/exact binding, target save
failure, concurrent confirm/abort, TLS pinning, and the focused pairing suite
passed.  Command `python -m unittest tests.test_remote_security
tests.test_window_nodes tests.test_cluster -v` ran 175 tests and passed.

**Recommendation:** mark the patch unsafe pending repair. Make confirm
completion durable with the exact binding (or an equivalent durable record)
and make retries idempotent after restart. Do not restore local trust merely
because a delivery became stale after a confirm may have committed; coordinate
rollback with a confirmed target outcome. Thread the cancellation event into
the confirm operation and transport, while preserving the rule that an abort
cannot revoke an already active grant. Add counter-tests for target commit
plus dropped response/restart, and for cancellation racing after target
commit.

### Opposing Agent 2
**Finding 1: P1 — a committed target grant is not durably idempotent after restart or a lost response.**

The target promotes a pending record and saves the active grant at
`maintenance/ui/window_discovery.py:499-523`, but records the transaction's
completion only in the in-memory `_completed_pairings` map at
`maintenance/ui/window_discovery.py:519-522`. The persisted schema serializes
the active grant and pending records, but no completion binding or transaction
identity (`maintenance/cluster.py:1261-1289`). On a fresh controller after a
successful save, `handle_pairing_confirm()` therefore reaches the missing
pending branch at `maintenance/ui/window_discovery.py:483-494`, finds no
`_completed_pairings` entry, and rejects the exact retry even though the active
grant is present.

restart cannot establish the committed outcome.

**Recommendation:** persist sufficient exact transaction completion binding,
or make the active grant carry a durable transaction record, so a matching
`pair_confirm` retry remains idempotently successful after restart. Add a test

same control request.

**Finding 2: P1 — cancellation does not cancel or coordinate an in-flight target confirmation.**

`cancel_pairing()` cancels only `node_operation_key(node, "pair")` at
`maintenance/ui/window_node_actions.py:637-648`; the confirmation is a separate
operation key, `node_operation_key(attempt.node, "pair-confirm")`, started at
`maintenance/ui/window_node_actions.py:760-765`. More importantly, that task
calls `confirm_target_pairing(transaction)` without its coordinator
`cancel_event` at `maintenance/ui/window_node_actions.py:760-763`, while the
coordinator contract is explicitly cooperative cancellation at
`maintenance/components/coordinator.py:671-680`. Thus closing the dialog after
the local save has completed can restore the previous local state and schedule
an abort, while the already-running confirm can still commit a target grant.
The target abort intentionally never removes active grants
(`maintenance/ui/window_discovery.py:526-544`), so this race leaves durable
remote authorization with no matching local trusted record.

The existing cancellation test only queues the confirmation result and checks
local restoration before delivery (`tests/test_window_nodes.py:2435-2495`); it
does not make the target commit before cancellation. The current implementation
also has no assertion that the confirm task receives the cancellation event.

**Recommendation:** cancel the confirmation key and propagate the event through
`confirm_target_pairing` and the transport, but do not treat cancellation as
proof that a remote confirm did not commit. Resolve the remote outcome before
discarding local state, or retain a recoverable pending-local state until the
target returns a definitive result. Add a counter-test where target commit
precedes cancellation and the confirm response is delayed.

### Opposing Agent 4
**Finding 1: P2 — cancelling or disconnecting during the initial pairing approval can leave an orphaned durable pending transaction.**

The initial request path has no cancellation state at the target UI boundary. `RemoteSocketServer` invokes `_handle_pairing_request(raw, pairing_handler)` without a cancel event (`maintenance/remote_support/server.py:106-110`), and `handle_pairing_request()` queues `ask_on_ui`, then waits a fixed 60 seconds (`maintenance/ui/window_discovery.py:378-433`). The callback persists the `PendingPairing` as soon as the target user answers yes (`:399-423`); it has no check that the initiator's socket is still connected or that the request has been cancelled. Closing the initiator's socket therefore only causes the eventual response write to fail; it does not prevent a later approval from creating durable pending state for an initiator that has abandoned the flow.

This is separate from the recorded confirm-after-commit race: it occurs before a transaction is returned and before local trust or a target grant exists. The impact is stale authorization material (the proposed secret, identities, and expiry) retained in the owner-only cluster JSON until expiry, plus a transaction the initiator cannot complete. One such request also occupies one bounded server handler for up to 60 seconds if the Tk event loop does not process the callback; the server admits only `DEFAULT_MAX_ACTIVE_HANDLERS` handlers (`maintenance/remote_support/server.py:48-50,171-184`).

Focused evidence command:

```text
python - <<'PY'
... queue handle_pairing_request() on a fake UI submitter, wait before invoking
the approval callback, then invoke it with askyesno=True and inspect state ...
PY
```

Result: `callback_queued=True handler_alive_before_callback=True`; after invoking the callback, `handler_alive_after_callback=False approved=True pending_count=1`. This demonstrates that the target-side operation remains live while approval is pending and that approval persists a pending transaction without any initiator cancellation signal. The source introspection probe also reported `request_handler_waits ['completed.wait(60.0)']` and the confirm worker source contains `lambda cancel_event, _progress: confirm_target_pairing(transaction)`, confirming that cancellation is explicitly absent from the initial target handler and is separately dropped for confirm. The failed first probe is not evidence: it raised because its fake Tk master lacked `tk`; the patched rerun above completed with the stated result.

**Recommendation:** make the initial pairing operation cancellation-aware end to end, or explicitly define disconnect as an abort signal that the target observes before persisting approval. At minimum, pass a cancellation/disconnect condition through the server handler and check it immediately before durable pending-state save; ensure the 60-second UI wait cannot leave an unbounded stale approval callback. Add a regression test that abandons/closes the initiating request while the target approval is outstanding, then approves, and asserts no pending transaction is persisted. Do not rely on TLS/socket timeout alone: Python documents timeout as an I/O timeout, not a distributed cancellation or rollback mechanism.

**Official documentation and applicability:**

- Python `threading.Event` is a cooperative signalling primitive; it does not asynchronously stop a running thread: https://docs.python.org/3/library/threading.html#event-objects
- Python documents that threads cannot be destroyed, stopped, suspended, or interrupted, and recommends signalling mechanisms for graceful stopping: https://docs.python.org/3/library/threading.html#thread-objects
- Socket timeouts bound socket operations and raise `TimeoutError`; they do not undo work already accepted by the peer: https://docs.python.org/3/library/socket.html#socket.socket.settimeout
- Tkinter's event loop is single-threaded and blocking handlers prevent event processing; long-running work should be moved out of event handlers: https://docs.python.org/3/library/tkinter.html#threading-model

**Other focused checks:**

- `ruff`/format/type gates were not rerun by this fallback reviewer; the review file records the patch's existing gate results. No application code or tests were edited.
- Existing mixed-version tests passed for legacy request rejection and transactional response shape. I found no mixed-version authorization bypass in the reviewed dispatch: `_handle_pairing_request()` requires the exact `pairing_mode="transactional"` shape (`server.py:215-245`), while control requests require the exact field set and future expiry (`protocol.py:237-297`). This does not establish restart-safe replay, which remains covered by Opposing Agents 1-3.

**Severity:** P2 reliability/state-lifecycle bug. It does not by itself activate a grant, but it can retain abandoned pairing secrets and consume a handler, and it leaves the target with state the initiator cannot reconcile.

### Phase 1: Evidence reconciliation

  `handle_pairing_confirm()` stores completion only in the controller-local

  `cancel_pairing()` invalidates only the `pair` operation, restores the local

- The sibling reviews consistently identify the absence of a durable
  target-side completion binding and the absence of a compensating grant
  revocation operation. Those remain current residual risks, not historical
  findings.

### Phase 4: Lifecycle, persistence, and validation mapping

The handshake spans target pending state, target active grant, initiator local
trusted state, the in-memory registry, persisted JSON, and asynchronous worker
deliveries. The patch correctly provides additive pending persistence, exact
binding checks for pending records, target transition serialization, expiry,
TLS pinning, and local-save-before-confirm ordering. It does not persist the
completion identity needed to recognize a lost-response retry after restart,
and it does not coordinate local cancellation with a confirm that may already
have committed remotely. The target's abort semantics intentionally cannot
remove an active grant, so best-effort abort is not rollback proof.

Official Python threading/Event and future-cancellation semantics support the
reviewers' conclusion that cancellation is cooperative and cannot stop an
already-running operation. Repository code and the corrected probes, rather
than external documentation, prove the patch-specific defects. Full-suite
static claims in the artifact were not independently rerun here; the focused
tests and hygiene results above are the evidence actually obtained by this
fallback audit.

### Phase 5: Conservative recommendation

**Go/no-go: NO-GO for unconditional release.** The patch is not safe to sign
off as a complete two-phase pairing implementation while exact confirm retries
fail after target restart and cancellation can restore local state after a
target commit. The returned-binding mismatch should also be repaired before
release. The initial-approval orphan pending record is lower severity because
it is expiring and does not activate authorization, but it needs an explicit
accepted-risk decision or a cancellation/disconnect guard.

**Verified findings and severity:**

- P1: committed confirms are not durably idempotent across target restart or
  lost response.
- P1: initiator cancellation does not reach or coordinate an in-flight target
  confirm, permitting local/remote authorization divergence.
- P2: target-returned transaction binding is accepted without comparison to
  the requested grant.
- P2: target approval can persist an orphaned pending record after the handler
  timeout and requester disconnect.
- Not a current finding: concurrent confirm/abort lost-update race; current
  transition locking selects one winner.

**Residual risks:** no authenticated, durable target-side grant-revocation or
completion record exists; no live two-node, power-loss, or restart integration
run was performed; full pyright/mypy and LR/drift gates remain unavailable for
the documented baseline/tooling reasons. These limitations do not negate the
deterministic P1/P2 findings.
