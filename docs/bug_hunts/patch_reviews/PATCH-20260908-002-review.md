# Explicit Peer Trust and Identity Continuity

## Main Auditor Scope

BugGuard Mode A; high-risk security/trust-boundary change; full A4 review.
User requested completion of explicit peer trust/pairing on top of Phase 14,
without rebuilding discovery, Node Registry, or the Nodes & Connections surface.

The audit found existing explicit ``DISCOVERED``/``TRUSTED``/``AUTHORISED``
states, persisted trusted records, HMAC transport authentication, read-only
trust promotion, reject/revoke actions, and stable-ID endpoint migration. The
patch adds identity fingerprints to discovery and persisted trust records,
explicit fingerprint confirmation before UI pairing, mismatch detection, and
re-pair recovery while preserving those existing boundaries.

## Patch Summary

- Added ``NodeIdentityStatus`` with unverified, verified, and mismatch states.
- Added stable-ID identity fingerprints using SHA-256 for display/verification;
  the existing HMAC secret remains the transport credential.
- Carried fingerprints through discovery TXT metadata, candidates, descriptors,
  trusted records, persistence, and Nodes & Connections presentation.
- Pairing now requires a fingerprint from the peer and asks the user to confirm
  the stable ID/fingerprint through a trusted channel.
- Trusted rediscovery rejects a fingerprint mismatch before endpoint migration;
  matching identities still allow address changes after existing HMAC hello.
- Mismatch candidates remain available for explicit revoke/re-pair.

## Opposer 1 - Reproduction Skeptic

### Finding: confirmed mismatch re-pair creates duplicate trusted records

**Verdict: reproducible bug; the patch is not safe for the advertised re-pair
flow.** This is a persistence/lifecycle defect, not a fingerprint-check
bypass. A trusted node with fingerprint `original` was rediscovered as the
same stable ID with fingerprint `changed`. `NodeRegistry.update_discovered()`
correctly marked the descriptor `MISMATCH` and retained the candidate (see
`maintenance/nodes.py:528-554`). `_sync_trusted_node_endpoint()` correctly
returned before provider construction or endpoint save at
`window.py:1651-1665`.

The problem is the next, explicitly offered UI action. The mismatch candidate
is still rendered in the discovered list, and `window.py:988-1032` accepts
the Pair callback after the user confirms the displayed fingerprint. It calls
`NodeRegistry.promote_to_trusted()` and then constructs the new record, but
`window.py:1034-1037` appends it to the old tuple instead of replacing the
record with the same `node_id`. `ClusterState.record()` returns the first
match (`maintenance/cluster.py:361-365`), so the old identity remains
effective.

**Exact reproduction command:**

```text

from tests.test_window_nodes import _make_window, _trusted_context
from maintenance.cluster import ClusterState, trusted_node_record

ctx = _trusted_context('peer-a', 'Peer A', cpu_value='peer', host_label='peer')

w._cluster_state = ClusterState(trusted_nodes=(trusted_node_record(
    node_id='peer-a', display_name='Peer A', hostname='peer-a', host='10.0.0.1',
    port=5000, secret='a'*64, identity_fingerprint='original'),))
w._save_cluster_state = Mock(return_value=True)
w._nodes_error = Mock(); w._nodes_status = Mock()
w._refresh_nodes_page = Mock(); w._refresh_cluster_page = Mock(); w._rebuild_node_selector = Mock()
w._node_registry.update_discovered(DiscoveredNodeCandidate(
    'peer-a', 'replacement', ('10.0.0.2',), 6000,
    'peer-a._system-analyzer._tcp.local.', '1', '1', 'Linux', False, True,
    1.0, 'replacement'))
with patch('window.messagebox.askyesno', return_value=True):
    w._pair_discovered_node('peer-a')

      [r.identity_fingerprint for r in w._cluster_state.trusted_nodes])

```

**Observed output:**

```text

```

This is reproducible without network access and with a successful save. It is
not merely a stale UI display: the old record is selected by
`ClusterState.record()`, and a restart restores the first record while the
duplicate is skipped by `window.py:243-250`. Thus the UI reports a successful
pair, but the newly confirmed identity does not become the effective persisted
record. The normal revoke action avoids this exact duplicate because
`window.py:1138-1144` removes all records for the ID before a later pair, but
the mismatch UI explicitly says `re-pair required` (`window.py:1661-1664`) and
offers Pair directly; requiring a user to discover and separately invoke

## Opposer 2 - Repo-Truth Skeptic

### Findings

#### P1: Identity mismatch is not a stable registry state or a selection gate

- `maintenance/nodes.py:532-550` computes `MISMATCH` against the existing
  descriptor fingerprint, but then writes `candidate.identity_fingerprint`
  back into that same descriptor. The next advertisement carrying the same
  changed fingerprint therefore compares equal to the already-overwritten
  value and changes the descriptor back to `VERIFIED`.
- Direct probe against the current code:
  `mismatch mismatch selectable_descriptor ['local', 'peer-a'] candidate_count 1`
  followed by the same candidate again:
  `repeat verified changed`.
- `maintenance/nodes.py:460-478` makes selectability depend on trust and
  operational provider/scheduler state only; `identity_status` is not a gate.
  With an operational trusted context, the mismatched node remains in
  `selectable_descriptors()`. `window.py:1654-1665` prevents endpoint
  migration and displays an error, but leaves the existing provider/context
  usable. Thus the UI's `re-pair required` message is advisory rather than an
  enforced identity boundary, and repeated discovery can hide the warning.
- The added test `tests/test_nodes.py:335-349` checks only one mismatch event
  and candidate retention; it does not assert repeated mismatch persistence,
  selectable-descriptor exclusion, or rejection of already-running remote
  work.

#### P1: Direct re-pair persists duplicate records and cannot replace the old identity

- `window.py:1017-1036` promotes the existing mismatched node and appends a
  new `TrustedNodeRecord` to `self._cluster_state.trusted_nodes`; it does not
  replace the record with the same `node_id`.
- `maintenance/cluster.py:361-365` returns the first matching record from
  `ClusterState.record()`. Therefore the old fingerprint/secret/endpoint stays
  authoritative after the UI's apparent re-pair, while the replacement record
  is later shadowed. On the next rediscovery,
  `window.py:1654-1665` compares against the old record and reports another
  mismatch. Persistence also contains duplicate stable identities and startup
  restoration (`window.py:243-249`) keeps only the first context.
- The available recovery is an indirect revoke-first flow:
  `window.py:1128-1149` removes all records for the ID, after which pairing
  can append a fresh record. The advertised mismatch flow itself does not
  perform that replacement, and the added window test
  `tests/test_window_nodes.py:549-596` covers rejection only, not re-pair
  replacement or duplicate persistence.

### Contracts checked and not found regressed

- Public/test constructor seams remain source-compatible: each new field is
  appended with a default (`TrustedNodeRecord`, `DiscoveryAdvertisement`,
  `DiscoveredNodeCandidate`, `DiscoveredPeerSpec`, and `TrustedNodeSpec`).
- Persistence is backward-readable: `ClusterStore._parse_record()` at
  `maintenance/cluster.py:524-528` treats the absent new key as `None`; the
  existing schema version is unchanged. The duplicate-record issue above is a
  re-pair update defect, not an old-file load incompatibility.
- Explicit trust versus management authorization remains separated in the
  inspected code. `maintenance/nodes.py:584-643` grants only the four
  read capabilities and rejects destructive capabilities; `remote.py:58-73`
  and `remote.py:411-417` retain capability-based read authorization. No new
  discovery-to-management grant was found.
- Stable IDs remain the registry/persistence keys, and the existing HMAC
  secret remains the remote credential. The new fingerprint is deterministic
  display data (`maintenance/nodes.py:224-233`), not authentication.
- Discovery, Nodes & Connections presentation, and local advertisement wiring
  carry the optional fingerprint through their existing injected seams
  (`network_discovery.py:119-129,365-406`, `window.py:1517-1536`, and
  `nodes_connections.py:222-253`). Remote feature wiring remains deferred as
  documented by `maintenance/remote.py:9-14`; this patch did not silently add
  destructive remote management.

### Follow-up After Fix

The two original P1 defects are fixed in the current uncommitted patch:

- **Mismatch selection gate and fallback:** `NodeRegistry.selectable_descriptors()` now excludes `MISMATCH` descriptors (`maintenance/nodes.py:468-479`). `update_discovered()` retains the persisted/original fingerprint in the descriptor, stores the changed candidate separately, and returns selection to the local node when the mismatched node was selected (`maintenance/nodes.py:529-555`). The window path mirrors that fallback through `_switch_selected_node()` (`window.py:1573-1589`). The focused suite passed, and `tests.test_nodes.DiscoveredBoundaryTests.test_identity_mismatch_is_not_silently_accepted` covers repeated changed advertisements and selection exclusion.
- **Stable-ID replacement:** `_pair_discovered_node()` now maps every existing record with the same `node_id` to the newly constructed record, appending only when no record exists (`window.py:1041-1050`). The save occurs before publishing `_cluster_state` (`window.py:1052-1060`), so duplicate records are not produced and `ClusterState.record()` resolves to the replacement. `test_confirmed_mismatch_repair_replaces_trust_record` passed with one record and the replacement fingerprint.
- **Rollback:** on save failure, the prior `NodeContext` is restored after the promoted context is revoked, and the prior selection is restored when applicable (`window.py:1052-1058`; `maintenance/nodes.py:646-664`). A direct save-failure probe confirmed the original context and mismatch status were restored, selection returned to local, and the old `ClusterState` remained unchanged. The rollback is incomplete for retry UX: `promote_to_trusted()` consumes `_discovered[node_id]`, while the failure branch does not restore that candidate, so a failed re-pair requires the peer to be rediscovered before retrying. This is a P2 reliability gap, not a persistence or authorization bypass.
- **Persistence compatibility:** `ClusterStore._parse_record()` treats an absent or non-string `identity_fingerprint` as `None`, and the schema version is unchanged (`maintenance/cluster.py:451-453, 513-529`). Existing records therefore remain loadable and retain the legacy HMAC endpoint behavior. New records serialize the optional field (`maintenance/cluster.py:532-551`).
- **Phase 14 seams:** the patch preserves stable IDs as registry/persistence keys, keeps discovery separate from trust, keeps promotion read-only, and leaves provider/scheduler operational attachment outside `NodeRegistry.promote_to_trusted()`. Added dataclass fields remain trailing defaults, preserving the existing constructor seams. The focused trust/discovery/window/UI suite ran 127 tests with `OK`.

One residual identity-continuity defect remains. Mismatch is sticky across repeated advertisements carrying the changed fingerprint, but `update_discovered()` recomputes status on every later candidate and sets it back to `VERIFIED` if the candidate returns to the original fingerprint (`maintenance/nodes.py:532-538`). A direct probe produced `mismatch` for `changed`, then `verified` for `original`, without an explicit revoke/re-pair. That conflicts with the required “sticky until explicit recovery” boundary: the descriptor becomes selectable again while the mismatch episode has not been explicitly cleared. The persisted fingerprint remains unchanged and endpoint sync still checks it, so this does not recreate the old duplicate-record or endpoint-migration bug, but the registry selection gate can be bypassed by advertisement fluctuation. The remaining fix should preserve `MISMATCH` until explicit revoke/re-pair, rather than treating a later matching advertisement as implicit recovery.

**Follow-up verdict:** the original duplicate-record and ordinary mismatch-selection findings are resolved and the Phase 14 compatibility seams remain intact. Acceptance is still blocked by the non-sticky mismatch reset above; rollback candidate restoration is a separate P2 retryability gap. No app code or normal tests were changed by this review.

## Opposer 3 - Architecture/Security Skeptic

### Findings

1. **Hardening opportunity: the advertised fingerprint is not an authenticated
   identity.** `node_identity_fingerprint()` is a deterministic SHA-256 of the
   self-asserted stable ID, and the ID/fingerprint arrive in unauthenticated
   mDNS TXT data (`maintenance/components/network_discovery.py:120-128,
   371-405`; `maintenance/nodes.py:224-233`). Any LAN peer can advertise a
   chosen stable ID and the corresponding hash. The confirmation dialog's
   trusted-channel instruction is a useful human control, and the existing
   HMAC secret remains the real transport authenticator, so this is not by
   itself an unauthorised-read or privilege-escalation vulnerability. It does
   mean the label "verified" can overstate what the protocol proved. A future
   pairing protocol should bind the displayed identity to an authenticated
   hello or an explicit out-of-band verification result, rather than treating
   discovery metadata as proof.

2. **Hardening opportunity: the registry accepts and verifies arbitrary
   fingerprint strings outside the current UI guard.** `promote_to_trusted()`
   uses the candidate's supplied string, or synthesizes one from the stable ID,
   and marks the descriptor `VERIFIED` when a candidate string is present
   (`maintenance/nodes.py:597-631`). Focused adversarial check: a candidate
   with `identity_fingerprint="forged"` promoted successfully and produced a
   `VERIFIED` descriptor. The current `AppWindow._pair_discovered_node()`
   rejects a missing fingerprint, but this domain API is the actual trust
   transition and has no requirement for canonical format or an independent
   verification result. This is not currently remotely reachable as an
   unauthorised capability path, but it is a future-caller/API-integrity risk.
   Require an explicit verified value (or keep the state unverified) and reject
   the stable-ID fallback for pairing.

3. **Vulnerability (P1): identity mismatch does not fail closed for an
   operational trusted context.** On a mismatch,
   `NodeRegistry.update_discovered()` replaces the trusted descriptor's
   `identity_fingerprint` with the candidate value while setting
   `identity_status=MISMATCH` (`maintenance/nodes.py:529-553`), but
   `selectable_descriptors()` gates only trust and operational state, not
   `identity_status` (`maintenance/nodes.py:460-478`). An already attached
   provider/scheduler therefore remains selectable and usable after the
   `re-pair required` warning. Repeated advertisements can then compare equal
   to the overwritten in-memory value and change the status back to
   `VERIFIED`, while the persisted trust anchor remains different. The
   endpoint-sync path correctly refuses migration, but that does not revoke or
   quarantine existing remote work. Keep the persisted fingerprint immutable
   for comparison/display and make mismatch remove the node from operational
   selection until explicit revoke/re-pair.

4. **Vulnerability (P1): the apparent re-pair path can leave the old persisted
   identity authoritative.** `_pair_discovered_node()` appends a new
   `TrustedNodeRecord` for an existing stable ID rather than replacing the old
   record (`window.py:1017-1037`), while `ClusterState.record()` returns the
   first match (`maintenance/cluster.py:361-365`). A user following the
   mismatch UI and pairing the replacement can therefore see the new descriptor
   but retain the old secret/fingerprint/endpoint on subsequent startup and
   rediscovery. This is a real recovery/identity-transition defect, although it
   does not immediately grant the replacement peer destructive capability;
   re-pair must atomically replace the record by stable ID (or require an
   explicit revoke before the pairing action).

5. **Hardening opportunity: authenticated requests do not bind the claimed
   sender ID to the service's configured peer.** `verify_request()` authenticates
   the entire envelope, but `RemoteService._solve()` never checks
   `request.node_id == self._node_id` (`maintenance/remote.py:229-278,
   411-417`). Focused adversarial check: a request signed with the service's
   valid secret but claiming `node_id="forged-client"` was accepted and the
   signed response identified the server. The secret still gates access and
   no current operation uses the claimed request ID for capability selection,
   so this is not a demonstrated privilege escalation. It is an identity and
   audit-boundary weakness that can become one if routing, authorization, or
   logging later relies on `request.node_id`; reject the mismatch at the
   service boundary.

6. **Effective controls verified.** Address changes are not accepted merely
   because discovery reports a new address: matching persisted identity is
   checked first, then `AuthenticatedNodeProvider.hello()` authenticates the
   endpoint before persistence (`window.py:1666-1713`). Mismatches leave the
   saved endpoint and secret unchanged. Pairing grants only `READ_CAPABILITIES`
   and rejects destructive capabilities (`maintenance/nodes.py:604-616`), while
   the remote protocol currently exposes read operations only
   (`maintenance/remote.py:67-73`). Discovery remains non-selectable until an
   explicit promotion. These paths are fail-closed for the tested attacker
   cases.

7. **Residual persistence risks, not introduced by this identity field:** the
   cluster file contains the HMAC secret in plaintext and parsing accepts any
   persisted capability enum, including destructive values
   (`maintenance/cluster.py:489-523`). With the current remote action wiring
   deferred, I found no demonstrated remote destructive path in this patch;
   however, future startup/action code must not treat a user-editable record as
   proof of destructive authorization. Protect the file and derive destructive
   grants from an explicit authorization transition, not merely persisted
   capability text.

### Follow-up After Fix

The latest Step 15.B changes resolve the two previously confirmed P1 lifecycle
defects on their normal paths:

- **Identity mismatch now fails closed for selection/use.**
  `NodeRegistry.update_discovered()` retains the trusted descriptor's original
  fingerprint as the comparison anchor and keeps `MISMATCH` sticky across
  repeated advertisements (`maintenance/nodes.py:529-555`). Mismatched
  descriptors are excluded by `selectable_descriptors()` and an active
  mismatched selection is moved back to local in `_on_discovered_candidate()`
  (`maintenance/nodes.py:460-479`, `window.py:1573-1589`). The endpoint-sync
  path still rejects before provider construction, hello, or persistence
  (`window.py:1659-1685`). This is an effective operational quarantine for
  subsequent dashboard selection and work admission; it does not pretend to
  authenticate the advertisement.

- **Confirmed re-pair now replaces the trusted record by stable ID.**
  `_pair_discovered_node()` replaces matching records rather than appending a
  second record, and the save-failure path restores the previous registry
  context/selection (`window.py:1015-1060`). The new window test verifies one
  replacement record and effective lookup. This closes the previously
  reproduced shadowed-record path for a normal state containing one record.

- **Destructive capability separation remains intact.** Pairing still supplies
  only `READ_CAPABILITIES`, and `NodeRegistry.promote_to_trusted()` rejects
  destructive requests (`maintenance/nodes.py:585-616`). The remote operation
  table exposes read operations only, while local process/file managers remain
  the final authority for termination and Trash validation. No discovery,
  mismatch, or re-pair path grants destructive capability.

Two narrower lifecycle risks remain, neither reproduces the original bypass:

1. The replacement comprehension substitutes the new record for every existing
   matching item; if a legacy or manually malformed cluster file already has
   duplicate records, it preserves multiple copies rather than canonicalising
   to exactly one. `ClusterState.record()` remains first-match based
   (`maintenance/cluster.py:361-365`). This is a P2 persistence-hygiene
   follow-up, not a new identity takeover, because the replacement path does
   not create duplicates from the normal single-record state.
2. If a mismatched node is not currently selected, `_on_discovered_candidate()`
   quarantines it from future selection but does not cancel an already
   in-flight component operation owned by that context. Selected-node mismatch
   does switch to local and invokes `_cancel_node_operations()`; the remaining
   case is bounded to cooperative completion of work already admitted, with
   no new selection-based admission. A future hardening change could cancel
   all operations for a quarantined context if immediate cessation is required.

The fingerprint assurance concern is correctly bounded as a residual design
limitation, not counted as a credential or an authentication bypass. The value
is still a deterministic SHA-256 display/continuity aid over self-asserted
discovery data; the existing HMAC secret remains the transport gate. The code
and Opposer 4 evidence should continue to avoid treating `VERIFIED` or the
yes/no prompt as cryptographic peer identity proof. Stronger assurance would
require binding a peer-controlled key/secret to the authenticated handshake
and an actual trusted-channel comparison/transfer. Subject to that claim
boundary, the original P1 findings are fixed; the residuals are hardening
opportunities rather than blockers for this patch's stated scope.

## Opposer 4 - External-Research Skeptic

**Verdict: confirmed identity-assurance overclaim; existing HMAC transport claim is accurate but does not repair it.**

- `maintenance/nodes.py:224-233` computes `SHA-256("system-analyzer-node:" + stable_id)` and formats the digest for display. This is a deterministic public hash of an already advertised value, not a fingerprint of a public key, device secret, or authenticated channel. Python's official `hashlib` documentation describes `sha256()`/`hexdigest()` as hash/digest operations; it does not provide proof of control of the input or its producer: [Python hashlib](https://docs.python.org/3/library/hashlib.html).
- The implementation marks the identity `VERIFIED` merely when a non-empty advertised fingerprint exists (`maintenance/nodes.py:598-631`), and the pairing dialog is only an `askyesno` acknowledgement (`window.py:1000-1019`). No fingerprint is entered, compared with an independently obtained value, or returned in the authenticated `hello` response (`maintenance/remote.py:418-426`). Consequently, a peer can advertise any stable ID/fingerprint pair, and a user click does not technically establish that the peer controls that identity. A later mismatch detects a changed advertisement, but it cannot detect an attacker that presents the same self-asserted pair.
- The wording in the UI, `"Confirm this fingerprint through a trusted channel before pairing"`, is a useful instruction, but the code does not enforce that step. This should be described as explicit user acknowledgement/instruction, not as a verification guarantee. NIST SP 800-63B's current out-of-band guidance specifically says that merely presenting values for comparison is insufficient and requires a secret transfer between channels to bind the authentication operation: [NIST SP 800-63B, Out-of-Band Devices](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/#out-of-band). That guidance is not a direct protocol requirement for this local-network feature, but it is relevant evidence against claiming that this yes/no prompt itself authenticates identity.
- The transport description is correctly bounded. `maintenance/remote.py:124-129` uses HMAC-SHA-256 with the separately stored secret, and `verify_request`/`verify_response` use `hmac.compare_digest` (`remote.py:229-246`, `281-297`). Python's official `hmac` documentation identifies HMAC as keyed message authentication and recommends `compare_digest` for verification: [Python hmac](https://docs.python.org/3/library/hmac.html). This proves integrity/authenticity for parties possessing the shared secret, not that the secret is bound to the advertised stable ID or fingerprint. The code also creates a fresh secret at local pairing (`maintenance/cluster.py:368-395`), so the patch provides no external evidence that the remote peer received or independently authenticated with that same secret.

**Focused evidence:** `python -m unittest tests.test_nodes tests.test_network_discovery tests.test_window_nodes tests.test_remote_contract` passed, 109 tests. Those tests cover deterministic/carry-through/mismatch/UI-gate behavior and the HMAC contract, but they do not prove an independently authenticated identity binding. No app or normal test files were changed.

**Required claim correction:** retain the SHA-256 value as a display/continuity aid and retain the existing HMAC statement as transport authentication. Replace any implication that `VERIFIED` or the yes/no prompt cryptographically verifies the peer identity. If stronger identity assurance is required, the authenticated protocol must bind a peer-controlled key or secret to the displayed identity and require an actual trusted-channel comparison/transfer before persisting trust.

### Follow-up After Fix

**Verdict: the lifecycle fix is supported, but the identity-assurance wording remains only partially corrected.** The current implementation now preserves the stored fingerprint as the continuity anchor, excludes `MISMATCH` descriptors from selection, and replaces an existing trusted record during re-pair (`maintenance/nodes.py:529-555,468-479`; `window.py:1031-1051`). Those changes address the prior Opposer 4 scope only indirectly; they do not change what the fingerprint cryptographically proves.

- The official `hashlib` documentation defines `sha256()` as constructing a hash object and `hexdigest()` as returning the digest in hexadecimal form ([Python hashlib](https://docs.python.org/3/library/hashlib.html)). The current `node_identity_fingerprint()` input remains a stable ID supplied through discovery (`maintenance/nodes.py:224-233`), so the value is correctly usable as a display and continuity comparison aid, but it is not evidence of peer key or secret possession.
- The official `hmac` documentation defines HMAC as keyed hashing for message authentication and recommends `compare_digest()` for verification ([Python hmac](https://docs.python.org/3/library/hmac.html)). The existing remote envelope is HMAC-SHA-256 signed and verified (`maintenance/remote.py:124-153,229-246,281-297`), so describing HMAC as the transport authentication mechanism remains accurate. That authentication establishes authenticity/integrity for messages under the shared secret; it does not by itself bind the self-asserted discovery fingerprint to a peer-controlled identity.
- The code comment explicitly says the fingerprint is a "verification aid, not a credential" (`maintenance/nodes.py:224-228`), but the UI still calls the dialog `Verify peer identity` and labels the resulting state `VERIFIED` (`window.py:1003-1009`; `maintenance/nodes.py:535-537,627-631`). The dialog only asks the user to confirm a value already supplied by the peer; it does not collect or compare an independently obtained value, and the authenticated `hello` response still carries no fingerprint (`maintenance/remote.py:418-426`). Therefore those labels can still be read as a technical identity-verification guarantee, which the current code does not provide.
- This conclusion is consistent with the relevant NIST out-of-band guidance, which says that merely presenting values for comparison is insufficient and requires transfer of a secret between channels ([NIST SP 800-63B, Out-of-Band Devices](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/#out-of-band)). That guidance is not a direct protocol mandate for this local-only feature, but it reinforces the distinction between user instruction/acknowledgement and enforced identity proof.

**Follow-up disposition:** retain the fingerprint as a display/continuity aid and retain the existing HMAC transport-authentication description. The remaining claim-boundary correction is to avoid presenting `VERIFIED` or `Verify peer identity` as cryptographic peer-identity verification unless the protocol adds an authenticated binding to a peer-controlled key/secret and an actual trusted-channel comparison or transfer. No new transport-authentication defect was found in this follow-up review.
