## Patch summary

The repair removes implicit grant preservation, carries grants explicitly
through node-state mutations, filters revoked grants, updates live service ACLs,
starts/stops/reconciles the listener after saved grant changes, and suppresses
connectable discovery advertisement for the deliberately loopback-only listener.
It does not invent target-side two-machine provisioning.

## Validator findings

### Opposing Agent 1 - Patch/Reproduction Skeptic

**Verdict: incomplete repair; revocation remains incorrect.**

- Grant persistence itself reproduces correctly. `ClusterStore.save()` followed
  by `load()` preserved a valid `PeerGrantRecord`, and the focused
  `test_target_owned_peer_grants_round_trip` passed.
- The live ACL replacement seam behaves correctly in isolation:
  `RemoteService.update_grants()` validates and replaces its map, and the
  focused per-caller authorization test passed. The controller save path also
  invokes `_sync_peer_listener_grants()` after a successful save.
- Revocation does not remove the target-owned grant. In
  `maintenance/ui/window_node_actions.py:316-326`,
  `revoke_trusted_node()` filters the revoked node from `trusted_nodes` but
  passes `controller._cluster_state.peer_grants` through unchanged. A direct
  controller reproduction produced a saved state with no trusted record but
  still with `peer_grants == (grant for "peer",)`. With a live server seam,
  `_sync_peer_listener_grants()` consequently called `update_grants()` with
  the revoked caller and did not call `stop()`.
- This is not just a persistence display issue: `RemoteService.handle()` uses
  the live grant map for credential selection and authorization
  (`maintenance/remote.py:523-529`, `621-629`). The revoked credential remains
  accepted until some unrelated ACL replacement removes it. No focused test
  currently covers revocation-to-live-ACL behavior.
- The revocation save-failure path is also non-atomic: the registry is mutated
  by `registry.revoke_trusted()` before `_save_cluster_state()` and returns on
  failure without restoring the prior trusted context (`window_node_actions.py:310-329`).
  I did not classify this as a separate patch-introduced finding because the
  primary confirmed defect already prevents correct revocation, but it is a
  regression risk for the same operation.
- Listener lifecycle behavior otherwise reproduced as intended. The existing
  discovery/session/network focused tests passed; the direct positive seam
  checks confirmed grant update and stop calls, and a `DiscoverySession` probe
  produced `connectable=False` and `port=None` when the listener endpoint
  reported loopback-only/unadvertisable. The 146-test focused command passed:
  `python3 -m unittest tests.test_cluster tests.test_remote_contract tests.test_discovery_session tests.test_network_discovery tests.test_discovery_end_to_end tests.test_window_nodes -v`.

**Conclusion:** grant creation/round-trip persistence, ordinary live ACL
replacement, listener lifecycle seams, and suppression of false connectable
advertisement are supported by tests and probes. Revocation is disproven by a
minimal reproduction and should not be accepted as repaired until it removes
the grant, stops the listener when no grants remain, and rolls back runtime
state if persistence fails.

### Opposing Agent 3 - Architecture/Security Skeptic

**Findings**

1. **P1 - Grant replacement is not concurrency-safe at the authorization boundary.**
   `RemoteService.handle()` selects a credential from `self._grants` and verifies
   the request, but `_solve()` and `_response_secret()` read `self._grants`
   again after verification (`maintenance/remote.py:516-605`). `update_grants()`
   replaces the mapping without a lock or generation/snapshot binding
   (`maintenance/remote.py:588-595`). A request verified with the old grant can
   therefore be solved under a newly installed grant. In a deterministic
   counter-test, a request with only `DASHBOARD_READ` was paused after
   verification; the grant was then replaced with a new secret and
   `PROCESS_REVIEW`; the old-credential request called `process_candidates()`
   and returned `accepted`. This is a stale-credential privilege-transition
   race, not merely a failed client response. Destructive operations have the
   same authorization race and could execute after the ACL snapshot changed.

2. **P1 - Empty live ACL updates fail open inside the service.**
   `RemoteService.handle()` treats an empty `_grants` mapping as legacy/root
   secret mode (`maintenance/remote.py:522-529`), while
   `update_grants({})` accepts and installs that empty mapping
   (`maintenance/remote.py:588-595`). A disposable counter-test called
   `update_grants({})` on a running grant-mode service and then authenticated
   with its bootstrap secret; `hello()` was accepted. The application-level
   `_sync_peer_listener_grants()` currently stops the server before passing an
   empty mapping (`window.py:642-660`), so this is not reproduced through the
   normal revoke callback, but the public live-update API itself is not
   fail-closed and is vulnerable to future caller/lifecycle drift. A revoked or
   transiently empty ACL must not reactivate bootstrap authentication.

3. **P2 - Listener lifecycle is safe but intentionally non-deployable for
   cross-machine pairing.** The current repair correctly makes
   `_listener_endpoint()` return `(False, None)` (`window.py:944-947`), so the
   discovery advertisement does not claim a reachable endpoint. The actual
   `RemoteSocketServer` still defaults to loopback (`maintenance/remote.py:803-817`)
   and the window starts it with `host="127.0.0.1"` (`window.py:979`). This is
   fail-closed endpoint exposure, not an authorization bypass, but it means the
   implemented pairing flow cannot provide two-machine operation. No LAN bind
   or target-side provisioning should be inferred from the local grant record.

4. **P2 - Pairing remains one-sided and cannot establish target authorization.**
   `pair_discovered_node()` creates a local `TrustedNodeRecord` and
   `PeerGrantRecord` (`maintenance/ui/window_node_actions.py:112-149`), but no
   authenticated pairing RPC writes the corresponding grant on the target.
   Consequently, local persistence and listener ACL state can agree while the
   other machine still has no matching credential. The existing identity
   fingerprint confirmation protects against silent identity replacement, but
   it does not solve credential delivery or target-side consent. This remains
   an explicit residual two-sided pairing risk, not a defect newly introduced
   by the ACL synchronization repair.

**Counter-tests and validation**

- `python3 -m unittest tests.test_remote_contract tests.test_cluster tests.test_window_nodes tests.test_discovery_session -q`: 106 tests passed.
- Disposable listener/service test confirmed `update_grants({})` followed by
  bootstrap-secret `hello()` was accepted.
- Disposable threaded service test paused a request after verification,
  replaced the caller grant, and confirmed the old-credential request gained
  the replacement permission and reached `process_candidates()`.
- No app code or tests were modified. `python` was unavailable; equivalent
  `python3` commands were used.

**Assessment**

The repair is materially safer on persistence, revocation through the window
path, and endpoint advertisement, and its normal zero-grant window path stops
the listener. It is not fully safe under concurrent ACL mutation, and the
service-level empty-ACL fallback is not fail-closed. The two-sided pairing
limitation remains unresolved by design.

### Opposing Agent 4 - External-Research Skeptic

**Scope and research basis**

- Reviewed the current repair in `maintenance/remote.py`,
  `maintenance/cluster.py`, `maintenance/components/discovery_session.py`,
  `maintenance/ui/window_node_actions.py`, and the listener/persistence callers
  in `window.py`. Existing worktree changes outside those paths were not
  attributed without direct evidence.
- Official references used: Python `socketserver` docs
  (<https://docs.python.org/3/library/socketserver.html>), Python `socket` docs
  (<https://docs.python.org/3/library/socket.html>), Python `threading` docs
  (<https://docs.python.org/3/library/threading.html>), Python `json` docs
  (<https://docs.python.org/3/library/json.html>), and Python Tkinter threading
  model (<https://docs.python.org/3/library/tkinter.html#threading-model>).
- These references establish library semantics only. The findings below rely on
  current repository call paths and focused local checks; no live second-host or
  production service was used.

**Finding**

1. **P1 confirmed: revocation still leaves the target-owned grant persisted and
   authorized in the running service.** `revoke_trusted_node()` retains
   `peer_grants=controller._cluster_state.peer_grants` while removing the
   trusted-node record (`maintenance/ui/window_node_actions.py:316-326`). The
   successful save then publishes that unchanged grant set and calls
   `_sync_peer_listener_grants()` (`window.py:632-660`), so the live service is
   explicitly updated with the revoked caller's credential rather than removing
   it. On reload, `ClusterStore` serializes/deserializes `peer_grants`
   (`maintenance/cluster.py:538-565`, `:705-716`), so JSON persistence does not
   provide deletion implicitly. A caller whose trusted-node row was removed can
   therefore continue to authenticate with the retained grant.

   Focused source check output:

   ```text
   revoke_constructs_peer_grants= True
   revoke_filters_node_grant= False
   ```

   This is repository proof, not an inference from JSON behavior. Python's JSON
   documentation says lists/objects are serialized and decoded as data; it does
   not define application-level cascade deletion.

**External-semantics checks and non-findings**

- The listener is now deliberately non-advertised: `_listener_endpoint()`
  returns `(False, None)` (`window.py:944-947`), and `DiscoverySession` omits the
  port when `connectable` is false (`maintenance/components/discovery_session.py:100-110`).
  This removes the prior false LAN endpoint. The actual server still binds
  `host="127.0.0.1"` (`window.py:979`); Python's socket documentation defines
  the IPv4 bind address as the address selected for the socket, and the
  `socketserver` documentation exposes that address through `server_address`.
  A focused real-server probe reported `('127.0.0.1', <ephemeral-port>)`, which
  is consistent with the intentionally loopback-only behavior, not a new bug.
- `ThreadingTCPServer` creates a handler per request. The implementation sets
  `daemon_threads=True` and `block_on_close=False` (`maintenance/remote.py:862-875`),
  matching the documented shutdown behavior for daemon handlers. `shutdown()`
  is called from the Tk/controller thread while `serve_forever()` runs on the
  server thread, satisfying the documented different-thread requirement. I
  found no confirmed shutdown defect in this repair.
- The length prefix is read with repeated `recv()` calls and bounded before
  `json.loads()` (`maintenance/remote.py:706-728`). This matches the official
  socket stream semantics and the JSON documentation's warning to limit
  untrusted input size. The request and response paths enforce the same
  `MAX_ENVELOPE_BYTES` bound; no framing or JSON semantic defect was confirmed.
- Listener handlers perform network/service work off the Tk thread. UI callbacks
  remain routed through the controller's queued UI path rather than invoking
  widgets from the socket handler. This is consistent with Tkinter's documented
  single-interpreter/event-loop model; no Tk/network threading violation was
  proven here.
- `update_grants()` replaces the grant mapping while threaded handlers may be
  active (`maintenance/remote.py:588-594`, `:623-629`). Python's threading docs
  establish shared memory and recommend synchronization for shared state, and
  `socketserver` likewise cautions that threaded services with mutable state may
  need locks. I did not promote this to a separate confirmed bug: the current
  replacement is a short-lived immutable-value transition, and no deterministic
  authorization bypass was reproduced. A lock or generation-consistent ACL
  test would be the safest follow-up if live ACL updates are required to be
  linearizable.

**Focused validation**

- `.venv/bin/python -m unittest tests.test_remote_contract tests.test_cluster tests.test_window -q`: 146 passed.
- Real `RemoteSocketServer` probe: bound address `127.0.0.1`, bound port was
  ephemeral, and the server thread was daemonized.
- `./lr --list` and `./lr impact` were unavailable because `./lr` is absent from
  this checkout. No result was inferred from that absence.
- No application code or tests were changed. The only artifact change is this
  reviewer-owned section.

**Conclusion**

The repair is externally consistent for loopback binding, bounded TCP framing,
daemon-thread shutdown, JSON size handling, and Tk-thread isolation. It is not
safe to approve as an authorization repair while revocation retains the
corresponding `peer_grants` record and reapplies it to the live listener. The
revocation finding is repository-proven P1; the concurrent ACL-transition point
is an explicitly unconfirmed follow-up risk.

## Agent 5 evidence audit

**Independent evidence audit: incomplete repair; three authorization defects are
confirmed.**

**Confirmed: revocation does not remove the target-owned grant.**

- `maintenance/ui/window_node_actions.py:306-326` removes the trusted-node
  record but copies `controller._cluster_state.peer_grants` unchanged into the
  replacement state. `ClusterStore._serialize()` and `_parse()` persist and
  restore that grant independently; there is no implicit cascade.
- I reproduced this through the controller seam using a synthetic trusted node,
  matching `PeerGrantRecord`, and a successful save callback. After
  `_revoke_trusted_node("peer")`, the trusted record was absent but the matching
  grant remained in `_cluster_state.peer_grants`.
- `_save_cluster_state()` publishes the state and calls
  `_sync_peer_listener_grants()`. With that retained grant, the live server
  received `update_grants()` and `stop()` was not called. The next request using
  the retained credential therefore remains eligible for authentication.
- This directly violates the plan's immediate-revocation rule (lines 239-241
  and 632-633), not merely a UI or registry consistency property.

**Confirmed: permission updates propagate for an existing grant.**

- `set_node_permissions()` updates the matching `TrustedNodeRecord` and
  `PeerGrantRecord` before calling `_save_cluster_state()`
  (`maintenance/ui/window_node_actions.py:226-274`). The save hook then maps
  the grant and calls the live server's `update_grants()`.
- My controller probe observed one live `update_grants()` call with the updated
  permission set. The repository's permission-toggle test also passed.
- This positive result does not repair revocation: revocation uses a separate
  state-construction path that never filters grants.

**Confirmed: listener reconciliation and stop behavior are correct on the
normal window paths, with one context-selection risk.**

- `_save_cluster_state()` synchronizes only after persistence succeeds. An
  existing server is updated in place; an empty grant mapping calls `stop()`
  and clears `_peer_server`; a missing server starts only when grants exist.
  Application shutdown also captures and stops the server before discovery
  teardown (`window.py:2468-2475`). These branches are supported by source
  inspection and the focused tests/probes.
- However, `_start_peer_listener()` constructs the target service from
  `self._node_registry.selected_context()` and the mirrored
  `self.analyzer`/`self.process_manager` (`window.py:964-977`). The selected
  context can be a trusted remote node, while this listener is the local
  target listener. If the listener is stopped and subsequently restarted while
  a remote node is selected, the new service can be built with remote context
  data. This is a confirmed caller/context mismatch by code path, although I
  did not start a real socket with a remote-selected context; impact is
  unresolved without an end-to-end scenario demonstrating restart in that UI
  state.

**Confirmed: false connectable advertisement is suppressed.**

- `AppWindow._listener_endpoint()` deliberately returns `(False, None)` and
  `DiscoverySession.start()` emits `port=None` whenever `connectable` is false
  (`window.py:944-947`; `maintenance/components/discovery_session.py:100-115`).
- The focused discovery tests passed, and the independent source/probe result
  was `connectable=False` with no advertised port. The actual server binding is
  also explicitly loopback (`window.py:979`), so no false LAN endpoint was
  found in this repair.

**Confirmed: empty live ACL is not fail-closed at the service API.**

- `RemoteService.handle()` uses the bootstrap `self._secret` whenever
  `self._grants` is empty (`maintenance/remote.py:521-529`), while
  `update_grants({})` accepts and installs an empty mapping (`:588-595`).
- I created a grant-mode service, called `update_grants({})`, then signed a
  `hello` request with the bootstrap secret. It was accepted. This is
  independently reproducible even though the normal window reconciliation
  stops the server before submitting an empty ACL.
- The application path therefore currently mitigates the state transition, but
  the public mutable service boundary itself violates the plan's revoked/empty
  ACL fail-closed requirement and is vulnerable to future caller or lifecycle
  drift.

**Confirmed: ACL replacement is not generation-consistent across one request.**

- `handle()` chooses the credential from `_grants`, verifies the request, then
  calls `_response_secret()` and `_solve()`. `_response_secret()` and
  `_solve()` read `_grants` again (`maintenance/remote.py:537`, `:596-605`,
  `:614-629`); `update_grants()` replaces the mapping without a lock or a
  request-bound grant snapshot (`:588-595`).
- I paused a request after signature verification, replaced the caller grant
  from `DASHBOARD_READ`/old secret to `PROCESS_REVIEW`/new secret, and resumed
  it. The request signed with the old secret successfully reached
  `process_candidates()` and returned `status="ok"`. This is a deterministic
  authorization race, not a timeout or a speculative threading concern.
- The same pattern can also produce inconsistent response-secret selection
  during revocation or replacement. The plan requires authorization on every
  request and immediate revocation; the current handler does not bind the
  verified request to the grant version used for verification.

**Persistence and malformed-data checks.**

- Grant round-trip persistence passed, and the existing malformed/duplicate
  grant tests passed. Those tests prove serialization validation only; they do
  not prove controller revocation or live authorization reconciliation.
- No two-sided target provisioning was added by this patch. That remains an
  unresolved product/design limitation rather than evidence that the local
  persistence repair succeeded end to end.

**Independent validation.**

- `python3 -m unittest tests.test_remote_contract tests.test_cluster tests.test_discovery_session tests.test_discovery_end_to_end tests.test_window_nodes -q`: 110 passed.
- Controller probes reproduced retained grants after revocation and live
  permission-update delivery.
- Service probes reproduced bootstrap acceptance after `update_grants({})` and
  the paused-request privilege transition after ACL replacement.
- No application code or tests were modified. No final patch decision is made

## Main auditor rebuttal

All four fallback opposers and Agent 5 completed. Their review caught a real
misapplied revoke filter in the first repair attempt. That filter has now been
placed in `revoke_trusted_node()` and ordinary state changes explicitly retain
grants. The service was then hardened so grant mode remains fail-closed when
the ACL becomes empty, and each request uses one immutable grant snapshot for
credential, response signing, and operation permissions.

Final validation after those corrections passed 1007 tests, Ruff, full Mypy,
touched-source Pyright, and `git diff --check`. Full Pyright still reports only
the two generated `build/lib` duplicate-module errors. The loopback listener is
not advertised as connectable, so the application is fail-closed rather than
claiming unsupported cross-machine connectivity.

The remaining two-sided pairing/provisioning limitation is intentional and
still blocks declaring the peer feature complete. Local ACL revocation,
permission propagation, listener reconciliation, empty-ACL handling, and false
endpoint advertisement are repaired. A target-side pairing ceremony and an
explicit network exposure policy remain necessary before enabling remote peer
operation across machines.

## Final patch decision

safe for the local ACL/lifecycle repair; peer feature remains incomplete

## Remaining risk

Two-sided target provisioning remains intentionally unresolved. Loopback-only
listener behavior is safe but does not provide cross-machine peer operation.
No live two-machine exchange or live Tk display smoke test was run.
