### Opposing Agent 3 - Architecture/Security Skeptic

**Findings**

1. **P1 - Remote activation is not deployable across machines.** `AppWindow._start_peer_listener()` constructs `RemoteSocketServer(service, host="127.0.0.1")` (`window.py:931-967`), while discovery advertises `connectable=true` and the bound port (`discovery_session.py:100-113`) and publishes non-loopback interface addresses (`network_discovery.py:487-528`). A peer therefore receives an apparently connectable LAN endpoint that is not listening on that LAN address. Counter-test: starting the real `RemoteSocketServer` confirmed `server._server.server_address[0] == "127.0.0.1"`. Impact is a broken remote-management trust boundary: users can approve a peer and receive a reachable-looking endpoint, but no cross-host authenticated exchange can complete. Either the service must deliberately bind a reachable interface with an explicit exposure policy, or discovery must not advertise it as connectable.

2. **P1 - Pairing does not establish a shared credential with the target.** `pair_discovered_node()` generates a new `TrustedNodeRecord.secret` and stores the same value in a local `PeerGrantRecord` (`window_node_actions.py:112-147`), but there is no authenticated pairing RPC or other target-side write. The target listener loads grants only from its own persisted `cluster.json` at startup (`window.py:931-960`). Thus the caller stores secret A while the target still has no grant (or an independently generated secret). Counter-test: a `PeerGrant` with secret `"a" * 64` rejected an `AuthenticatedNodeProvider` using `"b" * 64` with `RemoteAuthError`. This is not merely missing UI: the target-side authorization database is never changed, so activation cannot succeed from the implemented pairing flow.

3. **P1 - Revocation is not a credential revocation and can leave the listener authorizing the removed node.** `revoke_trusted_node()` creates a new `ClusterState` without `peer_grants` (`window_node_actions.py:297-329`). The controller's `_save_cluster_state()` explicitly restores the previous grants whenever the candidate has no grants (`window.py:630-646`), so the persisted grant survives revocation. Independently, the running `RemoteService` copied grants at listener startup (`window.py:936-967`, `remote.py:491`); revocation neither stops/rebuilds the listener nor updates that service. Counter-test using the actual `_save_cluster_state()` path reproduced that a revoke-shaped state still saved the original grant. A removed trusted node can therefore retain authenticated access until a separately corrected state and process restart, violating the expected revoke boundary.

4. **P2 - Pair/revoke lifecycle and listener lifecycle can diverge even when persistence succeeds.** The listener is started once during `AppWindow.__init__` before discovery (`window.py:219-223`) and only stopped on close (`window.py:2450-2454`). Pairing adds a grant after that point, but no listener refresh occurs; revocation removes a registry node but does not remove its live grant. This produces asymmetric behavior between persisted authorization, in-memory authorization, discovery's `connectable` advertisement, and the UI's trusted-node list. The defect is especially risky because the UI reports pairing/revocation as completed while the network service has not adopted the same state.

**Architecture/security controls verified**

- Discovery candidates remain untrusted and non-selectable in `NodeRegistry`; discovery alone does not grant capabilities (`nodes.py:509-538`, `nodes.py:563-630`).
- Requests are HMAC-authenticated, freshness-checked, replay-cached, target-bound, and caller-bound when grants are configured (`remote.py:272-344`, `remote.py:516-545`). Response node/request correlation is also checked client-side (`remote.py:1041-1059`).
- Remote operations enforce both target capability and caller permission below the UI (`remote.py:606-664`), and process actions remain delegated to the target's safety-checked `ProcessManager` (`actions.py:60-123`). No cleanup operation is exposed through the remote operation map.
- Node-qualified operation keys, generation checks, cancellation events, and render invalidation provide meaningful node/async isolation (`nodes.py:277-292`, `window.py:780-806`, `coordinator.py:438-484`). The 1007-test suite includes late-result, node-switch, and cancellation coverage, but does not cover live grant mutation/revocation or a real two-host exchange.
- Atomic persistence uses temp-file replacement and file/directory fsync (`persistence.py:38-106`), but atomicity cannot compensate for the authorization-state omission and stale in-memory listener noted above.
- Cleanup remains target-bound in the local implementation: `FileManager` rejects symlinks, paths outside resolved Downloads, non-files, and identity changes before `send2trash` (`actions.py:252-299`).
- UI delivery is routed through the queued `_submit_ui` path and drained on the Tk thread (`window.py:1401-1414`; `coordinator.py:301-310`, `coordinator.py:644-655`). Partial-init guards exist for discovery/daemon paths, but listener startup assumes `_cluster_state` and a selected context have already been constructed (`window.py:931-967`); this is safe for normal construction order, not for arbitrary partial-window invocation.

**Findings**

1. **P1 confirmed: a connectable peer listener is advertised but is bound only
   to loopback.** `window.py:961` constructs `RemoteSocketServer(service,
   host="127.0.0.1")`. The new `_listener_endpoint()` reports its bound port
   as connectable (`window.py:926-929`), and
   `DiscoverySession.start()` puts that value into the discovery advertisement
   (`maintenance/components/discovery_session.py:98-112`). A peer on another
   machine therefore receives `connectable=True` and a port, then
   `AuthenticatedNodeProvider` attempts `SocketRemoteTransport(address, port)`
   (`window.py:1138-1153`), but the target accepts only connections addressed to
   its own loopback interface. Python's official socket docs define
   `127.0.0.1` as a local loopback address and `socketserver` binds the server
   to the supplied address. Focused evidence: a real `RemoteSocketServer`
   instance in this environment reported `server_address ==
   ('127.0.0.1', <ephemeral-port>)`; the source simultaneously reports that
   endpoint as connectable. This is a network behavior mismatch, not merely an
   untested deployment assumption. Either the listener must bind an address
   reachable by the advertised peers, or discovery must not advertise it as
   connectable.

2. **P1 confirmed: pairing does not make the newly paired target reachable, and
   the grant direction is not provisioned across machines.**
   `maintenance/ui/window_node_actions.py:131-147` creates a local
   `PeerGrantRecord` for the discovered node using the newly generated local
   `record.secret`; it only calls `controller._save_cluster_state()` at
   `:149`. There is no remote grant-provisioning operation anywhere in the
   current source (`PeerGrant`/`peer_grants` references are confined to the
   local store, local listener construction, and tests). The listener is also
   attempted only once during startup (`window.py:221`), before the pairing UI
   can create a grant, so a process started with no grants never starts a
   listener after pairing. On the remote side, `RemoteService.handle()` selects
   credentials from its own `_grants` map (`maintenance/remote.py:521-529`), so
   saving a grant on the caller cannot configure the target's authenticator.
   Consequently, a normal two-machine pair cannot establish the advertised
   authenticated exchange: the caller's local grant is not a credential known
   by the target, and the target listener is absent unless grants were already
   persisted before startup. The in-process grant unit test
   (`tests/test_remote_contract.py:446-476`) proves authorization when grants
   are manually injected; it does not prove the pairing flow provisions them.

3. **P1 confirmed: revocation preserves the revoked peer's grant and leaves an
   already-running listener authorized.** `revoke_trusted_node()` constructs a
   `ClusterState` without `peer_grants` (`maintenance/ui/window_node_actions.py:307-316`),
   but `_save_cluster_state()` explicitly replaces an empty grant set with the
   previous one (`window.py:630-636`). Thus the subsequent JSON persistence
   still contains the revoked caller's credential. The running
   `RemoteService` also captures a copy of grants when the listener is created
   (`window.py:936-958`; `maintenance/remote.py:491-493`), and revocation does
   not stop/recreate that server. A revoked caller can therefore continue to
   authenticate to the target until process shutdown, and the grant survives
   reload. This is directly reproducible from the state construction and
   preservation branch; JSON's documented object/list serialization semantics
   do not provide any deletion behavior that would counteract it.

### Five-phase evidence audit

#### 1. Challenge each opposition claim

- **Opposition 1:** The three grant/listener claims survive current-tree review.
  Pairing creates a `PeerGrantRecord` in the initiating process's local state
  (`maintenance/ui/window_node_actions.py:131-147`), never sends a target-side
  provisioning request, and does not retry `_start_peer_listener()` after the
  startup-only call (`window.py:221`, `931-967`). Revocation and permission
  changes construct states without grants, but `_save_cluster_state()` preserves
  the old grants (`window.py:630-642`). This means revocation cannot remove the
  grant and permission changes cannot update its ACL. The opposition's impact is
  therefore confirmed, with the important refinement that ordinary pairing also
  uses the wrong grant direction: it authorizes the discovered node as a caller
  of the initiator rather than provisioning the initiator on the target.

- **Opposition 2:** The target-provisioning finding is confirmed. Its older
  claim that ordinary state updates silently lose grants is disproven for the
  current tree because `_save_cluster_state()` now publishes the preserved state
  to `self._cluster_state`. That repair does not make intentional revocation
  possible; it creates the narrower, confirmed revoke/ACL-staleness defect.
  The claimed non-bounded shutdown hang is disproven by current code:
  `daemon_threads=True` and `block_on_close=False` (`remote.py:854-866`). The
  duplicate-grant claim is also disproven: `_parse()` removes all grants for a
  duplicated caller (`cluster.py:548-555`). The missing target provisioning and
  endpoint/lifecycle findings remain.

- **Opposition 3:** The source and official socket semantics support the
  cross-host usability concern, but not a LAN exposure concern. Production
  binds `host="127.0.0.1"` (`window.py:961`), while discovery publishes a port
  as connectable whenever the server exists (`discovery_session.py:101-110`).
  Thus the endpoint is not reachable from another installation, although it is
  not exposed on the LAN. The pairing and post-cancellation target-work claims
  remain confirmed. The claimed shutdown hang is not current behavior; daemon
  handlers bound application shutdown, while provider work may still continue.

- **Opposition 4:** The P2 unbounded-handler-admission concern survives. The
  current `ThreadingTCPServer` creates a handler per accepted request; queue size
  16 limits pending connections, not active handler threads (`remote.py:854-869`).
  This is a resource-policy defect, not the disproven non-daemon shutdown hang.
  The “no LAN binding” conclusion is correct as stated, but it does not rescue
  the product requirement for two ordinary installations to connect. The
  readiness/interleaving concern remains **needs more evidence**, not a failure
  proven by the immediate start/stop probe.

#### 2. Independent counter-test/reproduction

The state probe reproduced `save_empty_grants_preserved=True`: a revoke-shaped
state still saves the prior target grant. The listener probe reproduced
`listener_binding=127.0.0.1`. Static source probes independently reported
`pair_has_remote_provisioning_symbol=False`,
`pair_local_grant_caller_field=True`, and
`revoke_explicitly_filters_peer_grants=False`.

The focused and full suites passing is useful positive evidence for codec,
projection, and local lifecycle behavior, but none exercises a two-process pair,
post-pair listener startup, live grant mutation, or a revoked request against a
running service. The absence of those tests cannot disprove the reproduced
source paths.

#### 3. Sibling bugs and lifecycle/drift search

The prior peer-network plan explicitly lists target provisioning, atomic
revocation, bounded handlers, and listener endpoint lifecycle as required
boundaries (plan lines 221-241 and 353-377). The current implementation matches
the transport authentication and typed-denial portions, but the pairing,
revocation, and listener lifecycle remain incomplete. Related prior reviews and
the active bug ledger show a recurring pattern of UI/persisted-permission state
drift; this patch repeats that pattern at the target-owned grant boundary.
No evidence was found that the existing process/file safety boundaries or
snapshot node-correlation protections regressed.

#### 4. Least-reasonable assumptions and drift map

The least-reasonable assumptions are that persisting a local grant provisions a
remote target, that an empty grant tuple means "clear grants" despite a helper
that treats it as "preserve grants," that a daemon handler implies bounded
provider work, and that a connectable advertisement implies a reachable
endpoint. Each conflicts with an exact caller/callee path. The strongest drift
is between the plan's equal-peer/two-sided-pairing completion criterion and the
one-sided local `pair_discovered_node()` implementation. A secondary drift is
between the plan's bounded handler requirement and the unbounded
`ThreadingMixIn` admission model.

#### 5. Severity and fix scope

Confirmed release-blocking concerns are:

1. **P1 authorization/functionality:** ordinary pairing cannot establish a
   two-sided authenticated relationship and does not start a listener created
   after startup.
2. **P1 authorization:** revocation leaves the credential persisted and live;
   permission edits leave target-owned grant permissions stale. The UI's
   success message is misleading and the next request can remain authorized.
3. **P1 availability/functionality:** the advertised listener is loopback-only,
   so the required cross-machine path cannot complete.
4. **P2 availability/resource:** client cancellation returns locally while the
   target provider continues, and request admission has no active-handler bound.

The narrowest safe repair is to define and implement the two-sided pairing
ceremony, make target grants the sole authoritative mutable ACL, reconcile or
stop/restart the listener atomically after grant changes, advertise only an
actually reachable endpoint under an explicit exposure policy, and add bounded
handler/cancellation lifecycle tests. Do not repair this with a broad controller
rewrite or by weakening fail-closed checks.

**Disproven:** current non-daemon shutdown hang, duplicate-grant loading defect,
production LAN exposure, and the claim that ordinary non-revoke state updates
currently discard grants. **Needs more evidence:** immediate-stop readiness
interleavings and the exact duration/resource impact for each production
provider after cancellation. These uncertainties do not overturn the confirmed
pairing, revocation, endpoint, and admission defects.

## Main auditor rebuttal

All four portable fallback reviewers and the independent Agent 5 audit
completed. Their evidence converges on three confirmed P1 defects and one P2
resource-lifecycle concern:

- Pairing writes a local grant but never provisions the target authenticator or
  starts/reconciles the listener created after startup.
- The listener advertises a connectable endpoint while binding only to
  `127.0.0.1`, making the intended cross-machine path unusable. Binding to a
  wider interface is not an automatic fix because it changes the exposure
  boundary and requires an explicit policy.
- Revocation preserves the grant in persisted state and in the running service;
  permission edits likewise leave the target ACL stale.
- Handler admission and remote cancellation remain insufficiently bounded;
  the exact operational impact needs additional measurement, but the current
  `ThreadingMixIn` structure does not itself provide an active-handler limit.

The earlier claims of a non-daemon shutdown hang, duplicate-grant loading bug,
production LAN exposure, and ordinary non-revoke state updates discarding
grants were not confirmed. The full test suite passing does not cover the
missing two-machine pairing, post-pair listener lifecycle, live ACL mutation,
or revoked-request paths. The newly exposed Mypy dynamic attributes were fixed
by adding class-level annotations for `settings_home` and `thermals_page`;
these are type-only corrections and preserve runtime behavior.

The confirmed pairing and listener findings cannot be safely fixed by a
mechanical extraction change. A two-sided pairing ceremony, target-owned ACL
authority, listener reconciliation, and an explicit bind/exposure policy must
be specified before implementation. The review therefore blocks approval of
the current peer-network behavior rather than treating passing local tests as
evidence of a working whole application.

## Final patch decision

unsafe - confirmed P1 peer-network authorization/functionality defects
