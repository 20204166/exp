## Mode and risk

BugGuard mode: Mode A — code-edit validation

Reason: this changes the execution boundary of network pairing while touching

## Patch summary

Keep pairing confirmation, registry mutation, persistence, rollback, and UI
updates on Tk. Run only target-side grant provisioning through the existing
AppCoordinator using a node-qualified key. Preserve direct synchronous callers.

## Original bug / task evidence

Pairing was blocking the Tk event loop because target grant provisioning ran
synchronously from the pairing dialog callback. The approved ownership model
requires AppWindow to own dialogs and AppCoordinator to own slow work while
preserving fail-closed trust semantics.

## Validator findings

### Opposing Agent 1 — Patch/Reproduction Skeptic
**Verdict: no confirmed patch bug.**

- **Network placement:** `window.py:699-715` selects the async path only when
  the owned pairing dialog exists. `window_node_actions.py:534-540` performs
  only the injected provisioner in the coordinator task; `_prepare_pairing()`
  and `_finish_pairing()` remain outside that task. A counter-test with a real
  worker thread recorded the provisioner thread ID as different from the Tk
  caller thread, observed no cluster record before delivery, and observed the
  record appear only after invoking the coordinator's injected delivery
  callback. This disproves a Tk-thread network call in the dialog path.
- **Cancellation/stale completion:** `cancel_pairing()` increments the local
  generation, calls `AppCoordinator.cancel()`, removes the attempt, and
  restores the discovered candidate (`window_node_actions.py:572-581`). The
  counter-test cancelled before queued worker execution, then executed the
  queued worker and its late delivery; no trust record was created and the
  dialog completion callback was not called. Existing focused test
  `test_async_pairing_failure_restores_discovered_candidate` also passed.
  `is_current()` at `window_node_actions.py:528-532` rejects a delivery whose
  attempt was removed or whose generation changed.
- **Dialog lifecycle:** `PairingDialog.close()` invokes cancellation only when
  not completed (`pairing_dialog.py:99-104`); `complete()` marks completion
  before closing (`91-93`). Focused dialog tests passed, including staying open
  until completion, failure state, and cancellation. No double-close or
  completion-after-close reproduction was found.
- **Direct synchronous compatibility:** when `_pairing_dialog` is absent,
  `AppWindow._pair_discovered_node()` calls the unchanged synchronous
  `pair_discovered_node()` path (`window.py:699-707`). The focused legacy
  synchronous pairing tests passed, including confirmed mismatch repair and
  missing target-grant rejection.
- **Residual limitation, not disproven:** once `task()` has passed its initial
  cancellation check, `provisioner(attempt.grant)` has no cancellation
  argument (`window_node_actions.py:534-540`). Therefore an already-running
  network request is only cooperatively cancellable: local rollback and stale
  delivery suppression occur, but the remote request itself may finish. No
  local trust-state corruption was reproduced; assess separately if hard
  interruption or remote grant revocation is a required contract.

  — 119 passed.

### Opposing Agent 2 — Repo-Truth Skeptic
**Finding: P1, confirmed revoke race and state resurrection.**

- `AppCoordinator.run` requires `(cancel_event, progress)` task factories and
  delivers `on_result(key, result)` / `on_error(key, message)` through its
  injected delivery path (`maintenance/components/coordinator.py:442-487`,
  `489-538`). The async pairing task and callbacks match that contract.
- The operation key is `node:<node_id>:pair` via `node_operation_key`
  (`maintenance/ui/window_node_actions.py:519-524`,
  `maintenance/nodes.py:425-432`). The read-only counter-test ran two node
  keys concurrently and observed two workers, generation `1` for each, and
  callbacks delivered with the corresponding keys.
- Existing callers remain compatible: the window uses the async path only
  when `_pairing_dialog` exists and retains `pair_discovered_node` for the
  dialog-less/synchronous path (`window.py:699-715`; tests
  `tests/test_window_nodes.py:2132-2159`). `PairingDialog.confirm` still
  dispatches only the node id and remains open until explicit completion
  (`maintenance/ui/pairing_dialog.py:82-104`; tests
  `tests/test_node_toplevel_dialogs.py:253-330`).
- Pairing semantics are fail-closed locally: preparation promotes only
  read-capability trust after explicit confirmation; failure/cancel restores
  the prior context or the discovered candidate (`window_node_actions.py:333-408`,
  `320-330`, `572-581`). Successful persistence is delegated to
  `save_cluster_state`, which publishes `_cluster_state` only after store save
  (`maintenance/ui/window_context.py:37-55`).
- Revoke does not invalidate the new pairing operation. It increments only
  `_activation_generations` and cancels `test_connection`/`connect`
  (`maintenance/ui/window_node_actions.py:797-803`), while the pairing
  completion still accepts its unchanged pairing generation and calls
  `_finish_pairing` (`window_node_actions.py:519-569`). A read-only counter-test
  started async pairing, revoked `peer-a` before worker delivery, then
  delivered a successful result. It observed a persisted `peer-a` record while
  `NodeRegistry.context(NodeId("peer-a"))` remained absent. This leaves the
  persisted cluster state trusted and the live registry revoked; restart can
  restore the revoked record.
- **Residual ownership risk, not newly proven by this patch:** target grant
  provisioning precedes local persistence (`window_node_actions.py:534-569`,
  `411-441`). On local save failure, or cancellation after a non-cooperative
  remote request has already succeeded, `_restore_pairing` removes only local
  trust; no target-grant revoke operation is called. The existing remote API
  exposes capability revocation, but no pairing-grant rollback
  (`maintenance/remote.py:844-862`; no `revoke_grant` implementation found).
  Current tests cover local rollback and async false provisioning, not this
  remote orphan-grant outcome (`tests/test_window_nodes.py:2202-2229`). This
  is a follow-up ownership gap rather than a confirmed regression in the
  changed coordinator wiring, but the revoke race above is patch-introduced.

**Evidence:** `scripts/run_tests.sh tests.test_window_nodes
tests.test_node_toplevel_dialogs tests.test_components -v` — 251 passed;
inline read-only coordinator key counter-test — passed; inline revoke-race
counter-test — reproduced the finding. No app code or normal tests were

### Opposing Agent 3 — Architecture/Security Skeptic

**Finding: P1, proven — revoke can be undone by a late pairing completion.**

- **Evidence:** `pair_discovered_node_async()` promotes the candidate to a
  trusted registry context in `_prepare_pairing()` (`maintenance/ui/window_node_actions.py:367-408`),
  then records the attempt and uses a pairing-local generation (`:519-532`).
  `revoke_trusted_node()` increments only `_activation_generations` and
  cancels test/connect operations (`maintenance/ui/window_node_actions.py:797-803`);
  it does not invalidate or cancel the `node:<id>:pair` generation. The late
  `on_result()` therefore still satisfies `is_current()` (`:542-546`) and
  `_finish_pairing()` writes the trusted record back to cluster state (`:418-435`).
- **Counter-test:** A focused harness started async pairing, called
  `revoke_trusted_node(controller, "peer-a")` before worker delivery, then
  delivered the successful worker result. Observed output was
  `persisted= True registry_context= False`. Thus the revoked node is
  re-persisted while its live registry context remains absent.
- **Impact:** A user revoke is not authoritative. The target-side grant was
  already provisioned before this late completion, so the completion can
  resurrect local trust/authorization state after revocation and leave the
  runtime registry and persisted cluster state inconsistent. On restart, the
  re-persisted trust record can restore access that the user revoked.
- **Scope:** This is a patch-introduced cancellation/generation and
  authorization-state race, not a speculative concern. Existing focused tests
  cover pairing failure and ordinary cancellation, but not revoke during
  provisioning.

**Risk, not separately proven as a bug — cancellation after target acceptance.**

`cancel_pairing()` invalidates the UI generation and immediately restores local
registry state (`maintenance/ui/window_node_actions.py:572-581`), while the
cooperative worker may still be inside `provisioner(attempt.grant)`
(`:534-540`). If the target has accepted the grant before cancellation is
observed, the target may retain an authorization grant that the cancelled local
flow does not persist. The code has no compensating target-side revoke in this
path. This audit did not make a live remote call or prove target behavior, so
this remains a residual design risk rather than a confirmed finding.

- Deterministic revoke/late-delivery counter-test: reproduced the state
  resurrection described above.
- No application code, normal tests, wheels, or unrelated documentation were
  modified.

### Opposing Agent 4 — External-Research Skeptic

**Finding A4-1: cancellation is cooperative but the pairing task does not pass the
cancel signal into the remote request.**

- **Classification:** Confirmed P1 reliability/security-consistency bug.
- **Repo evidence:** `maintenance/ui/window_node_actions.py:534-540` checks
  `cancel_event` only before calling `provisioner(attempt.grant)`. The default
  provisioner is `request_target_grant` (`:516-518`), whose signature at
  `:584-606` has no cancellation argument and calls
  `AuthenticatedNodeProvider.request_pairing` without one. The underlying
  `SocketRemoteTransport.request` explicitly accepts `cancel_event` and polls
  it (`maintenance/remote_support/transport.py:116-163`), so the cancellation
  seam exists but is not used by this new task boundary.
- **External evidence:** The official Python `concurrent.futures` docs state
  that `Future.cancel()` returns `False` when the call is already executing and
  cannot be cancelled:
  <https://docs.python.org/3/library/concurrent.futures.html#concurrent.futures.Future.cancel>.
  The same documentation says running futures are not cancelled by executor
  shutdown. Therefore `AppCoordinator.cancel()` (`maintenance/components/
  coordinator.py:687-699`) can set the event and invalidate delivery, but cannot
  stop an in-progress network call. The task does not propagate the event to
  that call.
- **Impact/reproduction:** Start pairing, allow the worker to enter the network
  request, then close the dialog. `cancel_pairing` immediately restores local
  discovery state (`maintenance/ui/window_node_actions.py:572-581`), while the
  worker may continue and the target may accept the grant. Its eventual result
  is dropped by the coordinator, so there is no compensating target-side revoke.
  This leaves target authorization and local trust state divergent, and can
  also retain the worker until the transport timeout.
- **Scoped remediation:** Make the grant-provisioning callable accept and pass
  the coordinator's `cancel_event` through to the transport/provider path, and
  define whether cancellation after a remote acceptance requires a compensating
  revoke. At minimum, check cancellation after the request before treating the
  operation as successful; do not claim that `Future.cancel()` interrupts a
  running request.

**Tk thread-affinity assessment: no finding.** The official Tkinter threading
model says long-running work should run outside event handlers and that Tk calls
from another Python thread are posted to the interpreter event queue when
supported: <https://docs.python.org/3/library/tkinter.html#threading-model>.
Here, preparation and `_finish_pairing` run in delivered callbacks, while the
worker body is limited to provisioning (`:534-540`); `AppWindow` injects
`deliver=self._submit_ui` (`window.py:238-243`), and `_submit_ui` queues work for
the Tk drain (`window.py:963-970`). I found no evidence that this patch invokes
widgets from the worker. Tcl's official `after` documentation also states that
scheduled commands execute only when the event loop is entered:
<https://www.tcl-lang.org/man/tcl8.6/TclCmd/after.htm>; this supports the
queue/drain model but does not cure the cancellation issue above.

**Research boundary:** Official Python/Tkinter and Tcl documentation was used
first. The Python documentation targets the repository's supported Python
range (`pyproject.toml:9`, `>=3.10`) for the cited `Future.cancel` contract;
the cited rule is not version-specific in the relevant API. No secondary web
source was used.

## Agent 5 evidence audit

**Independent verdict: both reported concerns are patch-relevant; the revoke
race is proven, and the cancellation concern is proven at the request-boundary
level with conditional target-side orphan impact. Both remain P1 until the
trust/grant lifecycle is made authoritative.**

### 1. Revoke during pairing can resurrect persisted trust

- **Confirmed, patch-introduced.** `pair_discovered_node_async()` stores the
  attempt under `_pairing_generations` and the `node:<id>:pair` coordinator key
  (`maintenance/ui/window_node_actions.py:519-532`). The revoke path only
  advances `_activation_generations` and cancels `test_connection`/`connect`
  (`maintenance/ui/window_node_actions.py:797-803`); it does not invalidate
  the pairing generation or remove `_pairing_attempts[node]`.
- A late successful delivery therefore still passes `is_current()` and
  `_finish_pairing()` calls `_save_cluster_state()` (`:542-546`, `:418-435`).
  Revoke has already saved a state without the node (`:781-795`), so the late
  completion can write a fresh `TrustedNodeRecord` back. The registry remains
  without the context because revoke deleted it (`maintenance/nodes.py:1020-1030`),
  while startup restoration trusts persisted records
  (`maintenance/components/node_context.py:80-139`). This is an actual
  persisted/live-state inconsistency, not merely a stale UI callback.
- Opposer 2/3's deterministic reproduction (`persisted=True`, registry
  context absent) is consistent with the code path. The impact statement that
  a restart can restore the record is accurate. The relevant safe fix boundary
  is to invalidate/drop the pairing attempt and cancel the pairing key as part
  of the successful revoke transition, before any late completion can be
  accepted. Do not call the current `cancel_pairing()` blindly after deleting
  the context: its rollback assumes the promoted context still exists and
  could itself raise or restore state over a completed revoke. Use a revoke-
  specific invalidation/cleanup ordering that never re-registers the revoked
  node.

### 2. Cancellation does not reach the running remote request

- **Confirmed request-boundary regression, patch-introduced exposure.** The
  coordinator supplies `cancel_event` to `task()`, but the task checks it only
  once and then calls the one-argument `provisioner(attempt.grant)`
  (`maintenance/ui/window_node_actions.py:534-540`). The default path reaches
  `request_target_grant()` and `AuthenticatedNodeProvider.request_pairing()`,
  whose signatures do not accept or forward a cancellation event
  (`window_node_actions.py:584-606`; `maintenance/remote.py:547-569`).
- The cancellation seam exists below this boundary: `SocketRemoteTransport`
  polls an optional event while connecting/receiving
  (`maintenance/remote_support/transport.py:116-163`), and the normal provider
  `_request()` forwards one when its caller supplies it (`maintenance/remote.py:946-980`).
  This patch does not connect those seams to pairing. The coordinator's
  `cancel()` is explicitly cooperative and a running future cannot be
  interrupted; this matches the official Python `Future.cancel()` contract:
  <https://docs.python.org/3/library/concurrent.futures.html#concurrent.futures.Future.cancel>.
- **Orphan-grant impact is conditional but credible and architecturally
  supported.** The target server handles `pair_request` outside the ordinary
  client request path and, after local approval, persists the `PeerGrantRecord`
  before returning (`maintenance/remote_support/server.py:96-110`;
  `maintenance/ui/window_discovery.py:369-413`). Client-side cancellation or
  socket closure cannot undo a target handler that has already accepted and
  saved that grant. The late local result is intentionally discarded by the
  coordinator, and no pairing-grant revoke/rollback operation exists. No live
  remote call was made, so the exact timing-dependent orphan outcome is not
  independently reproduced; it must not be described as guaranteed for every
  cancellation.
- The safe remediation boundary is narrow: thread `cancel_event` through the
  async grant-provisioning callable, `request_target_grant()`, pairing request,
  and transport; check it before and after the request and never commit local
  trust for a cancelled attempt. That only bounds the client request and does
  not retract a grant already persisted by the target. If cancellation after
  target acceptance must guarantee no orphan, the protocol needs an explicit,
  authenticated, idempotent target-side grant-revocation/transaction or a
  bounded grant lease; `Future.cancel()` and socket cancellation are not such
  a mechanism. Preserve the existing synchronous compatibility path and do
  not weaken target approval or fail-closed local rollback.
