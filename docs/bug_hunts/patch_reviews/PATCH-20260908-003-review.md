# Discovery Startup and Missing TXT Identity Fix

## Main Auditor Scope

BugGuard Mode A; high-risk network-discovery and stable-identity lifecycle
change; full A4 review.

The reproduction was deterministic: two discovery instances advertised the
literal stable ID ``local``, causing the second Zeroconf registration to fail
with an empty exception string. Zeroconf could also deliver a service record
before TXT properties, producing the noisy ``local._system-analyzer._tcp.local.:
missing id`` warning.

## Patch Summary

- Persisted a unique installation node ID in the existing cluster store.
- Migrated old/default ``local`` identities to a ``node-<random>`` identity.
- Used the persisted identity for the local node descriptor and advertisement.
- Preserved the existing discovery/registry/coordinator architecture.
- Ignored transient service records without TXT identity data until a later
  update, rather than logging them as malformed peers.
- Preserved the current trust/fingerprint changes in the same worktree.

## Reproduction Evidence

Before the fix, two ``NetworkDiscovery(NodeId("local"), ...)`` instances
produced:

```text

second False 'Discovery start failed: '
```

After the fix, two independently persisted IDs produced:

```text

started True True
```

The post-fix run emitted no missing-ID warning.

### Verdict

**Primary finding: disproven after the patch.** The pre-fix duplicate local
identity failure and missing-TXT warning are reproducible from `HEAD`. A normal
startup now generates a unique local ID, persists it, reuses it on reload, and
advertises it. Failed discovery starts clean up and can be retried, while an
empty TXT record can be followed by a valid update.

### Residual issues

**Persistence failure remains a reliability gap (P2, confirmed).** If the
identity migration save fails, `ClusterStore.load()` logs the error but returns
the generated ID. A direct probe using `ClusterSaveError('disk full')` produced
different IDs on two loads (`first == second: False`). A restart under this
condition can therefore recreate the duplicate-registration risk. This is not
a normal-path regression, but the patch does not guarantee a persisted unique
identity when the store is unwritable.

The new missing-ID branch treats every ID-less record as transient, so a
genuinely malformed peer with permanently missing identity is silently ignored
rather than warned about. The focused tests verify the intended transient
behavior, but do not distinguish transient from permanently malformed records;
this is a diagnostic/observability tradeoff, not evidence of the original
startup failure.

## Opposer 2 - Repo-Truth Skeptic

### P1: Migrated local advertisements carry the legacy fingerprint

`window.py:212-220` calls `local_node_descriptor()`, which computes
`identity_fingerprint` from the hard-coded `LOCAL_NODE_ID` (`"local"`) in
`maintenance/nodes.py:216-226`. The subsequent `replace()` changes only the
descriptor ID to `ClusterState.local_node_id`; it does not recompute the
fingerprint. `_start_discovery()` then prefers that non-empty stale value at
`window.py:1548-1560`, so a migrated installation advertises `id=node-...`
with the fingerprint for `local`. The same happens for every migrated
installation, making the advertised fingerprint independent of the persisted
ID and defeating the identity-continuity check used by trusted rediscovery.

This is not covered by the current startup tests: the window integration
fixture has no persisted cluster state and asserts the legacy ID at
`tests/test_window_nodes.py:463-473`. The direct invariant check reproduced
the mismatch: after replacing the descriptor ID with `node-persisted`, its
stored fingerprint differed from `node_identity_fingerprint("node-persisted")`.

### P2: Identity migration failure causes a new local identity on every restart

`ClusterStore.load()` generates an ID and calls `_save_identity_migration()`
for a missing file or legacy `local` state (`maintenance/cluster.py:412-425`).
That helper catches `ClusterSaveError` and returns (`maintenance/cluster.py:428-432`),
while `AppWindow` continues with the newly generated in-memory ID. If the
cluster directory is temporarily unwritable, the current process works, but
the next startup generates another ID because no retry occurs and no durable
fallback exists. This breaks the promised stable installation identity and
can leave trusted/discovery records keyed to an identity that the installation
will not present again. Existing save-failure coverage tests `save()` directly
but does not exercise `load()` migration failure or a restart (`tests/test_cluster.py:246-258`).

## Opposer 3 - Architecture/Security Skeptic

### Findings

1. **P1: migrated local nodes advertise the wrong fingerprint.**
   `local_node_descriptor()` computes its fingerprint from the legacy
   `LOCAL_NODE_ID` (`nodes.py:208-227`), then `AppWindow` replaces only the
   descriptor ID with the persisted random ID (`window.py:211-220`). A focused
   probe reproduced `migrated_fingerprint_matches_id False` and
   `legacy_fingerprint_retained True`. `_start_discovery()` prefers that stale,
   non-empty descriptor fingerprint, so a migrated installation advertises
   `id=node-...` alongside the digest for `local`. This makes the displayed
   identity independent of the advertised stable ID and can cause trusted
   rediscovery to report a mismatch or, worse, mislead a user performing an
   out-of-band check. It is not a collision issue; it is an identity-binding
   defect introduced at descriptor composition.

2. **P1/P2: identity is not stable when its first persistence fails.**
   `ClusterStore.load()` generates a `node-<128-bit-random>` ID and catches
   `ClusterSaveError` in `_save_identity_migration()`, allowing startup to
   continue with an identity that exists only in memory (`cluster.py:412-432`).
   A focused probe patched `save()` to fail twice and observed two different
   IDs from two loads in the same directory:
   `identity_persistence_failure_changes_id True`. This is fail-open for the
   stable-identity contract: every restart can advertise a new node, invalidate
   peer continuity, and leave stale trusted references. It is not an
   authentication bypass, and the random ID itself has adequate collision
   resistance (128 bits from `secrets.token_hex(16)`), but startup should not
   present a durable-identity feature as stable after durable creation failed.

3. **P2 hardening: the domain layer permits fingerprint-gate bypass.**
   `AppWindow._pair_discovered_node()` rejects a candidate without TXT
   `fingerprint` before calling `promote_to_trusted()` (`window.py:1006-1031`),
   so the current UI path does not promote a TXT-less candidate. However,
   `NodeRegistry.promote_to_trusted()` accepts the same candidate and replaces
   the absent fingerprint with `node_identity_fingerprint(node_id)`
   (`nodes.py:606-612`). A focused probe promoted an ID-bearing,
   fingerprint-less candidate successfully and confirmed the fallback is the
   public hash of the stable ID. Any future caller, test seam, or alternate UI
   using the registry API can therefore create a `TRUSTED` record without the
   advertised fingerprint gate. This is not currently a remote exploit because
   discovery candidates are local observations and the normal UI blocks them;
   it is a broken security invariant at the architecture boundary and should
   be fail-closed in the promotion method itself.

4. **No confirmed service-name identity bypass.**
   Discovery uses TXT `id` as the candidate key and treats the service name as
   metadata/removal routing (`network_discovery.py:287-289, 358-377`). An
   adversary can advertise a service name that differs from its TXT ID, or
   reuse a victim's TXT ID, and can overwrite the displayed untrusted
   candidate. That does not grant capabilities: discovered entries remain
   untrusted/non-selectable, and a known trusted node is marked `MISMATCH` when
   its advertised fingerprint differs (`nodes.py:535-563`). A focused probe
   confirmed that a record named `claimed-name...` with TXT ID `txt-id` is
   stored under `txt-id`, not under the service name. The remaining effect is
   spoofed presence/UI churn, not trust escalation.

5. **Fingerprint is collision-resistant as a display digest, not an identity
   authenticator.** `node_identity_fingerprint()` is SHA-256 over a public
   attacker-selectable ID (`nodes.py:230-239`), and discovery accepts the TXT
   fingerprint without recomputing or validating it (`network_discovery.py:370-384`).
   This is suitable only for the explicitly stated out-of-band confirmation;
   anyone can generate a syntactically plausible matching digest for a chosen
   ID. The pairing dialog does tell the user to confirm through a trusted
   channel, and the separately paired secret remains the transport
   authenticator. No direct fingerprint forgery bypass was found, but accepting
   the dialog without independent confirmation is susceptible to mDNS spoofing
   by design.

### Focused adversarial probes

- TXT-less service add followed by a later TXT update: no malformed warning or
  candidate was created for the first event; the later update discovered the
  peer successfully.
- Persistence failure during identity creation: repeated loads generated
  different IDs (`True`), confirming the stable-identity failure above.
- Direct promotion of an ID-bearing candidate with no fingerprint: promotion
  succeeded and synthesized the public fallback fingerprint (`True`), while
  the normal window pairing path separately rejects missing fingerprints.

### Verdict

Random-ID collision resistance and TXT-absence handling are sound. The
durability failure is a confirmed identity-continuity defect; the registry
fallback is a confirmed defense-in-depth gap, currently unreachable through
the normal pairing UI but unsafe as a public domain boundary. Service-name
spoofing and public fingerprint forgery do not bypass trust/fingerprint gates
in the current UI flow, provided the user performs the required out-of-band
confirmation.

## Opposer 4 - External-Research Skeptic

### Findings

- **P2, confirmed residual cleanup bug: failed registration leaks the Zeroconf instance.** The official python-zeroconf API documents that `register_service()` probes for conflicts and may raise when the service name is already registered; it also documents `allow_name_change=False` as the default. The backend constructs `zc` at `network_discovery.py:118`, calls `zc.register_service()` at `:138`, and only assigns `self._zeroconf = zc` at `:141`. Therefore a duplicate-name or other registration failure leaves the created Zeroconf object unreachable to `stop()`, which only closes `self._zeroconf` at `:153-159`. Focused evidence using a fake Zeroconf whose registration raises produced `close_calls_after_failed_register=0`. This is not disproved by the new unique IDs: collisions remain possible across stale/manual records, old processes, or any registration failure, and the existing `NetworkDiscovery.start()` cleanup path explicitly calls backend `stop()` after failure.

### Semantics Checked

- **Service registration naming:** The official `ServiceInfo` API describes `name` as the complete service-instance name including type/domain. `f"{advertisement.stable_id}.{SERVICE_TYPE}"` therefore has the correct shape for `SERVICE_TYPE = "_system-analyzer._tcp.local."`; the generated `node-<hex>` IDs are valid DNS-SD instance labels. No naming defect was found in the patch.
- **Duplicate-name behavior:** The official API reference says `register_service()` probes for conflicts and, when `allow_name_change` is enabled, renames until unique. This code leaves the default disabled, so the observed failed second registration is expected rather than a Zeroconf semantic anomaly. Persisting a per-installation ID is a valid fix for the intended collision, but it does not eliminate the cleanup defect above.
- **TXT availability timing:** The official `ServiceBrowser` documentation describes callbacks for services appearing, changing, and disappearing; `get_service_info()` returns the resolved `ServiceInfo`, whose `properties` are the TXT dictionary. A service can therefore be observed before all records have converged. The focused probe delivered an empty-properties `add` followed by a populated `update`; the code ignored the first and produced one candidate on the second. That behavior is correct for this discovery contract and avoids treating a transient incomplete record as a peer.
- **Ignoring missing TXT identity:** The official `ServiceInfo` documentation identifies TXT properties as optional data carried by the service record, so an empty/missing `id` is not sufficient to construct this application’s stable identity. Returning `None` at `network_discovery.py:370-376` is correct and fail-closed for discovery. The focused probe yielded one candidate only after the later update; no peer or warning was emitted for the incomplete record.

### Evidence

- Focused existing suite: `python -m unittest tests.test_network_discovery -v` passed, 24 tests.
- Focused timing/cleanup probe: failed registration closed the Zeroconf object 0 times; empty TXT followed by populated update resulted in `peer_count_after_empty_then_update=1` and one candidate event.
- Authoritative references: python-zeroconf API reference, `ServiceInfo`, `ServiceBrowser`, and `Zeroconf.register_service()`: https://python-zeroconf.readthedocs.io/en/latest/api.html; project usage example: https://github.com/python-zeroconf/python-zeroconf/blob/master/README.rst.

### Verdict

The patch’s service-name, TXT timing, and missing-identity decisions are externally consistent. **Opposer 4 confirms one residual P2 cleanup bug in the failure path; no bug is found in the patch’s decision to ignore incomplete TXT records.**

## Agent 5 Evidence Audit

### Scope and evidence

I independently read the complete patch review, current worktree diff, affected
code, focused tests, and current test results. The focused discovery,
registry, cluster, window, and UI run passed 132 tests. The full current suite
passed 940 tests. `ruff check .`, `ruff format --check .`, `pyright`, and
`mypy --ignore-missing-imports .` all passed. The python-zeroconf API reference
was checked at https://python-zeroconf.readthedocs.io/en/latest/api.html.

### Finding-by-finding verification

- **Duplicate local identity at startup: disproven for the normal path.**
  `ClusterStore.load()` creates and persists a `node-` identity for a missing
  or legacy store. `_build_local_node_context()` uses that same ID, and
  `_start_discovery()` advertises the selected descriptor ID. The existing
  legacy reproduction still demonstrates the pre-patch failure, while the
  current reload probe produced one stable persisted ID and the current
  startup tests passed. A filesystem/persistence failure is covered separately
  below.
- **Missing TXT warning: disproven for the reported transient case.**
  `_normalize()` returns `None` when TXT has no `id`, so the transport handler
  emits neither a malformed warning nor a candidate. A subsequent update with
  an ID is accepted and produces one candidate. This is consistent with
  python-zeroconf exposing service callbacks separately from resolved TXT
  properties. A permanently malformed service remains silently ignored; that
  is an observability tradeoff, not the reported startup warning.
- **Migrated fingerprint binding: disproven.** `_build_local_node_context()`
  replaces both the legacy descriptor ID and its fingerprint, computing the
  latter from `self._cluster_state.local_node_id`. `_start_discovery()` then
  carries that descriptor fingerprint into the advertisement. The dedicated
  migrated-identity test passed and directly equals the fingerprint for the
  persisted ID.
- **Identity persistence failure behavior: narrowed, not a remaining
  duplicate-startup bug.** A failed migration save still returns an in-memory
  ID with `local_identity_persisted=False`, so repeated loads while storage is
  unwritable necessarily generate different IDs. However, `_start_discovery()`
  retries the save and returns without advertising while persistence remains
  unavailable. The direct failure probe and test confirmed the marker; code-path
  inspection confirmed the no-advertisement gate. Residual risk is reduced
  availability and identity continuity after repeated storage failure, not
  silent duplicate advertising by the current window startup path.
- **Direct registry fingerprint gate: disproven.**
  `NodeRegistry.promote_to_trusted()` now rejects a candidate without a
  fingerprint before creating trusted context. The direct promotion probe
  raised `ValueError`, and the regression test passed. The normal window gate
  is therefore backed by the domain boundary rather than being its only
  protection.
- **Zeroconf cleanup after failed registration: disproven on the production
  path.** The backend stores the newly constructed Zeroconf object before
  `register_service()`. When registration raises, `NetworkDiscovery.start()`
  invokes `backend.stop()`, which closes that object. A probe through the
  production `NetworkDiscovery.start()` path observed `start=False`,
  `active=False`, and exactly one `close()` call. Calling the backend's
  `start()` method directly and inspecting it before its caller invokes
  `stop()` is not the application lifecycle contract.
- **Retry/lifecycle ownership: disproven.** `AppCoordinator` clears the
  failed discovery instance, handlers, and callback ownership when start
  returns false. The retry probe returned `False` then `True` for the same
  object, with coordinator ownership restored only on the successful retry;
  `test_failed_start_releases_lifecycle_ownership_for_retry` also passed.
  `NetworkDiscovery` independently remains inactive after failure and clears
  partial peers.
- **Backward compatibility: supported with explicit migration.** Existing
  schema-shaped stores and trusted records without the new optional fingerprint
  field still parse. The legacy-record probe loaded one trusted record with a
  `None` fingerprint while generating and persisting a new local ID; reload
  returned the same ID. New serialization includes the optional fields, while
  omitted old fields retain their defaults. Old `local` state is intentionally
  migrated rather than advertised.

### Residual risks

The current discovery fingerprint is a public SHA-256 display aid over the
public node ID, not authentication; a user who skips the required trusted
out-of-band confirmation remains exposed to mDNS spoofing. A permanently
missing-TXT peer is not diagnosed, and an unwritable cluster store disables
discovery until a later retry can persist the identity. Those are documented
residual behavior and do not reinstate any of the reported normal-path
findings.

### Agent 5 conclusion

The Opposer 2, 3, and 4 findings that were based on earlier code are resolved
in the final worktree. The duplicate identity, transient missing-TXT warning,
migrated fingerprint binding, direct registry gate, failed-registration
cleanup, and retry/lifecycle findings are disproven by current code and
focused probes. Identity persistence failure remains a bounded availability
and continuity risk because the code fails closed by withholding discovery;
it is not a silent startup identity guarantee when storage remains unwritable.

## Main Auditor Rebuttal and Final Decision

The original startup defect is confirmed and fixed. The literal ``local``
service identity caused duplicate Zeroconf registration failures; production
startup now creates and persists a unique installation ID, uses it consistently
for the local registry/advertisement, and retries only after durable identity
storage succeeds. The exact missing-TXT callback is treated as an incomplete
transient record and ignored until a later complete update, eliminating the
reported warning without promoting a peer.

The opposition also found and the patch fixed: migrated IDs retaining the
legacy fingerprint, direct registry promotion without a fingerprint, failed
registration cleanup leaks, and silent identity rotation when persistence is
unavailable. Existing discovery lifecycle ownership remains in
``AppCoordinator``; discovery and ``NodeRegistry`` were not rebuilt.

Residual risks are bounded and documented: discovery remains unavailable while
the cluster store cannot persist the local identity, and permanently malformed
TXT records are silently ignored rather than repeatedly logged. The existing
fingerprint remains a display/continuity aid, not cryptographic peer
authentication; HMAC transport authentication and explicit user confirmation
remain the security controls.

Mode path: A (high-risk network lifecycle) -> full A4 independent fallback
opposition -> final evidence audit.

Final decision: fixed for the reported discovery startup failure and missing-ID
warning. The final fallback opposition and Agent 5 audit additionally confirm
two bounded P2 follow-ups: legacy trusted records do not hydrate the live
descriptor with a newly learned fingerprint until rebuild/restart, and a
trusted descriptor that enters identity mismatch does not recover to verified
after a later correct rediscovery. Identity persistence failure remains a
separate P2 availability/continuity risk. These fail closed and do not create
an authorization bypass, but should be tracked separately rather than folded
into the fixed startup defect. No commit or push was performed.

## Fallback Opposer 2 - Repo-Truth Skeptic

### Scope and repo-truth checks

I independently traced the current worktree across the persisted cluster
state, local-context construction, `NodeRegistry`, `NetworkDiscovery`,
`AppCoordinator`, `AppWindow` discovery callbacks, and the Nodes & Connections
UI adapters. The focused command
`python -m unittest tests.test_cluster tests.test_network_discovery
tests.test_nodes tests.test_nodes_connections_page tests.test_window_nodes -v`
passed 132 tests. `ruff check .`, `ruff format --check .`, `pyright`, and
`mypy --ignore-missing-imports .` also passed.

The persistence change is backward-compatible at the document boundary:
`local_node_id` and `identity_fingerprint` are optional reads, old trusted
records still parse, and legacy `local` state is explicitly migrated. The
schema version is unchanged because the new fields have defaults and the
parser accepts their omission. Every `ClusterState` reconstruction in
`window.py` carries the new local-identity fields forward.

Discovery lifecycle ownership remains in `AppCoordinator`: it owns the active
instance, bridges events onto the injected delivery path, clears ownership
after failed startup, and performs expiry ticks. `NetworkDiscovery` remains a
single transport-agnostic instance with idempotent start/stop behavior; the
window does not rebuild the registry for each candidate. The UI path carries
fingerprints into peer/trusted specs and displays mismatch state, while pairing
still requires explicit confirmation and the registry promotion boundary also
requires a fingerprint.

### Finding: legacy trusted records do not hydrate the live descriptor (P2,
bounded follow-up)

For a pre-patch trusted record with no `identity_fingerprint`, startup restores
the descriptor as `UNVERIFIED`. On rediscovery,
`NodeRegistry.update_discovered()` intentionally preserves the descriptor's
`None` fingerprint when the known context has no prior fingerprint. Then
`AppWindow._sync_trusted_node_endpoint()` accepts the backward-compatible
record, verifies the endpoint with the existing HMAC provider, and persists the
candidate fingerprint into `TrustedNodeRecord`. It does not update the already
registered descriptor with that newly persisted fingerprint/status.

A focused direct probe with a trusted operational context lacking a fingerprint
and a rediscovered candidate carrying `new-fingerprint` produced:

```text
descriptor_fingerprint None
identity_status unverified
```

This is not a trust or authorization bypass: the node remains trusted only
through the existing persisted pairing secret, selection is still governed by
the normal operational/trust checks, and endpoint updates require `hello()`.
It is nevertheless an incomplete UI/registry migration. The saved record has
the new identity data, but the current session continues to render the node as
unverified and does not show its fingerprint until a later rebuild/restart.
The existing `test_trusted_rediscovery_updates_saved_endpoint_after_hello` tests
the old-record compatibility path but does not assert descriptor hydration.

### Verdict

The reported duplicate local identity and transient missing-TXT behavior are
handled by the current patch, and no persistence-schema incompatibility or
discovery-lifecycle ownership regression was found. The legacy descriptor
hydration gap is a confirmed P2 follow-up, not evidence that the patch is
unsafe for normal startup or that its compatibility path is intentionally
breaking old stores.

the candidate and fail-closed status without making that transition; after a
successful `hello()`, an explicit registry transition should set `VERIFIED`.

fail-closed state. A matching fingerprint must not by itself recover trust
state, because it is a public, derivable display value.

### Legacy fingerprint hydration assessment

candidate fingerprint of `arbitrary-not-derived`, and a successful authenticated

```text

```

Thus the current code correctly gates hydration on HMAC-backed `hello()`, but it
does not validate the fingerprint being hydrated. The response contract has no
authenticated fingerprint field, and `_sync_trusted_node_endpoint()` persists
the candidate TXT value at `window.py:1757-1759`. Since the documented
fingerprint is the canonical SHA-256 display value derived from the stable ID,
the minimal required fix is to derive `node_identity_fingerprint(record.node_id)`
after successful hello and persist that canonical value, rather than persisting
TXT. Alternatively, the protocol would need an authenticated hello fingerprint
field and an explicit equality check before persistence; the current hello
contract does not provide that alternative.

This is a separate P2 identity-integrity/availability hardening issue. HMAC
prevents an unauthenticated endpoint from completing hydration, so this probe
does not demonstrate an authorization bypass. It does demonstrate that an
attacker who can alter TXT while the legitimate endpoint remains reachable can
poison the saved continuity fingerprint and cause later legitimate discovery
to be treated as a mismatch.
