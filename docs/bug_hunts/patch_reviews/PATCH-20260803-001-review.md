### Opposing Agent 3 — Architecture/Security Skeptic

**Independent decision: ACCEPT**

This is an unconditional acceptance for the scoped Mode A patch. The queue
removes worker-side Tk calls, the timer ledger and cancellation fencing now
cover the supported close/mainloop lifecycle, and the focused plus real-Tk
checks found no normal-path behavior regression. Queue retention after a close
is bounded daemon-worker cleanup risk, not a correctness or security blocker
for the `main.py:4-6` application lifecycle.

**Findings**

- **Main-thread result and error delivery — `window.py:339-357,359-384`; `tests/test_window.py:56-79` (accepted).** Each background task increments `_background_tasks` before starting, places either the existing `_show_snapshot` or `_show_error` callback and its unchanged payload into the thread-safe `Queue`, and always places one `None` sentinel in `finally`. Only `_drain_background_queue`, invoked by the Tk timer poll, calls those callbacks. Real-Tk probes delivered a successful `"payload"` and a `"division by zero"` error on the same thread as `mainloop()`, with `background_tasks=0` and an empty queue afterward. The worker body no longer calls `master.after`; the only `master.after` in `window.py` is the main-thread `_schedule_timer` implementation at `window.py:478`.

- **Poll timing, no busy-loop, and multiple-task accounting — `window.py:41,359-384`; `tests/test_window.py:56-66`.** `_start_background_poll` schedules one 10 ms timer only when no poll is active. `_drain_background_queue` drains all currently available items, decrements once per sentinel, and schedules another 10 ms poll only while `_background_tasks > 0`. A read-only fake-master check recorded `[350, 500, 14400000, 10]` for the initial scan, dialog rescan, auto scan, and background poll; each timer ID was removed after its wrapper ran. A real-Tk two-task probe delivered `first` then `second` on the main thread, finished with `multi_tasks=0` and `multi_queue=0`, and did not create concurrent polls. The 10 ms interval adds bounded delivery latency but no extra scan or immediate spin.

- **Close and mainloop-exit behavior — `window.py:471-485,508-517,526-533`; `tests/test_window.py:68-79,89-102`.** Timer callbacks remove their own IDs before invoking application callbacks and skip them once `_is_closing` is true. `_close` marks closing before cancelling pending timers, clears the poll/auto IDs, and destroys the root. `run()` performs the same closing/cancellation cleanup in `finally`. A real-Tk close-before-completion probe produced no late UI events, an empty pending-timer set, and no worker-side Tk error. `_show_snapshot` and `_show_error` retain execution-time late guards at `window.py:389-391,519-521`; a queue item already present during close is ignored by `_drain_background_queue` at `window.py:379-381`.

- **Cancellation failure fencing — `window.py:449-458,487-501`; `tests/test_window.py:34-37,116-128` (accepted).** `_cancel_timer` removes an ID only after successful `after_cancel`, or intentionally while closing. A non-shutdown `RuntimeError` is logged, returns `False`, and leaves the ID in `_pending_after_ids`; `_schedule_auto_scan` then refuses to replace the existing timer. The focused failure test confirms the original ID remains tracked and no replacement is scheduled. During intentional close, retaining an unusable ID is unnecessary because root destruction follows; the explicit discard is appropriate.

- **Queue and daemon-worker residual — `window.py:347-357,512-517`; real-Tk close probe (bounded accepted risk).** If the root closes while a task is still running, the daemon worker can finish and enqueue its result plus sentinel after the poll has been cancelled. The probe observed `late_ui_events=[]`, `pending_timers=set()`, `background_tasks=1`, and `queued_items_after_close=2`. No Tcl command or UI callback remains untracked, and the application-local `AppWindow` is released when `main()` returns; if an external caller retains the closed object, the queue temporarily retains the bound callback and result until the worker completes and the object is collected. The worker itself also continues its pre-existing task after close. This is bounded cleanup/memory residual, not a user-visible, data-integrity, or security regression within the stated application lifecycle.

- **Failure observability — `window.py:477-482,491-498`; `tests/test_window.py:81-87,116-128`.** Unexpected timer scheduling and non-closing cancellation failures remain logged with `LOGGER.exception`; they are not silently converted into normal success. A poll scheduling failure is visible through the same path, although no retry is attempted and a queued task can remain busy if Tk cannot accept a new timer. This is an abnormal event-loop failure, and its diagnosis is preserved without changing normal successful UI behavior. Task exceptions still use the existing user-facing `_show_error` route when the main-thread poll is available.

- **Public behavior and scope — `window.py:389-414,416-447,519-524`; `main.py:4-6`; `algo.py:269`.** The queue changes delivery mechanism only. Snapshot text formatting, resource iteration/order, status transitions, dialog routing, and error message payload construction remain unchanged. `TkFixedFont` is now passed as the correct named string at `window.py:32,40,211-227`. `algo.Analyzer.dashboard_snapshot` is unchanged; the separate current `algo.py` and `.gitignore` worktree changes are not attributed to this patch. Existing worker patterns in `maintenance/dialogs.py` are outside this target diff.

- **Test and type quality — `tests/test_window.py:1-151` (strong selective evidence).** The nine focused tests cover main-thread queue delivery, late queue suppression, named font, timer logging, close cancellation, timer cleanup, cancellation fencing, late UI guards, and auto-scan ID clearing. The fake master uses `Any` at `tests/test_window.py:42-51` and does not itself model real Tk thread scheduling; the real-Tk probes supplement that gap. `python -m unittest discover -s tests -v` passed all 16 tests, `pyright window.py tests/test_window.py` passed with zero diagnostics, and `mypy --follow-imports=skip window.py tests/test_window.py` passed. Ordinary `mypy window.py tests/test_window.py` still reports 12 pre-existing imported-module/stub/type errors in `algo.py` and `maintenance/`; those failures are not treated as a full-repository pass or as target regressions.

## Main auditor rebuttal

The independent reviewer re-read the final patch after the residual-risk fixes and
returned unconditional `ACCEPT`. The reviewer evidence matches the current repo
truth: workers no longer call Tk from background threads; results and task errors
are delivered by a thread-safe queue drained from a tracked 10 ms main-thread
timer; all timers are tracked, late callbacks are guarded, and failed cancellation
does not replace a still-live auto-scan timer.

The queue adds bounded delivery latency of at most one poll interval in the normal
case, but it preserves callback payloads, scan ordering, status transitions, report
formatting, dialog routing, and the existing 350 ms, 500 ms, and four-hour timer
delays. The named `TkFixedFont` contract is now implemented correctly. The bounded
post-close queue retention while a daemon worker finishes is an accepted teardown
risk, not a normal-lifecycle correctness or security defect.

The full-repository format/type gates remain independently blocked by existing
repository issues: seven unrelated files need Ruff formatting, `app/` does not
exist for the requested `mypy app` command, and full type checks report existing
dependency/import/type errors outside the changed target. Those failures do not
point to `window.py` or `tests/test_window.py` in the targeted checks.
