### Opposing Agent 3 - Architecture/Security Skeptic

**Verdict: no confirmed P0-P2 architecture or security defect.**

Reviewed the extracted worker, scan-lifecycle, discovery-session, node-context,
node-selection, coordinator, timer-delivery, and shutdown paths. The relevant
boundaries remain intact:

- Worker callbacks enter the window through the queue/delivery path; queue
  draining and timer callbacks are UI-owned, and callbacks are suppressed once
  closing begins.
- Discovery transport events are posted rather than applied on the transport
  thread. The coordinator clears ownership and advances a lifecycle generation
  before stopping, so queued events from a stopped or replaced discovery
  instance are rejected.
- Discovery candidates update observation state only. Selection is limited to
  registered selectable contexts, and pairing/endpoint refresh still requires
  the existing trust and authenticated-hello checks.
- Shutdown stops discovery before cancelling coordinator work, cancels scan and
  component operations, cancels tracked Tk timers, shuts down render delivery,
  and only then destroys the master. Persistent node workers are also stopped.
- Node-qualified operation keys and source-context callbacks prevent a result
  from one node from being applied to a replacement selection.

### Opposing Agent 4 - External-Research Skeptic

**Research performed**

- Python `queue` documentation: https://docs.python.org/3/library/queue.html
- Python `tkinter` threading model: https://docs.python.org/3/library/tkinter.html#threading-model
- Python `threading.Thread` daemon semantics: https://docs.python.org/3/library/threading.html#threading.Thread
- Python `tkinter.Misc.after`/`after_cancel`: https://docs.python.org/3/library/tkinter.html#tkinter.Misc.after

**Findings**

1. **The queue handoff is supported, not contradicted.** Python documents `queue.Queue` as a synchronized multi-producer/multi-consumer queue for exchanging data between threads. The patch puts worker results and discovery/UI callbacks into that queue and drains it from a scheduled callback. This supports the claimed worker-to-UI boundary; no external semantic defect was found in the `Queue.put()`/`get_nowait()` use.

2. **The Tk delivery design is directionally correct.** Python’s Tkinter documentation says Tk is event-driven, event handlers must remain quick, and long-running work should run in another thread while UI work is processed by the interpreter’s event loop. `TimerDelivery` uses `after()` to schedule callbacks and tracks the identifier for `after_cancel()`, matching the documented API. The close guard additionally prevents a callback that was already queued from touching destroyed widgets.

3. **Daemon shutdown remains an accepted lifecycle risk, not a newly proven regression.** Python documents that daemon threads are abruptly stopped at interpreter shutdown and may not release resources. `background_orchestration.run_daemon()` explicitly creates daemon threads, but this preserves the prior `window.py` behavior. The patch’s cancellation `Event` is cooperative only; it cannot make arbitrary provider work stop. This is a residual risk if a task owns resources, but the cited documentation does not show that this patch worsens it.

4. **Boundary caveat: `threading.main_thread()` is not the Tk owner-thread contract.** Python’s Tkinter documentation says each `Tk` object records the thread that created its Tcl interpreter, and cross-thread calls are posted to that interpreter’s event queue. `BackgroundOrchestrator.start_poll()` instead permits scheduling only when `threading.current_thread() is threading.main_thread()` (`background_orchestration.py:133-139`). That is safe for this application’s normal `main.py` path, where the root is created on the main thread, but it is not a general guarantee for an embedded caller that constructs `AppWindow`/Tk on another thread. I find no evidence this patch introduces a regression for the supported entrypoint, so this remains a compatibility limitation rather than a validated patch bug.

**External-research verdict**

No confirmed patch-introduced bug from the official semantics reviewed. The patch’s queue, timer, and UI-thread direction is supported. Retain the non-main Tk-owner caveat and daemon-resource caveat as residual risks; neither validates the broader claimed risks without an application contract requiring non-main-thread Tk ownership or graceful worker shutdown.
