## Opposer 3 - Architecture/Security Skeptic

### Scope and method

Independent fallback review of the current worktree, focused on target-side
authorization, trust versus permission separation, replay and identity
binding, arbitrary command exposure, process safety, credential scope,
fail-closed behavior, and the recovery/permission/UI paths. No application
code or normal tests were edited.

### Direct-service and action probes

- `python -m unittest tests.test_remote_contract tests.test_nodes tests.test_window_nodes tests.test_nodes_connections_page -v`: **108 tests passed**.
- A validly HMAC-signed `hello` request with `node_id="forged-client"` was
  accepted by a service configured as `node_id="target"`. The response was
  signed and identified `target`. `RemoteService._solve()` verifies the
  secret, but `verify_request()`/`RemoteService` do not bind the claimed sender
  identity to a configured peer identity.
- A service configured with `PROCESS_TERMINATION` capability and
  `permissions=None` accepted a signed `process_request_quit` request and
  invoked the injected manager. The same service with only
  `PROCESS_REVIEW` permission rejected the action. The explicit permission
  check works, but the constructor fallback at `maintenance/remote.py:413-419`
  derives permissions from capabilities, so omission of the new policy silently
  restores destructive authorization.
- With explicit termination capability and permission, `process_request_quit`
  forwarded only `[pid]` and the supplied create-time map to the injected
  manager. `process_force_quit` was rejected when its capability was absent;
  malformed NaN create times, unexpected parameters, and unknown `shell`
  operations were rejected before manager invocation. No arbitrary subprocess
  or command execution path was found.
- Sixteen concurrent submissions of one replay key produced exactly one
  acceptance, confirming the new replay-cache lock closes the race. However,
  with `max_entries=1`, request `r1` was accepted, `r2` evicted it, and replayed
  `r1` was accepted again at the same timestamp. This permits replay of a
  destructive signed request within the freshness window after cache pressure.

### Findings

1. **P2 hardening: authenticated sender identity is not bound at the service
   boundary.** A party possessing the shared secret can claim any `node_id` in
   the signed request and receive a successful response. Current capability and
   permission decisions are not keyed by that claim, so this did not produce a
   privilege escalation in the present single-secret service. It does weaken
   audit identity and creates a future authorization-routing bypass if callers
   later use `request.node_id` for policy selection. The service should reject a
   request whose claimed identity is not the identity associated with that
   credential, or the protocol should explicitly model and authenticate the
   target/caller identities separately.

2. **P1/P2 hardening: permission separation fails open when the service policy
   is omitted.** `RemoteService` treats `permissions=None` as all permissions
   corresponding to advertised capabilities. Therefore a target assembled from
   capability metadata can expose process termination without an explicit
   authorization grant. The current UI normally persists explicit permissions
   and the direct explicit-permission path rejects unauthorized actions, but the
   target service is the security boundary and must default destructive
   permissions to deny rather than infer them from capability advertisement.
   Because the current patch does not wire a production socket service, this is
   an architecture/API boundary defect rather than a demonstrated deployed
   exploit; it becomes P1 if service construction consumes untrusted or merely
   descriptive capability state.

3. **P2 hardening: replay eviction can re-enable an action within freshness.**
   `ReplayCache` is thread-safe and rejects duplicate keys while retained, but
   it evicts the oldest entry at `max_entries`. A valid captured request can
   therefore be replayed after enough distinct authenticated requests evict its
   tuple, even though its timestamp remains fresh. This is especially relevant
   now that process termination operations exist. The implementation is
   fail-closed under ordinary cache capacity but not under bounded-cache
   pressure; the documented claim that requests are rejected for at least the
   freshness window is not guaranteed by the eviction policy.

4. **P1: storage dialog composition crosses the selected-node boundary.**
   `AppWindow.open_resource()` correctly uses `context.provider` and
   `context.process_manager` for the process dialog, but the storage branch
   still passes `self.analyzer` and `self.file_manager` (`window.py:2631-2644`).
   For a selected remote context, this is the local provider/manager, not a
   target-bound remote backend. The storage read-only decision also checks only
   `NodeCapability.CLEANUP`, not `NodePermission.CLEANUP`. Although the current
   remote operation table does not expose storage cleanup and restored remote
   contexts are not operational in this patch, this is a real UI composition
   bypass of target isolation: future remote storage wiring could display or
   invoke local data/cleanup from a remote-target dialog. The storage branch
   must use the selected context's provider/backend and require both capability
   and permission before enabling cleanup.

### Controls verified and not bypassed

- The operation table is closed: no arbitrary command, shell, subprocess, or
  caller-supplied method name is dispatched.
- Authorization runs below the UI and requires both capability and permission;
  unknown operations, malformed process references, NaN timestamps/create times,
  stale requests, bad signatures, and wrong secrets fail before action
  dispatch. Socket authentication failures close without a response.
- Process actions are target-bound through the injected target manager and pass
  PID/create-time references into the existing manager. The local
  `ProcessManager` remains responsible for protected PIDs, same-user checks,
  PID reuse, executable/name protection, and child safety. I found no remote
  path that turns a PID into an arbitrary command or bypasses those manager
  checks.
- Discovery/trust/UI permission changes do not themselves grant remote action
  authority. Pairing grants read capabilities, and the UI's permission callback
  persists explicit values. Remote storage cleanup is not exposed by the
  operation table; the remote process adapter is the only new destructive
  adapter and is not wired into a live target service in this patch. However,
  the storage dialog still composes local objects for a remote selection, as
  noted above; this is an isolation defect even though it did not yield a new
  remote protocol operation in the direct-service probe.
- Response HMAC, request-ID correlation, timestamp freshness, and wrong-node
  response rejection held in the focused tests. There is no response replay
  cache, but a captured response cannot satisfy a new client request because
  the request ID must match.

### Verdict

No direct arbitrary-command, remote-process-to-local-process fallback,
discovery-to-action, or unauthorized explicit-permission process-action bypass
was reproduced. The patch's normal operation and action probes are fail-closed.
I raise the service-policy default as the highest direct-service concern, with
the storage cross-target composition as the highest UI/isolation concern;
sender identity binding and replay-cache eviction are narrower hardening
findings. The current review scaffold's statement that remote management is not
production-wired materially limits exploitability, but it does not remove
defects in the new direct-service and UI security boundaries that future wiring
would inherit.

No app code or normal tests were changed by this review.

## Opposer 4 - External-Research Skeptic

### Scope and sources

Reviewed the changed `maintenance/remote.py` and
`maintenance/components/network_discovery.py` against the official Python
`socketserver`, `socket`, `hmac`, and `json` documentation, plus the official
python-zeroconf API reference. Focused checks used the repository's remote,
discovery, cluster, node, window-node, and connections-page tests, all of
which passed: 155 tests in total.

Sources:

- https://docs.python.org/3/library/socketserver.html
- https://docs.python.org/3/library/socket.html
- https://docs.python.org/3/library/hmac.html
- https://docs.python.org/3/library/json.html
- https://python-zeroconf.readthedocs.io/en/latest/api.html

### Findings

#### P1: socket timeout does not bound target operation execution

`RemoteSocketServer` applies `settimeout()` to the accepted socket before
reading the frame, and `SocketRemoteTransport` applies the same timeout to
connect/send/receive. Python documents socket timeouts as applying to socket
operations; they do not cancel arbitrary Python work executed between the
reads and the response write. Here `service.handle()` calls `_solve()`, which
can invoke `process_manager.request_quit()` or `force_quit()` before the
handler sends its response (`maintenance/remote.py:627-639` and
`491-506`).

Focused runtime check: with a process manager that sleeps for 0.25 seconds and
a 0.05-second client/server timeout, the client returned
`RemoteTransportError` after about 0.053 seconds, while the process action
still completed after the client had timed out. Therefore the timeout is an
I/O/exchange bound, not a bounded lifecycle for a destructive target action.
This is especially relevant to the patch summary's stated bounded lifecycle:
disconnecting or timing out a caller does not prevent the already-authorized
operation from continuing. The code may intentionally accept this semantics,
but it needs an explicit contract and cancellation/idempotency treatment if
the timeout is intended as an operation deadline.

#### P2: `allow_reuse_address` is set after the server has already bound

The implementation constructs `socketserver.ThreadingTCPServer` at
`maintenance/remote.py:644-649`, then assigns
`server.allow_reuse_address = True`. Official `socketserver` source documents
that `TCPServer.__init__` calls `server_bind()` before returning, and
`server_bind()` reads `self.allow_reuse_address` while setting the socket
option. The assignment therefore cannot affect this bind. A focused runtime
check showed `SO_REUSEADDR == 0` immediately after construction and remained
0 after the late attribute assignment; a subclass with the class attribute set
before construction produced `SO_REUSEADDR == 1`.

This is a restart/rebind reliability mismatch, not an authentication bypass.
It is also not covered by the current socket tests, which verify round trips
but not the socket option or rapid restart behavior.

### Semantics not found to contradict the patch

- `_recv_exact()` correctly handles TCP's stream framing reality; a single
  `recv()` is not guaranteed to return one `sendall()` payload.
- `hmac.compare_digest()` is the documented comparison primitive for supplied
  digests, and the implementation uses it.
- The canonical JSON used for HMAC verification is stable across wire
  whitespace/order because the wire JSON is parsed before canonicalization.
  Python's JSON implementation does accept and emit `NaN`/infinity by default,
  outside strict JSON; this patch rejects non-finite timestamps, and the
  focused operation paths did not expose a separate interoperability failure.
- python-zeroconf documents `ServiceBrowser` add/update/remove callbacks,
  byte-valued TXT properties, and fully qualified service names in the forms
  used here. In installed zeroconf 0.151.3, `Zeroconf.close()` also invokes
  service unregistration when its loop is active, so the apparent shutdown
  concern is not confirmed as a defect.

### Verdict

External semantics confirm the HMAC framing and zeroconf API usage generally,
but contradict treating the socket timeout as a bound on target execution and
show that the reuse-address setting is ineffective as written. Both findings
should be resolved or explicitly accepted in the main auditor's final
synthesis; no app code or normal tests were edited by this review.

## Opposer 2 - Repo-Truth Skeptic

**Scope and method**

Audited the changed node, cluster persistence, remote transport/provider, UI
page, dialog, coordinator, and window lifecycle paths against their actual
callers. No application code or normal tests were changed.

**Findings**

1. **P1: persisted remote nodes are never made operational.**
   `AppWindow._restore_trusted_nodes()` (`window.py:241-290`) restores every
   trusted record as a `NodeContext` with `provider=None`, `scheduler=None`,
   and `process_manager=None`. The only later remote construction in the
   window is in `_test_connection()` and `_sync_trusted_node_endpoint()`
   (`window.py:1324-1341`, `1795-1800`), where an
   `AuthenticatedNodeProvider` is created transiently for `hello()` and then
   discarded. No `RemoteProcessActionBackend` is constructed anywhere in the
   repository, and no remote scheduler/context replacement is wired from the
   saved host, port, and secret. Consequently persisted trusted/manual nodes
   remain non-selectable (`NodeRegistry._is_operational`,
   `maintenance/nodes.py:521-530`) and cannot exercise the provider or dialog
   path. This conflicts with the patch review scope describing remote provider
   and process-dialog integration, even though `maintenance/remote.py` itself
   documents live feature wiring as deferred.

2. **P1: an operational remote process context would still be incompatible
   with `ProcessDialog` actions.** `open_resource()` checks process review and
   termination permissions (`window.py:2604-2629`), but passes
   `context.process_manager` to `ProcessDialog`. The remote context creation
   paths currently set that field to `None`; the available
   `RemoteProcessActionBackend` (`maintenance/remote.py:806-834`) is never
   installed. If a remote context is later attached with termination
   capability, the dialog will enable “Quit Selected” and eventually call
   `None.request_quit`/`None.force_quit` rather than the authenticated target.
   The local path remains compatible: `ProcessManager` accepts
   `(pids, expected_create_times)` exactly as the dialog calls it, while the
   remote adapter exposes the same callable shape.

3. **P2: old cluster records silently lose read permissions after the new
   permission field is introduced.** `ClusterStore._parse_permissions()`
   (`maintenance/cluster.py:563-575`) returns an empty set when `permissions`
   is absent. `AppWindow._restore_trusted_nodes()` copies that empty set into
   the descriptor (`window.py:262-279`), while `RemoteService` independently
   defaults permissions from capabilities (`maintenance/remote.py:413-418`).
   Thus a pre-permission persisted record with `DASHBOARD_READ`/
   `PROCESS_REVIEW` capabilities is restored with no caller permissions, and
   its UI authorization checks refuse process review even when the record was
   previously trusted. New pairing/manual records explicitly use
   `READ_PERMISSIONS`, and the round-trip test covers explicit permissions,
   but there is no migration/default test for existing records.

4. **P2: the `RemoteService` capability-to-permission default is not total.**
   Its fallback comprehension (`maintenance/remote.py:413-418`) converts
   every `NodeCapability` to `NodePermission`. `REMOTE_MANAGEMENT` is a valid
   capability (`maintenance/nodes.py:101`) but has no corresponding
   `NodePermission` (`maintenance/nodes.py:104-114`), so constructing a
   service with that otherwise valid capability set raises
   `ValueError: 'remote_management' is not a valid NodePermission`. This was
   reproduced directly with the public constructor. Explicit `permissions=`
   avoids the failure, but the documented/default constructor contract is
   still unsafe for the complete capability enum.

**UI/spec and coordinator checks**

- `NodesConnectionsCallbacks` and `TrustedNodeSpec` match their `window.py`
  composition (`maintenance/ui/nodes_connections.py:27-74`,
  `window.py:759-780`, `800-869`); permission checkbuttons emit a filtered
  `frozenset[str]` and the controller persists it.
- `ProcessDialog` preserves the local legacy manager call shape and uses
  node-qualified coordinator keys (`maintenance/dialogs.py:719-741`,
  `877-902`), but this only proves local compatibility and the shared
  coordination seam, not remote lifecycle wiring.
- Node-qualified `AppCoordinator` keys and shutdown cancellation are present
  (`window.py:1515-1547`, `3272-3311`), but they cannot coordinate remote
  scans until a remote context gets a provider and scheduler. The transient
  hello path is not a lifecycle-owned provider.

**Targeted validation**

- `python -m unittest tests.test_cluster tests.test_remote_contract
  tests.test_nodes tests.test_nodes_connections_page tests.test_process_table
  tests.test_window_nodes tests.test_render_coordinator -v`: **161 passed**.
- `python -m compileall -q maintenance window.py`: **passed**.
- Touched-surface `ruff check` and `ruff format --check`: **passed**.
- Direct constructor probe reproduced the `REMOTE_MANAGEMENT` fallback
  `ValueError` above.

**Opposer 2 verdict**

The local persistence/UI/dialog/coordinator seams are internally consistent,
but the requested remote integration is not complete in the actual application
call graph. The patch should remain **needs more evidence** until operational
remote contexts, remote action backend selection, and legacy permission
defaults are demonstrated by caller-level tests. The independent remote
contract tests passing do not establish window lifecycle integration.

by the reviewers. No application code, normal tests, or the main auditor's

Independent validation performed here:

- `python -m unittest tests.test_cluster tests.test_remote_contract tests.test_nodes tests.test_nodes_connections_page tests.test_window_nodes -q`: **131 passed**.
- A fresh direct probe reproduced: missing legacy `permissions` parses as an

  `REMOTE_MANAGEMENT` capability; a request evicted from a one-entry replay
  cache is accepted again while its timestamp is fresh; a valid HMAC request
  claiming `forged-client` is accepted by a service configured as `target`;
  and `SO_REUSEADDR` is false after `RemoteSocketServer.start()`.
- The probe initially used an invalid schema version and did not produce
  evidence; it was corrected to the repository's `CLUSTER_SCHEMA_VERSION=1`
  before the legacy-record result above was recorded.

### Reconciled findings

#### Confirmed implementation gaps

1. **Trusted remote placeholders are non-operational.**
   `_restore_trusted_nodes()` creates trusted contexts with no provider,
   scheduler, process manager, or coordinator. The only provider construction
   in `window.py` is transient verification for `hello()`. No
   `RemoteSocketServer`, `RemoteProcessActionBackend`, or lifecycle-owned
   remote scheduler is constructed in the application call graph. The
   registry's operational gate therefore correctly keeps restored/manual
   trusted peers non-selectable. This is a confirmed end-to-end integration
   failure, not disproved by the passing transport contract tests.

2. **Process dialog/backend wiring is incomplete.**
   The dialog now selects `context.provider` and `context.process_manager`,
   which is correct for an operational context, and the direct adapter has the
   expected `(pids, expected_create_times)` shape. However, no production path
   installs either the authenticated provider or
   `RemoteProcessActionBackend`; restored contexts contain `None`. Thus the
   requested remote process operation is not reachable through the UI. If a
   context were manually made operational with only a provider, the dialog
   could still receive a `None` manager. This is a confirmed wiring gap.

3. **Storage target binding is wrong.**
   The storage branch of `open_resource()` always passes `self.analyzer` and
   `self.file_manager`, unlike the process branch. A remote-selected dialog
   consequently reads local state and carries the local cleanup manager. Its
   current remote non-selectability limits runtime reachability, but the
   composition is already target-incorrect and would cross the boundary as
   soon as remote contexts are wired. The storage read-only check also tests
   `CLEANUP` capability without testing `NodePermission.CLEANUP`.

4. **Permission migration/defaulting is unsafe and inconsistent.**
   `_parse_permissions()` returns an empty set for old records with no field,
   so previously trusted read capabilities lose UI permissions after reload;
   no migration fallback restores the historical read behavior. Separately,
   `RemoteService` infers permissions from capabilities when omitted. That
   fallback fails open for destructive capabilities and is not even total:
   `REMOTE_MANAGEMENT` has no matching `NodePermission`, producing
   `ValueError`. Explicit permissions avoid both observations, but the public
   omitted-policy path remains defective. The safe conclusion is not that
   capabilities and permissions are equivalent: legacy records need an
   intentional, documented migration policy and service authorization must
   default destructive permissions to deny.

5. **Authenticated sender identity is not bound to the credential.**
   HMAC proves possession of the service's shared secret, but
   `verify_request()` accepts any non-empty `node_id`, and `RemoteService`
   never compares it with an identity associated with that secret. The fresh
   probe accepted a signed `node_id="forged-client"` request and returned the
   target response. No privilege escalation was demonstrated because the
   current service has one policy and does not route authorization by the
   claimed sender. The identity/audit boundary is nevertheless a confirmed
   implementation gap and becomes security-significant if policy selection or
   peer accounting later uses the claim.

6. **Replay eviction violates the stated freshness-window guarantee.**
   The cache serializes check-and-record correctly, and immediate duplicate
   replay is rejected. But when full, it deletes the oldest key. A captured
   request can therefore be replayed after enough distinct requests, before
   its freshness timestamp expires. This is confirmed under the documented
   bounded-cache behavior; it is not a concurrency race.

7. **Socket timeout is not operation cancellation.**
   Socket timeouts bound connect/send/receive and the focused timeout probe
   confirms that the client returns promptly. They do not interrupt
   `RemoteService._solve()` or an already-started process manager call. The
   opposer's delayed-manager probe showed the action completing after the
   client timed out. Client cancellation is only checked before a request for
   read methods and cannot cancel an in-flight destructive operation. This is
   a confirmed lifecycle/contract gap if the patch promises bounded target
   work; otherwise it must be explicitly documented with idempotency and
   post-timeout semantics.

8. **`allow_reuse_address` is assigned too late.**
   `ThreadingTCPServer` is constructed before the attribute is set, so bind has
   already read the old value. The fresh probe observed `SO_REUSEADDR == 0`.
   This is a confirmed restart/rebind reliability defect, not an auth bypass.

#### Controls that held

- The operation table remains closed; no arbitrary command, shell, subprocess,
  or caller-selected method dispatch was found.
- Explicit target-side capability plus permission checks reject unauthorized
  process operations in the direct service path.
- Process references are validated and forwarded with create times to the
  injected manager; the existing manager remains responsible for protected
  PIDs, user checks, PID reuse, and child safety.
- HMAC, freshness, request correlation, wrong-node response rejection, stream
  framing, and immediate replay rejection passed the focused probes/tests.
- Discovery fingerprint display and mismatch handling do not themselves grant
  trust or action authority.

#### Residual risks and limits

- The highest-impact remote-action findings are presently blocked from the
  normal UI by the missing operational-context wiring. That reduces current
  exploitability but does not make the incomplete boundaries safe to ship as
  the requested feature.
- Sender spoofing is an identity/accountability weakness under the current
  single-secret policy, not a reproduced privilege escalation.
- Replay eviction impact depends on request volume/cache sizing and freshness;
  the proof establishes reacceptance, not a production attack rate.
- Timeout/cancellation remediation needs an explicit operation model. A
  socket deadline cannot safely be described as cancellation of arbitrary
  target work.
- No live external service was contacted. The focused suite and direct probes
  are local evidence only; no full-suite or whole-repository static result is
  claimed by this audit.

### Agent 5 verdict

The opposer findings reconcile consistently. The patch's low-level auth,
validation, and direct target-manager seam are substantially functional, but
the requested remote management integration is not operational and several
new security/lifecycle contracts are incomplete. The confirmed gaps above
should remain visible in the main auditor's synthesis; none should be
reclassified as disproven merely because the isolated transport tests pass.

## Final Main Auditor Rebuttal

The final worktree extends the existing HMAC transport and adds reusable
permission, target-process-action, replay, framing, and dialog-binding seams.
It also adds coordinator-backed activation from the Nodes & Connections Open
action, attaching a provider, scheduler, and remote process action backend only
after authenticated hello succeeds. Process and storage dialogs now use the
selected context's provider/manager and UI availability checks both permission
and capability.

The reviewers' central conclusion remains valid: this is not yet a complete
LAN management deployment. The repository has no durable inbound peer-grant
model or configured target-service startup path, so a persisted peer cannot be
guaranteed to expose a usable target service. Target cancellation also remains
cooperative only; a client socket timeout cannot interrupt already-running
target work. These are explicit follow-up requirements, not silently accepted
as complete.
