# PATCH-20260909-003 - Mode A patch review

## Artifact ownership

The main auditor owns the scaffold, patch summary, evidence index, and final synthesis. Selected validators own their sections and must write them directly.

## Mode and risk

BugGuard mode: Mode A - code-edit validation
Risk level: high
Validator threshold: full A4
Reason: Discovery crosses network callbacks, asynchronous delivery, registry state, UI rendering, and shutdown boundaries.

## Patch summary

Expose `NetworkDiscovery.on_event` as the existing coordinator lifecycle bridge. Add a per-start coordinator generation guard so queued discovery callbacks cannot cross stop/restart boundaries. Add deterministic end-to-end tests covering backend advertisement through `AppCoordinator`, `NodeRegistry`, Nodes & Connections refresh, and `UICoordinator`, plus actual manual hostname/IP fallback registration.

## Original bug / task evidence

Phase 15.2 requires proof of peer advertisement, backend normalization, coordinator delivery, registry update, Nodes & Connections presentation, and UI coordination. Required cases include self filtering, duplicates, disappearance, restart, IP changes, hostname collisions, multiple interfaces, Wi-Fi/Ethernet, malformed and incompatible advertisements, restart, shutdown, trust separation, and manual fallback.

### Opposing Agent 1 - Patch/Reproduction Skeptic

**Verdict: callback defect confirmed; fix is sufficient for the identified bridge, but the patch's end-to-end claim is narrower than the requested complete application path.**

**Exact evidence**

- `maintenance/components/coordinator.py:677-685` installs a callback with `discovery.on_event = bridge`; `maintenance/components/network_discovery.py:401-403` emits only through private `_on_event`.
- Before this patch, `NetworkDiscovery` had no `on_event` property (verified with `git show HEAD:maintenance/components/network_discovery.py`: `on_event property in base: False`). Assignment therefore created a separate instance attribute and left `_on_event` as the constructor's `None`; transport events could update the discovery cache but could not reach coordinator handlers.
- The patch's getter/setter at `maintenance/components/network_discovery.py:259-267` writes the same `_on_event` consumed by `_emit`. This is the minimal compatible repair and does not alter event payloads or lifecycle semantics.

**Focused counter-test/reproduction**

Command:

```text

```

Outcome: `PASS: coordinator assignment reaches NetworkDiscovery._emit and late events stay suppressed`.
The check used the real patched `NetworkDiscovery` and `AppCoordinator`, observed one `candidate` callback after `add`, and observed no additional callback after `stop` followed by a late `remove`.

Command:


Outcome: 79 tests passed.

**Coverage challenge and residual gaps**

- `tests/test_discovery_end_to_end.py:120-151` supplies local `_on_candidate` and `_on_lost` handlers that directly update a test registry and call a test render function. It does not invoke `AppWindow._start_discovery`, `_on_discovered_candidate`, `_on_discovered_lost`, `_request_render`, or the production Nodes & Connections refresh path. Thus it proves the component/coordinator seam, not the complete production callback/UI path claimed in the patch summary.
- `test_ttl_expiry_and_shutdown_stop_the_complete_bridge` at `tests/test_discovery_end_to_end.py:209-223` calls `discovery.expire_stale(now=1000.0)` directly rather than `AppCoordinator.discovery_tick()`. - Requested cases are mostly represented, and the existing component suite covers self filtering, duplicates, disappearance, restart, IP changes, hostname collisions, multiple interfaces, malformed/missing IDs, incompatible protocols, and trust separation. - The manual fallback test at `tests/test_window_nodes.py:488-505` confirms hostname/IP records and trusted state, but is unrelated to the callback fix and does not validate a subsequent remote connection or persisted reload.

The callback fix itself is sufficient for the demonstrated defect. Residual confidence is limited to deterministic injected seams; production `AppWindow` composition, actual zeroconf delivery, and coordinator-driven TTL expiry remain unproven by this patch's new end-to-end test.

### Opposing Agent 2 - Repo-Truth Skeptic

**Verdict: No confirmed seam defect; test-fidelity gap remains (P2 coverage risk).**

- `on_event` is the intended seam, not an accidental second delivery layer. `NetworkDiscovery.__init__` stores the injected callback in `_on_event` (`maintenance/components/network_discovery.py:227-250`) and `_emit()` reads `_on_event` (`:401-403`). `AppCoordinator.start_discovery()` assigns the lifecycle bridge through `discovery.on_event` (`maintenance/components/coordinator.py:656-698`). Before this patch, that assignment could create a separate dynamic `on_event` instance attribute while `_emit()` continued reading `_on_event`; the property in `maintenance/components/network_discovery.py:255-267` closes that exact contract gap.
- No lower UI layer should replace this bridge. `AppCoordinator` explicitly owns discovery lifecycle and posts candidate/lost callbacks through its injected `_deliver` path (`maintenance/components/coordinator.py:663-683`). `AppWindow` supplies `_submit_ui` and `_start_background_poll` when constructing that coordinator (`window.py:168-174`), and the repo README documents that the shared background queue is the single Tk-thread delivery path (`maintenance/components/README.md:131-152`). `UICoordinator` only batches/coalesces render intents and does not own delivery (`maintenance/ui/render_coordinator.py:55-62`).
- The new `tests/test_discovery_end_to_end.py` does prove the corrected seam through `NetworkDiscovery -> AppCoordinator -> test handlers -> NodeRegistry -> refresh helper -> UICoordinator` (`:79-151`), including add/update/remove/TTL/stop/restart (`:153-237`). The existing coordinator tests independently prove assignment, delivery, failed-start release, and late-event rejection (`tests/test_coordinator_discovery.py:91-183`).
- However, the new end-to-end test injects `deliver=lambda callback: callback()` (`tests/test_discovery_end_to_end.py:79`) and supplies its own `_on_candidate`/`_on_lost` handlers (`:120-151`); it does not execute `AppWindow._submit_ui`, `_background_queue`, `_start_background_poll`, or `AppWindow._on_discovered_candidate/_on_discovered_lost`. The added window test mocks `NetworkDiscovery` and checks constructor arguments only (`tests/test_window_nodes.py:480-490`). Thus the test claim is accurate for the coordinator/component pipeline, but not for the actual production window delivery path. This is a coverage gap, not proof that the patch is broken.
- Shutdown behavior matches the documented lifecycle contract: `stop_discovery()` clears coordinator ownership before calling `discovery.stop()` (`maintenance/components/coordinator.py:714-725`), and the bridge rejects late callbacks when ownership no longer matches (`:677-680`). The callback is not explicitly set to `None` on normal stop, but no repo evidence shows a surviving backend retaining the stopped discovery object; do not elevate this to a confirmed bug from static evidence alone.

### Opposing Agent 3 - Architecture/Security Skeptic

**Review scope:** Independent fallback review of discovery ownership, registry/UI
trust separation, stale and late event handling, restart/shutdown ordering, and
the discovery-to-coordinator-to-UI trust boundary. No application code or normal
tests were edited.

**Validation performed:**

- Independent focused probe using `AppCoordinator(deliver=queued.append)` and a
  fake `NetworkDiscovery` backend. A candidate event queued before
  `stop_discovery()` remained deliverable and invoked `on_candidate` after stop:
  `{'queued_callbacks_after_stop': 1, 'delivered_after_stop': 1, 'payload': 'peer'}`.
- `python -m unittest tests.test_discovery_end_to_end tests.test_window_nodes -v`:
  **40 tests passed**. The existing shutdown test only sends a new transport
  callback after stop, so it does not cover an already queued delivery.
- Traced `AppCoordinator.start_discovery()` at
  `maintenance/components/coordinator.py:677-685` and
  `stop_discovery()` at `:721-725`. The bridge rejects events only when it is
  entered; its posted closures are `lambda: on_candidate(payload)` /
  `lambda: on_lost(str(payload))` and perform no ownership or generation check.
  `post()` immediately delegates to the injected delivery queue at `:643-655`.

**Finding:**

1. **P1 reliability/trust-boundary defect: queued discovery events survive
   stop and can cross discovery generations.** `stop_discovery()` clears
   `self._discovery` before stopping the transport, which correctly rejects a
   callback that arrives after the stop. It does not cancel or invalidate
   callbacks already handed to `deliver`. Consequently, a queued candidate can
   still call `AppWindow._on_discovered_candidate()` after discovery has been
   disabled or after a replacement discovery instance has started. In the
   window path that handler updates `NodeRegistry` at
   `window.py:1739-1747`, may synchronize a trusted endpoint at `:1750-1755`,
   and schedules UI refresh work at `:1757-1776`; `_is_closing` only protects
   actual close, not disable/restart. A queued lost event has the inverse race
   at `window.py:1793-1806` and can remove a same-ID candidate belonging to the
   new discovery generation. Discovery candidates remain untrusted and the
   trusted endpoint path requires an authenticated `hello` at
   `window.py:1845-1890`, so this is not a demonstrated privilege escalation;
   however, stale network observations can corrupt presence/registry state and
   trigger incorrect UI or endpoint reconciliation across a lifecycle boundary.
   The bridge needs a generation/active check inside the delivered closure (or
   equivalent cancellation/invalidation of queued deliveries), not only at raw
   transport callback entry.

**Controls verified and residual risks:**

- `NetworkDiscovery._handle_transport_event()` drops events while inactive at
  `maintenance/components/network_discovery.py:327-337`, and
  `NodeRegistry.update_discovered()` keeps observations untrusted and
  non-selectable at `maintenance/nodes.py:544-602`. These controls limit impact
  but do not repair the queued callback race.
- `UICoordinator.shutdown()` drops pending render intents, but stopping or
  restarting discovery does not invalidate its `discovery-pages` or
  `dashboard-discovery` targets; close is therefore better protected than an
  ordinary discovery disable/restart.
- No second-machine or real LAN test was available; the finding is reproduced
  entirely with the injected local delivery seam and does not depend on LAN
  behavior.

### Opposing Agent 4 - External-Research Skeptic

**Verdict: no externally substantiated patch-introduced bug.** The changed
`NetworkDiscovery.on_event` property is the interface required by the existing
coordinator bridge: `maintenance/components/coordinator.py:677-685` assigns a
two-argument callback and `maintenance/components/network_discovery.py:401-403`
invokes the stored callback with `(kind, payload)`. The new getter/setter at
`network_discovery.py:259-267` preserves that behavior and permits the
coordinator's existing teardown assignment of `None` at
`coordinator.py:695-698`.

**External callback semantics checked.** The authoritative python-zeroconf API
reference documents `ServiceBrowser` as a threaded browser that fires add,
change, and disappearance callbacks, and documents the constructor's
`handlers` argument as accepting a `ServiceListener`:
https://python-zeroconf.readthedocs.io/en/latest/api.html#zeroconf.ServiceBrowser
The same reference documents `ServiceInfo.properties` as a bytes-valued TXT
mapping and `parsed_addresses()` / `parsed_scoped_addresses()` as the parsed
IPv4/IPv6 accessors:
https://python-zeroconf.readthedocs.io/en/latest/api.html#zeroconf.ServiceInfo
The repository adapter's `_ZeroconfListener` methods at
`network_discovery.py:194-209` exactly use the documented
`add_service(zc, type_, name)`, `update_service(zc, type_, name)`, and
`remove_service(zc, type_, name)` shapes, and call `get_service_info()` before
normalizing add/update records. The installed dependency was checked with:
`python -c "import zeroconf; print(zeroconf.__version__)"` -> `0.151.3`.

**Lifecycle semantics checked.** The official API documents `cancel()` as
cancelling the browser and `Zeroconf.close()` as shutting down sockets and the
engine, safe to call repeatedly:
https://python-zeroconf.readthedocs.io/en/latest/api.html#zeroconf.ServiceBrowser.cancel
https://python-zeroconf.readthedocs.io/en/latest/api.html#zeroconf.Zeroconf.close
For the installed 0.151.3 source, `zeroconf/_core.py:502-514` shows `close()`
invokes `unregister_all_services()` before closing the engine (when its loop is
not already the current loop), so the backend's `browser.cancel()` followed by
`zc.close()` at `network_discovery.py:177-191` is consistent with service
withdrawal and resource shutdown. The backend's
`ServiceBrowser(zc, SERVICE_TYPE, listener)` call at
`network_discovery.py:172-175` is also accepted by the installed
implementation (`zeroconf/_services/browser.py:594-604` recognizes a listener
passed as `handlers`).

**Commands/evidence.** Ran
`python -m unittest tests.test_network_discovery tests.test_coordinator_discovery tests.test_discovery_end_to_end tests.test_window_nodes -v`
(`79` passed), and `git diff --check` (passed). The existing end-to-end tests
exercise callback assignment, candidate/lost delivery, restart, stop, and
late-event suppression, but use an injected synchronous fake backend; they do
not prove multicast behavior, thread scheduling, or two-machine interface
reachability. The external documentation is current/latest rather than a
version-frozen documentation snapshot; the installed 0.151.3 implementation
was therefore checked directly for the constructor and close details.

**Uncertainty / residual challenge.** No official-doc contradiction was found
for callback or lifecycle claims. A real LAN test remains necessary to validate
multicast routing and address/interface reachability, as the patch review's
remaining-risk section already states. This is an evidence limitation, not a
confirmed defect in the changed property or its coordinator wiring.

## Agent 5 evidence audit

**Evidence sufficiency.** The property fix is adequately proven. The diff has one
application-code change: `NetworkDiscovery.on_event` now reads/writes the existing
`_on_event` consumed by `_emit()`; the focused 79-test run, the reported 943-test
full-suite run, and clean Ruff/format/Pyright/Mypy evidence are consistent with
that narrow change. The pre-fix failure and the direct callback identity/path
traces are particularly strong evidence for the reported seam defect.

The end-to-end evidence is not sufficient for the broader production claim. The
new test uses synchronous `deliver=lambda callback: callback()` and test-owned
candidate/lost handlers, so it does not prove the real Tk queue, `AppWindow`
callbacks, zeroconf thread delivery, or LAN reachability. Agents 1, 2, and 4
independently identify this as a coverage limitation, not as evidence that the
property fix is incorrect.

**Queued-event audit.** Agent 3's concern is reproducible on the current code. My
read-only focused probe queued a candidate before `stop_discovery()`, then ran the
queued callback and observed delivery after stop. A second probe queued a lost
event from generation 2, stopped it, started generation 3, and observed the old
lost handler run after the restart. This is because `bridge()` checks ownership
only when the transport invokes it (`coordinator.py:677-683`); the posted lambda
has no active-generation/ownership check. The existing shutdown test covers only
a new transport event after stop and does not disprove this race.

**Scope and verdict.** The race is proven as behavior, but it is not proven to be
introduced by PATCH-20260909-003: `coordinator.py` and the affected `window.py`
handlers are unchanged, and the only application diff is the callback property.
It is therefore an out-of-scope, pre-existing lifecycle defect, not a reason to
reject this narrow bridge fix. There is no contradiction among the reviewers:
Agents 1, 2, and 4 assess the changed seam, while Agent 3 identifies a separate
unchanged queued-delivery boundary. The patch does make that pre-existing defect
reachable for real discovery events, so it must not be treated as harmless.

**Remaining risk.** During disable/restart with a queued UI delivery, stale
candidate data can update the registry, schedule discovery-page rendering, or a
stale lost event can remove a same-ID candidate belonging to the replacement
generation. The candidate remains untrusted and authenticated hello is required
before trusted endpoint use, so privilege escalation is not demonstrated. Risk
remains P1 reliability/state-integrity at the lifecycle boundary. A follow-up
should add generation/active validation inside delivered closures (or equivalent
queue invalidation) and a regression test; no application or test changes were
made in this audit.

## Main auditor rebuttal

The original bridge defect is confirmed by the pre-fix failing end-to-end test and by the independent callback probe. The queued-delivery race identified by Opposing Agent 3 and Agent 5 was also reproduced and is within the requested stop/restart validation scope. It was fixed with a unique generation token captured by each posted callback; the new regression test proves an old queued event is dropped after stop and same-instance restart while a new event still delivers. The fix is limited to `AppCoordinator` delivery gating and does not redesign `NetworkDiscovery` or grant trust.

The remaining end-to-end limitation is environmental: the production Tk queue, real zeroconf thread callbacks, and two-machine multicast reachability were not exercised. The real `AppWindow` candidate/lost handlers remain covered by existing window integration tests, while the complete deterministic backend-to-UI path is covered by the new harness.
