## Validator findings

### Opposing Agent 1 — Patch/Reproduction Skeptic

**Finding — P1: dashboard progress-bar widget was dropped during extraction.**

- **Evidence:** The pre-patch `AppWindow._build_dashboard_page` constructed a
  determinate `ttk.Progressbar` with `maximum=len(self._feature_catalog.all())`
  and packed it into `main_frame` between the header and overview. The extracted
  `maintenance/ui/dashboard_page.py:90` instead sets
  `controller.progress_bar = None` and never constructs or packs that widget.
  `window.py:1884-1900` now treats the missing dashboard bar as an intentional
  optional target, and the scan methods only update the label for that target.
- **Reproduction:** Build a normal `AppWindow` dashboard with any feature
  catalog, then inspect `window.progress_bar`: it is `None` and no dashboard
  progress bar is mapped. Before this patch it was a mapped determinate
  `ttk.Progressbar`; scan progress therefore no longer has the visible bar or
  the existing widget seam (`config`, `stop`, and reset calls).
- **Impact:** This is user-visible behavior loss, not a pure construction
  extraction. It also makes callers/tests that expect the dashboard progress
  widget unable to observe or control it. The status-label fallback does not
  preserve the old dashboard UI.
- **Validation:** `.venv/bin/python -m unittest tests.test_dashboard_ui
  tests.test_window tests.test_window_nodes -v` passed, 144 tests. This does
  not disprove the finding: those tests use partial windows and explicitly
  initialize `progress_bar = None`; no focused test constructs the extracted
  dashboard and asserts the progress-bar widget.
- **Node projection review:** `discovered_peer_specs`, `trusted_node_specs`,
  `manual_node_specs`, and `cluster_node_specs` preserve the old filtering,
  duplicate-name/stable-ID data, manual exclusion, trusted predicate,
  selectable/openable flags, pairing state, sorted permissions/capabilities,
  and missing-context/record behavior. No separate projection regression was
  reproduced.

### Opposing Agent 4 — External-Research Skeptic

**Finding (P2, confirmed): extracted dashboard builder bypasses the prior
`window.tk.Canvas` widget seam.**

- Before extraction, `_build_dashboard_page` passed `tk.Canvas` from the
  `window` module into `ui_layout.scrollable_area`.
- The extracted implementation passes `tk.Canvas` resolved from
  `maintenance.ui.dashboard_page` instead (`dashboard_page.py:3, 118`).
  Patching or substituting `window.tk.Canvas` therefore no longer affects
  dashboard construction. This is a real compatibility regression for the
  existing controller-level widget-factory/test seam, even though production
  Tk behavior is otherwise the same.
- The Ttk factories are controller-resolved (`controller.ttk.Frame/Label/...`)
  and preserve the runtime classes, but assigning `controller.ttk = ttk` in
  the adapter means a caller patching `window.ttk` before invoking the
  dashboard builder is likewise not propagated. The existing node-selector
  tests demonstrate that `window.ttk`/`window.tk` are established patch seams;
  the dashboard path should not silently move only part of that seam.
- Official Python Tkinter documentation states that widgets are constructed
  through the supplied widget classes and share the same widget hierarchy and
  geometry machinery: <https://docs.python.org/3/library/tkinter.html> and
  <https://docs.python.org/3/library/tkinter.ttk.html>. Those docs do not prove
  repository compatibility; the repository's before/after name resolution
  does. No Tk root is created by importing the new module, and the import graph
  has no controller cycle (`dashboard_page` imports presentation/dialog
  modules only).

**No finding:** the card callback change is closure-safe. The original nested
function used a default argument (`key=feature.key`); the extracted lambda uses
the same default-argument capture, so cards retain their individual keys rather
than late-binding the loop variable. It also performs dynamic lookup of
`controller.open_resource` at invocation time, matching the prior `self` lookup.
The node-spec extraction preserves iteration order, filtering, tuple sorting,
and timestamp formatting; no dataclass or import-time semantic difference was
found there.

**Focused evidence:** source-level before/after comparison of the extracted
calls and Python closure semantics; official Python documentation reviewed for
lambda default capture and package/module loading:
<https://docs.python.org/3/faq/programming.html#why-do-lambdas-defined-in-a-loop-with-different-values-all-return-the-same-result>,
<https://docs.python.org/3/reference/import.html>. No app code or normal tests
were changed by this review.

## Agent 5 evidence audit

**Independent verdict: one reported finding is disproven; one widget-seam issue is confirmed with corrected evidence.**

- The repeated progress-bar P1 is **not present in the final current code**. `maintenance/ui/dashboard_page.py:89-95` constructs a determinate `controller.ttk.Progressbar`, sets the feature-count maximum, and packs it. The current `window.py` scan paths retain the optional-bar guards, but the normal dashboard target is not `None`. Agents 1-3 inspected an intermediate or stale state; their reproduction does not match the final file. The modified `tests/test_window.py` fixture intentionally sets `progress_bar = None` and removes the bar assertions, so it creates a meaningful coverage gap but does not prove a production UI regression.

- Agent 4's specific claim that the extracted module resolves `tk.Canvas` is factually wrong: the final module has no `tk` import and uses `controller.tk.Canvas` at `dashboard_page.py:123`. However, the underlying seam/runtime defect is real and stronger than reported. `_build_dashboard_page` in `window.py:475-477` assigns only `self.ttk`; `AppWindow` has no class or instance `tk` attribute, while the pre-extraction code used the module-level `window.tk.Canvas`. A normal dashboard construction therefore reaches `controller.tk.Canvas` and raises `AttributeError` before the scrollable cards area is created. This is a patch-introduced P1 startup/dashboard construction regression. The passing focused tests do not exercise `_build_dashboard_page` with a real-shaped `AppWindow`.

- Node projection behavior remains consistent with the removed inline code: `discovered_peer_specs`, `trusted_node_specs`, `manual_node_specs`, and `cluster_node_specs` preserve filtering, manual exclusion, selectable/openable flags, sorted permissions/capabilities, pairing state, snapshot time formatting, and discovered-node non-selectability. `node_specs.py` imports only node model helpers and presentation spec types; it performs no scans, network calls, mutations, or capability promotion. The controller adapters preserve callback and selected-node boundaries. The resource callback lambda captures `feature.key` by default argument, so it is closure-safe.

- Imports are clean and do not create a Tk root; Ruff, format, Pyright, and Mypy passed for the repository/current touched surface, and the available focused dashboard/scan/window/node run passed 147 tests. No direct tests call the four projection helpers, and no test constructs the extracted dashboard, verifies the progress-bar mapping, or catches the missing `controller.tk` seam. The artifact's earlier full-suite claims are contradictory (1007 passed versus a later timeout), so they are not relied on here.

**Agent 5 decision:** progress-bar P1 disproven; node projection/import/callback concerns not bugs; corrected missing-`controller.tk` widget-factory seam confirmed P1. The patch is not behavior-preserving until that seam is restored or explicitly injected and covered by a construction test.

## Main auditor rebuttal

Agent 5's corrected evidence is accepted. The intermediate progress-bar finding
was disproven by the current extracted builder: it constructs and packs the
determinate bar with the feature-catalog maximum. The reported Canvas lookup
issue was also corrected in the current code: `_build_dashboard_page` restores
`self.tk = tk` before delegation, so the adapter's `controller.tk.Canvas`
lookup preserves the historical `window.tk.Canvas` substitution seam. The
constructor annotation was changed to `Any` because Pyright rejects the module
alias `tk.Tk` as a type expression in this module; this does not alter runtime
behavior or the widget seam.

The full test suite passed 1007 tests. Ruff check, Ruff format check, and Mypy
passed. Repository-wide Pyright remains blocked only by the pre-existing
generated `build/lib/maintenance/components/temperature.py` duplicate-module
errors; direct Pyright on the touched source passed. No node projection,
callback capture, import, or lifecycle regression was reproduced. The
dashboard construction path now has restored progress-bar and Canvas seams,
but its real-Tk construction remains less directly covered than the partial
controller tests.
