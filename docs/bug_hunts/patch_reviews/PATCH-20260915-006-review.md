## Opposition

### Opposing Agent 1
Findings: 2 reproducible P2 reliability/state-consistency defects.

1. **P2 — in-process transport ignores cancellation and still reaches the target.**
   `maintenance/remote_support/transport.py:39-40` accepts `cancel_event` but
   calls `self._service.handle(envelope_text)` without checking it. The pairing
   provider also has no pre-dispatch cancellation check in
   `maintenance/remote.py:566-602`, so an already-cancelled pairing request sent
   through `MemoryRemoteTransport` still invokes target-side handling. This is
   not only a return-value issue: target-side UI/persistence work can occur
   after the initiator has cancelled. The production socket transport checks
   cancellation around connect/read, but the documented in-process/loopback
   transport does not preserve the same cancellation contract.

   Counter-test command:

   ```text
   python - <<'PY'
   import json, threading
   from maintenance.remote import AuthenticatedNodeProvider
   from maintenance.remote_support.transport import MemoryRemoteTransport
   from maintenance.nodes import NodeId, NodePermission

   class Service:
       def __init__(self): self.calls = 0
       def handle(self, _envelope):
           self.calls += 1
           return json.dumps({"approved": False})

   service = Service()
   event = threading.Event(); event.set()
   result = AuthenticatedNodeProvider.request_pairing(
       transport=MemoryRemoteTransport(service),
       caller_node_id=NodeId("caller"), identity_fingerprint="id",
       transport_fingerprint="tls", proposed_secret="a" * 64,
       permissions=frozenset({NodePermission.DASHBOARD_READ}),
       cancel_event=event,
   )
   print(result, service.calls)
   PY
   ```

   Result: `False 1` (expected cancellation to prevent the service call, i.e.
   `False 0`). Recommendation: make `MemoryRemoteTransport.request` fail before
   dispatch when the event is set, and add the same early check in
   `AuthenticatedNodeProvider.request_pairing`; retain the post-call check in
   the coordinator as a race defense.

2. **P2 — timed-out target approval can create an orphan pending transaction.**
   `maintenance/ui/window_discovery.py:385-431` waits only 60 seconds and
   returns `{"approved": False}` when the wait expires, but the queued
   `ask_on_ui` callback has no timeout/cancel guard. If the user approves after
   the wait, it still calls `_save_cluster_state` at lines 411-413 and persists
   `PendingPairing`; the caller has already received denial and cannot confirm
   or abort that transaction. It remains durable until the normal five-minute
   expiry/prune path, and repeated late approvals can leave misleading pending
   state in the target settings.

   Counter-test command:

   ```text
   python - <<'PY'

       "proposed_secret": "b" * 64,

        patch.object(window_discovery, "_window_symbols") as symbols:
       symbols.return_value.messagebox.askyesno.return_value = True
   ```

   Result: `{'approved': False}` followed by `1` pending pairing. Recommendation:
   associate a live/cancelled request token with the UI callback and refuse to

### Opposing Agent 2
Findings: 1 reproducible P2 persistence defect; no protocol authorization bypass or coordinator generation defect was found in the audited paths.

1. **P2 — expired pending pairings are pruned in memory but not durably removed when confirm rejects them.**
   `maintenance/ui/window_discovery.py:476-495` handles an expired `pair_confirm` by calling `state.prune_pending_pairings(now=now)` and immediately returning `False` at line 494. That branch does not call `controller._save_cluster_state`. `ClusterState.prune_pending_pairings` mutates only the in-memory tuple (`maintenance/cluster.py:637-642`), while `ClusterStore.save` is the persistence boundary (`maintenance/cluster.py:750-779`). Consequently, a stale pending record, including its plaintext proposed secret, remains in `cluster.json` after an expired confirm rejection. The next `ClusterStore.load()` prunes it in memory, but does not rewrite the file; absent a later successful state mutation, the stale record persists indefinitely.

   Reproduction command:

   ```text
   python - <<'PY'

   import time

   from maintenance.cluster import ClusterState, ClusterStore, PendingPairing
   from maintenance.nodes import NodeId, NodePermission
   from maintenance.remote_support.protocol import PairingControlRequest
   from maintenance.ui import window_discovery

   pending = PendingPairing('tx-expired', 'caller', 'id', 'tls', 'b' * 64,
       frozenset({NodePermission.DASHBOARD_READ}), time.time() - 1)

       path = Path(directory) / 'cluster.json'
       store = ClusterStore(path)
       store.save(state)
       controller = type('Controller', (), {})()
       controller._cluster_state = state
       controller._save_cluster_state = lambda updated: (
           setattr(controller, '_cluster_state', updated) or store.save(updated) or True
       )

           'pair_confirm', 'tx-expired', NodeId('caller'), 'id', 'tls',
           'b' * 64, frozenset({NodePermission.DASHBOARD_READ}), pending.expires_at
       )

              'memory_pending': len(controller._cluster_state.pending_pairings),

   PY
   ```

   Result: `{'result': False, 'memory_pending': 0, 'disk_pending': 1}`. This demonstrates that the rejected transaction is gone from runtime state but remains durable. The existing `tests.test_remote_security.RemoteSecurityTests.test_target_confirm_rejects_binding_mismatch_and_expiry` checks only the in-memory grant/pending state after expiry (`tests/test_remote_security.py:378-417`); it does not provide a persistence assertion. Recommendation: persist the pruned state in the expired-confirm branch, or centralize expiry pruning behind a save-aware state transition. Add a regression test that seeds a durable expired pending record, rejects confirm, reloads the file, and asserts `pending_pairings == ()`.

1. **P2 — repeated/replayed pairing requests are not idempotent.**
   `maintenance/ui/window_discovery.py:378-425` creates a new random
   `PendingPairing.transaction_id` and appends it to `pending_pairings` for
   every approved `pair_request`. There is no request identity, caller/secret
   deduplication, or consumed-request marker. Thus retrying the same request
   after a lost response, or replaying an identical request, produces multiple
   independently confirmable pending records for the same caller and secret.
   This violates the transaction/replay boundary: two target approvals can
   race or be confirmed sequentially, and a later confirmation replaces the
   active grant while the other transaction remains pending until expiry.

   Counter-test command:

   ```text
   python - <<'PY'

   from maintenance.nodes import NodeId, NodePermission

   from maintenance.ui import window_discovery

   class Controller:
       def __init__(self):
           self._cluster_state = ClusterState(local_node_id='target')
           self.master = object(); self.callbacks = []

       def _save_cluster_state(self, state): self._cluster_state = state; return True

       result = {}

           window_discovery.handle_pairing_request(controller, request)))

       controller.callbacks.pop(0)()
       thread.join()

          'pending_count': len(controller._cluster_state.pending_pairings),

          second.get('transaction_id')})

   ```

   Result: `{'first': True, 'second': True, 'pending_count': 2,
   'transaction_ids_distinct': True}`. The existing tests cover exact control
   binding and confirm replay, but not duplicate `pair_request` delivery.
   Recommendation: define retry identity for the request and atomically reuse

### Opposing Agent 4
Findings: 4 reproducible P2 pairing reliability/state-consistency defects. The
normal TLS pinning, exact confirm/abort binding, and authenticated replay-cache
paths were not shown defective by the focused suite. The following findings are
based on current repository behavior and the official Python semantics for
socket timeouts, thread cancellation, and Tk event delivery.

1. **P2 — cancellation is not preserved by the in-process transport.**
   `maintenance/remote_support/transport.py:39-40` accepts `cancel_event` but
   dispatches directly to `self._service.handle(envelope_text)`. The pairing
   facade at `maintenance/remote.py:566-602` has no pre-dispatch cancellation
   check either. An already-cancelled request therefore still executes target
   code; the caller only observes the eventual denial/return value. This is a
   contract mismatch with `SocketRemoteTransport`, which checks cancellation
   before connect and while receiving (`transport.py:122-155`). It matters for
   loopback and test-backed production paths because target-side UI or
   persistence can occur after the initiator has cancelled.

   Exact evidence command:

   ```text
   python - <<'PY'
   import json, threading
   from maintenance.remote import AuthenticatedNodeProvider
   from maintenance.remote_support.transport import MemoryRemoteTransport
   from maintenance.nodes import NodeId, NodePermission
   class Service:
       def __init__(self): self.calls = 0
       def handle(self, _envelope):
           self.calls += 1
           return json.dumps({'approved': False})
   service = Service(); event = threading.Event(); event.set()
   result = AuthenticatedNodeProvider.request_pairing(
       transport=MemoryRemoteTransport(service),
       caller_node_id=NodeId('caller'), identity_fingerprint='id',
       transport_fingerprint='tls', proposed_secret='a' * 64,
       permissions=frozenset({NodePermission.DASHBOARD_READ}),
       cancel_event=event)
   print({'result': result, 'service_calls': service.calls})
   PY
   ```

   Result: `{'result': False, 'service_calls': 1}`. A cancellation-preserving
   transport boundary should produce zero service calls. Recommendation: check
   the event before memory dispatch and before pairing-request dispatch, while
   retaining the post-response cancellation check as a race defense.

2. **P2 — the network timeout does not cancel a target pairing handler.**
   `RemoteSocketServer` applies `self._timeout` to socket I/O
   (`maintenance/remote_support/server.py:90-104,148-149`), but the pairing
   callback runs synchronously at lines 108-110. The client timeout in
   `SocketRemoteTransport` is also an I/O timeout, not a cancellation signal.
   Consequently a target handler can remain blocked in the 60-second UI wait
   (`maintenance/ui/window_discovery.py:428-431`) after the client has already
   received a transport timeout. If the user then approves, the callback still
   persists `PendingPairing` (`window_discovery.py:399-413`) although the
   initiating operation has failed. This is the network-level version of the
   late-approval race and can consume one bounded handler slot per pending UI
   request until the callback returns.

   Exact evidence command:

   ```text
   python - <<'PY'
   import json, threading, time
   from maintenance.remote_support.server import RemoteSocketServer
   from maintenance.remote_support.transport import SocketRemoteTransport
   started = threading.Event(); finished = threading.Event()
   def pairing_handler(_request):
       started.set(); time.sleep(0.35); finished.set()
       return {'approved': False}
   server = RemoteSocketServer(object(), timeout=0.10,
                               pairing_handler=pairing_handler); server.start()
   try:
       payload = json.dumps({'op':'pair_request','pairing_mode':'transactional',
           'caller_node_id':'caller','identity_fingerprint':'id',
           'transport_fingerprint':'tls','secret':'a'*64,
           'permissions':['dashboard_read']})
       try:
           SocketRemoteTransport('127.0.0.1', server.bound_port,
                                 timeout=0.20).request(payload)
           outcome = 'response'
       except Exception as exc:
           outcome = type(exc).__name__ + ': ' + str(exc)
       print({'client_outcome': outcome, 'handler_started': started.is_set(),
              'handler_finished_before_print': finished.is_set()})
       finished.wait(1)
       print({'handler_finished_after_wait': finished.is_set()})
   finally:
       server.stop()
   PY
   ```

   Result: `{'client_outcome': 'RemoteTransportError: remote transport failed: timed out', 'handler_started': True, 'handler_finished_before_print': False}` followed by `{'handler_finished_after_wait': True}`. Python documents socket timeouts as exceptions from timed-out socket operations, not interruption of arbitrary Python callbacks: https://docs.python.org/3/library/socket.html#socket-timeouts. Python also documents that threads cannot be destroyed or interrupted by `threading`: https://docs.python.org/3/library/threading.html#thread-objects. Recommendation: make the pairing handler explicitly cancellation-aware and bind the UI callback to a request token that is invalidated on transport timeout; do not treat client timeout as proof that target work stopped.

### Phase 1: Evidence Reconciliation

- **Repaired predecessor findings:** the current code now persists
  `PeerGrantRecord.transaction_id`, uses it for restart-safe exact confirm
  replay, serializes target confirm/abort with `_pairing_transition_lock`,
  validates every returned transaction binding, and forwards cancellation into
  pairing and confirmation transports. The current focused suite and direct
  checks support these repairs. The PATCH-20260915-004 lost-update finding is
  stale against this tree and is disproven by the current lock-protected
  implementation.
- **P2 confirmed: cancelled in-process transport still dispatches.**
  `MemoryRemoteTransport.request()` accepts `cancel_event` but immediately
  calls `self._service.handle()` without checking it. This contradicts the
  cancellation contract implemented by the socket transport and exposed by
  `AuthenticatedNodeProvider.request_pairing()`. It can execute target-side
  work after cancellation on loopback/in-process paths.
- **P2 confirmed: approval after the target wait timeout persists pending
  state.** `handle_pairing_request()` waits 60 seconds, returns a denial when
  the event is not set, but leaves the queued `ask_on_ui` callback live. A late
  approval still calls `_save_cluster_state()` and writes `PendingPairing`.
  This does not create an active grant, and the five-minute TTL bounds the
  record, but it leaves a transaction and secret that the initiator cannot
  complete or abort.
- **P2 confirmed: expired-confirm pruning is not durably saved.** The expired
  branch calls `state.prune_pending_pairings()` and returns `False` without
  `_save_cluster_state()`. The record is removed from memory but remains in
  `cluster.json`, including its proposed secret, until another durable state
  mutation or reload-side cleanup path.
- **P1/P2 confirmed: local rollback can remain durable after a failed save.**
  `_restore_pairing(..., persist=True)` returns the save result but cannot undo
  the previous successful disk write when the compensating save fails. The
  current caller reports recovery failure, which is better than silently
  claiming success, but durable local trust can still survive the failed
  cancellation/confirmation rollback. I classify the ordinary write-failure
  divergence as P2; explicit cancellation after local trust was saved is P1
  state-integrity impact if the failure leaves trust enabled across restart.
- **P2 hardening concern: duplicate approved requests create independent
  transactions.** `handle_pairing_request()` generates a fresh ID and appends a
  pending record on every approved request. The design explicitly specifies
  confirm/abort idempotency, but does not define a request retry identity, so
  this is a reliability gap rather than a proven violation of an explicit
  request-idempotency requirement. It should not be confused with confirm
  replay, which is now durable and exact.

### Phase 4: Lifecycle, Persistence, and Validation Mapping

The patch now has a substantially safer transaction boundary: target approval
creates pending state, local state is saved before confirm, target transitions
are serialized, exact bindings are checked, committed grants carry a durable
transaction ID, and stale local deliveries are generation-gated. Those controls
explain why the earlier findings do not all remain valid.

They do not cover every lifecycle edge. The pending approval callback has no
live request token, the memory transport does not honor cancellation, expiry
pruning is not save-aware, and rollback failure has no durable quarantine or
retry marker. The state machine therefore still spans independent target and
initiator persistence boundaries without an end-to-end commit/revocation
protocol.

Structured searches used: `pair_request|pair_confirm|pair_abort`,
`pending_pairing|peer_grants|transaction_id`, `cancel_event|MemoryRemoteTransport`,
`_restore_pairing|_save_cluster_state`, `revoke_grant`, and sibling review IDs
PATCH-20260915-002 through PATCH-20260915-005. Official Python documentation
used: `threading.Event`/thread lifecycle, socket timeout behavior, and
`concurrent.futures.Future.cancel()` semantics. These docs support cooperative
cancellation only; repository code and the two direct probes prove the
patch-specific defects. No LR or drift output was available.

### Phase 5: Conservative Recommendation

**Go/no-go: NO-GO for unconditional release.** The ordinary pairing paths and
the major predecessor repairs validate, but the patch does not yet provide a
complete cancellation/persistence boundary. At minimum, cancellation must be
honored before memory dispatch, timed-out approval callbacks must be invalidated
or made save-safe, and expiry pruning must durably remove stale records. The
rollback failure outcome needs a durable fail-closed recovery strategy or an
explicit accepted-risk decision. Duplicate request handling should receive a
defined retry policy before claiming request-level idempotency.

**Verified findings and severity:**

- P1: explicit cancellation/local rollback can leave durable local trust when
  the compensating save fails; target-side orphan authorization after a
  post-commit transport failure remains a conditional P1 residual risk.
- P2: `MemoryRemoteTransport` dispatches an already-cancelled request.
- P2: late target approval after the 60-second wait persists orphan pending
  state.
- P2: expired-confirm pruning is not durably persisted.
- P2: duplicate approved requests create multiple live transactions absent a
  defined retry identity.
- Not current findings: the earlier mixed-version bypass, returned-binding
  mismatch, restart confirm replay defect, and concurrent confirm/abort
  lost-update race; the current implementation and focused tests address them.

**Residual validation risk:** no live two-node, power-loss, or real restart
integration run was performed; full pyright/mypy and LR/drift gates remain
unavailable for the documented reasons. These limitations do not weaken the
deterministic findings above, but they prevent a stronger release claim.
