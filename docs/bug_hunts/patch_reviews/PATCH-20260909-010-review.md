### Opposing Agent 3 - Architecture/Security Skeptic

**Scope and challenge:**

I independently traced the changed authorization, discovery, worker-delivery,
shutdown, destructive-action, persistence, installer, and UI paths. I looked
for a fix-induced widening of trust, a fail-open error path, cross-node result
confusion, process/file target substitution, privilege escalation, or a
shutdown race that could leave an unsafe operation active.

**Security boundary analysis:**

- Discovery remains observation-only. `NetworkDiscovery` normalizes the
  advertisement and validates the port range, while `NodeRegistry.update_discovered`
  creates an untrusted descriptor with no capabilities. Discovered nodes are
  excluded from `selectable_descriptors()` and `select()`; discovery therefore
  cannot directly create an actionable target.
- Promotion is still explicit and read-only. `promote_to_trusted()` rejects
  destructive capabilities, and `_set_node_permissions()` only changes the
  explicitly managed process permission subset while preserving the other
  persisted permissions. `open_resource()` checks both capability and explicit
  permission before opening process/storage actions; missing or unknown state
  is refused or rendered read-only.
- Remote activation uses the persisted node secret and authenticated hello,
  verifies the returned node ID, and only then attaches the provider and
  remote process backend. Endpoint changes are accepted only after an
  authenticated hello. A discovery fingerprint mismatch marks the node
  mismatched and does not update the endpoint or reactivate it.
- The remote service still parses supplied process references but delegates
  execution to `ProcessManager`, which rechecks PID ownership, protected PID /
  name, and expected create time. Force-quit descendants receive the same
  ownership/protection checks and are rejected when their identity cannot be
  read. The added child create-time check is fail-closed rather than an action
  widening.
- File cleanup remains constrained to a resolved regular file below the
  resolved Downloads root, rejects symlinks, and now compares device/inode
  before calling `send2trash`. This reduces, but cannot eliminate, the
  check-to-use race inherent in a path-based trash API. That residual race is
  already documented as remaining risk and is not introduced by this patch.

**Data-flow and thread-boundary trace:**

Transport callbacks enter `AppCoordinator`, which posts delivery onto the
application delivery path. Registry mutation and UI callbacks therefore do
not run in the transport thread. Discovery lifecycle generations reject
queued events after stop or restart. `NetworkDiscovery` protects peer maps and
active state with its re-entrant lock. Background workers enqueue completion,
error, and UI callbacks; `BackgroundOrchestrator.drain_queue()` is the only
normal callback execution point and drops ordinary UI delivery while closing.
Render generation/node checks remain in the window path, so a prior node's
result cannot populate the selected node.

The new peer lock does not make `NetworkDiscovery.start()` and `stop()` an
atomic lifecycle transition. `start()` checks `_active` under the lock, calls
the backend outside the lock, and sets `_active` only after that call returns;
`stop()` can observe inactive and return during the backend call. A focused
probe with a backend blocked inside `start()` reproduced the interleaving:
`stop()` returned without invoking backend stop, then `start()` published
`active=True`. This can leave advertising/browsing alive after application
shutdown and is a confirmed P1 reliability/lifecycle regression. It does not
grant trust or authorization and does not directly trigger destructive work,
but it violates the shutdown boundary and can leave a stale discovery
transport running until a later cleanup.

A separate synchronous-start callback ordering concern is weaker: the
coordinator assigns its generation token after installing the bridge and
before normal discovery returns. A custom transport callback during
`discovery.start()` could therefore be discarded as stale. This is not
reproduced by the normal backend and remains a P2-at-most notification-loss
possibility, not a security issue.

**Shutdown and privilege review:**

`_finalize_shutdown()` stops discovery before clearing coordinator lifecycle
state, cancels scan leases and all known operations, shuts down the executor,
disposes UI state, cancels tracked Tk timers, and shuts down rendering before
the root is destroyed. Late discovery and UI deliveries are rejected by the
identity/closing checks. Registered providers are subsequently asked to stop
their persistent workers. Daemon workers may finish outside the window, but
their queued callbacks cannot mutate the destroyed UI; no new destructive
operation is started by shutdown.

The PowerShell change adds `--force-reinstall` only. It does not add elevation,
change the existing explicit `-System` selection, or turn a per-user install
into a system install. The script still downloads a wheel from the existing
source and verifies its published checksum before invoking pip. No new
privilege transition was found.

**UI impact:**

The refactored selection and lifecycle adapters preserve local-vs-remote
context routing, qualify coordinator keys by node, cancel the old context's
operations before scheduling the new scan, and keep remote process/storage
dialogs read-only unless both authorization dimensions permit mutation. The
changed finite-value thermal handling is presentation-only and cannot grant an
operation.

**Focused validation:**

- Command: `python -m unittest tests.test_process_protection tests.test_network_discovery tests.test_coordinator_discovery tests.test_discovery_session tests.test_window_nodes -v`
- Result: 103 tests passed; no failures or errors.
- Coverage included PID reuse and child identity changes, protected/foreign
  processes, malformed/out-of-range discovery ports, discovery stop/restart
  event rejection, discovery shutdown, trusted identity mismatch/recovery,
  permission preservation, node isolation, and remote read-only UI behavior.
- No live network, remote host, installer, or destructive filesystem operation
  was invoked.
- Probe: a blocked-backend `NetworkDiscovery.start()` raced against
  `stop()`; result was `active_after_stop=True` and `backend_stopped=False`.

**Findings:**

The fixes preserve authorization and destructive-action boundaries, but the
discovery lifecycle refactor introduces a confirmed P1 reliability regression:
an overlapping start/stop can republish an active transport after shutdown.
The path-based trash check-to-use race remains a residual safety limitation,
not a new regression. The synchronous callback ordering issue is only a weak
secondary concern.

**Verdict:** Confirmed adjacent P1 lifecycle/reliability regression; no
confirmed authorization or destructive-action security regression. Security
impact is not P1, but the shutdown violation should be repaired or explicitly
accepted before approval.

### Opposing Agent 4 - External-Research Skeptic

#### Scope and method

Independent review of the changed discovery locking/lifecycle, callback
delivery, endpoint bounds, thermal Canvas inputs, process identity, filesystem
checks, and Windows installer invocation. I did not inspect other validator
sections. Repo source was read at `maintenance/components/network_discovery.py`,
`maintenance/components/coordinator.py`, `maintenance/actions.py`,
`maintenance/ui/thermal_graph.py`, `maintenance/cluster.py`,
`maintenance/ui/nodes_connections.py`, and `install/install-online.ps1`.

#### Findings

##### P1: `RLock` does not serialize start/stop lifecycle transitions

`NetworkDiscovery.start()` checks `_active` under `_peer_lock`, releases the
lock, and then calls the backend. It sets `_active = True` only after that
call. `stop()` can therefore acquire the lock while `start()` is blocked in
`backend.start()`, observe inactive state, and return without stopping the
backend. When `backend.start()` later returns, `start()` sets `_active` true.
This leaves a transport running after the caller's stop/shutdown request and
is not repaired by the lock around peer-map access.

This is reproduced without a live LAN: a fake backend blocks in `start()`;
another thread calls `stop()`; releasing the backend yields
`active_after_concurrent_stop=True`. The existing lifecycle tests cover
sequential calls, not this interleaving. The minimal repair would serialize
the lifecycle transition or add an explicit starting/stopping generation and
ensure a stop requested during startup stops the successfully-started backend.

##### P2: port `0` remains accepted at destination/record boundaries

The changed checks use `0 <= port <= 65535` in discovery and trusted-node
records, and the manual-host UI reports the same range. Python socket
documentation distinguishes a destination `(host, port)` from a source
address: port `0` has OS-default/ephemeral meaning for a source bind, while a
TCP service endpoint must identify a listening service. The local probe showed
`bind(('127.0.0.1', 0))` succeeds but assigns an actual ephemeral port; it did
not make port 0 a usable remote listener. Thus a discovered/trusted/manual
host with port 0 can be displayed or passed as a destination even though it
does not identify the advertised service. `None` already exists as the
semantic representation for no port, so accepting 0 is not needed for the
optional-port case.

This is a contract concern only where the value is consumed as a remote
service port; the Zeroconf advertisement builder intentionally uses `0` when
no port is advertised, so that internal registration convention must not be
confused with an accepted connectable peer port.

#### Semantics verified and limits

- Python `threading.RLock` documentation says same-thread acquisitions are
  allowed, each acquisition must be paired with a release, and only the final
  release unlocks it. The `with self._peer_lock` blocks are balanced. The
  callback from `_emit` is invoked while the lock is held, so same-thread
  callback reentry is permitted by `RLock`; a callback on another thread will
  wait. This avoids a self-deadlock but does not solve the start/stop race or
  make arbitrary callback code safe.
- The `AppCoordinator` bridge posts callback work and checks both component
  identity and lifecycle generation before delivery. This is consistent with
  Tkinter's documented single-interpreter/event-loop model; no cross-thread
  widget call was found in this path. The coordinator guard does not protect
  `NetworkDiscovery.start()` itself.
- `psutil` documents that a `Process` is PID-bound and can refer to a new
  process after PID reuse, while creation time is part of psutil's process
  identity/hash semantics. The added create-time comparisons therefore reject
  the tested PID-reuse and pre-action identity changes. They remain a
  best-effort check: a process can change after the final comparison and
  before `action(target)`; no user-space check can make that pair atomic.
- Python `Path.stat()` documentation says each call looks up fresh status and
  returns device/inode data. The added second stat correctly detects the
  tested replacement/type changes on POSIX. It is still a check-then-use
  window before path-based `send2trash`, especially on filesystems/platforms
  where replacement can occur after the second stat; the artifact's remaining
  risk is accurate.
- Thermal samples and finite thresholds are filtered with `math.isfinite`
  before geometry; non-finite thresholds are not drawn. The finite geometry
  probe and existing telemetry tests pass. `current` is guarded before Canvas
  text, while min/max are only formatted into text and do not become Canvas
  coordinates. No NaN/Infinity coordinate path remains in the changed graph
  builder.
- pip's official option definition states `--force-reinstall` reinstalls
  packages even when already up to date. The PowerShell command places that
  flag before the local wheel and checks `$LASTEXITCODE`; the requested force
  reinstall behavior is present. I could not execute Windows PowerShell here.

### Residual limitations and final evidence decision

Unavailable evidence is limited to the missing `./lr` gates, live LAN/
Zeroconf execution, display-backed Nodes accessibility, Windows PowerShell
execution, and hostile PID/filesystem replacement timing. These are recorded as
limitations, never as passes. The reproducible startup race does not depend on
LAN availability, and the fractional-port result is a direct pure-component
probe.

The prior repairs are supported by the current full/static gates and focused
tests, but the patch is **not safe to approve as submitted**. Another repair
iteration is required for the discovery startup/shutdown transaction and the
fractional discovered-port validation, followed by targeted race/port tests and
the available full/static gates. No additional repair is required for the
other findings on the evidence currently available.
