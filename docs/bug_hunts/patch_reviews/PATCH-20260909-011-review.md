# PATCH-20260909-011 - final discovery-boundary repair review

## Mode and risk

BugGuard mode: Mode A - code-edit validation
Risk level: high
Validator threshold: full A4
Reason: Final repair of the two adjacent NetworkDiscovery regressions identified by PATCH-20260909-010.

## Patch summary

This patch repairs the remaining discovery start/stop lifecycle race by
serializing backend startup with the lifecycle lock, and rejects fractional or
otherwise non-integer discovered ports instead of coercing them with `int()`.
It adds focused regression tests for both boundaries.

### Opposing Agent 1 - Patch/Reproduction Skeptic

**Independent reproduction result: both PATCH-20260909-010 regressions are repaired in the current patch.** I did not edit application code or normal tests.

#### Lifecycle fix

- Focused command: `python -m unittest tests.test_network_discovery tests.test_coordinator_discovery tests.test_discovery_session tests.test_discovery_end_to_end -v`
- Result: **50 tests passed**.
- The new `test_stop_serializes_with_start` passed.
- A deterministic blocked-backend probe started `NetworkDiscovery.start()` in one thread, invoked `stop()` while backend startup was blocked, then released startup. Result: `backend_start_calls=1`, `backend_stop_calls=1`, `active=False`.
- The same probe repeated this overlapping start/stop interleaving **100 times**, with all iterations passing and no thread left alive. A concurrent second `start()` also returned `True` without a second backend start.

The fix is causally sufficient for the prior failure: `start()` now holds `_peer_lock` through backend startup and active-state publication, so `stop()` cannot observe the transient inactive state and escape before startup completes. Once it acquires the lock, it stops the backend and clears state.

#### Fractional-port fix

- Direct `_normalize()` probe results were: `1.9 -> None`, `'123' -> None`, `True -> None`, `-1 -> None`, `65536 -> None`, `0 -> 0`, and `65535 -> 65535`.
- The focused fractional, out-of-range, boolean, and invalid-port tests all passed.
- This removes the prior `int(1.9) == 1` truncation; no endpoint was emitted for the fractional input.

#### Static evidence and residual risks

- Targeted `ruff check`, `ruff format --check`, `pyright`, `mypy --ignore-missing-imports`, and `git diff --check` all passed for the changed module/test pair.
- No real LAN, Zeroconf implementation, or hostile external callback environment was available; the lifecycle result is proven with deterministic injected backends, not the live transport.
- Transport callbacks delivered synchronously during `backend.start()` remain ignored while `_active` is false. This ordering predates the current lifecycle fix and was not reproduced as a new regression; it remains a possible startup notification-loss edge for custom backends.
- `_emit()` can run while `_peer_lock` is held. `RLock` permits same-thread re-entry, but a callback that synchronously waits on another thread needing this lock could still cause application-level blocking. No such callback deadlock was reproduced in the focused suite.
- Port `0` and the live Zeroconf endpoint semantics remain the contract questions recorded by PATCH-20260909-010; this patch does not change them.

**Skeptic verdict:** both targeted fixes reproduce safely under deterministic tests and repeated race probing. No new defect was confirmed in this scope. The patch is supported for these two regressions, subject to the stated live-transport and callback-ordering residual risks.

### Opposing Agent 4 - External-Research Skeptic

**Scope:** `NetworkDiscovery` lifecycle locking and discovered-port normalization.

**Finding (P2, confirmed):** The lifecycle lock does not serialize the complete stop operation. `stop()` marks `_active = False` while holding `_peer_lock`, then releases it before calling `self._backend.stop()` (`maintenance/components/network_discovery.py:315-326`). A concurrent `start()` can therefore call `_backend.start()` while backend shutdown is still running. A focused injected-backend reproduction confirmed overlapping backend start/stop and left the component reporting `active == True` after the old stop completed. The added `test_stop_serializes_with_start` does not cover this unlocked backend-stop phase.

Python's official `threading` documentation says an `RLock` blocks another thread only while it is held and recommends context-manager scope for the protected block: <https://docs.python.org/3/library/threading.html#rlock-objects>. Zeroconf's official API documents `ServiceBrowser` as a threaded browser and `cancel()` as browser cancellation, making this backend overlap relevant: <https://python-zeroconf.readthedocs.io/en/latest/api.html#zeroconf.ServiceBrowser>.

**Port assessment:** No bug found in the changed normalization. Zeroconf's official `ServiceInfo` API declares `port` as `int | None`: <https://python-zeroconf.readthedocs.io/en/latest/api.html#zeroconf.ServiceInfo>. Rejecting strings, floats, booleans, and values outside 0-65535 avoids the old `int()` truncation/coercion while preserving valid Zeroconf values. Port `0` remains consistent with the separate `connectable` flag as an unknown/non-connectable endpoint.

**Verdict:** Do not sign off the lifecycle claim without addressing the stop/start interleaving (or narrowing the contract). Port handling is externally compatible and the fractional-port regression is valid.

**Validation:** `python -m unittest tests.test_network_discovery tests.test_coordinator_discovery -v` passed (43 tests). The one-off injected-backend race reproduced overlap. `./lr --list` and `./lr impact` were unavailable because `./lr` is absent. No application code or normal tests were modified.

### Opposing Agent 3 - Architecture/Security Skeptic

**Scope and verdict:** I traced `NetworkDiscovery` through
`AppCoordinator`, `DiscoverySession`, and `AppWindow`, including transport
callbacks, queued delivery, retry, and final shutdown. I also checked the
discovered-node trust boundary and every changed port-validation caller. No
authorization or destructive-action bypass was found. One P1 lifecycle defect
remains: the `RLock` does not serialize the complete backend start/stop
transaction.

**Confirmed P1 finding: start can republish discovery after shutdown.**

- `NetworkDiscovery.start()` holds `_peer_lock` only around the call to
  `_start_locked()`; `_start_locked()` releases no separate lifecycle lock
  while it calls `backend.start()` and only sets `_active = True` afterwards
  (`maintenance/components/network_discovery.py:279-312`).
- `stop()` sets `_active = False`, releases the lock, and calls
  `backend.stop()` outside the lock (`:315-326`). A concurrent start can
  therefore invoke backend start while stop is still blocked in backend stop.
  If the start then returns, it can publish active state after the shutdown
  request.
- A deterministic probe with a backend whose `stop()` blocked produced:

  ```text
  {'start_returned_while_stop_blocked': True, 'backend_start_calls': 2, 'overlap': True}
  ```

  This violates the component's documented idempotent lifecycle boundary and
  can leave Zeroconf registration/browser resources active after shutdown or
  retry. Coordinator bridge clearing prevents the normal UI from receiving
  late events, but it does not close this transport race. This is a reliability
  and shutdown-boundary failure, not a trust escalation.

**Boundary review:** Candidates remain untrusted and non-selectable in
`NodeRegistry`; explicit promotion and authenticated endpoint synchronization
are still required before a provider is attached. Coordinator identity and
generation checks protect queued event delivery, and a synchronous-start
callback probe delivered its candidate successfully. Discovery, persisted
records, and manual-host input now reject non-boolean integer ports outside
`0..65535`; no malformed port path independently authorizes or executes a
remote action. Port `0` is a possible destination-contract question, but not a
confirmed defect under the repository's current inclusive-range contract.

**Validation:**

- `python -m unittest tests.test_network_discovery tests.test_coordinator_discovery tests.test_discovery_session tests.test_discovery_end_to_end -v`: **50 passed**.
- Deterministic blocked-backend start/stop probe: **reproduced** the overlap and
  post-shutdown active-state risk.
- Deterministic synchronous-start callback probe: candidate delivery succeeded.
- No application code or normal tests were edited; no live LAN, remote host,
  installer, or destructive operation was invoked.

**Required repair direction:** serialize the complete backend lifecycle
transaction, or add an explicit starting/stopping state that ensures a stop
requested during startup performs cleanup after startup returns and prevents a
stale start from publishing active state. Add a regression test for the
blocked-stop/concurrent-start interleaving.

## Agent 5 evidence audit

### Phase 1: Evidence inventory

I read the complete PATCH-20260909-011 artifact, current `git diff`, all four
validator sections, PATCH-20260909-010, the related BUG-20260909-001 evidence,
the affected `NetworkDiscovery`/`DiscoverySession`/`AppCoordinator` source and
tests, and the recorded validation results. The ordinary evidence is strong:
133 discovery/window tests passed in my targeted rerun, while the artifact
records 992 full-suite tests plus Ruff, format, Pyright, and Mypy passing.
`./lr`, live LAN/Zeroconf, display-backed Tk, Windows PowerShell, and hostile
platform race environments remain unavailable and are not treated as passes.

### Phase 2: Contract and implementation check

The fractional-port repair is directly supported: `_normalize()` now accepts
only non-boolean `int` values in `0..65535`, and the new regression test passes.
The startup-side lifecycle repair is also real: `start()` holds `_peer_lock`
through `backend.start()` and active-state publication, so a stop cannot miss a
startup that is still in progress.

However, the documented lifecycle contract says `start`/`stop` are idempotent,
and `stop()` releases `_peer_lock` before calling `backend.stop()` at
`maintenance/components/network_discovery.py:315-326`. That leaves a second
lifecycle interleaving outside the repaired startup window: a concurrent
`start()` can begin while backend shutdown is still executing.

### Phase 3: Validator reconciliation and contradictions

Opposing Agents 1 and 2 concluded that both prior regressions were repaired,
based on the new blocked-start test and ordinary focused suites. Opposing
Agents 3 and 4 independently identified and reproduced the blocked-stop /
concurrent-start defect, noting that the added test does not hold
`backend.stop()` blocked. The disagreement is therefore explained by distinct
interleavings, not by ambiguous output: the patch closes start-to-stop ordering
but not stop-to-start ordering.

The port verdict is not materially contradicted. The repository and external
`ServiceInfo.port` semantics support rejecting fractional values. Port `0`
remains a documented contract question, not a newly confirmed defect in this
patch.

### Phase 4: Independent counter-test

I ran a fresh injected-backend probe without editing application code or normal
tests. It started discovery, blocked `backend.stop()`, then invoked `start()`
concurrently. The result was:

```text
{'start_returned_while_stop_blocked': True, 'start_result': [True],
 'backend_start_calls': 2, 'overlap': True, 'active_while_stop_blocked': True}
{'backend_stop_calls': 1, 'active_after_stop': True, 'start_thread_alive': False,
 'stop_thread_alive': False}
```

This is a deterministic reproduction of a stale active transport after the
shutdown request, and it confirms the Agents 3 and 4 finding. It is independent
of LAN availability and is not disproven by the passing startup-block test.

### Phase 5: Evidence decision and recommendation

The fractional discovered-port regression is repaired and the original
startup/stop interleaving is repaired. The patch is nevertheless **not safe to
approve as submitted** because the complete backend lifecycle transaction is
still not serialized: concurrent retry/start can overlap backend shutdown and
republish active state after shutdown. This is a confirmed P1 reliability and
shutdown-boundary regression, not an authorization or destructive-action
bypass.

Residual risk includes the unavailable live transport and hostile timing
environments, synchronous transport callbacks during startup, callback code
executing while the peer lock is held, and the pre-existing path-based
`send2trash` check-to-use window. These limitations do not weaken the direct
blocked-stop reproduction. Recommendation: require one more narrowly scoped
repair that serializes the complete backend start/stop transaction or uses an
explicit stopping state with post-start cleanup, plus a regression test for
blocked `backend.stop()` with concurrent `start()`. Re-run the focused race and
port suites and all available static/full validation; keep unavailable gates
explicitly unverified.
