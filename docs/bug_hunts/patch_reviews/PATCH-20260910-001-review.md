## Validator findings

### Opposing Agent 1 - Patch/Reproduction Skeptic
Findings (ordered by impact):

1. **P1: connection errors are all retried as transient timeouts.** `PeerConnectionManager._start()` installs an `on_error` callback at `maintenance/components/peer_connection.py:95-98` that always calls `failed(..., PeerFailure.TIMEOUT, ...)`; the exception/error value is not classified. The isolated reproduction used a queued coordinator worker whose connect operation raised `RuntimeError("identity changed by hello")`. The resulting state was `offline`, `last_failure=timeout`, `automatic_retry=True`, and `next_attempt_at=1.0`. Thus an authentication or identity failure raised by the actual connect path can be retried automatically, contrary to the explicit `RetryState` rule that those failures stop retry. The direct `failed(..., PeerFailure.IDENTITY_CHANGED)` test passes, but does not cover the production callback path. This undermines the claimed Phase 15.6 identity-rejection/retry guarantee and can repeatedly contact a peer whose identity must not be accepted.

2. **P1: destructive action coalescing is not implemented across dialogs.** `ProcessDialog` computes `_action_operation_key` at `maintenance/dialogs.py:749`, but `quit_selected()` at `1043-1088` uses a per-dialog `_action_in_flight` flag and `run_in_thread`; it never submits or checks that node-qualified key through `AppCoordinator`. Two dialogs for the same node can therefore pass their independent guards and issue two termination requests for the same PID. This also means a lost first response does not prevent a second dialog from retrying: `_process_action_error()` intentionally leaves the first dialog in-flight/disabled at `1175-1183`, while the other dialog has no shared unknown-outcome state. The existing duplicate-click test proves only repeated clicks in one dialog, not the cross-dialog or lost-response case required by the plan. Target binding itself is retained per dialog, but it does not provide idempotency.

3. **P2: malformed authenticated action results are accepted by coercion.** `process_action_result_from_dict()` at `maintenance/cluster.py:167-180` converts `requested` with `int()` and each `errors` entry with `str()` without validating their wire types or numeric domains. An isolated call with `{"requested": True, "stopped": [], "force_required": [], "errors": []}` returned `ProcessActionResult(requested=1, ...)` instead of rejecting the malformed result. A signed peer can therefore produce a syntactically authenticated but semantically malformed success response that is displayed and combined by the UI, corrupting action counts/reporting. This does not by itself cause an extra local termination, but it fails the plan's malformed-input contract and weakens claimed response correctness.

Counter-checks that survived review:

- `python -m unittest tests.test_peer_connection tests.test_remote_contract tests.test_process_protection tests.test_process_table -v`: 91 tests passed. These tests cover direct identity-failure state transitions, target/create-time revalidation, wrong target snapshots, duplicate clicks within one dialog, stale dialog generations, and lost-response disabling; they do not cover the production error-classification callback or multiple dialogs sharing an action key.
- The direct stale-generation paths are correctly guarded: `PeerConnectionManager.complete/failed()` compare `connection_generation`, and dialog result callbacks compare `_action_generation` and `_closed`.
- Remote request target identity, allowlisted action kinds, target-side offline/permission checks, and create-time forwarding are enforced in the exercised paths. No automatic destructive retry was found in `AuthenticatedNodeProvider`.
- The implementation is fail-safe for a lost response within one dialog by keeping the action unknown and the button disabled. That is safe, but it is not equivalent to shared idempotency or a recoverable reconciliation state.

Claimed impact assessment: the focused evidence supports read-only target binding and local target revalidation, but not full Phase 15.6-15.9 readiness. The retry callback bug and cross-dialog action gap remain production-reachable; the malformed-result issue is a protocol/data-integrity gap. No production code, normal tests, or plan files were edited by this review.

### Opposing Agent 2 - Repo-Truth Skeptic
1. **P1 - Pairing does not provision the target-owned grant, so the advertised peer flow cannot authenticate.** The repository contract requires two-sided pairing and says the target must install a grant for the initiating node before the initiator persists its record (`docs/PHASE_15_4_TO_15_8_PEER_NETWORK_PLAN.md:322-339`, especially `328-331`). `maintenance/ui/window_node_actions.py:105-150` instead promotes the discovered node locally, creates a secret locally, and writes `PeerGrantRecord(caller_node_id=node_id, ...)` into the same local `ClusterState`; there is no target-side RPC, UI approval, or remote grant installation. The target listener only loads `controller._cluster_state.peer_grants` (`window.py:970-999`), while the initiator's `AuthenticatedNodeProvider` uses the generated secret against the peer. Consequently the peer has no matching target grant and rejects the request as an unknown caller, while the initiator may still present the node as paired. This is not repaired by the existing `RemoteService` ACL: that service is correctly target-owned, but no code in this patch provisions it on the other installation. The existing tests cover in-process ACL mechanics, not the two-installation pairing path.

2. **P1 - Late remote activation can attach obsolete state after revoke/re-pair or node replacement.** The plan requires a successful connection completion to be rejected when node identity/generation is stale (`docs/PHASE_15_4_TO_15_8_PEER_NETWORK_PLAN.md:395-419`, `443-449`). `activate_remote_node()` captures `record` and `state` at `maintenance/ui/window_node_actions.py:528-562`, then its `on_result()` unconditionally looks up the node and mutates its descriptor, provider, action backend, scheduler, and selection (`:564-585`). It does not capture or check a connection generation, operation generation, current record/secret, trust state, identity status, or shutdown/revocation state. `AppCoordinator` coalescing prevents duplicate keys, but does not make a callback valid after the context changes. A queued hello started for a trusted placeholder can therefore complete after revoke/re-pair and attach the old provider/backend, or raise from a removed registry context instead of being safely ignored. The focused tests exercise stale dashboard/process callbacks and `PeerConnectionManager`, but no test covers this actual activation seam.

**Contract/integration verdict:** Discovery remains presence-only and the local `ProcessManager` safety boundary is preserved; the typed codecs, node-qualified keys, and existing monkeypatch-compatible constructor aliases are supported by the focused tests. Those controls do not make the end-to-end Phase 15.6-15.9 integration complete because target grant provisioning and stale activation invalidation are absent.

### Opposing Agent 3 - Architecture/Security Skeptic
Findings:

- **P1, high confidence: pairing does not provision the target-side grant required by the authenticated service.** `pair_discovered_node()` generates a secret in the initiator's `TrustedNodeRecord` and writes a `PeerGrantRecord` whose caller is the discovered node (window_node_actions.py:105-148). The target's `RemoteService` authenticates grant-mode requests by looking up the initiator's node ID in the target-local `grants` map (remote.py:537-547), but no pairing or activation path transfers/configures that reciprocal grant on the target. Consequently a normal pair cannot authenticate `hello`, reads, or actions unless an undocumented out-of-band configuration has already installed the matching secret. This is an availability/security-gate failure, not an authentication bypass; the plan explicitly says remote operations must not be exposed when target-owned grant provisioning is incomplete.

- **P1, high confidence: process action identity is optional, so an authorised caller can target a stale or guessed same-user PID without a create-time binding.** The wire validator accepts `{"pid": ...}` with no `create_time` (remote.py:427-455), `RemoteService` converts that into a `ProcessRef` with `None` (remote.py:675-689), and `ProcessManager._allowed_processes()` only compares creation time when an expected value exists (actions.py:183-189). User ownership, protected PID/name, and executable checks still apply, so this is not a cross-user or protected-process bypass, but it defeats the required PID-reuse/stale-list protection for any caller holding termination permission. The scanner normally supplies a timestamp, but the authenticated target must not rely on a client hint for process identity.

- **P2, high confidence: the intended node-qualified action key is dead code and destructive actions are not coalesced across dialogs.** `ProcessDialog` stores `_action_operation_key` (dialogs.py:749), but `quit_selected()` calls `run_in_thread()` directly (dialogs.py:1071-1087) rather than `AppCoordinator.run()` or another shared per-node action lease. `_action_in_flight` only protects one dialog instance. Two dialogs for the same node can submit distinct request IDs for the same PID, and normal/force work can race across instances; replay protection does not help because each request is newly signed. Target safety usually turns the second request into an error, but the action is not idempotent and a lost response remains unknown, so duplicate cross-dialog requests can produce inconsistent user-visible outcomes and avoidable target load.

- **P1 conditional, high confidence: HMAC provides integrity/authentication but no confidentiality for the socket path.** `SocketRemoteTransport` sends length-prefixed plaintext JSON over TCP (remote.py:782-810), while the envelopes expose dashboard/resource data, process names/usernames/PIDs, and action details. The transport accepts a caller-supplied non-loopback host, even though the current listener defaults to loopback. Anyone able to observe the configured network path can read these payloads; HMAC does not mitigate that. The plan allows HMAC-only only after an explicit acceptance of this limitation or requires pinned mutual TLS when confidentiality is needed. No such acceptance or TLS boundary is present in this patch, so this remains a release blocker for LAN use, though it is not an integrity/authentication failure on loopback.

Controls verified: `RemoteService` checks target node identity, capability, per-caller permission, and online state below the UI (remote.py:561-645, 669-709); target `ProcessManager` rechecks current user, protected PID/name/executable, and supplied create time before acting (actions.py:163-201, 229-249). The provider also verifies response node/request identity and inner snapshot identity (remote.py:1127-1135, 975-992). These controls fail closed for malformed/unauthorised requests but do not resolve the four gaps above.

Focused validation: `python -m unittest tests.test_remote_contract tests.test_process_protection tests.test_process_table -q` passed, 86 tests. Those tests cover supplied create-time mismatch, target permission checks, and per-dialog duplicate clicks, but do not cover omitted create-time, reciprocal grant provisioning, cross-dialog action coalescing, or plaintext confidentiality. No production code, normal tests, or plan files were modified by this review.

### Opposing Agent 4 - External-Research Skeptic
Findings:

- **P1 - The socket server is not bounded to 16 concurrent handlers.**
  `RemoteSocketServer.start()` sets `request_queue_size = 16` (remote.py:899-901),
  but uses `socketserver.ThreadingTCPServer`, whose documented behavior creates a
  handler thread for each accepted request. Python documents `request_queue_size`
  as the size of the queue for requests waiting while a handler is busy, not a
  cap on active handler threads. A peer or reachable attacker can therefore open
  many connections that each occupy a daemon thread in `_recv_frame()` or inside
  `service.handle()` until the per-socket timeout (remote.py:873-893). The
  `daemon_threads`/`block_on_close` settings make shutdown non-blocking; they do
  not provide admission control. This contradicts the bounded-handler implication
  in the implementation comments and leaves an availability/resource-exhaustion
  path when the listener is exposed beyond loopback. Evidence: Python
  `socketserver` docs, `request_queue_size`, `ThreadingMixIn`, and
  `daemon_threads` sections: https://docs.python.org/3/library/socketserver.html.

- **P1 - Request IDs are replay-protected only as a `(node_id, request_id, nonce)`
  tuple, so they do not make destructive requests idempotent.** `ReplayCache`
  records `(node_id, request_id, nonce)` (remote.py:228-264), while the service
  executes a process action before returning its response (remote.py:669-709).
  Re-submitting the same signed process action with the same `request_id` but a
  fresh nonce passes authentication and invokes `ProcessManager` again. A lost
  response or an intentional authenticated retry can thus repeat a termination
  request; the code comment/docstring claims “idempotent request IDs” (remote.py:5)
  but there is no request-ID result cache or duplicate-ID rejection. This matters
  despite the plan’s “never automatically retry” rule because the wire service
  itself accepts the repeated destructive operation. The existing replay test
  only repeats the complete envelope (remote.py tests:204-228), so it does not
  cover this case. Python’s executor cancellation documentation is not a remedy:
  cancellation only affects pending futures and cannot undo already-running work:
  https://docs.python.org/3/library/concurrent.futures.html.

External-semantics checks that did **not** produce findings:

- `_recv_exact` correctly handles TCP fragmentation; Python documents TCP as a
  byte stream with no correspondence between sends and receives. The explicit
  length limit is applied before body allocation on the socket path.
- `shutdown(wait=False, cancel_futures=True)` is correctly understood as
  cancelling only not-yet-running executor work. Running tasks remain dependent
  on the cooperative `Event`; Python documents both limitations and that worker
  threads can keep the interpreter alive. This is a residual shutdown bound, not
  proof of forced cancellation: https://docs.python.org/3/library/concurrent.futures.html.
- The target checks capability, permission, target identity, action kind, PID,
  ownership, protected status, and create time below the UI. This matches OWASP’s
  distinction between authentication and authorization, deny-by-default guidance,
  and requirement to check authorization at the protected boundary:
  https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html.
  No authorization bypass was established from the inspected paths.
- `ProcessManager` uses psutil’s target-side process objects and `wait_procs`; the
  external psutil documentation confirms process termination is an operation on
  a process object, but it does not make termination transactional or guarantee
  that a response loss means the action did not occur. The plan’s unknown-outcome
  rule remains necessary: https://psutil.readthedocs.io/en/latest/.

Validation: `python -m unittest tests.test_remote_contract tests.test_peer_connection tests.test_cluster -v` passed (74 tests), and the existing Agent 4 counter-test passed. These tests do not disprove either finding; neither has a repository regression test for handler admission limits or same-request-ID/fresh-nonce action replay.

### Phase 1: Verify reviewer claims

1. **Peer failure classification is confirmed.** `PeerConnectionManager._start()`
   maps every coordinator error to `PeerFailure.TIMEOUT` at
   `maintenance/components/peer_connection.py:89-98`. `RetryState` correctly
   stops retries only when it receives `AUTHENTICATION_FAILED` or
   `IDENTITY_CHANGED`, so the production callback cannot reach that fail-closed
   branch for an exception. The direct `failed()` tests do not cover this seam.
   The claim is accurate, although the current `AppWindow._peer_connections()`
   composition sets `can_connect` to `False`; this means the defect is in the
   reusable manager and any future enabling composition, while the current
   default app does not yet initiate those attempts.

2. **Cross-dialog action coalescing is confirmed.**
   `ProcessDialog` computes `_action_operation_key` at
   `maintenance/dialogs.py:744-750`, but `quit_selected()` invokes
   `run_in_thread()` directly at `:1081-1088`. Only the instance-local
   `_action_in_flight` flag is checked. The shared `AppCoordinator` key used for
   process reads is not used for actions. Two dialogs can therefore issue two
   distinct signed requests for the same target/PID. The unknown-outcome branch
   at `:1175-1183` disables only that dialog and does not create a target-wide
   action lease or reconciliation record. The claim is confirmed and is a
   correctness/idempotency blocker, even though target-side revalidation can
   deny some duplicate attempts.

3. **Malformed action-result coercion is confirmed.**
   `process_action_result_from_dict()` at
   `maintenance/cluster.py:167-180` applies `int()` and `str()` rather than
   validating booleans, integer domains, list element types, and result
   invariants. An independent call with `requested=True` returned
   `requested=1`. The client catches decoder exceptions, but the decoder does not
   raise for this authenticated malformed payload. This is a protocol/data
   integrity blocker, not evidence of extra process termination.

4. **Pairing/grant provisioning is confirmed, with impact narrowed.**
   `pair_discovered_node()` creates the secret and `PeerGrantRecord` in the
   initiator's local `ClusterState` at
   `maintenance/ui/window_node_actions.py:113-149`. No target RPC, target UI
   approval callback, or target-store write exists. `RemoteService` authenticates
   grant-mode requests only from its target-local `_grants` map at
   `maintenance/remote.py:540-547`. Therefore the implemented two-installation
   pairing ceremony is absent. The reviewers' conclusion that the normal flow
   cannot authenticate is supported when the target has no independently
   provisioned matching grant. It is not an authentication bypass; it is an
   unavailable/incomplete feature. The plan explicitly requires target-owned
   provisioning before remote operations are exposed.

5. **Stale activation is confirmed.** `activate_remote_node()` captures
   `record`/`state` and installs provider, backend, scheduler, and selection in
   `on_result()` at `maintenance/ui/window_node_actions.py:564-585`. That callback
   checks neither the current record/secret, registry membership, trust and
   identity status, connection generation, coordinator generation, nor closing
   state. `NodeRegistry.revoke_trusted()` deletes the context, so a late result
   can also raise from `registry.context(node_id)`. The existing generation tests
   cover scans and `PeerConnectionManager`, not this activation seam. The claim
   is confirmed.

6. **Optional create-time is confirmed as a safety gap.**
   `validate_operation_params()` accepts a process reference without
   `create_time` at `maintenance/remote.py:427-455`; the target constructs
   `ProcessRef(..., None)` at `:674-689`, and `ProcessManager._allowed_processes()`
   only compares creation time when one is supplied at
   `maintenance/actions.py:185-189`. An independent probe showed the wire
   validator accepts `{"pid": 42, "action": "request_quit"}`. The current UI
   forwards a timestamp when the scan has one, so this is not proof that every
   normal click is unsafe. It is nevertheless a contract violation for the
   target-side PID-reuse guarantee: an authenticated caller can omit the binding.

7. **Plaintext transport and handler admission claims are confirmed as
   conditional.** `SocketRemoteTransport` sends length-prefixed JSON over TCP
   without TLS at `maintenance/remote.py:782-810`; HMAC does not provide
   confidentiality. `RemoteSocketServer` subclasses `ThreadingTCPServer` and
   sets `request_queue_size=16` at `:899-911`, but Python's official
   `socketserver` documentation defines that as the waiting connection queue,
   while `ThreadingMixIn` creates a handler instance/thread per request. It is
   not an active-handler cap. These are release blockers for an exposed LAN
   deployment, but not additional loopback-only confidentiality or admission
   failures. The current app binds `127.0.0.1` and `_listener_endpoint()` returns
   no advertised endpoint, so the planned cross-machine listener is currently
   unavailable rather than safely deployed.

8. **Fresh-nonce replay claim is confirmed.** `ReplayCache` keys entries by
   `(node_id, request_id, nonce)` at `maintenance/remote.py:228-264`, and
   `RemoteService` executes the action before returning at `:669-709`. Reusing
   a signed action's request ID with a fresh nonce is therefore accepted and can
   execute again. The client does not automatically retry destructive work, but
   that does not make the service-side request ID idempotent. The reviewer claim
   is supported by the code and the plan's explicit request-ID requirement.

### Phase 3: Sibling-risk search in changed surfaces

- The listener lifecycle has additional divergence beyond the four reviewers'
  primary claims. `AppWindow.__init__` calls `_start_peer_listener()` before
  discovery at `window.py:228-229`, while pairing happens later and does not
  itself start/rebind the listener. `_sync_peer_listener_grants()` can update an
  existing service, but only after `_save_cluster_state()` is reached; it cannot
  create the missing target-side grant on the other installation. Revocation and
  permission changes must be checked against this live service path as well as
  persistence.
- `_start_peer_listener()` binds loopback and constructs its service from the
  currently selected context (`window.py:985-1000`). Any future enablement must
  ensure listener identity/provider are the local target, not a selected remote
  mirror, and must publish an endpoint only after successful bind.
- The existing `_save_cluster_state()`/grant-preservation behavior means callers
  that construct a `ClusterState` with an empty grant tuple cannot express grant
  revocation safely. This is a sibling lifecycle risk to pairing and must be
  resolved atomically with permission changes and server ACL updates.
- `ProcessManager.terminate()` safely reuses local checks, and the remote service
  allowlists operation kinds and target identity. No generic shell, signal,
  arbitrary-path, or cross-user process bypass was found. These controls are
  verified protections, not evidence that remote action idempotency is complete.
- Node-qualified read keys, dashboard inner-node validation, stale scan delivery,
  and local target revalidation are supported by code and passing tests. They
  should be preserved while fixing action and activation lifecycle rather than
  replaced with a second coordinator.

### Phase 4: Lifecycle, target identity, and drift mapping

- **Lifecycle:** The reusable connection policy has generation checks for
  `complete()`/`failed()` and cancellation, but its coordinator error path loses
  failure classification. The app composition currently disables connection
  attempts, so Phase 15.6 is not implemented end to end. Activation has no
  equivalent generation/state guard, and listener/grant lifecycle is not a
  two-sided ceremony.
- **Target identity:** Signed envelope target identity, response node identity,
  inner snapshot identity, typed process target identity, permission checks, and
  local process safety are present and exercised. Process create-time remains
  optional at the protected boundary, so PID identity is not mandatory for all
  authenticated action requests. A display/node selection change does not
  retarget an already constructed dialog, but two dialogs still lack a shared
  action identity/lease.
- **Persistence and drift:** Trusted records, grants, endpoint updates, and
  identity fingerprints are persisted through `ClusterStore`, but pairing writes
  only one installation's state. Revoke/permission operations can preserve stale
  grants, while a live `RemoteService` has its own copied ACL. The current plan
  also requires later compatibility, cleanup, packaging, and final validation;
  no evidence in this artifact proves those phases. The plan's own required
  full-suite/static/LR/deployment gates therefore remain outstanding.

### Phase 5: Continue assessment and exact gates

**Assessment: unsafe to continue to later trusted-cluster readiness work or
expose remote actions.** The patch may continue only as a blocked corrective
iteration. The combined P1 findings are sufficient to prevent readiness, and
the malformed-input, stale-identity, missing target provisioning, and
unbounded-handler issues match the plan's explicit `PHASE 15 BLOCKED` criteria.

Required gates before continuing:

1. Classify coordinator connection errors into transport timeout/refused/route,
   authentication, identity, cancellation, and unknown failure. Map
   authentication/identity failures to no automatic retry and add a test through
   the actual `on_error` callback. Replace the current `can_connect=False`
   composition with an explicitly gated authenticated connection owner only when
   provisioning and transport policy are complete.
2. Implement a real two-sided pairing ceremony: target-visible approval,
   target-owned grant installation, durable target and initiator commits, and
   crash/revoke behavior. Do not report a peer paired or expose remote
   operations until target provisioning and authenticated `hello` have both
   succeeded. Add a two-installation synthetic integration test.
3. Add activation operation/generation and current-record checks before every
   callback mutates a context. Invalidate on revoke, re-pair, identity mismatch,
   endpoint/secret replacement, and shutdown; late callbacks must be ignored, not
   raise or attach obsolete providers.
4. Route destructive actions through one node-qualified shared lease/coordinator
   with explicit unknown-outcome state and target-side request-result replay or
   duplicate-ID rejection. Cover two dialogs, normal-to-force transitions,
   response loss, and fresh-nonce reuse of one request ID.
5. Reject malformed action-result types and domains without coercion. Require a
   target-verified create-time binding for termination, or make the safe outcome
   an explicit denial when the target cannot supply one. Add counter-tests for
   booleans, negative/count mismatches, malformed PID lists, and absent identity.
6. Choose and document the transport exposure policy. Keep loopback-only and
   advertise no remote endpoint, or implement explicitly approved pinned TLS/
   reachable binding. If LAN exposure remains HMAC-only, record explicit
   confidentiality acceptance and add bounded active-handler admission and
   shutdown tests; `request_queue_size=16` alone is not sufficient.
7. Run the required repository-wide gates after fixes: full unittest discovery,
   `ruff check .`, `ruff format --check .`, `pyright`,
   `mypy --ignore-missing-imports .` with the duplicate-module baseline resolved
   or precisely isolated, `./install/verify.sh`, `git diff --check`, and the
   repository's LR checks if available. Do not treat the current format or Mypy
   failures as baseline passes.

**Unsupported or unproven claims:** the focused tests do not prove actual
