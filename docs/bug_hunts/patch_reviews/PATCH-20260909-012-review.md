## Mode and risk

BugGuard mode: Mode A - code-edit validation

## Patch summary

The final patch keeps the peer lifecycle lock across the complete backend
start/stop transactions, preventing overlapping startup and shutdown, and
accepts only non-boolean integer discovered ports in the valid range. Focused
regression tests cover blocked startup and blocked shutdown interleavings.

### Opposing Agent 1 - Patch/Reproduction Skeptic

**Independent reproduction result: the two targeted lifecycle regressions and
the fractional-port regression are repaired in the current patch.** I did not
edit application code or normal tests.

#### Validation

- Focused command: `python -m unittest tests.test_network_discovery tests.test_coordinator_discovery tests.test_discovery_session tests.test_discovery_end_to_end -v`
- Result: **51 tests passed**.
- The focused suite's `test_stop_serializes_with_start`,
  `test_start_serializes_with_blocked_stop`, and fractional-port test all passed.

#### Deterministic lifecycle probes

- **Blocked start:** a fake backend blocked inside `start()`. A second thread
  called `stop()` before startup was released. `stop()` remained blocked until
  startup completed, then invoked backend cleanup. Result:
  `start_calls=1`, `stop_calls=1`, `active=False`.
- **Blocked stop:** discovery was started, the fake backend blocked inside
  `stop()`, and another thread called `start()`. The second start remained
  blocked while backend shutdown was blocked. After release it started once,
  with no backend overlap. Result: `start_calls=2`, `stop_calls=1`,
  `overlap=False`, `active=True`.
- Both probes joined all worker threads within the timeout. No timeout was
  treated as a pass.

The current `NetworkDiscovery.start()` and `stop()` hold `_peer_lock` across
the complete backend transactions. This closes both prior interleavings: stop
cannot escape during a blocked start, and start cannot enter while backend stop
is still running. The fractional normalization accepts only non-boolean
integers in `0..65535`; a `1.9` advertisement is represented with
`port=None` rather than silently truncated.

#### Skeptic assessment

No new defect was confirmed in the reviewed lifecycle and port scope. The
remaining evidence limits are the unavailable live LAN/Zeroconf transport,
display-backed Tk environment, and hostile external callback timing. The
direct injected-backend probes are deterministic and do not depend on those
environments. Callback delivery during backend startup remains a pre-existing
ordering edge because `_active` is published only after `backend.start()`
returns, but it was not introduced by this patch and no shipped backend
reproduced a lost event in the focused tests.

**Skeptic verdict:** the targeted PATCH-20260909-011 lifecycle defect and
fractional-port defect are repaired; no additional patch-introduced defect was
reproduced in this scope.

### Opposing Agent 2 - Repo-Truth Skeptic

**Findings:**

- `NetworkDiscovery.start()` and `stop()` now hold `_peer_lock` across the
  complete backend start/stop transaction. This matches the component's
  documented idempotent lifecycle and prevents a concurrent retry from
  overlapping backend shutdown or republishing active state after stop.
- `AppCoordinator.start_discovery()` installs the bridge and lifecycle

  failed start, and invalidates queued deliveries before stopping. The
  coordinator's late-event fence therefore remains aligned with the component
  lifecycle.
- `DiscoverySession` owns the expiry timer while the coordinator owns the
  backend. `AppWindow` uses the session for startup, ticks, toggle-off, and

- Candidate ports are normalized to non-boolean `int` values in `0..65535`.
  Strings, floats, booleans, and out-of-range values become `None`; pairing

  `None`, rather than malformed input, as “not openable”.

The inclusive acceptance of port `0` remains a contract question: the repo's

### Opposing Agent 3 - Architecture/Security Skeptic

**Scope reviewed:** `NetworkDiscovery` lifecycle locking and port
normalization, `AppCoordinator` discovery ownership/bridge invalidation,
`DiscoverySession` startup/shutdown ordering, and the trusted-node endpoint
update path in `window.py`.

**Findings**

- **No confirmed trust-boundary bypass.** A discovered advertisement remains
  only an observation. `_sync_trusted_node_endpoint()` changes a persisted
  endpoint only for an already trusted descriptor and verifies the candidate
  endpoint with `AuthenticatedNodeProvider.hello()` before saving it. An
  attacker-controlled TXT record therefore cannot, by itself, replace a
  trusted node's host/port or obtain remote action authority.
- **Strict port handling is fail-safe at the discovery boundary.** Boolean,
  fractional, string, negative, and over-`65535` values become `None` in
  `NetworkDiscovery._normalize()`. The downstream trusted-endpoint path uses
  the existing record only when the candidate port is absent, and refuses an
  update when no usable port exists. The manual-host path applies the same
  non-boolean integer/range check before registration. No port-validation
  security regression was reproduced.
- **Shutdown ordering is fail-closed for late events.** The coordinator clears
  `_discovery` and its generation before calling `discovery.stop()`. The
  discovery object marks itself inactive before invoking backend stop. Both
  bridges consequently reject late callbacks, including callbacks queued
  before stop but delivered after a restart. Complete `_peer_lock` coverage
  serializes concurrent start, stop, event processing, peer reads, and expiry;
  a blocked stop did not allow a concurrent start to overlap.
- **Residual lifecycle availability risk, not a security bypass:**
  `_active` is assigned only after `backend.start()` returns
  (`maintenance/components/network_discovery.py:297-313`). A backend that
  synchronously emits an `add`/`update` callback during `start()` has that
  callback dropped by `_handle_transport_event_locked()` at lines 342-346. A
  safe injected-backend probe reproduced this with a valid peer: startup
  returned active but `peers()` remained empty. Zeroconf may deliver browser
  callbacks during startup, so a first peer can be missed until a later update
  or indefinitely if no update occurs. Candidate processing does not grant
  trust, so the impact is discovery completeness/availability only.
- **Lock-held callback/shutdown tradeoff:** event callbacks are emitted while
  `_peer_lock` is held. The lock is re-entrant for same-thread callbacks and
  the coordinator normally defers UI work, so the tested paths did not
  deadlock. A custom backend whose `stop()` waits for a callback thread that
  itself re-enters this discovery object could still create lock/backend
  coupling and shutdown delay. This is a backend-contract risk, not a
  demonstrated vulnerability in the current Zeroconf path.

**Safe probes and results**

- `python -m unittest tests.test_network_discovery tests.test_coordinator_discovery tests.test_discovery_session -v`:
  **47 passed**.
- Concurrent blocked-start/stop probe: **passed**; stop waited for startup,
  then completed with `active == False` and backend stopped.
- Adversarial port probe covering `True`, negative, over-range, fractional,
  string, `None`, `0`, and `65535`: **passed**; only valid integer boundary
  values were retained.
- Synchronous startup callback probe: **reproduced the residual availability
  risk**; a valid callback emitted from `backend.start()` yielded zero peers.

**Assessment:** No P0/P1 architecture or security defect was confirmed in
complete lifecycle locking or strict port validation. The synchronous-start
callback behavior is a scoped P2 availability hardening candidate if the
backend contract permits callbacks before `start()` returns; any fix should
preserve shutdown's stale-generation rejection and avoid invoking external
callbacks while holding the peer lock.

### Opposing Agent 4 - External-Research Skeptic

**Research performed**

- Python `threading` documents that `RLock` blocks another thread until the owner releases it and recommends context-manager usage for balanced acquire/release pairs: <https://docs.python.org/3/library/threading.html#rlock-objects>.
- Official python-zeroconf documentation describes `ServiceBrowser` as a `Thread`, `cancel()` as browser cancellation, and `Zeroconf.close()` as shutting down sockets/engine and being safe to repeat: <https://python-zeroconf.readthedocs.io/en/latest/api.html>.
- The declared dependency floor is `zeroconf>=0.131`; the official v0.131.0 source also implements `ServiceBrowser.cancel()` with `join()` and `Zeroconf.close()` by unregistering services, removing listeners, and shutting down owned threads.
- Zeroconf’s `ServiceInfo` API models `port` as `int | None`; the application’s `connectable` and `None` convention therefore remains the semantic policy for actionability.

**Challenge and findings**

1. **Lifecycle serialization is supported, not disproven.** `NetworkDiscovery` holds its `RLock` across the complete backend `start()`/`stop()` call. That makes a concurrent start wait for stop, or vice versa, consistent with Python’s documented lock semantics. The adapter’s `cancel()` joins Zeroconf’s browser thread before `close()` tears down the engine. I found no evidence that the final lock scope creates an invalid Zeroconf ordering or permits a browser callback to outlive the adapter’s documented cancellation boundary.
2. **The cleanup order is defensible.** Cancelling the browser before closing Zeroconf agrees with Zeroconf’s public removal path and avoids scheduling browser cancellation against an already-closed loop. Zeroconf’s blocking `close()` also unregisters services and removes listeners, so the adapter’s best-effort repeated cleanup is supported.
3. **The port range is wire-compatible but semantically permissive at `0`.** Rejecting booleans, non-integers, negatives, and values above `65535` is appropriate for a DNS-SD service port representation. However, `0` remains accepted. A malformed `connectable=true, port=0` record can look openable because UI predicates use `port is not None`, even though no usable TCP destination is established. The trusted-node path verifies with `hello()` before persisting a discovered endpoint, reducing impact. This is a residual policy concern, not a confirmed patch-introduced lifecycle bug; the available tests do not define the desired `connectable=true, port=0` behavior.

**External-research verdict:** No confirmed defect in the lifecycle lock or Zeroconf cancellation/close ordering. Keep the lifecycle decision. Record port zero as **needs explicit product-policy evidence**: either it is intentionally valid for presence-only advertisements, or actionable/openable paths should require a nonzero port. Live LAN validation remains unavailable as stated above.

### Phase 2: Contract and implementation verification

The lifecycle repair is present at `maintenance/components/network_discovery.py:279-326`:
`start()` acquires `_peer_lock` before checking/starting and retains it through
backend startup and active-state publication; `stop()` retains it through the
complete backend stop and state cleanup. This preserves sequential
idempotence and prevents both previously demonstrated interleavings: stop
escaping during blocked startup, and start entering during blocked shutdown.

The port repair at `:455-463` accepts only a non-boolean `int` in `0..65535`.
The focused tests cover fractional, string, boolean, and out-of-range values,
while valid `0` and `65535` remain accepted consistently with the repository's
current inclusive-boundary contract. Coordinator generation/bridge clearing
and session timer ownership remain aligned with the component lifecycle.

### Phase 3: Independent counter-test and contradiction reconciliation

I ran a fresh injected-backend probe without editing application code or
normal tests. With `backend.stop()` blocked, a concurrent `start()` remained
blocked; after release it completed one restart. The result was:

```text
{'start_results': [True], 'start_calls': 2, 'stop_calls': 1,
 'active': True, 'peers_after_restart': 0}
```

This disproves the PATCH-011 blocked-stop overlap in the current code. A
second probe used a backend that emitted a valid candidate synchronously from
`start()`. It produced `synchronous_start_callback_peers: 0` and
`events: 0`. That behavior is explained directly by `_active` being published
only after `backend.start()` returns. It is a real discovery-completeness
limitation, but it was already recorded by PATCH-011 and is not introduced by
the PATCH-012 changes. No reviewer provided evidence that the patch worsens
it.

The reviewer disagreement is therefore resolved by scope and timing: Agents
1 and 2 validated the repaired lifecycle/port contract; Agents 3 and 4
retained the startup-callback and port-zero policy questions as residual or
contract evidence gaps. Their conclusions do not contradict the direct
blocked-stop result. Port zero also remains unconfirmed because the repo
explicitly accepts it and uses `None` for absent connectivity, while the
desired actionability policy has not been specified.

## Main auditor rebuttal and final decision

### Rebuttal

The initial concern that complete lifecycle locking might overlap with
Zeroconf shutdown is not supported by the final implementation or the
independent blocked-stop probe. The lock now covers both backend calls and
state cleanup. The synchronous-start callback loss and port-zero semantics are
real evidence gaps, but they predate this patch and are not regressions caused
by it. Discovery remains observation-only until explicit trust and
authenticated endpoint verification.

### Final decision

PATCH-20260909-012 is **conditionally approved from available evidence**.
The two PATCH-011 regressions are repaired, 993 tests and all available
static/type/format checks pass, and all five independent A4 fallback reviews
completed. `./lr` gates and live platform/transport environments remain
unverified and must not be represented as passed.
