### Opposing Agent 4 - External-Research Skeptic

**Review date: 2026-09-11. Verdict: no official-documentation counter-finding; the closure patch's wording is accurate against Python/SQLite semantics and does not misrepresent them.** Official docs cannot establish this application's role, revocation, failover, or UI contract, but nothing in the new `capacity_basis` wording, the `History (logical bytes)` diagnostics label, the `docs/CLUSTER_ROLES_FAILOVER_2026-09-11.md` storage section, or the new persistence tests misapplies or misstates those official semantics. The P1 Cluster-page revoke residual from PATCH-20260911-001 is no longer present in the current tree, and the storage-cap contract residual is now explicitly documented as logical (P3-style contract clarification), not silently passed.

**Official-doc reconciliation (storage cap):** `_BatchStore.max_bytes` gates only on caller-supplied `batch.encoded_size` (`maintenance/components/cluster_storage.py:219-222`) and `status().bytes_used` is `SUM(encoded_size)` (`:345`); `_cluster_diagnostic` maps `database_bytes=status.bytes_used` and `database_cap_bytes=status.max_bytes` (`window.py:403-404`). SQLite's own maximum database size is page-count x page-size (`SQLITE_MAX_PAGE_COUNT`, default 4294967294, https://sqlite.org/limits.html#max_database_size and #max_number_of_pages_in_a_database_file), which is a physical bound distinct from any application payload total; that page-level limit returns `SQLITE_FULL` when the file cannot grow, exactly the disk-exhaustion case SQLite documents. The new property `capacity_basis` returning `"logical encoded payload bytes"` (`cluster_storage.py:208-212`), the label `History (logical bytes)`, and the doc statement that the cap is "not the physical SQLite file, journal, WAL, or filesystem allocation" therefore accurately describe the code and do not misrepresent SQLite semantics. The implementation uses the default rollback journal (no `journal_mode` change in `_connect`, `cluster_storage.py:154-158`), so the WAL mention in the doc is an explicit contrast, not a claim about this implementation's mode. A fresh probe with `max_bytes=1` and `encoded_size=0` returned `capacity_basis=logical encoded payload bytes`, `append=True`, `logical bytes_used=0`, and a 28,672-byte physical file, matching the PATCH-001 evidence and the new contract wording. The doc claim that "disk-full, locked-database, and SQLite I/O errors pause history writes" matches the `_record_sqlite_failure` path (`cluster_storage.py:408-415`); Python `sqlite3.connect(timeout=...)` is documented as a lock-wait before `OperationalError` (https://docs.python.org/3/library/sqlite3.html#sqlite3.connect), so `timeout=2.0` plus `PRAGMA busy_timeout=2000` is lock handling, not a size budget. No misrepresentation found. Minor pre-existing robustness note, not introduced by this patch: the pause detector string-matches `str(error)` for "full"/"i/o"/"locked"/"readonly" rather than using the structured `sqlite_errorcode`/`sqlite_errorname` attributes Python exposes since 3.11; official guidance favors error codes over message text, but this is out of the closure diff and not a confirmed defect.

**Non-finite-number handling (official JSON semantics):** Python's `json` documentation states that by default the module accepts and outputs `Infinity`, `-Infinity`, and `NaN` (https://docs.python.org/3/library/json.html#infinite-and-nan-number-values), with `allow_nan=True` on the encoder and no `parse_constant` on the decoder. The new persistence tests build the payload dicts with `float("nan")`/`math.inf` and write them with `json.dumps` (default `allow_nan`), then load through `ClusterStore.load()` with `json.loads` (default `parse_constant`), so the inputs are legitimate decodable JSON under the library's own defaults. The filtering is the repo's own: `_parse_invites` constructs `InviteRecord(..., float(expiry))` and `InviteRecord.__post_init__` raises `ValueError("invite expiry must be finite")` on non-finite values (`maintenance/cluster.py:857-874,80-88`), which `_parse_invites` catches and skips; `_parse_epoch` builds `CoordinatorEpoch`, whose `__post_init__` rejects non-finite `issued_at`/`lease_expires_at` (`maintenance/components/cluster_roles.py:78-87`), and on failure returns `None`, after which `load()` falls back to `_initial_epoch` (`maintenance/cluster.py:687-688`). A live probe reproduced exactly this: `dumps` emitted `NaN`/`Infinity`, `loads` returned `nan`/`inf`, the non-finite invite was dropped (`active_invites == ()`), and the epoch came back finite. The tests therefore exercise the repo's own filters, not a parser-side rejection, and are valid evidence.

**Recording-fake change (not a public/schema/API change):** `grid_forget` and `grid_columnconfigure` no-ops were added only to `RecordingWidget` in `tests/support/widget_recording.py:52-56`, a test-only fake under the `tests` package.
