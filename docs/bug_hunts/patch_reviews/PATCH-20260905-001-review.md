## Mode and risk

BugGuard mode: Mode A — code-edit validation
Risk level: high
Validator threshold: selective (Opposing Agent 1 + Opposing Agent 3)

## Patch summary

Task: keep hardware/system scans from freezing or wedging the GUI while preserving current scan output and public behavior.

Audit findings addressed:

- G1 (scanner.py): `SystemScanner.gpu_details()` could block the whole dashboard snapshot indefinitely. In-process pynvml calls (`_nvidia_gpu_details`) have no timeout primitive and cannot be interrupted; subprocess GPU probes already carry `timeout=10`, but a hung NVML/driver call blocked RAM/CPU/storage/network results forever.
- G2 (scanner.py): any single psutil sensor failure inside `scan_dashboard()` (e.g. `sensors_battery()` PermissionError, `disk_usage()` OSError) raised out of the whole scan and surfaced a modal error; partial scan failure was not handled per-resource.
- G3 (window.py): no deadline existed for the background scan task. A hung non-GPU call (e.g. `psutil.disk_usage` on a dead network mount) left the UI busy forever with no recovery.

Changes:

1. `maintenance/scanner.py`:
   - `SystemScanner.gpu_details()` now runs platform GPU detection on a short-lived daemon worker thread and joins with `GPU_QUERY_TIMEOUT_SECONDS = 12.0` (above the 10 s subprocess timeouts so subprocess-timeout messages still surface normally). On timeout it returns `("GPU information unavailable: query timed out",)`. Worker exceptions become "GPU information unavailable: ..." strings.
   - If a previous GPU worker is still holding `_static_gpu_lock` (hung pynvml), `gpu_details()` returns the timeout message immediately instead of piling up one blocked worker thread per 5 s auto-scan.
   - `scan_dashboard()` captures each psutil reading through `_psutil_value()` (None on failure) and builds each resource card via `_resource_with_fallback()`; a failing card degrades to an "Unavailable" summary while the rest of the snapshot still renders. `ScanCancelled` is re-raised so cancellation still propagates.
   - Success-path card construction code is unchanged (moved verbatim into `_*_resource` builders).
2. `window.py`:
   - `handle_analyze()` schedules a `SCAN_TIMEOUT_MILLISECONDS = 30000` watchdog timer per scan generation.
   - `_handle_scan_timeout(generation)` finishes that generation, sets/clears the analysis cancel event, and shows one error; a queued rerun request is intentionally dropped after a timeout.
   - A per-window `_resolved_scan_generation` high-water mark guarantees only the first resolution (completion, error, or timeout) of a generation can render or re-finish; late completions after a timeout are dropped instead of double-reporting.
   - Completion/error paths cancel the pending watchdog; `_close()`/`run()` clear it. Overlap prevention (ScanCoordinator + disabled Scan System button) is unchanged and already covered by existing tests.

Not changed (audit leftovers, reported honestly):

- `AppWindow.__init__` still constructs `Analyzer`/`FileManager` synchronously before the mainloop (pre-paint startup cost; deferring would require a broader refactor).
- `Analyzer.gpu_info()` / `full_report()` (non-GUI paths) are untouched.
- A hung pynvml worker thread cannot be killed in-process; the lock guard bounds the leak to one daemon thread.
- Whole-scan deadline is window-level (30 s) only; individual psutil calls are not individually threaded.

### Opposing Agent 3 — Architecture/Security Skeptic

#### Architecture analysis

- `gpu_details()` runs `GpuDetector.detect()` on a daemon worker and joins with 12 s (scanner.py:731-733). The `_static_gpu_lock.locked()` early-return (scanner.py:720-721) is intended to bound leaked threads, but `_nvidia_gpu_details` is wired as the raw nvidia loader (scanner.py:741), while only the mac/windows/linux loaders are wrapped by `_cached_static_gpu_details` (scanner.py:742-748). A hung pynvml call therefore never acquires `_static_gpu_lock`, so the guard does not prevent repeated hung workers from piling up on each auto-scan. The guard does protect the subprocess loaders, but it also false-positives: a legitimately in-progress subprocess query (up to 10 s) makes a concurrent `gpu_details()` return the timeout message immediately.
- The 30 s window watchdog (window.py:360-364) plus `_resolved_scan_generation` high-water mark (window.py:389-395, 411-416, 423-429) correctly serializes resolution: only the first of completion/error/timeout can render or finish a generation. `_handle_scan_timeout` drops queued reruns intentionally (window.py:392-400), but it does not call `_schedule_auto_scan()`, so a timeout can stop the auto-scan chain when no prior auto-scan timer is pending.
- Fallback cards preserve the `ResourceSummary` contract (`value="Unavailable"`, `percent=None`, `details` tuple) and are consumed safely by `ResourceCard.update_summary` and `InfoDialog`.
- All `None` values from `_psutil_value` flow into `_resource_with_fallback`-wrapped builders; `_battery_resource` handles `None` explicitly, so no unguarded formatting crash exists.

#### Confirmed issues

- **P1 — `maintenance/scanner.py:738-741, 711-736`** — The `_static_gpu_lock` guard does not bound the primary hung-pynvml leak. `_nvidia_gpu_details` is passed unwrapped to `GpuDetector`, so a hung pynvml worker never holds the lock; each `gpu_details()` call can spawn another 12 s daemon worker. The lock guard only applies to the subprocess loaders (mac/windows/linux), which are already bounded by their 10 s timeouts. This contradicts the patch's claim that the leak is bounded to one thread for hung pynvml.
- **P2 — `maintenance/scanner.py:720-721`** — For the subprocess loaders, the lock guard false-positives on a legitimately in-progress query, returning the timeout message even though the query may finish normally. Reachable when a zombie generation still holds the lock while a new generation calls `gpu_details()`.
- **P3 — `window.py:386-400`** — After a scan timeout, `_show_error()` is called but `_schedule_auto_scan()` is not, so the periodic auto-scan chain stops when the timeout occurs with no prior pending auto-scan timer.

#### Non-issues

- **Bounded thread leak (for subprocess paths).** `_static_gpu_lock.locked()` does prevent multiple concurrent subprocess workers, so the leak is bounded to one for those loaders.
- **Generation resolution correctness.** `_resolved_scan_generation` plus `ScanCoordinator.finish()` guarantees exactly one resolution per generation; completion/error/timeout interleavings are dropped correctly.
- **ResourceSummary contract.** Fallback cards supply `str` value, `percent=None`, and a non-empty `details` tuple; `ResourceCard.update_summary` and `InfoDialog` consume them safely.
- **None formatting crash.** All `None` sensor results are fed into `_resource_with_fallback`-wrapped builders; `_battery_resource` handles `None` explicitly, and any formatting exception becomes a fallback card.
- **GPU error-string disclosure.** Worker exception messages may include NVML paths, but pre-existing subprocess GPU probes already surfaced comparable error messages, so no material new privacy risk is introduced.

#### Verdict

**patch-unsafe** — the core architectural claim that the GPU worker leak is bounded to one thread is false for the hung-pynvml path (the exact G1 scenario), leaving the GUI exposed to unbounded accumulated hung workers until `_nvidia_gpu_details` is also wrapped under `_static_gpu_lock` or moved out-of-process.

## Main auditor rebuttal

The reviewers converged on one real defect in the first version of the watchdog and two design notes. Accepted in full:

1. **Accepted (Agent 1 P2 / Agent 3 P1 — hung-pynvml leak unbounded).** The audit summary's claim that the lock guard bounds the leak was wrong: `nvidia_loader` is wired into `_make_gpu_detector()` without the `_cached_static_gpu_details` wrapper, so a hung pynvml never touches `_static_gpu_lock`, and every `gpu_details()` re-spawned a 12 s worker. Reproduced by Agent 1 counter-test A.
2. **Accepted (Agent 1 P3 / Agent 3 P2 — lock-guard false positive).** The `locked()` guard misreads a legitimately in-progress subprocess loader as hung because the lock spans the whole loader run, including the within-budget portion.
3. **Accepted (Agent 3 P3 — auto-scan chain stops after timeout).** This is an intentional design decision, not an oversight: after a 30 s timeout, auto-retrying would loop into another likely-hang and repeat 30 s error modals. The UI returns to Ready and the user (or a dialog-triggered rescan) restarts the chain. Documented as accepted behavior; revisit only if users report the dashboard "stops refreshing".

### Post-review fix (supersedes the lock-guard part of the patch summary)

`gpu_details()` was redesigned (maintenance/scanner.py:712-747) and `SystemScanner.__init__` gained `self._gpu_query_in_flight = False` (scanner.py:118):

- The `_static_gpu_lock.locked()` guard was removed entirely.
- `gpu_details()` now: returns the timeout message immediately when `_gpu_query_in_flight` is True; otherwise sets the flag True BEFORE `worker.start()` (closing the fast-worker race), runs detection on the daemon worker, clears the flag in the worker's `finally` (so a late-finishing worker re-enables retries), catches `RuntimeError` from `start()` (flag reset, unavailable message — flag cannot be stranded True with no worker), joins with `GPU_QUERY_TIMEOUT_SECONDS`, and returns the timeout message when the worker is still alive.
- Why this is correct: the flag can only be observed True by a later sequential call if the previous worker genuinely exceeded its budget (a within-budget worker clears the flag in `finally` before `join()` unblocks, and `join()` synchronizes the write). This covers the nvidia path (which never touches the lock) and eliminates the within-budget false positive by construction. A slow worker that eventually finishes is picked up by the next scan; a truly wedged pynvml leaves exactly one leaked daemon worker and GPU shows the timeout message until restart (accepted trade-off; subprocess-based NVML is the possible future enhancement).

Verification of the fix: Agent 1 post-fix appendix (counter-tests D/E/F: hung-nvidia leak bounded to one worker with 0.000 s re-entry; flag False after within-budget success; `start()` RuntimeError resets flag) and fresh repo tests (92 OK), including new regression tests `test_gpu_details_bounds_hung_nvidia_query`, `test_gpu_details_avoids_new_worker_while_previous_query_in_flight`, `test_gpu_details_recovers_after_late_worker_completion`, plus the earlier `test_gpu_details_times_out_hung_query`. Live smoke on this machine reproduced the hung-nvidia scenario: call 1 = 0.20 s (budget), calls 2-3 = 0.000 s, one leaked worker.

Residual risk accepted and documented: GPU card stays unavailable until process restart after a truly wedged pynvml; auto-scan chain stops after a timeout (manual rescan restarts it); the theoretical non-atomic flag check-then-set is unreachable in the app's sequential scan flow (Agent 1 post-fix appendix).
