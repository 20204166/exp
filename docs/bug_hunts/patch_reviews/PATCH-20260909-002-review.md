## Patch summary

The patch carries validated `NodeSnapshot` metadata through dashboard scans,
stores it on the selected `NodeContext`, and adds a target node ID to remote
component-summary payloads. Existing `DashboardSnapshot` card and dialog APIs
remain unchanged. Follow-up hardening also binds trusted rediscovery to the
local caller identity, propagates activation cancellation, bounds connect
attempts when cancellation is active, and removes broad post-dispatch
`TypeError` retries.

## Original bug / task evidence

PHASE 15.7 required remote snapshots to remain node-bound through provider and
UI integration, with per-node isolation, stale-result rejection, and typed
capability metadata. The pre-patch UI discarded the remote `NodeSnapshot` and
accepted component payloads without an independently checked target ID.

### Opposing Agent 2 — Repo-Truth Skeptic

**Verdict: two lifecycle defects remain; the prior rediscovery and ordinary
grant-preservation findings are fixed.**

#### Finding 1 — Grant revocation is defeated by the preservation fallback (P1)

- `_revoke_trusted_node()` builds a state with no `peer_grants`
  (`window.py:1323-1343`), but `_save_cluster_state()` interprets every empty
  grant tuple as a legacy-shaped update and restores the previous grants
  (`window.py:1052-1063`). A direct state probe confirms that a grant remains
  in the live state after an empty update.
- The same preserved state is written to disk, so removing a trusted node does
  not remove its target-owned caller grant. The startup-created
  `RemoteService` also retains its grant map, and no revoke path updates or
  rebuilds that service (`window.py:1813-1849`).
- Required correction: make explicit grant removal distinguishable from a
  legacy omitted-grants update, then reconfigure or replace the live listener
  after revocation. Add a regression proving both persistence and authorization
  are revoked.

#### Finding 2 — Pairing does not activate or provision the new grant (P1)

- `_pair_discovered_node()` adds a `PeerGrantRecord` locally
  (`window.py:1159-1175`), but `_start_peer_listener()` is only called during
  startup and returns once `_peer_server` exists (`window.py:1813-1817`). If
  pairing occurs after startup, the listener never receives the new grant; if
  there were no grants at startup, no listener exists at all.
- The pairing flow generates the trusted record secret locally and has no
  remote grant/provisioning operation. The peer therefore cannot authenticate
  this caller from this one-sided pairing action. This is a fail-closed
  availability/integration defect, not an authentication bypass.
- Required correction: define and implement an explicit two-sided provisioning
  handshake, or make pairing explicitly require reciprocal pairing, and update
  the live listener grant map atomically.

#### Rechecked paths with no confirmed defect

- `_sync_trusted_node_endpoint()` now passes
  `caller_node_id=NodeId(self._cluster_state.local_node_id)`
  (`window.py:2029-2036`), matching `_test_connection()` and activation. The
  previous grant-enabled trusted-rediscovery authentication finding is fixed.
- `_save_cluster_state()` now publishes the exact state that was persisted
  (`window.py:1058-1064`), so ordinary discovery/rename/color/permission saves
  preserve grants in memory. The pairing path explicitly carries existing
  grants forward while replacing only the same caller entry.
- `_request()` uses `inspect.signature(...).bind(...)` to select the old
  one-argument transport form without retrying after an operation-level
  `TypeError`; existing legacy transport tests pass. No compatibility defect
  was reproduced.

### Opposing Agent 3 — Architecture/Security Skeptic

**Verdict: unsafe; two P1 lifecycle defects remain.**

- **P1, confirmed: pairing does not provision a usable peer credential.**
  `_pair_discovered_node()` generates `record.secret` locally and stores it as
  a local `PeerGrantRecord` (`window.py:1141-1175`), but performs no remote
  provisioning exchange or target-side state update. The target listener is
  built only from its own startup `ClusterState` (`window.py:1813-1855`). A
  fresh two-machine pairing therefore leaves the caller using a secret the
  target does not know; an independent cross-service probe was rejected by
  `RemoteService.handle`. This is fail-closed availability/integration loss,
  not an authentication bypass. Pairing after startup also does not start or
  reconfigure the listener, so even a locally created grant is not immediately
  served.

- **P1, confirmed: trusted-node revocation does not revoke target grants.**
  `_revoke_trusted_node()` constructs a grant-less state, but
  `_save_cluster_state()` intentionally restores the previous grants
  (`window.py:1052-1063`, `1323-1355`). The live `RemoteService` has no
  reconfiguration/removal path and retains its startup grant map. Thus the
  revoked caller remains authorized until a restart or explicit service
  mutation, while the UI reports removal. This is a privilege-revocation
  failure. The grant-preserving state is now published in memory for ordinary
  edits; I did not reproduce the earlier broader claim that pairing necessarily
  deletes unrelated grants.

- Node-qualified coordinator keys plus generation and selected-node guards

### Opposing Agent 4 — External-Research Skeptic

**Independent external-semantics review:** I inspected the current diff and the
exact provider, transport, envelope, and snapshot code. I did not edit
application code or normal tests.

#### Confirmed finding: cancellation timeout is misclassified

**Severity: P2 cancellation/reliability defect.** With a cancellation event,
`SocketRemoteTransport.request()` now correctly supplies
`min(self._timeout, 0.25)` to `socket.create_connection()` and to the connected
socket, so the previous full-timeout connection finding is obsolete. However,
if the event becomes set while connection establishment is in progress and the
250 ms socket timeout expires, Python raises `TimeoutError`; the transport
catches it at `maintenance/remote.py:766-769` and raises `RemoteTransportError`,
rather than the `RemoteExecutionError("cancelled")` used by `_check_cancel()`
and the receive loop. This is a bounded cancellation gap that can surface as a
generic transport failure instead of cancellation. It does not allow stale UI
delivery.

Official socket semantics confirm that `create_connection()` applies the
provided timeout before connecting and may try resolved addresses in turn, and
that socket timeout expiry raises `TimeoutError`:

- https://docs.python.org/3/library/socket.html#socket.create_connection
- https://docs.python.org/3/library/socket.html#socket.socket.settimeout

#### Protocol and typing result

- HMAC binding is correct in the inspected paths: all non-signature envelope
  fields are canonicalized and signed, and verification uses
  `hmac.compare_digest()`, which Python documents as the timing-attack-resistant
  comparison for externally supplied digests:
  https://docs.python.org/3/library/hmac.html#hmac.compare_digest
- The outer response checks bind both target `node_id` and request ID after
  authentication. Dashboard snapshots additionally validate the decoded
  snapshot's node ID, and component summaries validate their signed payload
  node ID. No response-confusion defect was confirmed in this scope.
- `typing.Protocol` and annotations are not runtime enforcement. The explicit
  `isinstance(result, NodeSnapshot)` and codec validation in the worker/provider
  are therefore necessary and present:
  https://docs.python.org/3/library/typing.html#typing.Protocol

#### Compatibility probe result

The earlier post-dispatch `TypeError` concern is not supported by the final
code. `inspect.Signature.bind()` is used only to choose the one-argument legacy
call versus the two-argument call; the actual request invocation is outside
that `try` block at `maintenance/remote.py:1029-1034`. A `TypeError` raised by a
transport after dispatch is not caught and retried. Python documents that
`Signature.bind()` raises `TypeError` for argument/signature mismatch:
https://docs.python.org/3/library/inspect.html#inspect.Signature.bind
**Skeptic verdict:** HMAC comparison, envelope binding, response correlation,
decoded snapshot validation, and the refreshed bounded connect timeout are
supported by repository behavior and official Python semantics. One P2
cancellation-classification gap remains; the grant provisioning, runtime
revocation, and state-lifecycle findings belong to the other opposition
sections and remain unresolved.

## Agent 5 evidence audit

**Audit scope and evidence status.** All four required opposing sections are
present. I re-read this artifact, `AGENTS.md`, the final diff, and the exact
snapshot, component, identity, grant, listener, activation, and transport
paths. The changed-surface suite passes 105 tests. Ruff check, Ruff format
check, and MyPy pass; source-target Pyright passes, while repository Pyright
reports only the two known generated `build/lib` errors. No LR executable or
live two-installation exchange was available.

**Controls confirmed.** Typed `NodeSnapshot` results are runtime-validated,
checked against the source node, and retained on the matching `NodeContext`;
generation and selected-node guards prevent stale delivery. Component
responses bind both the authenticated outer target and the signed payload
`node_id`. Endpoint sync and remote activation now send the local caller ID,
so caller-specific grants are selected correctly. Cancellation is propagated
through activation and requests, and socket connect/read timeouts are bounded
when cancellation is supplied. `_request()` uses signature binding before
dispatch, so operation-level `TypeError` is not retried as a duplicate
request. `_save_cluster_state()` publishes the exact persisted state, and
ordinary node-setting saves preserve target-owned grants. Focused wrong-target,
cancellation, compatibility, and grant-isolation tests support these results.

**Remaining lifecycle findings.** Two-sided grant provisioning is confirmed
missing: `_pair_discovered_node()` creates the caller's grant and secret only
in local `ClusterState`; it performs no reciprocal provisioning exchange or
target-side grant update. A fresh peer therefore cannot authenticate this
caller from pairing alone. This is a fail-closed P1 availability/integration
defect, not an authentication bypass. Runtime revocation is also confirmed
unsafe: `_revoke_trusted_node()` supplies an empty grant set, which the
legacy-preservation fallback restores, and the already-running `RemoteService`
has no grant-removal/reconfiguration path. The revoked caller can therefore
remain authorized until service restart or explicit mutation. The broader
claim that pairing necessarily deletes unrelated grants is not supported;
pairing explicitly carries existing grants forward.

**Verdict.** The snapshot, binding, identity, cancellation, dispatch, and
ordinary grant-publication fixes are supported, but the two confirmed P1
grant-lifecycle defects mean the patch is **not safe to sign off**. Evidence
disposition: `needs more evidence` pending scoped two-sided provisioning and
runtime revocation fixes with persistence, authorization, listener, and fresh
full-validation coverage. This section does not replace the main auditor's
final decision.

## Main auditor rebuttal

The reviewers' node-binding conclusions are supported: dashboard snapshots are
decoded as `NodeSnapshot`, checked against the selected node, retained on the
node context, and only then reduced to the existing dashboard payload. Remote
component responses now carry and verify their target ID. Existing full-suite
and focused tests pass, including 1007 discovered tests.

The reviewers also identified unresolved peer-lifecycle defects outside the
snapshot transport change. Fresh two-sided pairing still has no grant
provisioning exchange, revoke does not reconfigure the live listener, and
grant-preserving state is now published to the live model for ordinary saves.
The remaining two lifecycle findings are fail-closed availability/
authorization issues and mean this is not a complete peer-network
implementation. The transport retry and connect-cancellation findings were
addressed, including cancellation error classification, but no live
two-machine exchange was demonstrated.

## Final patch decision
unsafe

## Remaining risk

The snapshot/component patch is validated, but the full peer-network plan is
not safe to sign off until grant provisioning, runtime revocation, and durable
grant-state ownership are implemented and tested. Remote process/storage
payloads remain separate contracts, and HMAC transport still provides no
confidentiality without TLS.
