# Patch Review: Network Discovery Repair

**Date:** 2026-09-09
**Mode:** Mode A - code-edit validation
**Scope:** Repair the existing Zeroconf discovery path without redesigning node architecture.
**Initial risk:** High, cross-boundary runtime/package/network/UI path.

## Main auditor: initial evidence

The installed command and interpreter are both from the repository virtual
environment. `zeroconf` is installed there and is declared as a normal project
dependency in `pyproject.toml`; this is not currently a packaging omission.

The first broken runtime boundary was between Zeroconf service browsing and
candidate normalization. Direct Zeroconf probing showed that the advertised
service was visible by name, but `get_service_info()` returned no usable record
when `ServiceInfo` contained no concrete addresses. After adding addresses, the
record reached the application listener, where real Zeroconf TXT keys were
`bytes`; `_property_map()` converted them to strings such as `"b'id'"`, so the
stable ID lookup returned no candidate. Both defects prevented normalization.

The bounded fix adds local non-loopback IPv4/IPv6 addresses to the existing
`ServiceInfo`, decodes byte TXT keys using the existing text conversion helper,
and preserves the existing service type, stable-ID self-filter, registry,
coordinator, trust, and UI architecture. Startup status now distinguishes
disabled, running/no peers, backend unavailable, and startup error states.

### Repo-Truth Skeptic Addendum: IPv6 extraction

An independent installed-runtime probe found one confirmed interoperability
defect within the discovery path. With `zeroconf 0.151.3`, a valid IPv6-only
`ServiceInfo` constructed with `addresses=["2001:db8::1"]` reports
`info.addresses == []` while `info.parsed_addresses() == ["2001:db8::1"]`.
The current `_normalize()` path at `network_discovery.py:403` reads only
`info.addresses`, and `_address_texts()` consequently produces
`normalized_addresses=()`. Therefore an IPv6-only peer loses its usable
endpoint even though `_local_service_addresses()` collects IPv6 addresses for
advertisements. This is a **confirmed P2 discovery interoperability bug** for
IPv6-only peers, not a service-type or registry-trust defect. The existing
focused suite passes because its synthetic records provide string addresses;
it does not exercise a real IPv6-only `ServiceInfo`.

**Updated verdict:** no dependency, service-name, lifecycle, registry-trust,
coordinator-delivery, status-routing, or removed-seam defect was found, but the
IPv6-only normalization defect above means the patch is not fully safe as a
cross-platform discovery repair.

## Agent 4 fallback: External-Research Skeptic

**Role and scope:** Independent verification of `python-zeroconf` 0.151.3
semantics for `ServiceInfo` addresses, TXT properties, `ServiceBrowser`
callbacks, service-type naming, and interface behavior. No application code or
tests were changed.

### Official/current semantics

- The installed package is `zeroconf 0.151.3` from
  `/home/btn17/Downloads/exp/.venv/lib/python3.12/site-packages/zeroconf`.
- The official 0.151.3 source defines `ServiceInfo.addresses` as IPv4-only and
  explicitly directs callers to `addresses_by_version()` or `parsed_addresses()`
  for IPv6. Its `properties` property returns `dict[bytes, bytes | None]`, while
  `decoded_properties` returns string keys/values. Evidence: tagged source
  [ServiceInfo 0.151.3](https://raw.githubusercontent.com/python-zeroconf/python-zeroconf/0.151.3/src/zeroconf/_services/info.py),
  `ServiceInfo.addresses`, `addresses_by_version`, `parsed_addresses`,
  `properties`, and `decoded_properties`.
- The official API documents `ServiceBrowser` as firing add, change, and remove
  callbacks. The tagged source dispatches those callbacks with `(zeroconf,
  service_type, name)`, matching `_ZeroconfListener` in this patch, which then
  calls `get_service_info()`. Evidence: [ServiceBrowser 0.151.3 source](https://raw.githubusercontent.com/python-zeroconf/python-zeroconf/0.151.3/src/zeroconf/_services/browser.py)
  and [API reference](https://python-zeroconf.readthedocs.io/en/latest/api.html).
- `ServiceInfo.name` is the complete instance name including type/domain, and
  the installed constructor accepts `SERVICE_TYPE = "_system-analyzer._tcp.local."`
  with a name of `id._system-analyzer._tcp.local.`. A malformed type raises
  `BadTypeInNameException`. The patch's registration and browser type format are
  therefore correct.
- The installed `Zeroconf()` reports `_interfaces == InterfaceChoice.All` but
  `_ip_version == IPVersion.V4Only`; the official constructor documentation
  states that the default remains V4-only for backward compatibility. Concrete
  IPv6 addresses in a `ServiceInfo` do not change that socket/interface choice.

### Focused evidence checks

```text
zeroconf.__version__ = 0.151.3
ServiceInfo(..., addresses=[packed IPv6]).addresses = []
ServiceInfo(..., addresses=[packed IPv6]).addresses_by_version(All) = [packed IPv6]
ServiceInfo(..., addresses=[packed IPv6]).parsed_addresses() = ['2001:db8::1']
implementation _address_texts(info.addresses) = []
Zeroconf()._interfaces = InterfaceChoice.All
Zeroconf()._ip_version = IPVersion.V4Only
ServiceInfo.properties = {b'id': b'peer'}
ServiceInfo.decoded_properties = {'id': 'peer'}
```

The repository test module `python -m unittest tests.test_network_discovery
-v` passed all 25 tests, including byte TXT normalization and the fake
registration path. Those tests do not construct a real `ServiceInfo` with an
IPv6-only address.

### Findings

1. **P1/P2 reliability defect: IPv6-only peers lose all advertised addresses.**
   `network_discovery.py:403` passes `_attr(info, "addresses")` to
   `_address_texts()`. In zeroconf 0.151.3, a valid IPv6-only `ServiceInfo`
   consequently yields an empty tuple even though `parsed_addresses()` contains
   the IPv6 endpoint. This is a directly reproduced contract mismatch and can
   make a discovered IPv6-only peer non-connectable or unusable downstream.
   The exact severity depends on whether the application promises IPv6-only
   discovery; at minimum this is a confirmed P2 interoperability/reliability
   bug, not a documentation concern.

2. **P2 interoperability risk: interface/IP-version selection is implicit and
   inconsistent with the new IPv6 address collection.** `Zeroconf()` is created
   without an explicit `ip_version`, and the installed 0.151.3 default is
   `IPVersion.V4Only`, while `_local_service_addresses()` collects IPv6 and
   strips link-local scope/interface information before passing packed bytes to
   `ServiceInfo(interface_index=None)`. The official source says the interface
   index is what qualifies link-local IPv6 addresses in
   `parsed_scoped_addresses()`. Thus adding IPv6 address bytes does not provide
   a reliable IPv6 mDNS path, especially for link-local-only interfaces. This is
   a confirmed integration risk in the patch, though the local probe cannot
   prove every platform's resulting packet behavior.

### Non-findings and verdict

TXT key/value normalization is correct for the installed API: the patch decodes
both byte keys and byte values, and the runtime probe confirmed the raw
`properties` types. The listener method names, callback argument shape,
`get_service_info()` usage, complete service-instance naming, and add/update/
remove forwarding are also consistent with the official source. The prior
`Zeroconf.addresses` assumption is not present in this patch.

**Verdict: patch not fully semantically safe.** The main IPv6 address extraction
defect is confirmed by installed-runtime evidence and authoritative source. The
interface/IP-version issue is a confirmed cross-boundary risk that should be
resolved or explicitly narrowed before claiming complete IPv6 support. No
zeroconf defect was found in TXT types, browser callbacks, or service-type
formatting.

## Opposing Agent 3 - Architecture/Security Skeptic (fallback)

**Scope reviewed:** `maintenance/components/network_discovery.py`,
`maintenance/nodes.py`, `maintenance/components/coordinator.py`, and the
discovery lifecycle/status paths in `window.py` and
`maintenance/ui/discovery_refresh.py`.

### Evidence

- **Trust boundary:** Discovery candidates remain untrusted and have no
  capabilities. Pairing is the point at which a candidate is promoted, and
  trusted endpoint migration calls authenticated `hello()` before persisting a
  changed endpoint (`window.py:1846-1899`). I found no discovery-to-action or
  discovery-to-authorization bypass. The advertised address and port are not
  independently trusted for remote reads.
- **Self-filtering and stable identity:** `_normalize()` filters only an exact
  TXT `id` equal to the local node ID (`network_discovery.py:379-387`) and the
  registry repeats the local-ID rejection (`nodes.py:544-557`). Peer storage is
  keyed by the TXT stable ID, so multi-homing and hostname changes remain one
  peer. This is sound for well-formed records, but the service-name identity is
  not required to agree with the TXT identity.
- **Confirmed removal identity defect:** A focused injected-backend probe added
  service `alias._system-analyzer._tcp.local.` with TXT ID `peer`, then removed
  the same service. The peer remained: `service-id-mismatch-remove ['peer']`.
  Removal uses `_node_id_for_service(service_name)` (`network_discovery.py:294-299`)
  while additions key `_peers` by `candidate.stable_id` (`:308-338`). A
  malformed or noncanonical service name, and any legitimate name/ID mismatch,
  therefore leaves a stale peer until TTL expiry. This is a **P2 reliability /
  stale-presence issue**, not an authorization bypass.
- **Confirmed lifecycle containment defect:** After adding a peer, calling
  `NetworkDiscovery.stop()`, and then invoking the retained backend listener,
  a focused probe produced `late-event-after-stop 1 1`: the stopped component
  had one peer and emitted one event. `_handle_transport_event()` has no
  inactive guard (`network_discovery.py:291-305`), and the listener closure is
  retained by the backend. `AppCoordinator` protects the UI bridge with an
  identity check (`coordinator.py:677-680`), so this did not reach the window in
  the coordinator path, but the component's documented stop/clear lifecycle
  invariant is violated and direct consumers can observe post-stop data/events.
  This is a **P2 lifecycle/availability issue**, with UI impact limited by the
  coordinator bridge.
- **Malformed-event containment:** A remove callback with a non-string service
  name raised `AttributeError: 'object' object has no attribute 'endswith'`.
  The remove branch calls `_node_id_for_service()` before the exception handler
  can convert malformed input into an ignored advertisement
  (`network_discovery.py:294-300`, `:367-372`). Add/update malformed records
  are largely contained, but malformed remove events can escape the discovery
  callback boundary and depend on the Zeroconf thread's exception handling.
- **Address/interface handling:** Local loopback addresses are excluded before
  registration, IPv4 and IPv6 packed addresses are handled separately, and
  non-loopback VPN interfaces are not excluded. That is reasonable for local
  presence discovery, but IPv6 link-local addresses are advertised without an
  interface/scope identifier (`network_discovery.py:457-464`). No current code
  treats the first discovered address as authorized; when it is used for a
  trusted endpoint, the subsequent HMAC-authenticated hello remains the gate.
- Focused validation: `python -m unittest tests.test_network_discovery
  tests.test_coordinator_discovery tests.test_network_card -v` passed, 61
  tests. The two probes above were standalone read-only probes against the
  current worktree; no app code or tests were edited.

### Verdict

**Conditional pass for the reported Zeroconf repair, with two P2 follow-ups.**
The address injection and byte-TXT decoding repair is narrowly scoped and does
not widen trust or actionable capability. I do not find a confirmed security
boundary bypass, self-filter bypass, or stable-identity authorization flaw.
However, merge confidence should not be treated as clean until stopped
discovery ignores late callbacks, removal is keyed consistently with the
normalized stable identity (or otherwise tracks service-to-peer identity), and
malformed remove events are contained. The current coordinator prevents the
late-callback probe from updating the UI, but that is a secondary guard rather
than a complete component lifecycle guarantee.
