### Opposing Agent 2 - Repo-Truth Skeptic

**Verdict: findings requiring correction (P2 compatibility regressions).**

**Finding 1: closed `handle_analyze()` no longer preserves the early-return
contract for partial `object.__new__` fixtures.**

- Before this patch, `AppWindow.handle_analyze` checked `_is_closing` before
  reading the selected context/provider. The extracted lifecycle still has an
  `_is_closing` guard, but that guard is reached only after
  `window.py:2141-2145` evaluates `self._selected_context()` and then
  `self.analyzer`.
- Reproduction, with the same construction style used by
  `tests/test_window.py:46` and `tests/test_window_nodes.py:94`:
  `w = object.__new__(AppWindow); w._is_closing = True; AppWindow.handle_analyze(w)`
  raises `AttributeError: 'AppWindow' object has no attribute 'analyzer'` at
  `window.py:2144`. The expected closed-state behavior is a no-op.
- This is not a production startup failure when `__init__` has completed, but
  it violates the documented compatibility boundary for partial controller
  fixtures and can affect teardown/late callback paths. The lifecycle owner
  should retain the controller-level closing guard before provider/context
  resolution, or otherwise make that compatibility path safe.

**Finding 2: `_start_discovery()` lost its previous missing-registry no-op.**

- The pre-extraction implementation explicitly read
  `self.__dict__.get("_node_registry")` and returned when absent. The new
  `window.py:1703-1723` adapter constructs `DiscoverySession` using direct
  `self._coordinator` and `self._node_registry` attribute access, while
  `window.py:1734` calls it unconditionally.
- Reproduction: `w = object.__new__(AppWindow); w._is_closing = True;
  AppWindow._start_discovery(w)` raises `AttributeError` for missing
  `_coordinator` (and a fixture with only `_coordinator` then raises for
  missing `_node_registry`). The old method returned before either access when
  the registry was absent.
- This is a compatibility regression for object-created/partially initialized
  windows and makes the new discovery adapter less defensive than the caller
  it replaced. The adapter should preserve the old guarded lookup/no-op seam;
  the full `DiscoverySession` API itself has the correct explicit
  `NodeRegistry`/coordinator dependencies.

### Opposing Agent 4 - External-Research Skeptic

**Verdict: no confirmed finding from external-semantics review.**

**Repository evidence reviewed**

- `maintenance/components/background_orchestration.py:61-71` runs the task in a
  daemon `threading.Thread`; worker hooks only put completion/error/UI items into
  the `Queue` at `:89-112`. `:122-162` drains those items from the poll callback,
  checks `_is_closing()` before application callbacks, and batches rendering.
- `window.py:2121-2128` documents and implements the queue delivery boundary;
  `window.py:3145-3152` marks closing, finalizes lifecycle state, stops workers,
  then destroys the master. This is consistent with the Tk event-loop boundary,
  rather than relying on a worker to mutate widgets.
- `maintenance/ui/window_supports/timer_delivery.py:27-53` uses the identifier
  returned by `master.after`, removes it before invoking the callback, and skips
  delivery while closing. `:55-73` passes only returned identifiers to
  `after_cancel` and removes bookkeeping on cancellation.
- `maintenance/components/dashboard_scan.py:50-68` establishes the generation,
  cancellation event, timeout, and worker start order. `:93-113` makes timeout
  cancellation cooperative and `:115-142` handles completion/grace resolution
  without allowing a timed-out lease to remain indefinitely.
- `maintenance/components/discovery_session.py:114-142` starts the coordinator,
  schedules the reap timer, and stops by cancelling the timer before stopping
  discovery. `maintenance/components/coordinator.py:678-713` captures a
  per-discovery generation and rejects queued events from a stopped/restarted
  lifecycle.
- `maintenance/components/network_discovery.py:172-191` cancels the browser and
  closes Zeroconf during backend stop; `:277-318` clears partial state on failed
  start and makes the component inactive. `:194-209` adapts the documented
  zeroconf service-listener callbacks into the transport seam.

**Official semantics checked**

- Python Tkinter threading model:
  <https://docs.python.org/3/library/tkinter.html#threading-model> says each Tk
  object owns a Tcl interpreter associated with its creating thread, cross-thread
  calls are posted to that interpreter's event queue, and calls can fail if the
  event loop is not processing events. The patch's worker-to-`Queue`-to-Tk-poll
  path avoids direct worker widget calls; no contradiction was found.
- Python `queue.Queue`:
  <https://docs.python.org/3/library/queue.html> specifies a synchronized
  multi-producer/multi-consumer queue with locking semantics. The background and
  discovery bridges use `put` from producer threads and `get_nowait` from the UI
  poll, matching that contract. The queue is unbounded here, so no producer
  blocking/full-queue assumption is being made.
- Tkinter `after`/`after_cancel` and callback handling:
  <https://docs.python.org/3/library/tkinter.html#tkinter.Misc.after> documents
  that `after` schedules a callable and returns an identifier for cancellation;
  `after_cancel` accepts that identifier. Tkinter documents callback failures via
  `report_callback_exception` rather than requiring application callbacks to
  propagate through `after`. The `TimerDelivery` wrapper preserves the returned
  identifier and does not incorrectly treat a callback exception as a queue
  failure. (The Tcl mirror was unavailable from the documentation fetcher; the
  Python reference is the official API used by this code.)
- python-zeroconf API:
  <https://python-zeroconf.readthedocs.io/en/latest/api.html#zeroconf.ServiceBrowser>
  documents `ServiceBrowser` as a threaded browser that fires add/update/remove
  listener callbacks; this supports the need for the callback bridge and UI
  queue. The same official API reference documents
  <https://python-zeroconf.readthedocs.io/en/latest/api.html#zeroconf.Zeroconf.close>
  as shutting down sockets/engine and being safe to call repeatedly, consistent
  with the backend's best-effort stop path.

### Phase 2 - Reproduction and disproof

The following reviewer findings remain confirmed against the current checkout:

   `_node_registry` was absent. This is a concrete missed compatibility seam,

   A current-code probe with `_is_closing = True`, a present registry, and no
   `_coordinator` raises `AttributeError` while constructing
   `DiscoverySession`. The former implementation safely treated a missing
   coordinator as absent after cancelling the optional timer. This is the same
   newly extracted adapter boundary and remains unresolved even though the
   reviewers did not name it separately.
