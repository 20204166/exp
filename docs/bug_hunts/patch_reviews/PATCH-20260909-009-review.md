## Validator Findings

### Opposing Agent 1 - Patch/Reproduction Skeptic

**Validation performed**

- Ran the focused suites covering preferences, cluster persistence, discovery,
  discovery-session/coordinator lifecycle, process safety, thermal geometry,
  Nodes & Connections, window node integration, and packaging: 197 tests passed.
- Reproduced edge cases with small read-only Python probes; no application code,
  normal tests, or probe files were changed.

**Findings**

1. **P1: discovery retains invalid numeric ports.** `NetworkDiscovery._normalize`
   converts the raw value with `int()` but does not enforce `0 <= port <= 65535`
   or reject booleans. The probe produced candidates with ports `-1`, `65536`,
   and `True` (normalized to `1`). The string case is tolerated as `None`, but
   numeric invalid values can reach the candidate/UI/controller and can later be
   used as a connection endpoint. The persisted-record and manual-UI checks do
   reject the tested out-of-range values, so this is specifically a discovery
   boundary gap in the port repair.

2. **P2: stop does not close the NetworkDiscovery event window atomically.** A
   backend whose `stop()` blocks was used. While `stop()` was in progress, a
   transport callback added peer `y` and emitted it; only after backend stop
   returned did `NetworkDiscovery` set `_active = False` and clear the peer map.
   This violates the intended stop/late-event behavior for direct component
   listeners and permits a callback during shutdown. `AppCoordinator` drops its
   bridge before calling component stop, which limits the normal UI impact, but
   the component's own lifecycle contract is still racy. `_active` is also read
   and written outside `_peer_lock` in `start()`/`stop()`.

3. **P2: non-finite thermal thresholds still produce invalid Canvas coordinates.**
   The scale calculation correctly excludes `NaN`/infinite thresholds, but
   `threshold_y()` subsequently calls `y_for()` for them without the same
   finiteness check. Probes returned `warning_y=nan` for `warning_celsius=nan`
   and `warning_y=-inf` for `warning_celsius=inf`. This can pass invalid
   coordinates to `Canvas.create_line`; finite thresholds outside the sample
   range are handled correctly and remain within the plot.

4. **P2: the controller port guard is incomplete for non-integer direct input.**
   `AppWindow._add_manual_host()` checks booleans and numeric bounds but does
   not check `isinstance(port, int)`. A direct call with `port="5000"` reaches
   `0 <= port` and raises `TypeError` instead of rejecting the input at the
   controller boundary. The UI parser emits integers and the persisted-record
   parser rejects non-integers, so the repaired positive path is covered while
   this defensive boundary remains open.

5. **P2: permission merge accepts permissions outside the UI-owned process set.**
   `_set_node_permissions()` preserves unmanaged permissions, which is correct
   for the normal UI callback, but then unions every recognized value from
   `raw_permissions`. A direct callback with `{"cleanup"}` granted `cleanup`
   while leaving the existing read permissions intact. The page only emits the
   three process permission keys, so the normal positive toggle path passed;
   the controller should nevertheless restrict incoming values to that managed
   set before merging.

**Repaired hypotheses that reproduced safely**

- Permission merge preserved unmanaged dashboard/component/storage permissions
  when a process permission was toggled.
- Failed colour persistence restored the prior `rose` colour rather than
  resetting to `None`.
- Invalid UTF-8 in both preferences and cluster stores fell back to defaults
  without escaping startup parsing.
- Manual UI and persisted trusted-node records rejected tested invalid ports,
  including `70000`; valid `0`, `5000`, and `65535` remained representable.
- Thermal scaling included finite warning/critical thresholds; cool samples
  kept both threshold lines inside the plot.
- Process actions rejected changed create times, protected/foreign processes,
  protected executable names, and unreadable identity fields; matching create
  times allowed the intended action. File cleanup code performed the resolved
  path, file-type, and device/inode recheck before Trash movement in inspection.
- The PowerShell installer text places checksum verification before pip install,
  includes `--force-reinstall`, adds `--user` only for non-system installs, and
  retains a base-interpreter fallback when all discovered candidates are venvs.
  `pwsh` is unavailable here, so actual Windows execution semantics remain
  unverified rather than treated as a pass.

**Conclusion**

The repaired hypotheses are not fully reproduced as safe. The numeric discovery
port gap, stop-window race, non-finite threshold rendering, direct controller
type gap, and permission-set widening require follow-up. Process/file identity,
UTF-8 fallback, colour rollback, finite threshold bounds, and installer control
checks survived the available local reproduction.

### Opposing Agent 3 - Architecture/Security Skeptic

**Verdict: unsafe for the force-quit descendant path. One confirmed P1 safety issue; no separate confirmed bypass in discovery, persistence, cleanup, or installer privilege handling.**

**Confirmed finding: recursively discovered child PIDs are not identity-bound.**

- `maintenance/actions.py:84-100` recursively obtains children and admits a child after PID, username, protected-name, and executable checks, but does not capture or validate that child's `create_time()`.
- `maintenance/actions.py:102-114` only compares a target's creation time when `expected_create_times` contains that target PID. The caller normally supplies tokens for the selected process, not for children discovered after the scan, so a descendant target proceeds with no identity token.
- Focused in-memory probe: a parent with matching expected creation time and child PID `4243` with a different/current creation time was passed to `force_quit([4242], {4242: 999.0})`; result was `child_killed=True`, `parent_killed=True`, and `errors=()`. This demonstrates the authorization decision is based on a stale PID relationship rather than the scanned identity of every destructive target.
- Impact: between process discovery and force action, the original child can exit and its PID can be reused by another same-user process. The force action can then kill the replacement process. This is an unintended destructive authorization and availability boundary failure. Severity: **P1** because it affects an explicitly destructive operation and can terminate an unrelated process; it is not P0 because it requires PID reuse/race timing and is constrained to the current user plus the selected parent action.

**Control review and disproven concerns.**

- Discovery serialization is sound in the reviewed path: `NetworkDiscovery` protects mutable peer maps with `RLock`; `AppCoordinator.start_discovery` captures a lifecycle generation and rejects queued events after stop/restart before invoking registry/UI callbacks. No deadlock was reproduced; the reentrant lock is required by `_drop_peer` and `expire_stale` and does not wait on the UI thread while held.
- Discovery is not itself an authorization grant. Pairing starts from explicit user confirmation and persists read-only capabilities/permissions. Trusted endpoint movement is not accepted solely from mDNS metadata: `_sync_trusted_node_endpoint` performs authenticated `hello` before persistence, and identity mismatches are retained as mismatches.
- Direct process permission checks still require both capability and permission in `window.py:2533-2543`, while `RemoteService._solve` independently requires both at `maintenance/remote.py:489-498`. The repair therefore does not create a discovered-node-to-action bypass. The child-token gap remains inside the final local/remote process manager safety boundary after authorization.
- File cleanup re-resolves the target, rejects symlinks, requires a regular file under the resolved Downloads root, and compares device/inode before calling `send2trash` (`maintenance/actions.py:256-291`). There is still an unavoidable narrow TOCTOU window after the final stat, but no confirmed path escape or destructive primitive was found in this patch.
- Persistence uses a same-directory temporary file, flush/fsync, `os.replace`, and best-effort directory fsync (`maintenance/persistence.py:38-83`); malformed/unreadable input falls back without executing data. The serialized local identity is represented by the durable cluster file and no new corruption or authorization bypass was proven. The installer’s `-System` switch explicitly selects a system pip install and does not silently elevate; `--break-system-packages` changes system-environment risk but is user-selected, not an unexpected privilege transition.

**Required repair direction:** capture creation time for each recursively discovered child before admitting it, and require a stable identity check immediately before signaling it. If a child identity cannot be obtained or has changed, skip it and report a protected/changed target. A regression probe should specifically cover child PID reuse; the existing parent-only creation-time test does not cover this case.

## Findings

### P1: Path.stat identity recheck is useful but not a complete identity barrier

`maintenance/actions.py:263-287` resolves and stats the target, stats it
again, compares `st_dev` and `st_ino`, and then calls `send2trash` by path.
That correctly rejects an ordinary replacement occurring between the two
stats, and the use of the resolved path prevents the original symlink name
from changing the path selected for the operation. It does not make the
destructive operation atomic: the pathname can still be replaced after the
second `stat()` and before or during `send2trash`.

This is not merely theoretical on the tested filesystem. The following
read/write-to-a-private-temporary-directory probe created a file, recorded
`st_dev`/`st_ino`, replaced it immediately, and recorded the pair again; the
pair was unchanged (`identity-replacement-detected False`). Therefore a
replacement can pass this particular check when an inode is reused. The
official `pathlib.Path.stat()` documentation says the result is looked up at
each call, but does not provide a handle or reservation for the later
pathname operation. Microsoft documents the stronger Windows comparison as
being made from handle information (`VolumeSerialNumber` and `FileIndex`),
which this path-based implementation does not obtain.

Verdict: the repair is a correct defense-in-depth check and the new test proves
the ordinary changed-identity case, but it should not be described as a full
TOCTOU fix. A remaining destructive-action risk exists unless the final
Trash/move operation is performed through an identity-bound handle or an
equivalent OS-specific safe primitive. This is a residual limitation of the
repair, not evidence that the newly added check is itself wrong.

### P2: port 0 is accepted at connection-record boundaries although it is not
usable as a remote service port

`maintenance/ui/nodes_connections.py:541-549` and
`maintenance/cluster.py:545-551` accept the inclusive range `0..65535`.
That range is valid for some socket APIs: Python's official `socketserver`
example explicitly uses server port `0` to ask the OS to select an arbitrary
unused listening port. It is not a usable fixed destination for this
application's `host`/`port` remote connection metadata. The same Python
socket API probe showed `bind(('127.0.0.1', 0))` assigned an ephemeral port,
while `connect_ex(('127.0.0.1', 0))` returned errno `111` (`ECONNREFUSED`).

The repository model documents `port=None` as the no-transport state
(`maintenance/components/network_discovery.py:60`), and the local discovery
advertisement uses `port=None` (`maintenance/components/discovery_session.py:96-105`).
That makes `0` unnecessary as the sentinel for a discovered/trusted remote
record. The python-zeroconf API describes `ServiceInfo.port` as the service
port, while its `None` default is the absent-port form; it does not establish
that zero is a valid reachable service endpoint.

Verdict: accepting `65535` and rejecting negative/>65535 values is portable
and correct, but accepting `0` at these remote-record/UI boundaries admits an
unusable configuration. If zero is intentionally supported as a bind-only
configuration, that intent is not represented by these client-facing record
types. Prefer `None` for absent and `1..65535` for a configured remote
destination, or document and validate the separate bind-vs-connect contexts.

### RLock and callback reentrancy

The `RLock` in `network_discovery.py:251-253` is semantically appropriate.
`_handle_transport_event` holds it while updating peer maps and `_emit` may
invoke a callback synchronously. The Python threading documentation confirms
that an `RLock` can be acquired recursively by its owning thread and must be
released once per acquisition. This prevents same-thread callback reentry
through `_drop_peer`, `peers()`, or `expire_stale()` from deadlocking.

The lock is not held while `NetworkDiscovery.stop()` calls the backend stop,
which avoids the most obvious shutdown inversion. The callback itself is still
executed while the peer lock is held, so a slow or blocking callback increases
contention; in the production coordinator the callback only posts delivery,
and the focused lifecycle tests pass. I found no external-semantics defect in
the RLock repair.

### Thermal threshold geometry

`maintenance/ui/thermal_graph.py:55-90` includes finite warning and critical
values in the min/max domain, so finite threshold lines are within the plot
bounds even when all samples are cooler than the thresholds. The equality
case also keeps a constant-value series drawable. The focused test exercises
the important cool-sample case. I found no threshold-geometry contradiction.

One residual edge is that non-finite thresholds are filtered out of the scale
but are still passed to `threshold_y()`; if such values can enter a snapshot,
Canvas may receive `NaN`/infinite coordinates. The temperature defaults and
policy path reviewed here use ordinary finite values, so this is not a
confirmed PATCH-009 regression.

### pip force reinstall

`install/install-online.ps1:47` adds `--force-reinstall` to `python -m pip
install`. Current official pip documentation defines this option as
reinstalling packages even when already up to date, which matches the stated
repair. It is correctly passed to the selected interpreter and works with a
local wheel path. The local pip 24.0 help output contains both
`--force-reinstall` and the pre-existing `--break-system-packages` option.

The unconditional `--break-system-packages` remains a compatibility concern
for old pip versions, but it predates this patch and is outside the force
reinstall repair. No PATCH-009-specific pip defect was found.

### Other repairs checked

- The `create_time()` comparison is consistent with psutil's PID-reuse
  defense shape and rejects a changed process identity before action. No
  external-semantics contradiction was found.
- Catching `UnicodeError` around UTF-8 persistence reads is portable Python
  behavior and correctly preserves the documented startup-default fallback.
- Inclusive upper-bound validation rejects values outside the 16-bit TCP/UDP
  port number range and rejects `bool` despite `bool` being an `int` subclass.
  The zero exception is recorded above because this code stores remote
  destination metadata rather than only binding addresses.
