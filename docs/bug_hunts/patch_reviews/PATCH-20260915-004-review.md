# PATCH-20260915-004 — Two-phase pairing protocol review

## Mode

BugGuard Mode A, high risk, full A4. The patch changes a cross-node pairing
protocol and persisted authorization state.

## Scope

Additive `PendingPairing` persistence; TLS-protected pending approval;
transaction-bound `pair_confirm`/`pair_abort`; target-side expiry and atomic
promotion; initiator local-save-before-confirm ordering; rollback and UI
lifecycle coverage. Existing active grants and legacy injected provisioners
remain supported.

### Opposing Agent 1
**Commands and results**

- `python -m unittest tests.test_remote_security tests.test_window_nodes -v`: 124 passed.
- `python -m unittest tests.test_window_nodes.WindowDiscoveryIntegrationTests.test_pairing_success_after_worker_cancellation_is_not_persisted tests.test_window_nodes.WindowDiscoveryIntegrationTests.test_network_confirmation_failure_restores_local_trust_and_aborts -v`: 2 passed. Existing cancellation and normal rollback coverage passes.
- `ruff check .`: passed.
- `ruff format --check .`: passed.
- `pyright`: failed only on the six documented pre-existing errors in `tests/test_window_placement.py`.
- `mypy --ignore-missing-imports`: failed only on the same six pre-existing `tests/test_window_placement.py` errors.
- Inline counter-test against `handle_pairing_confirm`: after a successful promotion removes the pending record, replaying the same still-live `pair_confirm` returns `True` while `peer_grants` remains empty when starting without an active grant. Reproduced.
- Inline rollback counter-test against `pair_discovered_node_async`: first local save succeeded, confirmation returned false, and the rollback save returned false. In-memory state was untrusted, but the simulated persisted state remained trusted. Reproduced.

**Confirmed issues**

1. **P2, stale/unknown confirmation is acknowledged as success.** `maintenance/ui/window_discovery.py:467-470` returns `True` whenever `pending_pairing()` returns `None`, including when the transaction was aborted, pruned, or never existed. This is not distinguishable from the intentional idempotent replay after promotion. A delayed confirm can therefore tell the initiator that the target accepted a pairing even though the target has no corresponding grant. The local flow at `maintenance/ui/window_node_actions.py:726-740` then treats that response as success and retains local trust. The target-side operation should only be idempotently successful when an already-promoted matching active grant is proven; otherwise it must reject the transaction. Existing tests cover a repeat after promotion, but not the absent-pending/no-active-grant case.

2. **P2, rollback can leave durable local trust after persistence failure.** `_restore_pairing(..., persist=True)` at `maintenance/ui/window_node_actions.py:323-327` ignores the boolean result of `_save_cluster_state`. When target confirmation fails after the initiator's local save, the code restores memory but can leave the trusted node in `cluster.json`. The counter-test reproduced `memory trusted: False` and `persisted trusted: True` with the second save returning `False`. On restart the node appears trusted locally although the target rejected or never promoted its grant, producing a durable half-paired state. The rollback path needs an explicit failure outcome/retry or a fail-closed recovery state; silently ignoring the failed write is not sufficient.

**Cancellation and stale-delivery assessment**

The focused cancellation tests passed, and the current generation check plus stale `PairingTransaction` abort scheduling prevented a cancelled worker result from being promoted. I found no additional reproducible cancellation or stale-delivery issue beyond the unknown-confirmation acknowledgement above. The target expiry check correctly rejects an expired pending record while it is still present; the defect is the missing-record branch, not the direct expiry comparison.

**Recommendation**

Do not sign off this patch without addressing both P2 issues and adding counter-tests for (a) confirm after pending removal with no active grant, and (b) failed durable rollback after local-save-before-confirm. Preserve the existing successful replay behavior only with an exact matching active grant, and surface rollback persistence failure as an unresolved pairing/recovery error rather than reporting a clean rollback.

### Opposing Agent 2

**Commands and results**

- `python -m unittest tests.test_remote_security tests.test_window_nodes -v`: **124 passed**.
- `ruff check maintenance/cluster.py maintenance/remote.py maintenance/remote_support/protocol.py maintenance/remote_support/server.py maintenance/ui/window_discovery.py maintenance/ui/window_node_actions.py`: **All checks passed**.
- `ruff format --check maintenance/cluster.py maintenance/remote.py maintenance/remote_support/protocol.py maintenance/remote_support/server.py maintenance/ui/window_discovery.py maintenance/ui/window_node_actions.py`: **6 files already formatted**.
- Read-only mixed-version probe: current `AuthenticatedNodeProvider.request_pairing()` returned `True` for a legacy transport response of `{"approved": true}`; the legacy target-shaped `_handle_pairing_request()` also returned `{"approved": true, "error": null}` for the current request payload. **Reproduced.**

**Confirmed finding**

1. **P1, mixed-version pairing bypasses the two-phase safety boundary.** The design explicitly says the protocol remains additive but that old binaries, which do not send transaction metadata, “will be denied pairing” (`docs/specs/2026-09-15-two-phase-pairing-design.md:54-59,91-96`). That contract is not implemented. The current client accepts a successful response with no transaction at `maintenance/remote.py:594-598`, returning a legacy boolean approval; the async caller then treats that boolean as a completed provision at `maintenance/ui/window_node_actions.py:598-609` and persists local trust through `_finish_pairing()` at `maintenance/ui/window_node_actions.py:429-476`. The request itself contains no transaction marker (`maintenance/remote.py:576-584`), so a pre-patch target sees the same exact request shape and its old handler installs an active grant immediately (`git show HEAD:maintenance/ui/window_discovery.py:378-425`; old target flow persists `peer_grants`).

   This is not harmless compatibility. If a new initiator is cancelled after the old target has approved, or if the initiator's later local save fails, the new client has no `PairingTransaction` and therefore cannot send `pair_abort`; the old target's active grant remains. The target-side two-phase invariant (“no active authorization ... until initiator confirmation,” design `:105`) is consequently false for a mixed-version pair. The existing test `tests/test_remote_security.py:503-531` explicitly supplies `pairing_handler=lambda _request: True` and asserts the legacy boolean path succeeds, so current tests preserve rather than detect this contract violation. The new client’s legacy response fallback is therefore incompatible with the stated rollout/recovery contract and leaves a durable remote authorization after a failed or cancelled local transaction.

**Coordinator and persistence assessment**

- The focused cancellation and stale-delivery tests passed, and the generation checks at `maintenance/ui/window_node_actions.py:593-607` and `:726-743` do prevent a current two-phase transaction result from being treated as a stale local success. That does not cover the legacy boolean branch above because no transaction exists to abort.
- Additive `pending_pairings` load/save behavior and preservation of active grants in old JSON were covered by `tests/test_cluster.py:561-673` and passed. I found no additional persistence or coordinator defect proven independently of the mixed-version issue.

**Recommendation**

Do not sign off the patch with the legacy boolean fallback. Make the new pairing request distinguishable and rejectable by old targets, or perform an explicit capability/version negotiation that fails before any old target-side grant is installed. The initiator must not return success or persist trust without an exact transaction response. Add a mixed-version counter-test that proves an old target rejects the new request and that cancellation/local-save failure cannot leave an active target grant.

### Opposing Agent 3
**Independent scope**

Trust-boundary, authorization, transaction binding, persistence/promotion,
abort/expiry, replay/collision, rollback, and Tk/thread-lifecycle audit. No
application code or tests were edited.

**Commands and results**

- Read the changed protocol and lifecycle paths with `git diff --
  maintenance/cluster.py maintenance/remote.py maintenance/remote_support/protocol.py
  maintenance/remote_support/server.py maintenance/ui/window_discovery.py
  maintenance/ui/window_node_actions.py window.py`, plus the two-phase design
  specification. The target-side `pair_confirm` and `pair_abort` handlers run
  directly in socket handler threads and both call `_save_cluster_state`.
- Ran an inline concurrent confirm/abort counter-test using one live pending
  transaction and a save fake that forces both handlers to build from the same
  snapshot. **Pass:** both handlers returned `True`, both attempted a save, and
  the forced last-write-wins result contained zero pending records and zero
  active grants. This is a successful confirmation response with no resulting
  target authorization.
- Ran an inline cancellation counter-test with an already locally persisted
  trusted record and an in-flight `PairingTransaction`. Calling
  `cancel_pairing` invoked `_restore_pairing` but made zero persistence calls;
  in-memory grants became empty while the simulated durable state retained the
  trusted grant. **Pass:** the durable/memory divergence was reproduced.
- The first version of the cancellation harness failed because its minimal fake
  omitted `_refresh_nodes_page`; after adding that required controller seam,
  the counter-test passed. This harness failure is not application evidence.

**Confirmed findings**

1. **P1, confirm/abort are not transactionally serialized.**
   `maintenance/ui/window_discovery.py:452-508` reads the controller state and
   then saves a derived replacement without a lock, revision check, or atomic
   compare-and-swap. `RemoteSocketServer` dispatches both operations in
   independent threaded handlers (`maintenance/remote_support/server.py:88-143`).
   A concurrent confirm and abort can therefore both validate the same pending
   transaction and return success, while the later state write overwrites the
   earlier promotion. The reproduction ended with the pending record removed,
   no active grant, and `confirm=True`. This violates the design's atomic
   promotion and means the initiator can retain local trust despite the target
   acknowledging confirmation without an authorization grant. A duplicate
   transaction ID does not mitigate this because both requests use the exact
   same binding. Serialize all target-side pending/promote/abort state
   transitions or use an atomic revisioned persistence operation; return
   success only for the state transition that actually won.

2. **P1, user cancellation after local save leaves durable local trust.**
   In the network flow, `_finish_pairing(..., True)` persists local trust before
   `_schedule_pairing_confirm` (`maintenance/ui/window_node_actions.py:595-622`).
   If the user cancels while confirmation is pending,
   `cancel_pairing` schedules `pair_abort` and calls `_restore_pairing` without
   `persist=True` (`:629-647`). `_restore_pairing` consequently changes only
   `controller._cluster_state` in memory (`:323-328`); the persisted
   `cluster.json` still contains the trusted node. The counter-test reproduced
   zero save calls, empty memory, and one durable trusted grant. On restart the
   initiator can appear trusted even though the target aborts/removes the
   pending transaction. Cancellation must durably restore the previous state,
   with an explicit failure/recovery outcome if that rollback save fails, and
   must coordinate with the confirm callback so a late confirmation cannot
   reintroduce the state.

**Thread/Tk assessment**

The request approval correctly schedules the messagebox through `_submit_ui`,
and I found no direct worker-thread widget call in the reviewed pairing path.
However, target control handlers mutate `controller._cluster_state` and invoke
the persistence/listener synchronization path from socket threads while Tk
callbacks can read or replace the same state. The reproduced lost-update race
is the concrete thread-safety failure; state transitions need one serialized
owner or lock with a defined Tk delivery boundary.

**Severity and recommendation**

Both findings are **P1** because they can create a durable local/remote trust
state that contradicts the transaction result and bypass the intended
fail-safe pairing invariant. Do not sign off without regression tests for a
forced concurrent confirm/abort interleaving and cancellation after local save
but before confirm completion, including restart/durable-state assertions.

### Opposing Agent 4

**Scope and evidence**

**Focused commands and results**

- `python -m unittest tests.test_remote_security tests.test_window_nodes -v`: **124 passed**. This covered cancellation forwarding, pinned TLS, control binding/expiry, pending promotion/abort, target save failure, local-save-before-confirm, late worker completion, and shutdown/revoke cancellation paths.
- A read-only timeout probe patched only `window_discovery.threading.Event` and `_window_symbols`: `handle_pairing_request()` returned `{'approved': False}` after `wait(60.0)` with one UI callback still queued; executing that callback afterward produced one successful cluster save containing one `pending_pairings` record. **Reproduced.** This demonstrates that the server-side wait timeout does not cancel the already-posted Tk callback.
- The probe did **not** produce an active grant: the late callback writes `pending_pairings` at `maintenance/ui/window_discovery.py:400-423`, while `peer_grants` are created only by confirm at `:472-491`. The pending record is bounded by `PAIRING_PENDING_TTL_SECONDS = 300.0` at `:375` and load/access pruning in `maintenance/cluster.py:633-658,871-890`.

**Official documentation checks**

- Python `threading.Event.wait(timeout)` documents that a timeout returns `False`; it does not cancel the callback or stop another thread: <https://docs.python.org/3/library/threading.html#threading.Event.wait>.
- Tkinter documents that cross-thread calls are posted to the interpreter event queue and fail if the Tcl event loop is not processing events: <https://docs.python.org/3/library/tkinter.html#threading-model>. The repository correctly routes the approval prompt through `_submit_ui` at `window_discovery.py:429`; the delayed-callback behavior observed above is therefore consistent with Tk’s event-queue model.
- Python socket documentation states that `create_connection(..., timeout=...)` sets the socket timeout before connecting and that timeout failures raise `TimeoutError`: <https://docs.python.org/3/library/socket.html#socket.create_connection>. The repository additionally uses bounded connect/read timeouts in `maintenance/remote_support/transport.py:124-154`; cancellation is cooperative and checked between reads at `:53-64`.
- Python TLS documentation states that `SSLSocket` is a socket-like wrapper and that TLS I/O can have its own framing/behavior: <https://docs.python.org/3/library/ssl.html#ssl.SSLSocket>. The repository uses `SSLContext.wrap_socket()` and DER fingerprint comparison at `transport.py:131-145`; no transport-level evidence contradicted the pinning or framing assumptions in this patch.
- Python concurrency documentation states that running futures cannot be cancelled, and `shutdown(cancel_futures=True)` only cancels work that has not started: <https://docs.python.org/3/library/concurrent.futures.html#concurrent.futures.Future.cancel>. This supports treating `AppCoordinator.cancel()` as cooperative/stale-delivery control, not as proof that an in-flight target request was stopped.

**Findings**

1. **No additional confirmed bug beyond the findings already recorded by Opposing Agents 1-3.** The timeout probe can leave an orphaned pending record after the requester has received denial, but it cannot create an active grant, and the design explicitly says lost responses/crashed initiators leave only an expiring pending record (`design:68`). I therefore classify this as **P2 hardening/recovery opportunity**, not a new sign-off blocker. If the intended contract is that a 60-second target approval timeout must discard the request, add a cancellation/expiry guard checked by the Tk callback and a regression test; otherwise document that timeout is equivalent to a lost response.

2. **Mixed-version behavior remains a confirmed P1 already identified by Opposing Agent 2, not an independent new issue.** `AuthenticatedNodeProvider.request_pairing()` accepts `{"approved": true}` with no `transaction_id` at `maintenance/remote.py:594-598`, and `request_target_grant()` returns that boolean at `window_node_actions.py:677-680`. This conflicts with the design’s explicit “old binaries ... will be denied pairing” contract (`design:54-59,91-96`). The repository test `tests.test_remote_security` also preserves the legacy boolean path. Official Python socket/TLS documentation does not define application-version negotiation or transaction semantics; repository protocol evidence therefore controls the verdict. Recommendation: use an explicit capability/version marker and fail before accepting a legacy approval, as Agent 2 recommends.

**Cancellation, replay, persistence, and transport assessment**

- Cancellation is cooperative, not forceful: transport checks the event between timed `recv()` attempts, while confirm/abort stale delivery is guarded by generations and schedules abort for late transactions. I found no additional reproducible cancellation defect beyond Agent 3’s durable rollback race.
- Replay/unknown confirmation is already a confirmed issue from Agent 1: `handle_pairing_confirm()` returns `True` for a missing pending record at `window_discovery.py:467-470` without proving a matching active grant.
- Persistence is already covered by Agents 1 and 3: rollback ignores `_save_cluster_state()` failure at `window_node_actions.py:323-328`, and target confirm/abort state transitions are unsynchronized across socket handler threads at `window_discovery.py:452-508`.
- TLS/socket framing, timeout bounds, and certificate pin verification showed no separate defect in the reviewed paths. A timeout is not evidence that a transport request was cancelled or that a target-side callback did not later run.

**Recommendation**

Do not sign off until the three existing P1/P2 findings are resolved or explicitly accepted: missing-record confirmation success, durable rollback failure, target confirm/abort lost-update race, and the mixed-version legacy approval bypass. Add a focused timeout-after-UI-queue test and choose/document whether the resulting expiring pending record is intentional. No separate Agent 4 severity escalation is justified from official runtime documentation.

### Phase 1: Evidence reconciliation

- **Missing confirmation:** confirmed. `handle_pairing_confirm()` returns
  `True` at `maintenance/ui/window_discovery.py:467-470` whenever the pending
  record is absent. There is no matching active-grant check. This contradicts
  the design's fail-safe replay/unknown-confirmation rule at
  `docs/specs/2026-09-15-two-phase-pairing-design.md:36-39,68-69`. Agent 1's
  P2 classification is appropriate: it is a stale-acknowledgement/integrity
  defect, but does not itself grant target authorization.
- **Durable rollback failure:** confirmed. Confirmation failure calls
  `_restore_pairing(..., persist=True)`, but that function ignores the boolean
  result of `_save_cluster_state()` at
  `maintenance/ui/window_node_actions.py:323-328`. The in-memory restoration
  can therefore disagree with `cluster.json` after a failed write. Agent 1's
  P2 scope is supported for this narrow failure path; Agent 3's P1 scope is
  also credible for user cancellation after local persistence because
  `cancel_pairing()` restores with the default `persist=False` at
  `:635-646`, leaving durable trust behind.
- **Confirm/abort race:** confirmed and P1. The handlers read shared state,
  construct replacements, and save without a lock/revision/CAS at
  `window_discovery.py:452-508`, while the threaded server dispatches each
  socket request independently at `maintenance/remote_support/server.py:88-143`.
  This violates the design's atomic promotion property at design `:29-34`.
- **Mixed-version fallback:** confirmed and P1 for the stated rollout
  contract. `AuthenticatedNodeProvider.request_pairing()` accepts an approved
  response without `transaction_id` at `maintenance/remote.py:594-598`, and
  the caller can then complete local trust through the legacy boolean path.
  The design explicitly requires old binaries to be denied at design
  `:54-59,91-96`; the request also lacks a marker that an old target can
  reject. This is a protocol safety-boundary regression, not benign additive
  compatibility.
- **Timeout orphan pending record:** the Agent 4 probe is valid but is not a
  new active-grant bug. `Event.wait(60.0)` can time out while the queued Tk
  callback later persists only pending state (`window_discovery.py:428-431,
  :399-424`). It is a P2 recovery/hardening opportunity because TTL bounds the
  record and no active grant is created.

### Phase 5: Conservative recommendation

**Recommendation: no-go for this patch.** The ordinary happy paths and
existing cancellation/revoke regressions pass, but the patch does not yet
establish the advertised two-phase authorization invariant. At minimum, the
missing-record confirmation success, serialized target transition, mixed-
version denial, and durable cancellation/rollback outcome need scoped fixes
and focused regression evidence. The target-side orphan-grant risk also needs
an explicit accepted-risk decision or an authenticated compensating revoke /
transaction mechanism before claiming end-to-end cancellation safety.

**Verified findings and severity:** mixed-version untracked approval P1;
confirm/abort lost-update race P1; cancellation after local save can leave
durable local trust P1; failed durable rollback is P2; absent-pending
confirmation acknowledgement is P2. The P1/P2 labels reflect impact and
scope, not fix complexity.

**Residual validation risk:** full repository type gates remain blocked by
documented unrelated baseline issues, LR/drift gates are unavailable, and no
live two-node/restart/power-loss run was performed. Those gaps do not weaken
the deterministic findings above, but they prevent a stronger release claim.
