**Findings:**

**F1 — "Temperature not supported" is NOT reachable through the real page flow (confirmed by code path).**
The plan's Phase 3 Step 4 claims the fix makes the graph's existing `"Temperature not supported"` copy reachable for a permanently-empty-but-supported card. It does not. `ThermalsPage.render` (`maintenance/ui/thermals_page.py:120-122`) removes any component whose snapshot state fails `_should_show`, and `_should_show` (`thermals_page.py:147`) returns `False` for `state == TemperatureState.UNSUPPORTED` on every non-battery component regardless of card capability. So when the new counter transitions a supported-but-empty card to `UNSUPPORTED`, the card is removed from the page and the graph is never rendered with that snapshot. The user sees the card disappear and, if no graphs remain, the status label `"No supported temperature sensors detected."` (`thermals_page.py:130`) — never `"Temperature not supported"`.
Consequence: the patch's own new test `test_unsupported_state_draws_truthful_placeholder` (`tests/test_telemetry_graph.py`) drives `TelemetryMiniGraph._redraw()` with a hand-built `UNSUPPORTED` snapshot and asserts the `"Temperature not supported"` label — a code path that is unreachable in the actual application flow. The test is a widget characterization, not a description of user-visible behavior, and it will mislead future maintainers into believing the message is shown. The reported bug (permanent waiting) is still resolved — the card reaches a terminal presentation — but the plan's stated intent (truthful unsupported copy) is not what ships; card removal is what ships.

**F2 — Counter semantics are not strictly "consecutive" (confirmed by code path; `record_scan` half corroborated by Opposer 3's executed test).**
- `empty_reads` is incremented only on the no-samples branch of `record_summary` (`temperature.py:226`), but it is NOT reset on the `summary.failed` branch (`temperature.py:223-224`). An interleaved `[empty, failed, empty, failed, ...]` sequence accumulates toward the 20-read limit even though the empty reads are not consecutive, and a failed read (evidence the sensor path is alive but erroring) does not reset the budget. The field name and the plan's "consecutive empty reads" wording overstate the implemented semantics.
- `record_scan` (`temperature.py:287-294`) sets `state = VALID` and `current` when samples arrive but does NOT reset `empty_reads`, unlike `record_summary` (`temperature.py:218`). A caller mixing `record_scan` (valid sample) with a subsequent empty `record_summary` inherits the stale count and can hit `UNSUPPORTED` after a single post-scan gap. `record_scan` is currently called only by tests (`tests/test_temperature_telemetry.py:391-416`), not by app code, so this is a latent inconsistency rather than a live regression — but it violates the recovery contract the patch itself establishes in `record_summary` (valid sample ⇒ budget reset). Opposer 3's executed counter-test `test_record_scan_does_not_reset_empty_reads_counter` reproduces the same behavior.

**F3 — Valid samples are NOT suppressed; recovery and slow-sensor preservation hold (verified).**
- The samples branch sets `telemetry.state = TemperatureState.VALID` unconditionally and resets `empty_reads = 0` (`temperature.py:214-218`), so a valid sample arriving after the `UNSUPPORTED` transition recovers to `VALID` immediately, and the budget restarts from zero.
- Before the limit, `NO_DATA` (the documented waiting state) is preserved: `test_slow_sensor_still_waits_before_confirm_limit` (1 empty read → `NO_DATA`) and `test_empty_supported_reads_reach_unsupported_at_policy_limit` (20 empty reads → `UNSUPPORTED`) both pass, and the boundary is exact (19 → `NO_DATA`, 20 → `UNSUPPORTED`).
- Working Linux sensors never take the no-samples branch, so the patch does not alter behavior for platforms where sensors already work. The core fix therefore does not suppress or drop any valid sample.

**F4 — Test naming contradicts its assertion (test-quality finding).**
`test_permanently_empty_temperature_samples_never_report_unsupported` (`tests/test_thermal_capability_gap.py:38-48`) asserts `assertNotEqual(snapshot.state, TemperatureState.NO_DATA)` after 1000 empty reads — under the patched logic the state IS `UNSUPPORTED` at that point, so the name "never report unsupported" states the opposite of what the test verifies. The name was inherited from the RED proof (`tests/thermal_capability_gap_red.py`), where it was already misleading. Rename to something like `test_permanently_empty_temperature_samples_resolve_out_of_no_data`.

**Verdict:**

The patch **reproduces and fixes the reported state**: the RED proof is green, the full 1370-test suite passes, and a supported-but-permanently-empty card now resolves out of `NO_DATA` to a terminal presentation without suppressing valid samples (F3). It does **not** achieve the plan's stated "Temperature not supported" reachability — the card is removed instead (F1) — and the counter's "consecutive" semantics are loose across failed reads and the `record_scan` path (F2). F1 and F2 are findings to record and reconcile (F2's `record_scan` reset is a one-line consistency fix; F1 is a plan-vs-implementation intent gap that should be resolved by either keeping the card visible with the truthful copy or documenting card removal as the intended terminal UX), not blockers to the core fix. F4 is a rename. Static tools are available via `.venv/bin/` and the changed files are `ruff check`/`pyright`/`mypy` clean; the `ruff format --check` failure on `temperature.py` is pre-existing.

### Opposing Agent 3 - Architecture/Security Skeptic

**Scope of review:** thermal telemetry state machine, local/remote summary ingestion paths (`record_summary` vs `record_scan`), node-context lifecycle, controller-level capability confirmation, and fail-soft/edge-case behavior introduced by the bounded empty-read transition.

**Evidence commands run:**

```bash
python3 -m unittest docs.bug_hunts.poc.BUG-20260912-001.opposer3_patch_security_counter -v
python3 -m unittest tests.test_thermal_capability_gap tests.test_telemetry_graph tests.test_temperature_telemetry -v
```

(Static checks `ruff`, `ruff format --check`, `pyright`, and `mypy --ignore-missing-imports` are unavailable on PATH in this environment; the counter-test is hand-formatted and typed, but remains unverified by the hygiene gate.)

**Focused counter-test artifact:** `docs/bug_hunts/poc/BUG-20260912-001/opposer3_patch_security_counter.py`

**Findings:**

1. **State-integrity regression in `record_scan` (confirmed).**
   The patch resets `empty_reads` to 0 in `record_summary` when samples arrive, but `record_scan` (the alternate public ingestion path) sets state to `VALID` without resetting `empty_reads`.

   Counter-test result:
   ```
   test_record_scan_does_not_reset_empty_reads_counter ... ok
   ```

   Reproduction logic: 19 empty `record_summary` calls leave `empty_reads == 19` and state `NO_DATA`; a `record_scan` with a valid sample sets state to `VALID` but leaves `empty_reads == 19`; the next empty `record_summary` immediately transitions state to `UNSUPPORTED` instead of waiting another 20 reads.

   Impact: any caller that mixes `record_scan` with `record_summary` (or any future production use of `record_scan`) will see a flickering sensor incorrectly classified as unsupported after a single post-scan gap. This is a regression in the telemetry object's internal consistency.

2. **Controller/telemetry confirmation-threshold mismatch (confirmed).**
   The window controller confirms card-level unsupported capability after `UNSUPPORTED_CONFIRM_LIMIT == 2` reads (`window.py:154`), while `TemperaturePolicy.unsupported_confirm_samples` defaults to 20. The two counters observe different signals:
   - `observe_capability` looks at `ResourceSummary.capability`. If the card keeps reporting `SUPPORTED`, the controller never pauses polling or hides the dashboard card.
   - `TemperatureTelemetry` counts empty temperature samples. After 20 empty reads it transitions to `UNSUPPORTED` regardless of `ResourceSummary.capability`.

   Counter-test result:
   ```
   test_telemetry_unsupported_hides_graph_while_card_capability_stays_supported ... ok
   ```

   Impact: a supported card that returns empty temperatures for 20 polls will have a visible dashboard card but a hidden CPU graph on the Thermals page. The UI presents contradictory capability decisions because the two state machines are not synchronized.

3. **Per-node isolation holds (verified).**
   Each `NodeContext` owns a fresh `TemperatureTelemetry` instance; switching nodes swaps the context and its telemetry. The `empty_reads` counter does not leak across nodes.

   Counter-test result:
   ```
   test_lifecycle_context_switch_preserves_empty_reads_per_node ... ok
   ```

4. **Fail-soft boundary cases.**
   - A policy with `unsupported_confirm_samples == 0` transitions to `UNSUPPORTED` on the first empty read. The dataclass accepts this without validation.
   - `record_summary` with samples correctly resets `empty_reads` to 0.
   - An empty `TemperatureScan` never increments `empty_reads`, so it cannot contribute to the unsupported transition. This is consistent with the method's sample-only semantics but means `record_scan` and `record_summary` have asymmetric failure modes.

**Security/cross-node assessment:**

- **No privilege escalation or data exfiltration** is introduced. The change is local to in-memory telemetry state and does not touch the wire format, authentication, or persistence.
- **Cross-node consistency:** remote summaries decode through `resource_summary_from_dict` and then call `record_summary`, so the same 20-empty-read rule applies to remote nodes. A malicious remote node cannot force an immediate unsupported classification without sending 20 empty summaries, and it cannot influence another node's telemetry because state is per-`NodeContext`.
- **State-confusion risk:** the dual confirmation systems (controller capability map at 2 reads vs telemetry at 20 reads) create a trust-boundary inconsistency. An attacker who can influence scan scheduling or capability reporting could exploit the mismatch to keep a dashboard card polling while hiding its detail graph, degrading usability but not confidentiality/integrity.

**Verdict:**

The patch fixes the original stuck-`NO_DATA` defect, but it introduces a **state-integrity regression in `record_scan`** and an **architectural mismatch between controller-level and telemetry-level unsupported confirmation**. The `record_scan` bug is the higher-risk issue because it violates the recovery contract that valid samples reset the empty-read budget. The controller/telemetry threshold mismatch is a UX/architecture inconsistency that should be reconciled or documented.

**Recommended before approval:**

1. Reset `empty_reads` to 0 in `record_scan` when samples are recorded, matching `record_summary`.
2. Either align `unsupported_confirm_samples` with `UNSUPPORTED_CONFIRM_LIMIT` or explicitly document why thermal capability needs a separate, slower confirmation policy.
3. Add a regression test for `record_scan` resetting `empty_reads` to the repo test suite.

**Severity of findings:** P2 state-integrity regression / architecture inconsistency. Not a security vulnerability.

### Opposing Agent 4 - External-Research Skeptic

**Review Status:** Complete with reservations

**Scope of Review:**
- Python dataclass mutation semantics (frozen vs. non-frozen)
- Enum comparison and identity semantics (official Python documentation)
- unittest assertion semantics (assertNotEqual behavior)
- State machine design patterns for terminal vs. persistent states
- Threshold justification and external evidence
- Platform-specific behavior claims (Windows/macOS)

**Findings:**

**1. Python Semantics Verification (CONFIRMED CORRECT)**

Verified against Python 3.12 official documentation and runtime behavior:

- **Dataclass mutation:** `_ComponentTelemetry` is correctly declared as `@dataclass(slots=True)` (non-frozen), allowing mutation of `empty_reads` field. `TemperaturePolicy` is correctly `@dataclass(frozen=True, slots=True)`, preventing mutation of `unsupported_confirm_samples`. Runtime test confirmed: non-frozen dataclass allows `obj.counter += 1`, frozen dataclass raises `FrozenInstanceError` on assignment attempt.

- **Enum comparison:** `TemperatureState` inherits from `(str, Enum)`. Python documentation states "Enumeration members are compared by identity" and equality is defined. Runtime verification confirmed: `State.A is State.A` returns `True`, `State.A == State.A` returns `True`, `State.A == State.B` returns `False`. The `str` mixin allows `State.NO_DATA == "no_data"` to return `True`, but identity comparison `State.NO_DATA is "no_data"` returns `False` (with SyntaxWarning). All test assertions using `assertEqual`/`assertNotEqual` with enum members are semantically valid.

- **unittest assertions:** `assertNotEqual(first, second)` uses the `!=` operator and raises `AssertionError` if values compare equal. Runtime verification confirmed correct behavior for both equal and unequal enum values.

**2. Threshold Semantics Challenge (RESERVATION)**

The patch introduces `unsupported_confirm_samples: int = 20` as the transition threshold from `NO_DATA` to `UNSUPPORTED` after consecutive empty reads.

**External evidence search:** No external documentation, industry standard, or empirical study was found justifying the specific value of 20. The cross-platform audit execution design (`docs/specs/2026-09-12-cross-platform-compat-audit-execution-design.md`) specifies "default `unsupported_confirm_samples` limit of 20" but provides no rationale for why 20 rather than 10, 30, or 100.

**Semantic analysis:** The `CapabilityState` docstring defines:
- `NO_DATA`: "no sample exists **yet**" — implies a waiting state, not terminal
- `UNSUPPORTED`: "an authoritative probe proved the capability is absent" — terminal state

The patch transitions from `NO_DATA` to `UNSUPPORTED` after 20 empty reads. This is a **policy decision** (timeout heuristic), not a semantic violation. The state machine correctly implements:
- `VALID` when samples exist
- `UNSUPPORTED` when capability is explicitly `UNSUPPORTED`
- `ERROR` when `summary.failed`
- `NO_DATA` otherwise (no samples, capability is `SUPPORTED`)

**However**, the transition conflates two orthogonal concerns:
1. **Card-level capability** (`CapabilityState.SUPPORTED`): CPU exists and can report non-thermal metrics
2. **Thermal series capability** (`TemperatureState`): thermal samples exist or not

After 20 empty reads, the patch declares `TemperatureState.UNSUPPORTED`, but the card-level `CapabilityState` remains `SUPPORTED`. This is semantically defensible (thermal series is unsupported even though the card is supported), but the threshold of 20 is arbitrary without external justification.

**Boundary verification:** Runtime test confirmed exact boundary behavior:
- After 19 empty reads: `TemperatureState.NO_DATA`
- After 20 empty reads: `TemperatureState.UNSUPPORTED`
- After valid sample: counter resets to 0, state becomes `VALID`
- After 5 more empty reads: counter increments from 0, state remains `NO_DATA`

**3. Platform Claims Challenge (UNVERIFIED)**

The patch documentation and root-cause analysis reference Windows and macOS (Apple SMC) thermal acquisition:

**From `docs/platform_audit/THERMAL-ROOT-CAUSE.md`:**
> "Windows and SMC providers fail soft to empty scans."
> "Windows and Apple SMC acquisition can repeatedly return no samples while leaving that card capability supported."

**Verification status:** The current test environment is Linux (`platform.system() == "Linux"`). No Windows or macOS runtime verification was performed. The patch review states: "Native Windows/macOS behavior remains unverified."

**Challenge:** The threshold of 20 empty reads assumes a specific scan frequency. If scans occur every 5 seconds, 20 reads = 100 seconds. If scans occur every 30 seconds, 20 reads = 600 seconds. Without platform-specific scan frequency data, the threshold may be too aggressive (false positive on slow-starting sensors) or too conservative (delayed terminal state on genuinely unsupported hardware).

**External research gap:** No external evidence was found for:
- Typical thermal sensor warm-up times on Windows (WMI, CIM, vendor drivers)
- Typical thermal sensor warm-up times on macOS (SMC polling intervals)
- Industry-standard timeout heuristics for hardware capability detection

**4. State Machine Design Pattern Analysis (ACCEPTABLE)**

The patch implements a **bounded consecutive-failure counter** pattern, which is a recognized state machine design for distinguishing transient failures from permanent absence. This pattern is used in:
- Network connectivity detection (e.g., NetworkManager's connectivity check)
- Hardware presence detection (e.g., USB device enumeration retries)
- Sensor validation (e.g., IoT sensor health monitoring)

**However**, the pattern requires:
1. **Reset on success:** Confirmed — `empty_reads = 0` on valid sample
2. **Monotonic increment:** Confirmed — `empty_reads += 1` on each empty read
3. **Threshold comparison:** Confirmed — `empty_reads >= policy.unsupported_confirm_samples`
4. **Idempotent terminal state:** Confirmed — once `UNSUPPORTED`, remains `UNSUPPORTED` until valid sample

The implementation is correct, but the threshold value lacks external justification.

**5. Test Coverage Verification (ADEQUATE)**

The patch includes three regression tests in `tests/test_thermal_capability_gap.py`:
1. `test_slow_sensor_still_waits_before_confirm_limit`: Verifies state remains `NO_DATA` after 1 empty read
2. `test_empty_supported_reads_reach_unsupported_at_policy_limit`: Verifies state becomes `UNSUPPORTED` after 20 empty reads
3. `test_permanently_empty_temperature_samples_never_report_unsupported`: Verifies state is not `NO_DATA` after 1000 empty reads (original RED test)

All tests pass. The test coverage is adequate for the implemented behavior, but does not cover:

**6. Semantic Correctness of Original Bug Claim (PARTIALLY VALID)**

The original bug claim: "supported cards with permanently empty temperatures remain in `NO_DATA` and render a permanent waiting message."

**Semantic analysis:** The claim is **partially valid**:
- **Valid:** After 1000 empty reads, remaining in `NO_DATA` with "Waiting for the first sample" message is misleading to users. The state should eventually transition to a terminal state.

The patch resolves the UX issue by introducing a timeout heuristic, but the threshold of 20 is arbitrary.
