## Validator findings

### Opposing Agent 1 - Patch/Reproduction Skeptic
Independent review of the current worktree, the Phase 15 plan, and the
implementation callers/callees found the following reproducible blockers:

1. **P1: security/protocol failures are still retryable through the production
   callback.** `PeerConnectionManager._start()` now calls
   `classify_peer_failure(error)`, but classification is based on substrings in
   `str(error)` rather than the exception type or an explicit failure mapping
   (`maintenance/components/peer_connection.py:93-98`,
   `maintenance/nodes.py:86-108`). A focused counter-check produced:
   `RemoteAuthError("request has been replayed") -> DISAPPEARED`,
   `RemoteProtocolError("unsupported remote protocol version") -> DISAPPEARED`,
   and `RemoteAuthError("bad credentials") -> DISAPPEARED`. The reconnect policy
   therefore schedules automatic retries for replay/auth/protocol failures,
   while only messages containing the selected markers reach the no-retry
   branch. The added happy-path test uses `RuntimeError("remote authentication
   failed")` and does not disprove these reachable paths. This conflicts with
   the plan's identity/authentication rejection and malformed-peer gates.

2. **P1: stale activation protection is not intrinsic to revoke/re-register.**
   `window._revoke_trusted_node()` increments the activation generation before
   delegating to `revoke_trusted_node()`, and the activation callback checks the
   captured record and registry context (`window.py:716-723`,
   `maintenance/ui/window_node_actions.py:560-647`). However, the registry
   mutation API itself does not invalidate an activation generation, and the
   callback's validity is controller-dictionary state rather than a generation
   owned by the node context. A caller that invokes `NodeRegistry.revoke_trusted`
   directly, or a revoke/re-register cycle that restores the same record/context,
   can leave the old queued callback current and attach its old provider,
   backend, and scheduler. The existing test only replaces the persisted record
   and therefore exercises the unequal-record branch; it does not prove the
   revoke/re-register lifecycle required by the plan.

3. **P1: destructive action leases are keyed by exact request contents, not by
   node.** `ProcessDialog._process_action_key()` includes the action and sorted
   `(pid, create_time)` tuple (`maintenance/dialogs.py:1114-1122`). Two dialogs
   requesting the same refs coalesce, as the new test confirms, but two
   concurrent requests for different refs on the same target produce distinct
   `node:<id>:process_action:...` keys and both enter `AppCoordinator`.
   An isolated counter-check started both keys and observed both `in_flight`.
   Thus the claimed shared per-node action lease does not prevent concurrent
   target-side mutations, and UI-local `_action_in_flight` flags cannot enforce
   that invariant across dialogs.

4. **P2: malformed process input is accepted by the typed read codec.**
   `process_candidate_from_dict()` checks numeric types but not finiteness or
   ranges (`maintenance/cluster.py:336-379`). A focused counter-check accepted
   `pid=-1`, `memory_percent=NaN`, `cpu_percent=Infinity`, and
   `create_time=NaN` into a `ProcessCandidate`. This can reach sorting/rendering
   and can be used to create misleading action rows; later action validation is
   not a substitute for rejecting malformed typed snapshots at the decode
   boundary. The process-action result decoder is stricter, but its passing
   tests do not cover process-candidate or nested resource numeric fields.

The targeted repository validation passed: `python -m unittest
tests.test_peer_connection tests.test_remote_contract tests.test_process_table
tests.test_window_nodes tests.test_remote_compatibility -v` ran 140 tests with
0 failures. The counter-checks above intentionally failed their safety
assertions after printing the unsafe classifications/values, which is the
reproduction evidence rather than a validation pass. No production code,
normal tests, plan content, or other review sections were edited.

### Opposing Agent 2 - Repo-Truth Skeptic
Findings:

- **P1, later-phase lifecycle is not wired in production.** `window.AppWindow._peer_connections()` constructs `PeerConnectionManager` with `connect=lambda ...: None` and `can_connect=lambda ...: False` (`window.py:1074-1092`). Therefore discovery/presence can schedule reconciliation, but no authenticated hello, provider attachment, endpoint validation, retry outcome, or remote snapshot activation can occur from the normal application. `PeerConnectionManager` itself is exercised directly by `tests/test_peer_connection.py` and `tests/test_multi_node_concurrency.py`; those tests do not prove the `AppWindow` composition path. This matches the validation report's blocked 15.6/15.7 status and is a real wiring gap, not a test failure.

- **P1, two-sided pairing is only an injected test/application seam, not an implemented flow.** `pair_discovered_node()` refuses normal pairing when no `provision_target_grant` callback is supplied (`maintenance/ui/window_node_actions.py:101-113`). `main.py` only constructs `AppWindow`, and supplies no callback; there is no target-side approval UI/service or code path that durably writes the target's `peer_grants`. The callback receives a `PeerGrantRecord` and returns `bool` (`window.py:166-183`, `maintenance/ui/window_node_actions.py:142-161`), so `True` is not repo-verifiable evidence of target persistence. The passing tests inject `Mock(return_value=True)` and explicitly leave initiator `peer_grants` empty (`tests/test_window_nodes.py:857-895`). Consequently a clean two-installation pairing cannot be completed by the shipped application, and any claimed later remote activation depends on behavior outside this patch.

- **P2, the listener's target ownership is not invariant under node selection.** `_start_peer_listener()` builds the target `RemoteService` from `self._node_registry.selected_context()` and the selected-node mirrors (`window.py:1017-1027`), rather than resolving the local context explicitly. `_sync_peer_listener_grants()` can start or update that listener after cluster-state changes (`window.py:655-683`). If a grant update occurs while a remote context is selected, the local process can expose the selected remote descriptor/provider/process manager as its service identity and action target. The existing tests cover startup with the local context and do not exercise grant/listener synchronization after selection changes; this is a controller ownership issue, not a UI presentation detail.

Compatibility and seams checked:

- Existing local `ProcessManager.request_quit/force_quit` signatures remain compatible with `ProcessActionBackend`, and the remote codec rejects missing create times, unknown operations, and malformed action results in the targeted tests.
- `maintenance.components.__init__` re-exports `PeerConnectionManager`, while the new module has no worker/timer ownership; package structure and monkeypatch seams exercised by the targeted tests remain intact.
- `ClusterStore` preserves legacy records with absent permissions/capabilities and defaults permissions to deny. This is migration evidence only; it does not provision target grants or make old records operational.

Validation run: `python -m unittest tests.test_remote_contract tests.test_remote_compatibility tests.test_cluster tests.test_peer_connection tests.test_multi_node_concurrency tests.test_window_nodes -v` passed (142 tests); `ruff check .`, `ruff format --check .`, and `pyright` passed. These checks do not disprove the production-wiring findings above.

### Opposing Agent 3 - Architecture/Security Skeptic
- **P1 - Normal pairing cannot provision the target-owned grant.** `Window.__init__`
  stores `provision_target_grant` as an optional callback
  (`window.py:166-183`), but no production implementation is installed. The
  pairing path therefore reaches `pair_discovered_node`, rejects the operation
  when that callback is absent (`maintenance/ui/window_node_actions.py:102-113`),
  and never records a trusted node. This is fail-closed, so it is not an
  authorization bypass, but it means the shipped two-installation flow cannot
  complete the security-required target-side grant provisioning. The focused
  pairing test passes because it injects a test callback, which does not prove
  the application wiring exists. The target-owned grant invariant is therefore
  not operational in the real composition root.

- **P1 - The target listener can authenticate as the selected remote node while
  executing local actions.** `_start_peer_listener` obtains `descriptor` from
  `self._node_registry.selected_context()` (`window.py:1005-1029`) but passes
  `self.analyzer` and `self.process_manager`, which are the local machine's
  resources, into `RemoteService`. After pairing, the selected node is the
  promoted peer; when `_sync_peer_listener_grants` starts the listener, the
  service can consequently advertise/sign as that peer while serving local
  dashboard/process data. This violates the target identity/resource binding
  below the UI and can make an authenticated caller believe destructive actions
  are scoped to one node while they are dispatched to another. The listener
  should be bound to the immutable local context, independent of selection.

- **Security controls checked, no additional confirmed bypass:** HMAC fields,
  caller-bound grants, target/request correlation, signed denials, replay and
  destructive request-ID checks, bounded socket frames/handler admission,
  cancellation generations, and local process PID/create-time/user/protection
  checks all passed the focused adversarial suite. The socket implementation is
  loopback by default and does not provide TLS; that is a deployment/hardening
  concern if the host bind is exposed beyond loopback, but the current code did
  not provide enough evidence to classify it as a separate exploitable bug.

**Focused evidence:** `python -m unittest tests.test_remote_contract
tests.test_window_nodes tests.test_process_protection tests.test_lifecycle_stress
tests.test_peer_connection -v` (126 passed). Existing tests cover injected grant
provisioning and loopback behavior, but do not cover production composition with
a selected remote node or an actual target-side provisioner.

### Opposing Agent 4 - External-Research Skeptic
**Verdict: findings remain; several stronger claims are not supported by the cited APIs.**

- **P1, confirmed boundedness gap in destructive replay bookkeeping.** `ReplayCache._seen` is capped, but `_request_ids` is not: `check_and_record_request_id()` adds one entry per destructive `(node_id, request_id)` and `_prune()` only removes entries older than the TTL (`maintenance/remote.py:311-338`). A caller that can authenticate can therefore create an unbounded number of distinct destructive request IDs during one replay-TTL window, even though the class/docstring presents the replay cache as bounded. The max-entry refusal on `_seen` also does not bound this second map. This is a memory-exhaustion/reliability issue, not an authorization bypass. The Python docs describe `socketserver.request_queue_size` as a separate pending connection queue, so neither that queue nor `max_active_handlers` supplies a bound for this in-memory map: <https://docs.python.org/3/library/socketserver.html#socketserver.BaseServer.request_queue_size>.

- **P2, bounded socket admission is narrower than the apparent claim.** The semaphore bounds handlers that reach `process_request()` (`maintenance/remote.py:983-995`), and the test proves the provider has at most two active calls. It does not bound TCP accept/backlog occupancy: `ThreadingTCPServer` still has `request_queue_size = 16`, plus the platform listen backlog, before the non-blocking semaphore rejection runs. Python documents these as queued requests, not active handler permits: <https://docs.python.org/3/library/socketserver.html#socketserver.BaseServer.request_queue_size>. This is acceptable if the contract is explicitly “bounded service handlers”; it is not proof of a globally bounded socket admission surface or protection against many idle queued connections.

- **P1, executor cancellation is cooperative and shutdown is not bounded by this code.** `AppCoordinator.cancel()` sets an event but does not retain or cancel a `Future`; `shutdown(cancel_futures=True, wait=False)` only cancels pending futures. Python explicitly says running futures are not cancelled and that the interpreter waits for pending/running `ThreadPoolExecutor` work before exit: <https://docs.python.org/3/library/concurrent.futures.html#concurrent.futures.Executor.shutdown>. A task/provider that ignores `cancel_event` can therefore continue after UI shutdown and keep process resources alive. The generation checks prevent stale delivery, but they do not stop the work. Any claim of executor cancellation or bounded application teardown needs to be narrowed to “cooperative cancellation plus stale-result suppression.”

- **P2, psutil safety is good but not an atomic termination guarantee.** The process path rechecks ownership, protected status, and `create_time` immediately before `terminate()`/`kill()` (`maintenance/actions.py:132-147`), which is the correct defensive shape. psutil’s process API is still PID-based and documents process disappearance/reuse races and `NoSuchProcess`/`AccessDenied` behavior; its `Process` reference cannot make the check-and-signal operation atomic: <https://psutil.readthedocs.io/en/stable/#processes>. The patch should not claim that create-time matching eliminates all TOCTOU risk. I found no new bypass of the existing same-user/protected-process checks.

- **No external-research contradiction found for the main authz path.** `RemoteService.handle()` selects the target-owned grant before verification, verifies the HMAC/freshness/replay envelope, then checks target identity, capability, and per-operation permission (`maintenance/remote.py:600-720`). The client also rejects mismatched response/request identities. This is consistent with OWASP’s requirements to deny by default and validate permissions on every request: <https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#deny-by-default> and <https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request>. It does not establish transport confidentiality, but the server is currently loopback-bound by `window.py`; exposing it on a LAN would require a separate confidentiality/deployment review.

- **No codec or wheel defect established from the requested documentation.** The explicit schema/version checks and strict process-action result checks are compatible with a deliberately versioned JSON contract. The declared `[project.scripts]` targets match PyPA’s console-script object-reference model, and the explicitly listed setuptools packages/top-level modules are consistent with the wheel verification evidence: <https://packaging.python.org/en/latest/guides/writing-pyproject-toml/#creating-executable-scripts> and <https://packaging.python.org/en/latest/specifications/entry-points/#use-for-scripts>. This review did not find a serialization compatibility or installed-entry-point failure in the current diff.

### Phase 1: Verify reviewer claims

1. **Peer failure classification: confirmed.** `PeerConnectionManager._start`
   sends every coordinator error through `classify_peer_failure(error)`.
   `classify_peer_failure` uses message substrings and returns
   `DISAPPEARED` for `RemoteAuthError("request has been replayed")`,
   `RemoteProtocolError("unsupported remote protocol version")`, and
   `RemoteAuthError("bad credentials")`. A runtime error containing
   "authentication" is classified as authentication failure, but the typed
   auth/protocol exceptions do not carry matching message markers. The
   resulting retry policy therefore schedules retries for trust/protocol
   failures. The direct callback test covers only a matching string and does
   not disprove these cases. Impact is narrowed: the shipped AppWindow
   composition currently sets `can_connect=False`, so this is a defect in the
   reusable manager and any future enabled composition, not an active default
   connection attempt.

2. **Cross-dialog action lease: not confirmed as stated; current code closes
   the original gap for identical requests.** `ProcessDialog` now computes a
   node-qualified key, subscribes through the shared coordinator, and checks
   `in_flight` before starting the action. The fresh tests
   `test_two_dialogs_share_one_process_action_lease`,
   `test_response_loss_is_unknown_in_both_dialogs`, and the normal-to-force
   transition test pass. The narrower sibling risk remains: the key includes
   action and exact selected `(pid, create_time)` contents, so different
   process sets or a normal and force request use different leases on the same
   node. That is a real residual target-wide mutation coordination gap, but the
   reviewers' broad claim that identical cross-dialog requests bypass the
   shared lease is disproven by the current implementation.

3. **Malformed action-result coercion: disproven for the cited cases.** The
   current `process_action_result_from_dict` explicitly rejects booleans,
   negative counts/PIDs, non-string errors, duplicate PID lists, overlapping
   stopped/force lists, and result counts exceeding `requested`. The focused
   codec test passes, and independent probes rejected `requested=True`, a
   stopped PID with `requested=0`, and a non-string error. This reviewer claim
   appears to describe the prior PATCH-001 state, not PATCH-002. It must not
   be carried into the current decision as an unresolved defect. Numeric
   finiteness/range validation of nested resource/process snapshot fields is a
   separate concern below.

4. **Pairing and target-owned provisioning: confirmed, with fail-closed
   impact.** The production composition supplies no target-side provisioner.
   `pair_discovered_node` refuses pairing when the callback is absent, while
   the injected tests provide a mock callback. The target `RemoteService`
   authenticates grant-mode requests from its own grant map; no shipped
   target-side approval/RPC/store commit completes the two-installation
   ceremony. This prevents the normal flow from becoming operational rather
   than creating an authorization bypass. The application should remain
   blocked from exposing remote operations until this ceremony exists.

5. **Stale activation: substantially confirmed.** `activate_remote_node`
   does have an activation generation and checks closing state, current record,
   registry membership, trust, identity mismatch, and fingerprint before
   mutation. That is stronger than PATCH-001. However, revocation/re-register
   and other registry mutations do not intrinsically advance this generation;
   direct registry callers can leave an old generation valid, and the
   generation is controller-owned rather than part of the node-context
   lifecycle. The callback can still attach an old provider/backend/scheduler
   when the controller's activation generation and persisted record remain
   unchanged while registry trust/context is cycled. The risk is therefore a
   remaining lifecycle contract gap, not the older unconditional-callback
   claim.

6. **Optional process create-time: disproven for the current remote wire
   validator, but malformed local snapshot identity remains.**
   `validate_operation_params` now requires a finite, non-negative
   `create_time` for every process action reference, and the targeted test
   `test_process_action_requires_create_time` passes. An independent probe of
   a request without `create_time` is rejected. This PATCH-001 finding is not
   current. Conversely, `process_candidate_from_dict` still accepts `pid=-1`,
   `memory_percent=NaN`, `cpu_percent=Infinity`, and `create_time=NaN`; these
   values are accepted into typed snapshots and can reach presentation. That
   is a P2 protocol/data-integrity risk distinct from target action safety.

7. **Plaintext transport and active-handler claims: confirmed but
   conditional.** The socket transport is length-prefixed JSON over TCP with
   no confidentiality. HMAC authenticates/integrity-protects content but does
   not encrypt it. The current AppWindow binds only to `127.0.0.1` and does
   not advertise an endpoint, so LAN confidentiality is not an active default
   exposure; it remains a release blocker for any future reachable binding
   unless policy explicitly accepts HMAC-only transport or TLS is added.
   `RemoteSocketServer` does correctly use a non-blocking semaphore for active
   handler admission, and the tests demonstrate the configured active limit.
   Official `socketserver` documentation confirms that `request_queue_size`
   bounds waiting connections, while `ThreadingMixIn` creates a handler per
   accepted request. Thus the semaphore does not globally bound the kernel
   accept backlog or all pre-admission connection occupancy. The claim is
   valid only against a broader “all socket admission” interpretation.

8. **Fresh-nonce destructive request-ID replay: confirmed.**
   `ReplayCache.check_and_record` keys the replay map by
   `(node_id, request_id, nonce)`, while destructive ID tracking rejects a
   `(node_id, request_id)` only during the TTL. A fresh nonce with the same
   request ID therefore reaches the service's action path only if the ID map
   rejects it; the current code does reject that reuse and the focused test
   passes. The remaining defect is boundedness: `_request_ids` is not limited
   by `max_entries`, despite the class's bounded-cache contract. An independent
   probe with `max_entries=2` recorded three request IDs while `_seen` had zero
   entries. This is a P2 reliability/memory-bound issue, not a replay bypass.

9. **Executor shutdown limitation: confirmed as residual semantics, not a
   new patch defect.** `AppCoordinator.cancel` is cooperative and does not
   forcibly terminate a running provider. Official `Executor.shutdown`
   documentation confirms `cancel_futures=True` affects pending work only and
   running tasks can keep the interpreter alive. Generation checks suppress
   stale delivery, but they do not stop a provider that ignores its event.
   Claims should be worded as cooperative cancellation plus stale-result
   suppression, not bounded forced cancellation.

### Phase 3: Sibling-risk search in changed surfaces

- The production `_peer_connections` seam deliberately installs a no-op
  connector with `can_connect=False`. This is safe against unauthenticated
  attempts but means discovery/presence and the reusable lifecycle manager are
  not an end-to-end feature. Pairing has the same composition limitation:
  callback injection is test/application plumbing, not a shipped target-side
  ceremony.
- Listener state is selected from `selected_context()` while its provider and
  process manager are the local `AppWindow` resources. If grants are ever
  enabled while a remote node is selected, the listener can present the remote
  descriptor while serving local resources. Listener identity must be resolved
  from immutable local context, independent of dashboard selection.
- `_sync_peer_listener_grants` updates a live server after local persistence,
  but cannot provision the reciprocal target grant. Grant replacement and
  revocation also need atomic persistence/live-ACL lifecycle validation.
- The process candidate decoder converts accepted numeric values to `int` and
  `float` without finiteness or domain checks. The action wire decoder is
  stricter, so this is a snapshot integrity/UI risk rather than proof of an
  unsafe termination call.
- The action lease is exact-request keyed. Identical request coalescing is
  verified, but different selections on one target can run concurrently. The
  current unknown-outcome behavior is correctly conservative per dialog and
  does not provide target-wide reconciliation.
- No generic shell, arbitrary signal, arbitrary path, foreign-user process,
  protected-process, or cross-target authorization bypass was found. Existing
  target-side controls and remote cleanup read-only behavior should be
  preserved.

### Phase 5: Conservative continue/readiness assessment

**Assessment: not ready for Phase 15 readiness or remote-operation exposure.**
The independent evidence confirms multiple P1/P2 blockers: missing shipped
two-sided provisioning and authenticated connection composition, lossy
authentication/identity failure classification, residual stale activation
lifecycle risk, malformed process-candidate acceptance, unbounded destructive
request-ID bookkeeping, conditional plaintext/admission limitations for any
reachable listener, and incomplete required validation (Mypy/LR). The action
result coercion and omitted create-time findings are not current blockers and
should be removed or marked disproven in the later main rebuttal rather than
being repeated as facts.

Safe continuation is limited to a corrective iteration. Before readiness:

1. Use typed exception mapping for authentication, identity, protocol,
   cancellation, and transient transport failures; test the actual
   coordinator `on_error` callback and retain no-retry behavior for trust
   failures.
2. Implement and test a real two-sided target approval/grant ceremony with
   durable ordering, revoke/crash behavior, and no remote exposure before
   authenticated hello. Replace the disabled composition seam only behind
   that gate.
3. Make activation generation invalidation part of revoke, re-register,
   secret/endpoint replacement, identity mismatch, and shutdown; late results
   must be ignored without mutation or exception.
4. Decide and document loopback-only versus approved encrypted reachable
   transport. If reachable, bound the full admission/shutdown surface rather
   than relying on `request_queue_size`, and define the residual
   executor-cancellation contract.
5. Add finite/domain validation for process-candidate and nested resource
   numbers, and bound `_request_ids` consistently with the replay-cache
   contract. Preserve the already passing strict action-result and required
   create-time checks.
6. Define whether destructive coordination is target-wide or exact-request
   keyed. If target-wide, cover different process sets and normal/force races;
   retain unknown-outcome semantics and durable duplicate-ID handling.
7. Re-run the full suite, Ruff check/format, Pyright, Mypy after isolating the
   historical POC module collision, `./install/verify.sh`, available LR checks,
   and the plan-required deployment/resource evidence. Do not call the phase
   ready while Mypy/LR or required security gates remain blocked.

## Main auditor rebuttal
- Fixed PATCH-001 claims for missing create-time, malformed action-result
  coercion, and identical cross-dialog actions are disproven by current strict
  decoders and regression tests.
- Remaining blockers are confirmed: disabled production authenticated connection
  wiring, missing shipped two-sided grant provisioning, selection-derived
  listener identity, lossy typed exception classification, non-intrinsic
  activation invalidation, malformed process-candidate numbers, and unbounded
  destructive request-ID bookkeeping.
- Active socket handlers are bounded, but kernel backlog and pre-admission idle
  occupancy are not. HMAC remains loopback-only by default and provides no
  confidentiality for any future reachable binding.
- Tests, Ruff, formatting, Pyright, wheel verification, and diff checks pass;
  Mypy is blocked by historical duplicate POC modules, LR is unavailable, and
  cross-platform/live-network/resource evidence is not available.

The implementation is safe to retain as a fail-closed/read-only partial, but it
is not safe to expose remote operations or declare Phase 15 ready.
