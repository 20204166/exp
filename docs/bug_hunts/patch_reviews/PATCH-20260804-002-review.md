## Patch summary

Two disconnected, high-value component seams are added to `maintenance/components.py` only. Nothing is wired into production callers.

1. `ProcessSafetyPolicy` — consolidates the duplicated process-safety decision logic currently found in `SystemScanner.scan_processes()`/`SystemScanner._same_user()`/`SystemScanner._protected_pids()` (`maintenance/scanner.py:80-103, 301-397, 551-561, 796-801`) and `ProcessManager._allowed_processes()`/`ProcessManager._same_user()`/`ProcessManager._protected_pids()` (`maintenance/actions.py:24-47, 107-158`). It answers safety questions only: `protected_pids()`, `same_user()` (Windows domain-prefix normalization), `can_manage()` (fact-based decision), `can_manage_process()` (loader-based decision), failing closed when required safety information cannot be established. It never terminates processes, imports no Tkinter, requires no admin rights, and preserves the exact protected-name set.

2. `ResourceFeatureCatalog` + `ResourceFeature` — centralizes the currently repeated dashboard-resource metadata split between `AppWindow.RESOURCE_CARDS` (`window.py:44-51`), `SystemScanner.scan_dashboard()`'s six `ResourceSummary` entries (`maintenance/scanner.py:217-289`), `Analyzer._report_sections()` (`algo.py:212-221`), and `AppWindow.open_resource()` (`window.py:479-507`). Frozen `ResourceFeature` entries carry `key`, `title`, `order`, `action_kind`, `loader_name`, and optional `platforms`. The catalog provides `all()`, `get()`, `register()`, `available_on()`, duplicate-key rejection, deterministic ordering, per-instance isolation, and no mutable global registry. It imports no `window.py`, `scanner.py`, `actions.py`, or `dialogs.py`, instantiates no widgets, performs no scans, and executes no destructive action.

Files changed: `maintenance/components.py` (+290/-3), `tests/test_components.py` (+355).
No other production files or tests were modified.

### Opposing Agent 4 — External-Research Skeptic

**1. psutil semantics — VERIFIED, consistent with official docs**

- `Process.parents()` — official psutil API reference (https://psutil.io/api, "Process class" → `parents()`; also https://psutil.readthedocs.io/ 7.2.2): "Utility method which returns the parents of this process as a list of `Process` instances. If no parents are known return an empty list. **Added in version 5.6.0.**" `requirements.txt` pins `psutil>=5.9`, so `parents()` is guaranteed available at the pinned floor. The policy iterates `process.parents()` and reads `parent.pid` (`maintenance/components.py:192-196`) — `pid` is a documented read-only property of `psutil.Process`, and the `getattr(parent, "pid", None)` guard plus the type check (`components.py:193-194`) handles injected fakes; a real psutil parent always has an `int` `.pid`.
- Exceptions — official docs (https://psutil.io/api, "Exceptions"): `NoSuchProcess` "Raised by Process class or its methods when a process with the given pid is not found, no longer exists, or its PID has been reused"; `AccessDenied` raised "when an action is denied due to insufficient privileges"; `ZombieProcess` is "Subclass of NoSuchProcess ... on UNIX (Windows does not have zombies)". The Process-class note is explicit: "When calling methods of this class, **always be prepared to catch `NoSuchProcess` and `AccessDenied` exceptions**."
- Fail-closed `except Exception` (`components.py:167-173, 197-200`) — both broad catches **only ever return deny** (`False` / `(protected, False)`); there is no code path where the catch grants access. Since `ZombieProcess` is a subclass of `NoSuchProcess`, even the original implementations' narrow catches would cover zombies; the broad catch is a strict superset in the deny direction. This is consistent with the documented guidance to be prepared for these exceptions on every Process method call, and it is strictly safer than the originals: `SystemScanner._protected_pids` (`maintenance/scanner.py:551-561`) and `ProcessManager._protected_pids` (`maintenance/actions.py:143-151`) catch only `(NoSuchProcess, AccessDenied)` and then continue with the base `{0, 1, os.getpid()}` set, whereas the policy fails the whole decision closed when ancestry cannot be established. No regression; protective deviation.
- Windows `DOMAIN\user` format — the `username()` prose (https://psutil.io/api, `Process.username()`: "The name of the user that owns the process. On UNIX this is calculated by using the real process UID from `uids()`") does not spell out the Windows format, but the same official API page's `WindowsService.username()` example returns `'username': 'NT AUTHORITY\LocalService'`, evidencing the `DOMAIN\user` shape on Windows. `getpass.getuser()` (`maintenance/actions.py:112`), per Python docs, returns the first non-empty of `LOGNAME`, `USER`, `LNAME`, `USERNAME` — i.e. a bare local name, no domain. The domain-strip in `_normalize_username` (`components.py:220-224`) is therefore required to reconcile the two sources, exactly as the originals did (`scanner.py:796-801`, `actions.py:153-158`).

**2. Username normalization — VERIFIED with probe; one intentional fail-closed tightening**
